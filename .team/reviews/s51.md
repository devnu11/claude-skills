## Defects

### D1 (behaviour, design gap): a reorder while a started story is held demotes it for good

G4 and the worked example promise this: "Once released, it goes back to its place among
them." G11 says `state.order = change.order` "keeps the PO's intent for held stories". But
every change builds `change.order` from `with_first` / `with_move`, and both build it from
`self.queue(...)`. Since s51 that queue is **grouped**, so a held story already sits after
every in-progress story. Any reorder then writes that held position into `state.order`.

Repro (origin state, `order = [s45, s38, s21, s50]`, s38 and s21 started):
1. s38 gets a `quarantine` hold. The queue is `s21, s38, s45, s50`.
2. The PO runs `prioritise(["s50"], "")`. No started story is listed, so no reason is
   needed. `with_first` gives `state.order = [s50, s21, s38, s45]`.
3. s38 is released. In the in-progress group, s21 (listed 1) now ranks before s38
   (listed 2). **s38 is #2, not #1.**

The same happens with any `move_story` and with `start_sprint` (for the stories it does not
list) while a hold is open. Holds such as quarantine and questions are common, and the PO
reorders often, so the human will see this. Under s40 it did not matter, because a hold
did not change the rank.

The same mechanism also rewrites the PO's order of not-started stories listed before started
ones. In `test_move_story_of_a_started_story_behind_others…` the order becomes
`[s38, s45, s50, s21]`. That case is harmless, but it shows that the order is now "the queue",
not "the PO's intent".

`test_a_held_story_ranks_back_at_its_listed_place_when_released` checks the ranking only. No
test reorders while a story is held.

**Fix (architect):** say what base `with_first` and `with_move` build from. For example,
`with_first` could use the unfinished stories ranked by `(listed, natural)` with no tiers.
`with_move` must still read `position` as the board's #position in the grouped queue. The
architect has to define how that maps onto the order while keeping the held story's place.
Then the developer implements it, and the tester adds a test for the repro above, for both
`prioritise` and `move_story`.

### D2 (AC6): ADR-0016 is not amended

`.team/adr/0016-story-priority-in-code.md` has no s51 change. The design gives the exact
amendment text, which the scribe or PO must apply because `.team/adr/` is outside the
architect's and developer's scope. AC6 lists it, so the story cannot be accepted without it.

### D3 (style, minor): refusal chain repeated

`prioritise` and `move_story` each repeat this twice:
`reason = …; if reason: return text_result(refused(reason))`.
That makes four copies, and both methods are now 11–13 lines (the house rule says ideally
under 8). A helper that returns the first refusal from a sequence of checks would remove
the repetition. Fix it alongside D1; on its own it does not block.
