# Review s174: gate and boundary commands run without the runner's own venv

Diff reviewed: `ab91c1f2..7b401a7d` (feat 0e22f88a plus two fixups). Runner results: the
coverage gate passed (97.97%, `runner_venv.py` fully covered). I read the tests and did
not run them.

Verdict: **ship.** Both ACs are met for the commands they name. I found one gap outside
the ACs' list (F1) and a few small items. None of them blocks the story.

## Functions changed

### `runner_venv.strip_venv_bin(path, venv)` (new)
- **What it does:** removes each `PATH` entry whose parent is `venv` (its `bin` or `Scripts`)
  and keeps the others in order. `Path` normalises a trailing slash, so `/r/.venv/bin/`
  is removed too.
- **Tests:** `test_strip_venv_bin_*` cover removing the runner venv while keeping another
  venv, a `Scripts` dir, and a `PATH` with no venv entries. s174/AC1 (REQ-199) and
  s174/AC2 (REQ-200) are covered.
- **Defects:** none.

### `runner_venv.hide_runner_venv(env, inherited)` (moved from `dispatch`)
- **What it does:** returns the role environment with `VIRTUAL_ENV=""` and a `PATH`
  filtered through `strip_venv_bin`. If the runner has no venv, it returns `env`
  unchanged. Behaviour is the same as before the move (R1).
- **Tests:** `test_hide_runner_venv_keeps_a_launch_path_and_other_venvs`, and
  `test_dispatch_still_names_hide_runner_venv` checks that the re-export is the same
  object. `test_dispatch.py:69-74` still passes against the re-export. s174/AC2
  (REQ-200, one rule shared by roles and commands) is covered.
- **Defects:** none. The new test copies `test_dispatch.py:69-74` almost line for line.
  The design asked for this, so I don't count it as a defect, but one of the two copies
  could go later.

### `runner_venv.get_command_environ()` (new)
- **What it does:** builds the runner's environment for a command. It drops the
  `VIRTUAL_ENV` key and, when that variable was non-empty, filters `PATH` through
  `strip_venv_bin`.
- **Tests:** three `test_runner_venv.py` cases check:
  - the exact dict when a venv is set (HOME and other keys are kept);
  - that the result equals `fake.env` when there is no venv;
  - that an empty `VIRTUAL_ENV` key is removed and `PATH` is left alone.
  These cover s174/AC1 (REQ-199) and s174/AC2 (REQ-200).
- **Defects / notes:**
  - F3 (minor, s174/AC2): if `VIRTUAL_ENV` is set but `PATH` is missing, the function
    adds `PATH=""`. A shell treats an empty `PATH` differently from an unset one: it
    finds nothing instead of using its default path. Runners started by `uv run` always
    have `PATH`, so this is theoretical. `hide_runner_venv` has had the same behaviour
    since #55. No test covers it.
  - F4 (style, DRY): the design said to build this function on `hide_runner_venv`.
    Instead it repeats the "is a venv set" check. The filter itself is still the shared
    function, so REQ-200's "one function" holds. I accept it as is.

### `commands.CommandShell._watched` (changed)
- **What it does:** both the plain shell and the retry after `plugin_failed` now start
  from `get_command_environ()`. The tally run starts from `tally_watch.watching`, which
  also uses it now (R5). `_build_shell` still adds `COVERAGE_FILE` on top (R4).
- **Tests:** `test_a_plain_command_does_not_see_the_runners_venv` checks that there is no
  `VIRTUAL_ENV`, that `PATH` is filtered, and that `HOME` and `COVERAGE_FILE` are kept.
  `test_tally_run_and_retry_both_start_without_the_venv` covers the tally run and the
  retry. s174/AC1 (REQ-199) and s174/AC2 (REQ-200) are covered.
- **Defects:** F2 (minor, test strength, s174/AC1): the retry test loops over
  `fake.commands` but never asserts that there are two commands. If the retry stopped
  happening, the loop would still pass with fewer commands. Other s118 tests pin that
  the retry happens, so the risk is low. `assert len(fake.commands) == 2` would close it.

### `tally_watch.watching(run)` (changed)
- **What it does:** yields `plugin_env(get_command_environ(), path)`.
- **Tests:** `test_watching_yields_an_environment_without_the_venv` checks that there is
  no venv, that `PATH` is filtered, that `HOME` is kept and that `PYTEST_PLUGINS` is
  added. s174/AC1 and s174/AC2 are covered.
- **Defects:** none.

### `dispatch.py`
- `VENV_VAR` and the body of `hide_runner_venv` are removed and the function is imported
  from `runner_venv`. The unused `os` import is gone. Nothing else changed.

## Findings

- **F1 (medium; fits REQ-199's wording "every configured command the runner runs itself",
  but not the list in s174/AC1).** The acceptance-environment `prepare` and `start`
  commands still get the runner's whole environment: `sandbox.sandbox_env` uses
  `dict(system.environ())` (`sandbox.py:369`) and passes it to `sandbox.run_shell` (`:346`)
  and `_start` (`:441`). A customer sandbox that runs `uv run …` or a bare `python`
  therefore still sees the runner's `VIRTUAL_ENV` and venv `bin`. That is the same bug,
  in a place this story doesn't name.
  - The design's claim "Every command the runner runs from the config goes through
    `CommandShell`" (`docs/design/s174.md`, Cause) is therefore not true. The e2e
    commands themselves do go through `CommandShell`.
  - Roles launched with the sandbox env are safe, because `hide_runner_venv` filters
    the launch `PATH`.
  - **Recommendation:** a follow-up story (Product Backlog) that makes `sandbox_env`
    start from `runner_venv.get_command_environ()`, and a correction to that sentence in
    the design. The human decides whether that becomes a story.
- **F2 (minor):** retry test doesn't count its commands. See `_watched` above.
- **F3 (minor):** `PATH=""` is added when `PATH` was missing. See `get_command_environ`
  above.
- **F4 (style):** small repeated venv check. See `get_command_environ` above.
