## Changed functions

### `stages.Invocation`, `stages.CommandFailed` (new)
A frozen command/code pair, and an exception base that carries one (default `None`).
`GitError` and `UpstreamError` now subclass it. Every existing `UpstreamError(msg)` call
still works. Covered indirectly; fine.

### `stages.get_error_line` (new)
Returns the first non-blank stripped line, or `""`. Covered for multi-line and empty text.
Not covered for a leading blank line (D3's case), which is the corner the function exists for.

### `stages.Run.record_raise` (new), `entered`
Keeps the class, the error line, and the invocation's command/code, else `""`/`None`.
Correct for s175/AC1, REQ-204. Tests cover a tolerated 128 before the raise and a raise with
no call.

### `stages.Run.note`
- **D10, s175/AC1, REQ-204 (minor).** Round 0's `self.last = (command, code)` is still
  there (stages.py:278), but nothing reads it. It also sets an attribute that is not a
  declared field of the `Run` dataclass. Design E1 says "`Run.note` is unchanged". Remove it.

### `stage_log.show_error`, `Timed.data`
`None` stays `None`; anything else is `masked` and then cut to 500. The order (mask first,
then cut) is right. Covered: the 500 cut, `None` for a stage that returns, and the key order.
- **T1, s175/AC1, REQ-204.** No test shows the error is masked (design checklist: `token=abc`
  shows as `token=***`). Masking is the one part of this field that protects secrets, so it
  needs a test.

### `git_ops.format_git_command`, `Git.run`, `Git._exec`
These share one command-line formatter, and the message is unchanged.
- **T3, s175/AC1, REQ-204.** No test shows that `Git.run` raises a `GitError` whose
  `invocation` is `("git <args>", code)` (checklist E1). The only test builds the
  invocation by hand.

### `upstream.is_plain_text`, `trim_output`, `format_gh_call`, `describe_gh_failure`, `build_gh_error`
A plain-text body keeps today's `out.strip()`. A JSON-looking or empty body becomes
`gh <args>: exit N[, HTTP S]: <one line, ≤300 | (no output)>`. The logic is correct.
- **T2, s175/AC3, REQ-206.** The tests can't tell the new format from a weaker one:
  - `"1" in text.replace(RAISING, "")` is still round 0's weak assertion; any digit 1 passes.
  - `"HTTP 403" in text` passes on the raw output alone, so `GH_STATUS` (`, HTTP 403`
    after the exit code) is never checked.
  - Nothing checks `(no output)`, the 300 cut, or the exact `GH_FAILED` string the
    checklist gives.

  Assert the exact messages from the checklist (E5, items 1, 2 and 4).

### `GhPrs.close`
Raises `build_gh_error` for the `gh pr close` argv, so the message names the close and not
the `gh pr view` that ran after it. Correct.
- **T4, s175/AC3, REQ-206.** Untested (checklist E5, `close` item).

### `GhPrs._read_gh_json` (new), `find`, `job`, `list_checks`
Bad JSON on exit 0 raises `UpstreamError(GH_FAILED…, Invocation(cmd, 0))` from the
`ValueError`. Correct.
- **T5, s175/AC3, REQ-206.** Untested (checklist E6). Every existing test sends exit 1, so
  the decode branch, the exit 0 code and the chaining are never run.

### `GhPrs.checks` → `ci.checks_of`: not changed
- **D11, s175/AC3, REQ-206 (major).** `checks` (upstream.py:346-351) ignores gh's exit code
  and passes the output to `ci.checks_of`. On a body that isn't JSON, `checks_of` raises
  `UpstreamError(output.strip())` (ci.py:164) with no invocation. `gh pr checks` is what
  the land's CI wait polls, and a rate limit can hit it. Its `{` reply then gives event
  `detail ""`, `code null`, `error "{"`, and the hold reads
  `error: crashed: UpstreamError: {`. That is the incident's unreadable message (story,
  s167's `UpstreamError: {`). AC3 covers every upstream call ("When an upstream call fails
  with an empty or non-text body…"). Design E6 listed only find/job/list_checks, so this is a
  gap in the design that the code inherits. Route `checks` through the same builder: keep
  the argv and code that actually ran, and raise `format_gh_call` on a decode failure.
  Add a test.

### `handover.describe_hold` (new), `hold_reason`
An `error` trigger with a reason reads `error: <reason>`. Every other trigger, or an error
with no reason, keeps its bare name. Correct per E7.
- **T6, s175/AC3, REQ-206 (minor, was D9).** `test_router` now asserts a crashed role
  step's hold is `error: crashed: RuntimeError: boom`, so the new branch is covered (design E7
  names that exact case). Still missing: an error report with no reason reads bare `error`,
  and a hold for a landing error (only the end-to-end test would show that one).

### `scheduler.Scheduler.run_logged_land` (new), `run_land`
Appends the traceback to crash.log, swallows an `OSError` from that write, and re-raises the
landing's exception. Correct for s175/AC2, REQ-205, and a role step is no longer logged twice.
- **T7, s175/AC2, REQ-205.** No test makes the crash.log write fail and checks that the land's
  exception (and so `status: error`) still comes through (checklist E4). That was round 0's
  D8.

### `ci.UpstreamError`
Now subclasses `stages.CommandFailed`. Fine.

## Tests vs design test plan
`tests/test_s175_land_error.py` adds two tests since round 0, and the checklist is still
mostly open: E1 Git invocation, E1/E6 through `to_thread`, E3 masking, E5 exact
format / `(no output)` / 300 cut / `close`, E6 decode, E4 OSError, E7 hold, and the
end-to-end land (a real `Lander`, a tolerated 128, then a rate-limited gh call, asserting the
event, crash.log, the hold and the hand-over contain `exit 1, HTTP 403`). Coverage is 98% in
total; the charter says it is 100% today. The untested branches above (`describe_hold`'s
error branch, the `_read_gh_json` decode branch, the OSError suppress) are likely among the
misses. (`describe_hold` is covered through `test_router`.)
