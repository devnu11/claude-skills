## Changed functions (round 2)

### `upstream.GhPrs.checks`
Runs `gh pr checks … --required --json`, retries without `--required` when gh says there
are no required checks, and parses the output. On a body that isn't JSON it now re-raises
`UpstreamError(format_gh_call(...), invocation)` chained from `checks_of`'s error.
- **D12, s175/AC1 + s175/AC3, REQ-204 + REQ-206 (major).** The invocation's code is
  hard-coded `0` (upstream.py:354), and `self.run(argv)[1]` throws away the real exit code.
  When gh is rate-limited, `gh pr checks` exits non-zero with a `{` or an empty body. The
  event then says `code: 0`, and the hold and hand-over say `gh pr checks …: exit 0, HTTP
  403: {`. AC1 needs "its exit code or HTTP status" and AC3 needs the exit code. A recorded
  `exit 0` is wrong, and it misleads the reader the same way the original incident did.
  `_read_gh_json`'s `0` is right, because `_gh` already raised on any non-zero exit. Here
  the exit code is ignored on purpose (gh uses it for pass or fail), so it has to be kept
  and passed to `format_gh_call`.
- **D13, s175/AC1, REQ-204 (minor).** When the `--required` fallback ran, the output being
  parsed came from the second argv (without `--required`), but the invocation names the
  first one. "describe the call that raised" means the call whose output failed to parse.
  Keep the argv and result of the call that actually produced `out`.
- **D14, s175/AC3 (house rule, not an AC).** `checks` is now 11 lines, over the charter's
  8-line target. Extracting the parse-and-raise step (and C1's helper) brings it back under.
- **T8, s175/AC3, REQ-206.** No test sends non-JSON output to `GhPrs.checks`. The existing
  `checks` tests (`test_s81_ci.py:299-306`, `test_s111_ci_class.py:257-263`) all send valid
  JSON, so the new `except` branch never runs. Round 1 asked for this test. Assert the exact
  message for `(1, "{")`, i.e. `gh pr checks 14 --required --json …: exit 1: {`. That one
  test also catches D12.
