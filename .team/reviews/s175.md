## New finding (round 3)

### `upstream.Prs.checks` and `upstream.Prs._run_checks` (upstream.py:179-193)
f6ea18ef put the corrected `checks` body and a new `_run_checks` helper into the
**`Prs` Protocol**, the interface, and not into `GhPrs` (upstream.py:300). Nothing
subclasses `Prs` (grep for `(Prs)` finds nothing), and `GhPrs` defines its own `checks` at
:358, so this code never runs.
- **D15, s175/AC1 + s175/AC3, REQ-204 + REQ-206 (major).** The real gh client still records
  `exit 0` for a rate-limited `gh pr checks` and names the wrong argv. That is the D12 and
  D13 defect, unchanged. The event, the hold and the hand-over still mislead the reader the
  same way the original incident did.
- **D16 (no AC; design).** A Protocol is a structural interface. A method body that calls
  `self.run`, which `Prs` does not declare, is wrong there. It also changes the
  Protocol's contract: the docstring now talks about gh exit codes, but `NoPrs` and the
  fakes implement `checks` too. Fix: move `checks` and `_run_checks` into `GhPrs`,
  replacing its current `checks`. Give `_run_checks` a docstring (it is private, but it
  is the step that picks the argv). Restore the Protocol stub: docstring only, as before.
- Note: `_run_checks` is also the name of a `Branch`/env helper in other tests
  (`test_s151_conflict.py`, `test_s152_start.py`). That clash is harmless, but a more
  specific name (`_run_pr_checks`) would make grep easier.
