## Defects

### D1: the lint patterns sit in the test tier, so pytest's FAILED lines can be cut (s172/AC2, REQ-191; this also breaks sprint CI)

`ci.py:47` adds `^\S+:\d+(?::\d+)?: \S` to `FAILING_LINE`, which is one flat list. A
pytest traceback line such as `tests/x.py:12: AssertionError` now counts as a hit.
pytest prints its tracebacks first and its `short test summary info` (the `FAILED` lines)
last. So once there are 20 traceback `path:line:` lines, the `MAX_LINES` cap fills up and
the `FAILED` lines are dropped. Even with fewer traceback lines, they are mixed in with
the `FAILED` lines. Design rule 6 asks for tiers so that this can't happen: test lines
first, and lint findings only when there is no test line. `failing_lines` is shared, so
sprint and landing CI regress too. No test covers it: design checklist item "a pytest
log with traceback lines … gives the FAILED and count lines, not the traceback" is
missing. `test_pytest_still_shows_its_failed_lines_ac2` has no traceback line in it.

### D2: ruff's default output is not found; only `Found N errors.` is shown (s172/AC2, REQ-191)

The runner locks ruff 0.16.10 (`uv.lock:905`), and the workflows run plain
`ruff check .` (`.github/workflows/*.yml`). That prints the full form: a rule line
followed by ` --> path:L:C`. Neither line matches any pattern. The count row
`\b[1-9]\d* (?:failed|errors?)\b` does match `Found 1 error.`. So a red ruff step shows
`Found 1 error.` and nothing else: the finding is gone, and the tail isn't shown either.
This is the case AC2 is about. The design's `-->` join row and its `(?<!Found )` guard
were not built. `test_lint_shows_the_finding_lines_not_the_tail_ac2` uses only the
concise form, and it checks `got[:2]`, so it passes with `Found 2 errors.` in the
output.

### D3: house-rules findings as CI prints them are never matched; the `in function` pattern matches nothing real (s172/AC2, REQ-191)

CI runs `house-rules check --format github` (`house-rules.yml:40`). Its findings are
`::error file=…,line=…,title=house-rules <rule>::<message>` (`report.py:63-70`), which
GitHub may also log as `##[error]<message>`. Neither form matches. The new
`\bin function\b` row matches no house-rules message: `in function` appears nowhere in
`house-rules/runner/house_rules/`. It is the AC's wording turned into a regex. So the
s161 incident that motivated the story (`compile_pattern` is not a verb) would still
show only the tail.

`test_house_rules_shows_its_finding_lines_ac2` uses a format house-rules never prints
(`path:line: verb-name: … in function …`). The real text form is
`path:line: fail <rule>: <message>` (`report.py:26`).

### D4: house-rules warnings count as findings (s172/AC2, REQ-191)

In text format, `path:line: warn <rule>: …` lines match the `path:line:` row just like
`fail` lines do. house-rules prints many warnings, so they can fill all 20 lines and push
out the one failure. The design's `(?!warn)` guard and its "warnings never count" rule
were not built. `protocol.md` (`:3591-3597`) now says "Warnings never count" and
describes the `::error`/`##[error]` and `-->` handling. The code does none of this, so
the doc describes behaviour that doesn't exist.

### D5: tests the design asks for are missing (s172/AC1, REQ-190; s172/AC3, REQ-192)

These items from the design's test checklist have no test:
- `prs.job` raising `UpstreamError`: `read_checks` is `[]`, and the next poll describes
  the check again. The code does this (`story_ci.py:176-180`), but nothing tests it.
- a re-run (new link) is described again;
- a pending check among the checks (see the note on `describe` below);
- the `state.json` round trip of `StoryCi.checks`, and an old `ci` without `checks`
  loading as `[]`;
- a non-developer role (for example `unit-tester`) gets no `## Story CI` section (AC3).
  Nothing tests the `startswith("developer")` branch from the role side;
- `tests/test_ci_findings.py` does not exist.
