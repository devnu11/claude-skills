## Defects

### D1 (test, blocking): two RESTACK assertions can never fail
`tests/test_s108_follow.py:324` and `:356`:

```python
assert not [c for c in fake.commands if c.argv[1:2] == ["branch"] ...]
```

`system.Command.argv` is a `tuple`, so a tuple slice compared with a list is always
`False`. The worktree's git also runs as `("git", *REVIEW_GIT, "branch", ...)`, so
`argv[1]` is an option and not `branch` anyway. Both list comprehensions are always
empty. These lines are meant to pin M10/M12 ("no branch ref moves … until every entry
has passed") and checklist 7 ("RESTACK moves no head"). Today they check nothing. The
head assertions nearby only cover the `entry.head` field, not the git ref.
**Fix:** match on the subcommand wherever it sits, e.g. `"branch" in c.argv and
"--force" in c.argv`. Then confirm that each assertion fails when you plant a
`rebuilder.point` call.

### D2 (test, blocking): AC5's pinned test misses `-c`-prefixed git commands
`tests/test_s108_start.py:101` checks `c.argv[1] in MUTATING`. Both the team-branch
rebase (`Upstream.rebase_onto`, argv `("git", "-c", "rebase.updateRefs=false", …,
"rebase", …)`) and every review-worktree command (`("git", *REVIEW_GIT, …)`) have an
option at `argv[1]`. So the AC5 line "no `rebase`, `reset`, `merge` or `checkout` git
command runs" is not pinned for exactly the commands most likely to run. The outcome
check (`["pass", "pass", "done"]`) would catch a team rebase through its event, but a
direct git call would not be caught.
**Fix:** check whether any word of argv is in `MUTATING`. Alternatively, strip the
leading `-c k=v` / `-C path` pairs first, then check the subcommand.

# s108 review, round 2

**Verdict: ship.** Both blocking defects are fixed in `6244937`. The production code is unchanged since round 1. Coverage is 99.52% and all tests pass (runner results).

## Round 1 defects

- **D1, fixed.**
  - `test_s108_follow.py:356` (changed tree) now asserts that no command has `branch` anywhere in argv. That is stricter than before, and it fails if `Rebuilder.point` (`stack.py:110`, `wt.run("branch", "--force", branch, sha)`) is ever called. This pins M10: no branch ref moves until every entry has passed.
  - `:324` (nothing merged, main unmoved) changed what it asserts. Before, it said "no `branch --force`". Now it says every entry's head is still `NEW`, and every forced `branch` command points at `NEW`. The fixer cited M11, and that rule supports the change. M11 calls `point(entry, new)` for every entry that isn't dropped, with no condition, and M10 says that in this case new head = old head. So a forced re-point to the same sha is in the design, and the old intent was impossible to meet. The new assertion still fails if any branch moves to another sha, because `argv[-2:]` is `(branch, sha)` per `stack.py:110`. Checklist 7 ("moves no head") holds at the ref level.
- **D2, fixed.** `test_s108_start.py:101` now checks whether any argv word is in `MUTATING`, and `worktree` was added to that set. Commands with `-c` or `REVIEW_GIT` options in front of the subcommand are now caught, so AC5's "no rebase/reset/merge/checkout" line is pinned.
