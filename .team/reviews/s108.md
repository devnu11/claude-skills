## Defects

### D1 (test, blocking): two RESTACK assertions can never fail
`tests/test_s108_follow.py:324` and `:356`:

```python
assert not [c for c in fake.commands if c.argv[1:2] == ["branch"] ...]
```

`system.Command.argv` is a `tuple`, so a tuple slice compared with a list is always
`False`. The worktree's git also runs as `("git", *REVIEW_GIT, "branch", ...)`, so
`argv[1]` is an option and not `branch` anyway. Both list comprehensions are always
empty. These lines are meant to pin M10/M12 ("no branch ref moves … until every entry
has passed") and checklist 7 ("RESTACK moves no head"). Today they check nothing. The
head assertions nearby only cover the `entry.head` field, not the git ref.
**Fix:** match on the subcommand wherever it sits, e.g. `"branch" in c.argv and
"--force" in c.argv`. Then confirm that each assertion fails when you plant a
`rebuilder.point` call.

### D2 (test, blocking): AC5's pinned test misses `-c`-prefixed git commands
`tests/test_s108_start.py:101` checks `c.argv[1] in MUTATING`. Both the team-branch
rebase (`Upstream.rebase_onto`, argv `("git", "-c", "rebase.updateRefs=false", …,
"rebase", …)`) and every review-worktree command (`("git", *REVIEW_GIT, …)`) have an
option at `argv[1]`. So the AC5 line "no `rebase`, `reset`, `merge` or `checkout` git
command runs" is not pinned for exactly the commands most likely to run. The outcome
check (`["pass", "pass", "done"]`) would catch a team rebase through its event, but a
direct git call would not be caught.
**Fix:** check whether any word of argv is in `MUTATING`. Alternatively, strip the
leading `-c k=v` / `-C path` pairs first, then check the subcommand.

The new assertion still fails if any branch moves to another sha, because `argv[-2:]` is `(branch, sha)` per `stack.py:110`. Checklist 7 ("moves no head") holds at the ref level.

## Defects

### D3 (test, blocking): AC4 has no real-git test
AC4 says: "Tests with a scratch repo and a fake gh pin: the bottom PR merged by rebase leads to the next PR being rebased, retargeted and ready; tree equality; no PR left on a merged base; the over-100 note."

Checklist items 4–6 match it, and the design's test setup says to use "a scratch bare remote and a clone … replay a sprint branch's commits onto the remote's `main` in a second clone with a new committer date". Today every RESTACK and `Rebuilder` test scripts git through `FakeSystem`. `tests/e2e/` has no test that drives `Restacker`/`Rebuilder`/`_restack`. So none of these has ever run against real git:
- `Rebuilder.rebase`: detach, then `rebase --onto` inside the review worktree with the `REVIEW_GIT` `-c` options, and abort on a stop.
- `same_tree` after a real rebase-merge on GitHub's model (new committer dates, same trees). This is the condition that decides the fast path versus the fallback (M10/M12).
- `merge_base` after main moved, and emptied detection after a squash or local merge.

These are the scripted parts most likely to go wrong in real use. A wrong argv order or a worktree detail would make every END restack fall back, or abort. The unit fakes would not notice.

**Fix (integration-tester):** add `tests/e2e/test_s108_restack_e2e.py`. Reuse `test_s59_rebase_e2e.make_world` plus `s29_helpers.FakePrs`, and cover at least:
1. Checklist 4/5: a two- or three-entry stack with the bottom rebase-merged on the remote. Run the END boundary to CI. Check that the bottom is dropped, the next branch's remote ref is its new head with `same_tree`, its PR is based on `main` and `PrMode.READY`, and no open FakePrs PR has a dropped branch as base.
2. Checklist 6: a real `Rebuilder.rebase` onto the rebase-merged main keeps the tree. A conflicting case returns `None` and leaves no `REBASE_HEAD`. `merge_base` returns the old main tip.
3. Checklist 8: main gains an unrelated commit. The plan is refused with `TREE_CHANGED` and no remote ref moves.
4. The over-100 note may stay a unit test (it is pure arithmetic on `commits`). Say so in the handoff if you leave it out of the e2e test.
