# Review: s8, clean stop on a session limit, a crash or SIGTERM

Reviewed: 9b5f257 (design + ADR-001), 6770632 (tests), dd3b2aa (implementation),
diffed against `9b5f257~1`.
Checks: `pytest` passes with 100% coverage; `ruff check` and `ruff format --check` are clean.

**Verdict: changes requested (developer-cli).** There are two blocking defects (D1, D2). Each one comes with a test that is missing.

## Blocking defects

### D1. The reason keeps the SDK's " (exit code: 1)" suffix (AC1, AC3)

The real SDK (`_internal/query.py:528`) builds
`ResultError("Claude Code returned an error result: <text>", data=..., exit_code=e.exit_code)`.
`ProcessError.__init__` then appends ` (exit code: 1)` to the message. So `str(exc)` is:

```
Claude Code returned an error result: You’ve hit your session limit · resets 2:20pm (America/Edmonton) (exit code: 1)
```

The first `LIMIT_PATTERNS` entry captures `resets (?P<reset>[^\n]*\S)` to the end of the line. I ran it against a real `ResultError`:

```
reason='session limit, resets 2:20pm (America/Edmonton) (exit code: 1)'
```

That string goes into `status_reason`, the outbox note and the stderr line. AC1 expects exactly `session limit, resets 2:20pm (America/Edmonton)`.

The tests miss this because `limit_error()` in `test_halt.py:32` builds the `ResultError` without `exit_code`. A real SDK error never looks like that.

Fix (pick one):
- Match against the structured text when there is one: `exc.errors` / `exc.result` on a `ResultError`, falling back to `str(leaf)`.
- Or bound the reset capture so it stops after the first parenthesised zone, e.g. `resets (?P<reset>[^()\n]*?(?:\([^()]*\))?)`. Check this against `errors[]` joined with `"; "` too.

Test to add: `limit_error()` must pass `exit_code=1`, the way the SDK does. Also add a pattern case with a trailing ` (exit code: 1)` and one with a trailing `; other error`.

The curly apostrophe and the middle dot themselves are fine. The pattern searches from `hit your`, and `\W+` matches ` · `. I checked this with the real U+2019 and U+00B7 characters.

### D2. After a role step hits a limit, `settle_po` quarantines or commits the step's partial edits (focus 3)

`Runtime._run_planned` correctly skips `settle` when a role step raises. There is no handoff parse, no commit, no gate and no story change. But the PO's turn then ends normally, as the new `halted` prompt line tells it to. `PoRun.run` then calls `self.runtime.settle_po()` without any condition (`po_tools.py:274`). `settle_tree` audits the whole dirty tree against the PO's scope:

- The halted role's edits outside the PO scope (e.g. `agile_team/*.py`) go to `guard.quarantine`. That commits them as a quarantine attributed to `product-owner`, reverts them, and emits a `QUARANTINE` event for the PO. The partial work disappears from the tree.
- The halted role's edits inside the PO scope are committed as `chore(team): product-owner step`.

Either way, partial edits get committed and attributed to the wrong role. The docs then become false. protocol.md says "A step cut off mid-way can leave uncommitted edits". SKILL.md step 9 tells the liaison to check `git status --porcelain`, but the tree is already clean by then.

The behaviour is also inconsistent. If the PO's own query then raises the limit (likely, since it's the same login), `settle_po` is skipped and the tree stays dirty. The outcome depends on which side of the PO turn the limit lands.

Fix: when `runtime.halted_by` is set, `PoRun.run` must not call `settle_po`. Leave the tree as it is for the human and s9. Keep it table- or guard-shaped, with no flag parameter.

Test to add: a fake role writes an in-scope file and an out-of-scope file, then raises `limit_error()`. The PO ends its turn normally. Assert that:
- both files are still uncommitted,
- HEAD has not moved (no quarantine and no chore commit),
- no `QUARANTINE` event was emitted,
- the story's step and rounds are unchanged.

No current test writes files in a halted role step, so this path is untested today.

## Focus questions

1. **SIGTERM.** `add_signal_handler(SIGTERM, task.cancel)` cancels the main task. Every state write (`save`, `relay.post`, `settle`/git) is synchronous, so cancellation can only land at an `await`, never part-way through a write. `asyncio.run` re-raises `CancelledError`, `_run` catches it, and `halt_run` saves `stopped` and posts the note before the `pid_file` context exits. A role step in progress is cancelled through the SDK's task group, and `CancelledError` is not caught by `_run_planned`'s `except Exception`, so the step is not settled or gated. Two narrow windows remain and are not blocking: before the handler is installed, and after `loop.close()` restores `SIG_DFL`. In both, SIGTERM still kills the process the old way.
2. **Pattern vs. the real message.** The apostrophe and the middle dot match. The exit-code suffix leaks into the reason (**D1**).
3. **Limit in a role step.** The step itself is not committed or gated. The PO's settle then commits or quarantines its partial edits (**D2**). Partial cost is not recorded; that is left to s10, as planned.
4. **Resumed PO refused?** No. `PoRun.run` resets `halted_by` and calls `mark(RUNNING)`, which clears the reason, before the first turn. `halted()` only refuses `blocked`, `done` and sprint-cadence `sprint-end`. Covered for all three halt statuses, and end to end by `test_resume_after_cli_limit_stop`.
5. **crash.log location.** It is written to `config.run_dir` (`.team/run/`). This repo's `.gitignore` has `.team/run/`, and `onboard.gitignore_lines` always adds `RUN_IGNORE` for target repos. OK.
6. **Docs.** SKILL.md step 9, the protocol.md "Run status and stops" section (statuses, exit codes 70/75/143, `crash.log`, `status_reason`) and the README row all match the code, except the cut-off-step claim that D2 breaks. They become accurate once D2 is fixed. Minor: the "130 Ctrl-C, unchanged" row means Ctrl-C still leaves `running` and prints a traceback. That is outside AC2's scope (SIGTERM and exceptions) and documented honestly.
