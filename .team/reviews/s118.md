# Review: s118, the Flow chart in HTML (step review, round 1)

Reviewed: `git diff 7731f96~1 HEAD` (runner Python, `dashboard/index.html`,
fixture, tests, the two gate-fix commits b15440c and 392e707). I read the tests
but did not run them. The runner's coverage run at 53ba84b is green at 99.53 %.

**Verdict: changes requested.** The blocker is that the code does not meet

## Blocking

### B1. AC6 as written now is not implemented, and the design does not cover it (architect)

AC6 was amended at 682b68a (21:03, PO step), after the design was written.
The current AC6 asks for:

- four categories: Pass (green), **Warn = tests that recorded a warning**,
  **Skip (grey) = skipped, xfailed, xpassed**, and Fail. The example caption
  is `273 Pass + 32 Warn + 4 Skip + 9 Fail / 506 Total`;
- "% complete" defined as reports received / collected total;
- counts reported by **a small pytest plugin on the pytest-xdist controller**
  (`pytest_runtest_logreport`, `pytest_warning_recorded`, the total from
  `worker_collectionfinish`).

The design (still revised at 2917a0b, 21:05) and ADR-0053 do something else.
R5 parses `-q` progress lines, maps `s`/`x`/`X` to **Warn**, has no Skip
category, and ADR-0053 line 35 rejects a plugin outright ("no change to the
repo's commands and no plugin"). The code follows the design:

- `test_tally.OUTCOMES`: `s`, `x`, `X` count as `warned`. There is no skip,
  and recorded warnings are never counted.
- `index.html` `testParts`, `testsCaption`, `captionHtml`, `testBar`: these
  have only Pass/Warn/Fail.
- The fixture's `tests` has no skip count.
- `docs/customer/dashboard.md:138` documents "Warn (yellow: skipped or
  expected failures)".

So the customer proxy would have to reject AC6. The architect must update the
design and ADR-0053 to the amended AC: a plugin, a Skip category with its
colour token, and Warn = a recorded warning. If the architect thinks the
amendment should not apply to this story, the PO or the human has to say so
and the AC has to change back. The code should not ship against a design
that contradicts its AC.

### B2. The tally adds up across several pytest sessions in one stage (developer-gui; design should state the rule)

This repo's own `coverage` command is two pytest sessions joined by `&&`
(`.agile-team.toml:16`: agile-team runner, then unattended). Both run inside
one `gate.tests+coverage` stage. `Tallier` keeps one `Tally` for the whole
stage, and `test_tally.read` never resets it:

- `passed`/`warned`/`failed` keep adding into the second session;
- `total` is overwritten by the second session's `collected`/`workers [N]`
  line, so the caption can read e.g. `2400 Pass / 300 Total`, and
  `testBar` segment widths go above 100 % (`width:800.00%`);
- with `-q` and no total line, `_total()` estimates `ran * 100 / pct` from
  the cumulative `ran` and the second session's small `pct`, which is wildly
  wrong;
- `points` drops from 100 back to the new session's percentage, so the
  "% complete" sparkline saws, and `fail_at` from session 1 colours session
  2 red.

Every gate run in this very repo would show this. Fix: start a new tally
when a session starts, i.e. on a new total line, or when `pct` goes down. A
plugin (B1) gives each session's total too, but the stage would still have
to sum or reset. The design should say which; my guess is the reset, showing
the session that is running. Add a test that feeds two sessions' lines.
**No test covers this today.**

### B3. Gate fix 392e707 dropped s97's "may include sleep" check without a rule (integration-tester / developer-gui)

`tests/e2e/test_s97_awake_page_e2e.py::test_running_line_takes_out_sleep_or_marks_wall`
used to assert that a wall-clock running step is marked
`(may include sleep)`. That is s97 AC2: "An older event without `mono` falls
back to wall time and is marked 'may include sleep'". The rewrite tests only
`awakeSoFar` and `fmt.dur1`, and the `wall` case now just asserts
`10.0m`. `liveBlock` (index.html:1386) has no wall mark. The Superseded-tests
table does not list s97, and FC11 does not drop the mark, so the `asserts`
rule named ("Design s118 'Superseded tests' table") does not cover this.
That is a lost behaviour plus a weakened test. Either the live line keeps
the mark (e.g. `fmt.dur1(awake)` plus ` (may include sleep)` when the open
step's `clock === "wall"`, with the test restored), or the architect drops
it in the design explicitly.

### B4. Gate fix 392e707 relaxed the s86 test against s86 AC4's wording (integration-tester; PO)

`test_s86_dependencies_e2e.py` now exempts a story whose prose says
"depends on sN" when sN is also in `depends_on` (`_declared`). s86 AC4 says
"A test pins that no open story file still holds a prose 'Depends on'
line". The rule named (AC4 holds the dependency as data) is the reason a
prose line is harmless, but the AC pins the prose itself. The trigger is
the PO's own prose in s125 ("It depends on s118 because …"). Rewording that
sentence (e.g. "It needs s118 …") keeps the test as it was. This has
nothing to do with s118, so relaxing a test in this story is scope creep.
Revert the relaxation and have the PO reword s125. Or, if the team prefers
the relaxed rule, amend s86 AC4 first.
