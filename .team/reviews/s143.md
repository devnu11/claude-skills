## Changed functions / values

### `requirements.REF` (used by `parse_ref`, line 90)

What it does: `fullmatch`ed by `parse_ref` to split `sN/<ac id>` into `Ref`.

Shipped: `r"(s\d+)/([A-Za-z][\w-]*(?:\.[\w-]+)*)"`
Design (the contract, "One line, line 20"): `r"(s\d+)/([A-Za-z][\w.-]*)"`

**Defect D1 — the code doesn't match the design or the docs (s143/AC1, s143/AC2, REQ-069).**
The developer changed the pattern without saying why (fixup b76e482 only says
"Extended REF regex to allow dotted AC segments"). The shipped pattern refuses
any dot that isn't followed by a word character or `-`:

| ref | design rule 1 / AC2 / protocol.md row 9 | shipped code |
|---|---|---|
| `s141/AC1.` | ref (`.` is an allowed character) | `None` → BAD_REF |
| `s141/AC1..1` | ref | `None` → BAD_REF |
| `s141/A.` | ref | `None` → BAD_REF |

- AC2 defines malformed as "no story id, no AC id, or characters outside
  letters, digits, underscore, hyphen and dot". None of these refs has any of
  those problems, yet they are refused as `BAD_REF`.
- protocol.md row 9 (changed in this story) says the AC id is "a letter, then
  letters, digits, `_`, `-` or `.`". That is the design's pattern, not the
  shipped one, so the docs now describe behaviour the code doesn't have
  (charter: docs move with behaviour).
- Design rule 5 says story files never restrict AC ids. A story AC with a
  trailing or doubled dot would get the gate's `BAD_REF` message (`is not
  "sN/ACk"`) for an id the docs say is valid. That's unlikely, but the bug
  would be hard to diagnose when it happens.

Fix: use the design's line exactly. If the developer thinks the stricter form
is better, that is a design change: dispute it so the architect can amend
design rule 1, AC2 and protocol.md together. Don't leave it as an unexplained
change.

Everything else is correct with either pattern: groups unchanged, old refs
give the same `Ref` (rule 3), `fullmatch` still blocks leading/trailing junk
and a trailing `\n` (rule 2), the message text is unchanged (rule 4).
Pre-existing, not a finding: `\w` also accepts non-ASCII letters after the
first character, as before.

### `parse_ref` (unchanged body)

Not changed; the docstring names no characters, so the design leaves it alone. OK.
