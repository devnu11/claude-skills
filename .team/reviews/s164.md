# Review: s164, the scheduler's own writes never wake it

Diff reviewed: `fc8d7355~1..03ade1a` (`run_writer.py`, `scheduler.py`,
`tests/test_s164_idle_tick.py`, docs, ADR-0085 amendment). I read the tests and did not run them;
the runner's coverage run passed (97.64 %).

**Verdict: changes requested (developer).** The wake rule (W1, W2, W5) is right. But the new
`has_pass_to_hear` skip in `run_loop` is not in the design. It can make the loop run forever
without ever awaiting, which hangs the whole run (D1).

## Functions changed

### `RunWriter.__init__`, `bind`, `release` (run_writer.py)
They keep and forget the owner task, as the design says.
- Tests: `test_release_forgets_the_owner` covers both. **No defect.**

### `RunWriter.is_on_owner` (new property)
Returns True only on the bound thread when the current task is the owner. It returns False when
unbound, on another thread, or when `current_task()` raises.
- Tests: owner task (tests 1 and 5), another task (2), worker thread (3, and
  `test_is_on_owner_false_on_a_thread_without_a_loop`), unbound (4).
- Not tested: the loop thread outside any task (`current_task()` is None, so the write wakes). The
  design names this case. It is benign, so I raise no finding.
- The `except RuntimeError` branch can't be reached: the thread check runs first, and the bound
  thread always has a running loop while bound. It is harmless and coverage passes. **No defect.**

### `RunWriter.submit`
It queues the write and wakes the scheduler only when the caller is not the owner
(s164/AC1, REQ-174).
- Tests: tests 1 to 4 cover the wake and no-wake cases. Test 8 shows that a write from another
  task ends `wait_for_change` at once. Story CI results still wake the scheduler:
  `StoryCiPoll.settle` emits `STORY_CI` from the ci task, which is not the owner. **No defect.**

### `Scheduler.wait_for_change`
It flushes the writer before it waits (W2).
- Deviation: the design says `drain()`, the code calls `flush()`. `flush()` drains only on the
  bound loop thread, which is always the case here. Both are equivalent, and `flush` is the safer
  choice. The docstring was not updated as the design asked ("write the scheduler's own queued
  lines, then wait for … a write from another task or thread …"). This is a nit
  (s164/AC1, REQ-174).
- Tests: test 6 checks that the write lands and the wait runs the full `POLL_S`. Test 8 checks an
  early wake. **No defect.**

### `Scheduler.run_loop` / new `Scheduler.has_pass_to_hear` (not in the design)
The loop now skips the wait when `is_finished` or `has_pass_to_hear` holds
(`po_task is None and not desk.is_empty`). Its job is to start the turn for the idle report at
once, which used to happen through the self-wake (W4).

**D1 (blocker, s164/AC1, REQ-174): the loop never awaits once a pass sits on the desk that
`start_turn` won't take.** `run_loop` has no `await` except in `wait_for_change`. Once
`has_pass_to_hear` stays true, the loop never yields. Every other task (the running steps, the PO
turn, the CI poll) is starved, so nothing can end, and the runner spins at 100 % CPU forever.
`has_pass_to_hear` stays true whenever the desk holds a pass and `start_turn` starts no turn.
Both of these cases happen:

1. **A halt or stop while a step runs.** `start_turn` returns at once when `self.ended()`
   (scheduler.py:584). A halt or stop does not cancel running steps, and `is_finished` waits for
   them. Two ways to get here:
   - A graceful `stop` (or a halt) arrives while a pass is queued and a step is still running.
   - A PO turn ends with `halted_by` set. Then `run_turn` skips `desk.done()`
     (scheduler.py:608), so the taken passes stay queued.

   In both cases `is_finished` is false (a task is still busy), `has_pass_to_hear` is true, and
   the loop spins without yielding. The step never finishes, so the run never ends. This is worse
   than the bug the story fixes: the old spin still yielded on every `await asyncio.wait`.
2. **A pass with no kinds.** `po._hand_over` returns None for such a pass (po_tools.py:1123), so
   `build_turn` starts no turn and the desk keeps the pass. `check_idle` filters these out, but
   `queue_pass` does not.

Fix, per the design's own rule W4: drop `has_pass_to_hear`. Set the one-shot `self.hurry = True`
where the pass is queued: in `check_idle` after `queue_pass`, or in `queue_pass` itself. This
mechanism already exists, it can't stick, and the design says to use it. If the developer keeps a
property instead, it must also be false when `self.ended()`, and the build-returns-None case still
needs a guard. The design also asked for this flow to be named in the handoff (W4).

- Tests: nothing tests `has_pass_to_hear` directly, and no test covers a pass that is queued
  after the run has ended while a step still runs. Add a test with an ended run (stop requested
  or `halted_by` set), one never-ending step task, a queued pass and `po_task` None. Run
  `run_loop` under a deadline and assert that it awaits, i.e. ticks no more than
  window / `POLL_S` + 2. This test goes in the unit tester's or developer's file, not mine.

The extra `is_finished` term in the skip condition is safe: the next tick returns from the loop.

## Tests (`test_s164_idle_tick.py`)

- Tests 1 to 8 match the design checklist. No temp-dir fixtures are used. Durations are read
  with `real_monotonic` and compared with `about` (REQ-024, REQ-025).
- Test 7 (`test_idle_loop_does_not_spin_ac1`) runs `run_loop` under `asyncio.wait_for`. On
  Python ≥ 3.12, `wait_for` awaits the coroutine in the same task, so the owner check holds.
  The test injects its own owner write in each tick, which is a good proxy for the guard event.
  It does not assert "guard events ≤ ticks" as the checklist said, but its tick bound is the
  stronger check. Acceptable.
- Top level holds only imports, constants, `sched = Late(...)` (the repo's lazy-import constant
  pattern) and defs. Checklist met.

## Copy/paste

There are no repeated blocks. `is_on_owner` repeats the `threading.get_ident() == self._thread`
check that `flush`, `call_from_thread` and `check_owner` already make. A private
`_on_loop_thread` helper would remove the repetition. This is a nit and not required.
