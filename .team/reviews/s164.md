# Review: s164, the scheduler's own writes never wake it

Diff reviewed: `fc8d7355~1..5cf6dea`. This covers `run_writer.py`, `scheduler.py`,
`tests/test_s164_idle_tick.py`, the docs and the ADR-0085 amendment. I read the tests and did
not run them. The runner's coverage run at 5cf6dea passed (97.64 %).

**Verdict: done (round 2).** D1 from round 1 is fixed the way the design asks (W4). The fix
uses the one-shot `hurry`, not a property that can stick. Two regression tests now cover both
ways D1 could happen. What is left are nits.

## Functions changed

### `RunWriter.__init__`, `bind`, `release` (run_writer.py)
They keep the owner task and forget it on release (s164/AC1, REQ-174).
- Tests: `test_release_forgets_the_owner`. **No defect.**

### `RunWriter.is_on_owner` (new property)
It returns True only on the bound thread, and only when the current task is the owner. It
returns False when unbound, on another thread, or when no loop runs.
- Tests: the owner task (tests 1 and 5), another task (2), a worker thread (3 and
  `test_is_on_owner_false_on_a_thread_without_a_loop`), unbound (4).
- Not tested: the loop thread outside any task. That case wakes, which is benign.
  **No defect.**

### `RunWriter.submit`
It queues the write and wakes the scheduler only when the caller is not the owner
(s164/AC1, REQ-174).
- Tests: tests 1 to 4. Test 8 shows that a write from another task ends the wait at once.
  Story CI (`StoryCiPoll.settle` on the CI task) and `report_back` (on the step task) are not
  the owner, so they still wake it. **No defect.**

### `Scheduler.wait_for_change`
It calls `writer.flush()` before it waits (W2). The design says `drain`, but `flush` does the
same on the loop thread and is safer.
- Tests: test 6 checks that the line lands and the wait lasts the full `POLL_S`. Test 8
  checks the early wake.
- Nit (s164/AC1, REQ-174): the docstring still says "a write to be submitted". It should say
  that only writes from other tasks or threads end the wait. Not blocking.

### `Scheduler.run_loop`
It skips the wait on `hurry or is_finished`. With `is_finished`, the next tick returns from
the loop at once. This is safe.

### `Scheduler.check_idle` (sets `hurry = True` after `queue_pass`)
This is the W4 flow: it starts the PO turn for the idle report on the next pass, with no
self-wake.
- It can't stick. `run_loop` clears `hurry` on every pass, and `check_idle` returns early
  while the desk holds a pass. So a pass that `start_turn` refuses (the run has ended, or the
  pass has no kinds) sets `hurry` once at most, and from then on the loop awaits. The other
  `queue_pass` callers are `queue_news`, `ask_permission` and `poll_story_ci` (in `tick`,
  before `start_turn` in the same pass), and `report_back` and story CI (on other tasks, which
  wake the scheduler). None of them needs `hurry`.
- Tests: `test_ended_run_with_a_queued_pass_still_awaits_d1` covers a halted run with a never-ending step.
  `test_queued_pass_without_kinds_still_awaits_d1` covers a pass with no kinds. Both bound the
  ticks to window / `POLL_S` + 2 (s164/AC1, REQ-174). No test asserts that the idle-report turn
  starts with no `POLL_S` delay. If the line were lost, that turn would only start up to 5 s late.
  Coverage reaches the line. Not blocking.
- The design asked for this flow to be named in the handoff (W4). The code comment names it.

## Tests (`test_s164_idle_tick.py`)

- Tests 1 to 8 and the two D1 tests are the right size. Durations use `real_monotonic` and
  `about`.
- Top level holds only imports, constants, the `sched = Late(...)` lazy-import constant and
  defs. The checklist is met.
- Nit (house rule "no boolean parameters"): `count_loop_ticks(..., halted: bool)` takes a
  flag. This is a test helper, and the house-rules gate let it pass. An enum, or two small
  setup callables, would follow the rule. Not blocking.

## Copy/paste

the `threading.get_ident() == self._thread` check that `flush`, `call_from_thread` and
`check_owner` also make. This is a nit carried over from round 1.
