**Verdict: changes requested (developer).** Five defects block shipping (D1 to D5). D6 is a

## Blocking defects

### D1. The Manager review blocks every story (s159/AC6.8, REQ-156)
- `router.Router._offered` (router.py:327) returns only `[boundary, manager]` while
  `state.manager_due` is set, so no story work is offered.
- `Runtime.refusal` (dispatch.py:554) also refuses every non-Manager step while `manager_due`
  is set.
- `manager_due` is cleared only when the Manager's step settles (dispatch.py:1721).

So while the sprint-start review runs, no story starts. AC6.8 says "It blocks no story", and
design C2 says it "blocks none of them". No test covers this: design checklist line 1226,
"The Manager review runs alongside a story step", has no test. `test_s159_scheduler.py` only
checks the constants.

### D2. A step's settle and gate run on the event-loop thread (s159/AC6.2, REQ-153; design C6)
- `Runtime.settle_work` (dispatch.py:1129) calls `self.settle(...)` synchronously. Its docstring
  admits "a long gate delays the other stories' tasks".
- At `implement`, the settle runs `tests_green_and_covered`, the whole test suite (gates.py:906).
- `Scheduler.run_boundary` (scheduler.py:425) also calls `boundaries.step()` synchronously. That
  covers the full checks, and `ci.py`'s CI waits with `system.sleep`/`wait_checks` up to
  `ci_timeout_s`.
- `StoryPusher.after_step` (git push) and `StoryCiPoll.poll` (`gh api`) are also blocking calls
  on the loop.

While any of these runs, every other story's SDK stream, the PO turn, the writer drain, `stop`,
tells and the heartbeat all stop. That breaks AC6.2 ("run at the same time"), AC6.7 ("keeps
serving PO turns") and AC11.3 ("carries on within seconds"). Design C6 says worker threads
(`system.in_thread`) run the commands and git. The test-checklist line "Two stories run steps at
once…" (design line 1219) has no test. No test runs a story step through
`run_in_worktree`/`uses_worktree`. `story_branches = True` appears only in two unrelated tests
(s111, s128).

### D3. A PO turn races a land and story steps in the main checkout (s159/AC1.3, AC2.4, REQ-132, REQ-137; design C6)
Design C6: "The main lock … is held … by `settle_po` and the story-admin commits."
- `PoRun._turn` → `_settle` → `settle_po` (po_tools.py:1110) commits to the main checkout
  without `main_lock`.
- `record_checkout` then moves `entry.head` (`_follow_sprint_head`, dispatch.py:1273).

Two failure paths follow:
1. A land holds the lock across its CI wait, which takes minutes. A PO turn ending inside that
   window commits a story edit on the sprint branch. `Lander.push_sprint` then pushes the merge,
   which succeeds (it descends from `entry.pushed`). `fast_forward(merge)` then fails because the
   local branch has the PO commit, so the run halts in `halt_diverged`. At that point the remote
   sprint branch has moved, but `entry.pushed` hasn't been updated.
2. `PoRun._turn` calls `checkout_moved()` at its start without checking the lock. A turn that
   starts between a land's `fast_forward` and its `record_checkout` sees an unrecorded HEAD and
   halts the run as checkout drift. That window covers the `open_sprint_pr` and `prs.close`
   calls, a few seconds each.

The pre-switch mode is the mode every existing run is in. There, `Scheduler.dispatch` runs a
story's role step in the main checkout without the lock (scheduler.py:347–350), at the same
time as the PO's turn. The PO's story edits land in the role's tree, where the guard quarantines
them or `commit_step` commits them as the role's. The `test_priority_e2e` change (D6) shows the
symptom.

### D4. A failing story-CI poll crashes the run, and landed or cancelled stories are polled forever (s159/AC8.3, REQ-158)
`Scheduler.poll_story_ci` (scheduler.py:489) → `StoryCiPoll.poll` (story_ci.py:95):
- It is called on every tick, outside any try. `GhPrs.sha_checks` raises `UpstreamError` when
  `gh` exits non-zero, for example on a network blip or an expired token. `NoPrs.sha_checks`
  always raises, and `poll` never checks `prs.missing()`. The error propagates out of
  `Scheduler.run`, so the run ends as a crash. AC8.3 says a story-PR result "doesn't hold the
  run".
- It loops over every story in `state.stories` with `pushed` set, done and cancelled ones
  included, so the `gh api` calls grow with every landed story. The docstring says "each open
  story".
- A done story's `ci` is overwritten by its old PR result: `source="pr"` replaces the landing's
  `source="landing"`. The Board then shows the PR verdict instead of the landing verdict, and a
  red PR result on an already-landed story still raises `story_ci_red`.
- Every non-green settled verdict (`infra`, `main`, `none`) is handed over as
  `"verdict": "red"` (`queue_story_ci`).

### D5. A carried story's stash is lost on a conflict, and it may pop another story's stash (s159/AC2.13, REQ-144)
`StoryReplay.run` (replay.py:183):
- `save_edits` stashes an interrupted step's edits. On a conflict, `queue_rebase` aborts and
  checks out the old branch but never pops the stash. The edits stay hidden in `refs/stash`
  while the story's next step continues "from the worktree" (AC11.2). AC2.13 says the edits are
  "re-applied after".
- `refs/stash` is shared by every worktree of the repo. If an interrupted step had no edits,
  `git stash push` saves nothing, and `restore_edits`' `stash pop` then pops the top of the
  shared stack. That can be another carried story's stash left by the path above.
- A `stash pop` that conflicts raises `GitError` from `tree.run` in the boundary (no handling).
- There is no test for the conflict-with-stash path.

### D6. A gate-fix assertion change its cited rule doesn't support (s159/AC6.2; REQ-153)
Commit db35045c changed `test_priority_e2e.py::test_pipeline_runs_stories_in_the_order_the_po_set`
from `first_steps == ["s3","s1","s2"]` to "s3 before s2". It cites C3/C8. C3 is the open cap and
C8 is hold/cancel; neither says stories may start before the PO's opening turn. The comment
("s1 may start before the PO's turn sets the order") describes D3: `begin()` creates the opening
turn, and the same tick starts story work beside it. This test runs with story branches off,
where `check_free` promises "one step at a time". The old assertion was right, so restore it once
D3 is fixed. The other gate-fix changes are supported: R5/AC2.12 (`-r<k>` branches), I6/AC11.4
(`LIMIT`), G1/G2/AC4.x (removals), I4/AC11.3 (waiting stays `running`) and I1/AC11.2 (no salvage
commit).

    `story_ci.find_sprint_entry`.
  - The "replay a story, then push it with its old PR" code appears twice:
    `BoundaryRunner._run_carried` (boundary_runner.py:808–812) and
    `Runtime._run_returning_replay` (dispatch.py:909–917). The dispatch copy compares
    `.outcome.value == "rebased"` as a string.

    "developer"` with the same `StoryRebase(...)` build, in `Lander.queue_rebase` (landing.py:342)
    and `StoryReplay.queue_rebase` (replay.py:215).
  - `diff --name-only --diff-filter=U` parsing is written five times (git_ops, landing, replay×2,

- **S3. `scratch_rebase.py` is kept** (s159/AC2.6, REQ-139). The design says
  `scratch_replay.py` replaces it, and AC2.6 drops `HAS_MERGES`. It still runs for a line with
  no story merges (`_make_replay` → `rebase_onto`, `_get_scratch`). That is defensible for the
  pre-switch line, but it isn't documented as a deliberate branch.
- **S4. A revert landing skips the permission wait** (s159/AC2.11, REQ-143).
  `Lander.land_revert` goes straight to `run_attempts` → `deliver` → `push_landing` and never
  calls `find_wait`. With permission still `UNASKED` (a story that landed locally while `gh` was
  missing), it pushes before the run has asked. When a revert's report has no `gate` (a halt),
  `Scheduler.run_revert` sends it to `refuse_revert` and the queued call is lost.
- **S5. A storyless step that hits the usage limit halts the run at once**
  (`_stop_for_limit`, dispatch.py:1169), while story steps are still running (s159/AC11.4,
  REQ-163). AC11.4 says the status becomes `limit` "when no step is running".
- **S6. Side effects in queries.** `Scheduler.check_land` and `StoryPusher._confirm_ready` set
  `state.permission_asked = True` from inside checks (no AC). It works, but a `can_start` query
  shouldn't write state.
- **S7. `recover_stories`/`prune_stale` removes the worktree of every open story without an
  interrupted step, but leaves `worktree_head` set** (s159/AC10.2, REQ-160). The worktree is
  rebuilt on the story's next start, but `open_count` (C3) counts stories whose worktree is gone.

## What would make this shippable
1. Let story work start while the Manager review runs (D1), with a test.
2. Run settles, gates, boundary stages, story pushes and CI polls through `system.in_thread`
   (D2). Add a test with two scripted story steps running in worktrees at once.
3. Have the PO's settle and story-admin commits, and the `checkout_moved` check at a turn's
   start, take the main lock. With story branches off, run a story step and a PO turn one at a
   time (D3). Then restore the priority assertion (D6).
4. Make the story-CI poll skip finished stories, skip when `prs.missing()`, and treat an
   `UpstreamError` as "no result" (D4).
5. Pop or drop a carried story's own stash on a conflict, and only when something was stashed
   (D5).
