## Blocking defects

### N9. The story push now writes run state from a worker thread (s159/AC6.4, AC2.11, AC8.1; REQ-154, REQ-143, REQ-158; design C6)
`apply_settled` runs `StoryPusher(self).after_step` through `system.in_thread`
(dispatch.py:1150). `after_step` does more than run git and `gh`. From the worker thread it
writes:

- `story.pushed = head` (story_ci.py:48);
- `story.pr = …prs.create(...)` (line 81);
- `rt.state.permission_asked = True` (line 65);
- `entry.pushed = entry.head` on the sprint's stack entry (line 72).

C6 says one task writes the run state, and the commands run in a thread and return data.
Round 2 asked for exactly that split. Two things go wrong now:

- With two stories settling together (AC6.2), both threads can run `_open_sprint_branch` at
  once. Both see `entry.pushed` empty and both push the sprint branch with an empty lease.
  The loser is refused, and whether it then opens its PR depends on timing.
- `run_ci_poll` on the loop reads `story.pushed` while the thread may be writing it. N6's
  fix captures the sha, but it can capture the old head between the push and the write.

`test_the_story_push_runs_through_in_thread_r1` monkeypatches `after_step` to a no-op, so it
can't see any of this.

Fix: split `after_step` the way `Lander` does (landing.py:237). Decide on the loop whether to
push and which `Lease`. Run only `upstream.push` and `prs.create` in the thread and return
their results. Then set `pushed`, `pr`, `permission_asked` and `entry.pushed` on the loop. A
test should drive two stories' `apply_settled` at once and check that the sprint branch is
pushed once and both PRs open.

### R1b. The gate still blocks the event loop (s159/AC6.2, AC6.3, AC11.3; REQ-153, REQ-154, REQ-162; design C6)
`Runtime.settle_work` (dispatch.py:1135–1141) still calls `self.settle(plan, result)`
synchronously, and its docstring now says that "a long gate delays the other stories'
tasks". The gate is the story's full suite and coverage run, which takes minutes. During it,
no other story's step advances, the PO desk serves no turn and the heartbeat stops. That
breaks AC6.2 ("at the same time") and AC11.3 ("carries on within seconds of an answer").
Round 2 said that running the gate's suite in `system.in_thread` and applying its verdict on
the loop is enough. That part was not done. A test should show a PO turn or a second story's
task advancing while a gate's suite run is pending.

### R3. The Manager now takes no lock, where C6 says it takes it around its settle (s159/AC6.8, AC1.3; REQ-156, REQ-132; design C6 line 500)
`uses_main_checkout` (scheduler.py:372–373) returns `False` for the Manager once story
branches are on. The comment says "the Manager reads". But its step still ends in `settle`,
which commits its handoff and files in the main checkout. That settle runs on the loop
between the awaits of a `Lander` that holds `main_lock` while its merge runs in a thread
(landing.py:237). So a Manager commit can land in the middle of a landing's merge, or in the
middle of `settle_po`. AC1.3 says the main checkout moves only by landing and story-admin
commits. C6 says: "The Manager takes it only around its settle." The fix dropped the step-long
lock, as round 2 asked, but took nothing in its place.

Fix: for the Manager under story branches, run the role unlocked and take `main_lock` around
`settle_work` and `apply_settled`. `test_with_story_branches_the_manager_step_does_not_hold_the_lock_r2`
only checks the unlocked half. Add a test that the lock is held while the Manager's settle
runs.
