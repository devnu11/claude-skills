## Blocking defects

### N5. A sprint boundary waiting on a DevOps fix deadlocks the run (s159/AC6.7, AC2.6; REQ-156, REQ-139)
`BoundaryRunner.due()` (boundary_runner.py:181–188) returns
`Due(FIX_KINDS[case], "devops", brief)` when the boundary has a failure, a team-check failure
or a replay/rebase conflict. `Router._boundary_work` turns that into
`Work("devops", None, brief, StepKind.TEAM_FIX | REBASE_FIX)`. The new
`Scheduler.is_held_by_boundary` (scheduler.py:255–257) holds every work item whose kind is not
`BOUNDARY` and whose role is not Manager while `due()` is not `None`. That includes the
boundary's own DevOps fix. So:

- the fix never starts, and the boundary failure is never cleared;
- `due()` stays non-`None`, so every story step stays held;
- `start_work` starts nothing, and the run sits there or goes to `check_idle`.

Every sprint-end replay conflict (AC2.6) and every red team check at a boundary now stalls
the run. No test drives the scheduler through a boundary fix. `test_s151_conflict_e2e` calls
`br.after_fix` directly, which is why the runner's suite stays green.

Fix: don't hold the boundary's own work. Compare against the work `_boundary_work()` offers,
or exempt `FIX_STEPS` with `story is None`. Then add a scheduler-level test in which a
boundary conflict's DevOps fix starts and the boundary finishes.

### R1. The gate blocks the event loop again (s159/AC6.2, AC6.3, AC11.3; REQ-153, REQ-154, REQ-162; design C6, D2)
`Runtime.settle_work` now calls `self.settle(plan, result)` on the loop thread. `_settle` →
`_apply` runs the gate, which is the story's full suite and coverage run and takes minutes.
`apply_settled` runs `StoryPusher.after_step` (git push, `gh pr create`) on the loop too, and
the boundary stage runs inline in `run_boundary`. While any of these runs:

- no other story's task advances, which breaks AC6.2's "at the same time";
- the PO desk serves no turn, which breaks AC6.3 and AC11.3 ("within seconds of an answer");
- the heartbeat stops.

The developer's handoff says so ("settle, push and boundary stages are back on the loop
thread, not split per C6"). C6 already says how to split this. Run the commands (the gate's
suite, git, `gh`, the push) through `system.in_thread` and get data back. Then apply the state
change on the loop: `Lander` already does this through `system.in_thread` (landing.py:237),
and `run_ci_poll` now does too. Doing it only for the gate's suite run and the push is enough
to close D2. The rest of `settle` is fast.

### R2. The Manager holds the main lock for its whole step (s159/AC6.8, AC11.3; REQ-156, REQ-162; design C6)
`Scheduler.uses_main_checkout` (scheduler.py:365–369) returns `True` for `MANAGER`, so
`dispatch` holds `main_lock` around the whole Manager step. C6 line 500 says: "The Manager
takes it only around its settle." While a Manager review runs, every land and every
`settle_po` waits for it. A PO turn's tool calls then don't land until the review ends.
`is_turn_refused` no longer waits, but the turn's settle does. Take the lock only around the
Manager's settle once story branches are on. Before the switch, the current behaviour is
right.

## Should fix

- **N6. A story-CI result can be recorded against a newer head** (s159/AC8.3, REQ-158).
  `run_ci_poll` reads checks for `story.pushed` in a thread (`read_checks`). Then `settle` →
  `_record` builds `StoryCi(story.pushed, …)` from the head at record time
  (story_ci.py:129). If the story's own step task finishes and pushes during that `await`,
  red checks for the old sha are recorded and handed over as the new head's CI. Have
  `read_checks` return the sha it read and record that sha.
- **N7. `restore_edits` pops `stash@{0}`, not the story's stash** (s159/AC2.13). It is safe
  today only because replays run one at a time on the loop. Use `git stash pop <index>` for
  the entry whose sha is `stashed.sha`, so a later concurrent replay can't pop another
  story's edits. The point of `Stash.sha` is to name it.
- **N8. The kept-stash note goes only to the PO** (s159/AC2.13, AC11.2). The story's next
  step resumes "from the worktree" without the edits and with no mention of them. Put the
  `KEPT_STASH` line in that step's brief too, or record it on the story.
