## New blocking defects

### N1. Settles, story pushes, boundary stages and CI polls change `RunState` off the loop thread (s159/AC6.4, REQ-154; design C6)
C6 says: "In-memory `RunState` changes happen only on the event-loop thread. Worker threads …
run commands and git and return data. They never touch `RunState`." The design checklist
(line 1222) adds: "A save from a worker thread raises `WrongWriter` (AC6.4)."

The fix does the opposite:
- `RunWriter.run_off_loop` runs whole state-changing calls in `asyncio.to_thread`. These are
  `Runtime.settle` (handoff, quarantine, commit, gate, story advance), `StoryPusher.after_step`
  (records `pushed`), `boundaries.step` (a whole boundary stage) and `StoryCiPoll.poll` →
  `_record` (sets `story.ci`, emits).
- The `_lent` set exempts those threads from `check_owner`, so the `WrongWriter` guard
  no longer guards them.
- Meanwhile the loop thread keeps changing and reading the same objects. That covers PO tool
  calls (hold, cancel, move, edit), other stories' `apply_settled`, `router.apply_queues`,
  `queue_news`, and `drain()`, which serialises `state` while a thread changes it. Two settles
  can also run in two threads at once, in a stage-log context (`stage_log.within`) that is not
  thread-local, as far as I can tell.

Failures that follow: a PO `cancel_story` or hold applied between a settle's read and its write
is overwritten by the settle's advance (AC11.1). A save can serialise half of a step's
change, or raise `dictionary changed size during iteration` when a thread adds a key. None of
this shows up in tests, because no test runs two steps at once.

Fix as C6 says: run only the commands (the gate's suite, git, `gh`, the push) in
`system.in_thread`, return data, and apply the state change on the loop through `writer.apply`.
Keep `check_owner` strict.

### N2. A PO turn can't start while a land, a boundary stage or the Manager holds the main lock (s159/AC6.7, AC11.3, REQ-156, REQ-162)
`PoRun.is_turn_refused` now takes `main_lock` before every turn. These hold that lock for
minutes:
- a land, from its merge through its CI wait to its fast-forward (C6, up to `ci_timeout_s`);
- `Scheduler.run_boundary_stage`, for a whole stage, including sprint-end CI waits;
- a Manager step, which holds it for the whole step (`uses_main_checkout`). C6 says "The
  Manager takes it only around its settle."

So while a story lands or a boundary runs, the PO serves no turn. That breaks AC6.7 ("keeps
serving PO turns") and AC11.3 ("carries on within seconds of an answer"). My last review
recommended exactly this lock ("the `checkout_moved` check at a turn's start, take the main
lock"). That recommendation was wrong.

The right fix follows `Scheduler.tick`: skip the drift check while the lock is held
(`if not main_lock.locked()`), because the holder records its own checkout move. Only
`settle_po` then waits for the lock. Separately, the Manager should take the lock only around
its settle, as C6 says, when story branches are on.

### N3. A stash pop that conflicts silently drops the cut-off step's edits (s159/AC2.13, REQ-144)
`StoryReplay.restore_edits` handles a failed `stash pop` with `reset --hard`. That removes the
conflicted tree, and the edits stay only in the shared `refs/stash`. No note, hand-over or
state field says so, and nothing pops that stash later. The story's next step continues
"from the worktree" without its edits (AC11.2).

On the rebased path this is likely, not rare: the edits were made against the old branch tip,
and the new sprint head holds other stories' landed changes. AC2.13 says the edits are
"re-applied after".

At least, keep the stash and tell the PO and the step, naming the stash ref, so its owner can
apply it. Also, on the clean-pop path, check that untracked files from a partly failed pop
aren't left behind (no test covers either path).

### N4. A story step starts while a boundary stage runs, with story branches on (s159/AC6.7, REQ-156; design C7)
`Scheduler.run_boundary` used to run the stage synchronously. Now it creates the
`BOUNDARY_KEY` task, returns `True`, and `start_work` goes on through the rest of
`router.works(...)` in the same loop. `check_free` refuses other work only when story branches
are off (`ONE_AT_A_TIME`). With them on, a story key isn't busy, so story steps start while
the sprint-end replay or sprint-start stage runs. Their worktrees come from a sprint head that
is being replayed and pushed.

C7 says "A due boundary starts nothing new". The same gap existed before the fix while a due
boundary waited for running tasks (`run_boundary` returns `False` and the loop continues).
I missed it last time. Refuse story starts while a boundary is due or its task runs, and test
it (the AC6.7 test the story lists as "scheduler boundary tests" is missing).

## Should fix

- **S8. `revert_story` on an unbranched story reverts in the main checkout without the lock**
  (s159/AC3.3, REQ-150; D3 residue). `Reverter.revert` runs the old revert path (`is_clean`,
  the revert commits, `record_checkout`, reverts.py:256–264) inside a PO tool call during the
  query, outside `main_lock`. Before the switch, a story step may be running in that same
  checkout under the lock.
- **S9. `NOTHING_TO_STASH` matches git's English message** (s159/AC2.13). `Git` doesn't set
  `LC_ALL=C`, so under another locale a no-op stash reads as `SAVED`, and the pop takes another
  story's stash from the shared `refs/stash`. That is the D5 bug again. Comparing
  `rev-parse -q --verify refs/stash` before and after the push doesn't depend on the locale.
- **S10. `ci_task` sits outside `tasks`** (s159/AC8.3). `stop_tasks` doesn't cancel it,
  `is_finished` ignores it, and an exception from the last poll before the run ends is never
  checked. That is minor, but it is the only task the C10 stop path doesn't own.
- S1 to S7 from the last review stand unchanged: coverage at 97.04% against the charter's
  100%, the copy/paste list, `scratch_rebase.py` kept, the revert landing skipping the
  permission wait, the storyless step's limit halting at once, side effects in queries, and
  `prune_stale` leaving `worktree_head` set.

## What would make this shippable
1. Follow C6: commands in threads, state changes on the loop through `writer.apply`, and a
   strict `check_owner` (N1).
2. Don't lock the PO turn's start. Have the Manager take the lock only around its settle when
   story branches are on (N2).
3. Start no story work while a boundary is due or running (N4).
4. Keep and report a stash that didn't pop cleanly (N3), and detect the no-op stash without
   relying on the locale (S9).
5. Add tests for the D1, D4, D5, N1, N2 and N4 paths, and restore the priority assertion (D6).
   These are tester work once the code is fixed.
