# Review: s180, the runner's own commits are carried over a green landing

Reviewed at d3ad98ca, diffed against d1c33886 (the commit before the story's first
commit, 97f4a053). I read the design (`agile-team/docs/design/s180.md`), the source diff and
the two new test files. The runner's coverage run is green: 100% on the changed modules.

**Verdict: changes requested.** There are two blocking findings (F1, F2). The rest are minor.

## Blocking findings

### F1. REQ-191 does not hold while a landing is held on CI, or after a restart (s180/AC1, REQ-191)

`RunFlags.landing_base` is set only while `Lander.land` runs. `land`'s `finally` clears it
(`landing.py:132-135`). A landing waiting on CI is not always inside `land`:

- **A CI hold.** `wait_ci` times out on pending CI, or infra fails twice. `hold_ci` then
  returns a HOLD report (`landing.py:649-652`), `land` returns, and `landing_base` becomes
  `""`. `story.landed.pushed` is still set, so the landing is still waiting. Until the
  story's land runs again, often hours later, `_is_held_by_landing` holds nothing
  (`router.py:343-349`).
- **A restart.** `RunFlags` lives in memory. After a restart `landing_base` is `""` until
  that story's land step reaches `check_resume`. Any story the router offers first is not
  held.

During either window, a sprint story with no branch can start. `Workspaces._fork` then sets
its `base_sha` to the moved sprint head (`workspaces.py:48-51`). That head is the story-file
commit, which is exactly AC1's scenario. On resume, `find_fork` refuses with `FORKED`, and
the landing drops with `sprint head moved`. That is the s165 incident again, and REQ-191
names this case: "While a landing holds a merge (made, checked, pushed **or waiting on
CI**) … a story that has no worktree yet doesn't start". The s165 incident itself looks like
the hold-and-resume path, not the in-`land` ShaWatch wait.

The design causes this. C6 says to clear the flag "when `land`/`land_revert` end
(`finally`)", so the fix goes back to the architect. One way to fix it: derive the base from
state instead of an in-memory flag, for example the first parent of the merge of any story
whose `landed.pushed` is set. That state is already saved and survives both windows. No
test covers either window. Every C6 test sets the flag by hand or checks it inside one
`land` call (`test_s180_landing_carry.py:256-323`).

### F2. The end-to-end tests the design and the story's Tooling section name do not exist (s180/AC1, AC2, AC3; REQ-190, REQ-192)

The design's checklist lists five real-git cases in `tests/e2e/test_s180_carry_e2e.py`
(design lines 353-374). Its Files list names that file. The story's `## Tooling` section
(commit 566606dc) says "AC1/AC2/AC3: automatic today: tests/e2e/test_s180_carry_e2e.py …".
The file is not in the repo (`tests/e2e/` has no s180 file, and no commit in the story adds
one).

Every lander test runs on fake git with scripted replies (`carryable`,
`test_s180_landing_carry.py:40-53`). So nothing checks the git behaviour this story depends
on:

- that `cherry-pick --allow-empty --keep-redundant-commits base..head` in a detached land
  worktree gives the copies in order, with authors and trailers kept (REQ-190);
- that `reset --keep` moves the main checkout to the tip;
- that `git log --first-parent` of the sprint branch shows the story-file commit right
  above `merge(s1): …`, and that the remote sprint branch is the merge (AC1's own by-hand
  check);
- the storyless-style commit (AC2);
- a real merge in the span giving `MERGED` with `merge(s2): …` among `moved` (AC3);
- an amend of the story's own story file during the wait that conflicts and gives `STOPPED`
  with the remote unchanged.

The Tooling section is also false as written. Fix it in the same round.

### `router.py`

`_story_offers` and `_is_held_by_landing` implement C6 as designed, and the parametrised
test covers the four cases plus a story at `land`. There are two defects. F1 is blocking.
The other is minor (s180/AC1, REQ-191): the rule keys on `worktree_head`, not on `branch`.
A story that already has a branch but lost its worktree (see s179) is held too, though
`Workspaces.ensure` would not fork it again (`workspaces.py:40-41`). This holds a story
that needs no hold, but it is never wrong. The fix for F1 is a good moment to key the rule
on `not story.branch`.

## Copy/paste

- `check_resume` and `take_carry` both run "refusal → set `not_carried` → `give_up(attempt,
  GIVE_UP_MOVED)`" (minor, see above).
- `check_resume` and `plan_carry` both run "read_move, is_unmoved, find_refusal". That is
  acceptable: the two have different outcomes.
- Tests: the stack setup `StackEntry(1, SPRINT, OLD, OLD, head=HEAD, pushed=HEAD)` with
  `landing_base` is repeated in `held` and `test_a_story_at_land_is_never_held…`
  (`test_s180_landing_carry.py:295-323`). `held` could take `step` as a parameter. Also,
  `[a for a in (tuple(c.argv) for c in fake.commands)]` (line 103) is a redundant
  comprehension. Both are minor.

## What must change

1. Architect: change C6 so the hold also covers a landing held on CI and the time after a
   restart (F1). Update the protocol text to match.
2. Developer: implement it, and add a lander test where a story's `base_sha` or
   `rebase.onto` is in the span and the landing drops with `FORKED`.
3. Tester: add `tests/e2e/test_s180_carry_e2e.py` with the design's five cases, plus one
   for the hold window from F1. Make the story's Tooling section true (F2).
