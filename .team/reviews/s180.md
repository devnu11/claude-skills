## New findings

### N1 (must fix, unit-tester): tests for F1 and F2 (s180/AC1, AC2, AC3; REQ-234, REQ-235, REQ-236; design C1, C3)

1. `Carrier.carry` with a land tree already there: assert that `worktree remove --force`
   comes before `worktree add --detach <tree> <merge>` in the fake's call log. Also assert
   that a failed `worktree add` still runs the `finally` removal. That second part is the
   other half of F1: the add now sits inside the `try`.
2. `Lander.check_carry` (or `land` through the resume path) where `rev-parse <merge>^1`
   fails: the result is `Carry(refusal="the merge <sha7> has no first parent")`, the merge
   is given up with a `landing-dropped` event whose `refusal` is that text and whose
   `moved_by` is `[]`, and `list_carried` is never called (no `git log` with a `fatal:`
   range).
3. F4: make the assertion exactly `add.argv[-3:] == ("--detach", str(TREE), M)`.

### N2 (minor, developer-cli): `CARRY_NO_BASE` is a sixth refusal the docs don't list (s180/AC3; REQ-236; design C2)

The design's C2 and the architecture row list the refusals as off head, a merge, pushed, a
forked story and a conflict. `CARRY_NO_BASE` is new. It is the right fail-safe, but
`protocol.md`'s refusal list and the design's C2 should name it so the PO can read a
`landing-dropped` `refusal` of this kind. The wording "has no first parent" is also not
quite accurate: the usual cause is a merge object missing after a restart or a gc, so
"the first parent of the merge {merge} can't be read" says what actually happened. This is
not blocking alone; fix it together with N1 if you can.
