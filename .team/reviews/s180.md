## Findings

### F1 (must fix): `Carrier.carry` never clears a leftover land worktree, so a crash mid-carry wedges the landing (s180/AC1, AC2; REQ-234, REQ-235; design C3)

`landing_carry.py` `Carrier.carry`:

```python
self.upstream.git.run("worktree", "add", "--detach", str(self.tree), span.merge)
try:
    return self.run_replay(span, commits)
finally:
    remove_land_tree(self.upstream.git, self.tree)
```

The `worktree add` runs before the `try`, and nothing removes an old tree first.
`Lander.merge` does remove it first (`await self.clear_tree()` before its own
`worktree add`, landing.py:339). Here is how it breaks:

1. The runner is killed or crashes during the cherry-pick (the window between the add and
   the `finally`). `.team/run/land` stays, either on disk or registered with git.
2. On restart `story.landed.pushed` is still set, so `run_land` takes the resume path:
   `check_resume`, then the CI wait, then `move_sprint`, then `push_and_follow`, then
   `prepare_carry`, then `Carrier.carry`. That path never goes through `merge()`, so
   nothing calls `clear_tree`.
3. `git worktree add` fails ("already exists", or "missing but already registered
   worktree"). `Git.run` raises `GitError`. The exception escapes `push_and_follow` and the
   land step crashes. The `finally` never runs because the add sits outside the `try`.
4. Every retry repeats steps 2 and 3, so the story can't land until someone removes the
   tree by hand.

C3 says "the worktree is always removed afterwards", and REQ-234/235 need the landing to
complete. Fix: call `remove_land_tree(self.upstream.git, self.tree)` before the add, as
`merge()` does. Test: a `Carrier.carry` test where a worktree is already there checks that
`worktree remove --force` runs before `worktree add`.

### F2 (should fix): `Lander.read_span` dropped the rev-parse exit-code check (s180/AC3; REQ-236; design C1)

The old `is_on_head` checked `parent[0] == 0`. `read_span` now uses
`parent[1].strip()` as the base whatever the exit code. `Git.attempt` returns stdout plus
stderr, so a failed `rev-parse <merge>^1` makes the base a `fatal: …` text. Then
`check_carry` calls `list_carried`, which calls `list_commits` with
`git.run("log", …, "fatal: …..H")`. That raises `GitError` and crashes the land step. The
old code gave the merge up cleanly instead. A failed rev-parse is rare (a merge object
missing after a restart or a gc), but the old code handled it and the new code doesn't.
Fix: when the exit code isn't 0, return a span that `check_carry` refuses, for example
`base=""` handled before `list_carried`, so the merge is given up with
`CARRY_OFF_HEAD`. No test covers this.

`_check_merges` has a smaller version of the same problem. A failed `rev-list --merges`
returns its stderr words, and those become "merge shas" in the refusal text. That fails
safe (the carry is refused) but the reason is wrong. Note only.

### F3 (minor): `read_story_number` duplicates `priority.natural` and has no docstring (no AC; engineering rules DRY and "every public function documented"; design names the existing sort)

The design says "sorted by the numeric id, as `requirements` and `landing_queue` sort".
`priority.natural(sid)` already does this, and `requirement_changes` uses it. The new
`read_story_number` strips non-digits instead, so `s12` and `s1a2` both become 12, and a
storyless id becomes 0. Use `natural`. `run_replay` and `stop_pick` are public methods
with no docstrings either.

### F4 (minor): weak assertion in `test_carry_cherry_picks_the_span_onto_the_merge_in_the_land_tree` (s180/AC1; REQ-234; design C3)

`assert add.argv[-3:] == ("--detach", str(TREE), M) or M in add.argv` passes whenever `M`
is anywhere in the argv, so the `or` makes the exact-argv half meaningless. It should
assert the exact tail (`--detach`, the land tree, `M`).

### F5 (minor): no lander-level test of a `CARRY_CONFLICT` refusal (s180/AC3; REQ-236; design C6)

Every refused carry in `test_s180_landing.py` is `CARRY_OFF_HEAD`, from `check_carry`.
The conflict refusal comes from `Carrier.carry` inside `prepare_carry` and then goes
through `push_and_follow`'s `if carry.refusal`. It takes the same branch, so coverage is
100%, but nothing shows that a conflict refusal reaches `landing-dropped` with
`moved_by`. The planned AC3 e2e covers it. Fine to leave to e2e.

### F6 (note): copy/paste

The conflicted-files read (`diff --name-only --diff-filter=U`, then split) now appears in
7 places (`landing.py:370`, `replay.py:169`, `replay.py:262`, `git_ops.py:157`,
`upstream.py:597`, `landing_carry.py:163`). The pattern was there before this story.
s180 adds one more. A follow-up could add a `Git.conflicted_files()` helper. Not
blocking. No other repeated blocks: `emit_carried`, `apply_carry` and `prepare_carry` are
new, and `clear_tree` now calls the shared `remove_land_tree`, which removes a duplicate.
