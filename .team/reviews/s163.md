## Non-blocking findings

- **N14 (new, s163/AC5, REQ-171, test gap).** No test puts a `LAND` task in `sched.tasks` and
  asserts `may_apply_queues is True`. That is the exact M1 regression (the old code waited on a
  landing). Today the predicate (`scheduler.py:173-175`) has no `LAND` term, and K1 is tested at
  the lock level in `Lander`, so the risk is low. A one-line extra case in
  `test_s163_scheduler.py` would guard it.
- **N15 (new, s163/AC6, REQ-172, test gap).** `Scheduler.follow_boundary` (`scheduler.py:456-464`):
  no test that a second call while `follow_task` is live starts no new task, that a call within
  `beat_s` of the last is skipped, or that `check_follow_task` re-raises what the follow raised.
  The two B6 tests also repeat the `Event` + `create_task(BOUNDARY_KEY)` setup (DRY, tests only).

- **N1 (s163/AC1, REQ-167, still open).** The scheduler-level checklist for AC1 is still missing: two stories at
  `land` where the smaller lands first and the other waits with `waits to land after <id>`;
  a held or bounced story rejoining by size; `RunState.landing` across a save and load.
  `test_s159_scheduler.py:75-90` still sets the removed `rt.state.land_queue`. That test
  passes only because both stories are size 0 and `s1` sorts first, so it tests nothing
  about the queue. Rewrite it against the s163 queue (e.g. give `s2` the smaller diff and
  assert that `s2` lands first) and drop the `land_queue` lines. This is cheap, so do it with B1 to B3 if you can.
- **N2 (house rule, no AC).** `LandingQueue._accept(placement, order, smallest)` and
  `BoundaryRunner._run_replay(b, tools, progress)` take 3 parameters, and the charter allows 2.
  `Lander.move_to_remote`, `push_and_follow` and `LandingQueue.place` run past 8 lines.
- **N3 (DRY, s163/AC1 + AC3).** The `revert_queue` membership test is written out three times
  (`LandingQueue._is_live`, `_get_span`, `_queued_ids`). The landing-branch delete
  (`landing_branch(...)` + `run_off(upstream.delete, Lease(branch, merge, ""))`) is
  duplicated in `Lander.give_up` and `finish_pushed`. In the tests,
  `test_s163_landing.py:26,38,58` repeats the `LANDING_DROPPED` filter that
  `test_s163_landing_moves.py:31` already has as `dropped()`.
- **N4 (s163/AC3, REQ-169, design-sanctioned).** A give-up in K2 step 1 deletes the landing
  branch under the lock, and `finish_pushed`'s `finally` deletes it a second time. That second
  delete is refused harmlessly.
- **N5 (s163/AC6, REQ-172, design-sanctioned B4).** REPLAY holds the main lock for the whole
  stage, including the rebase-fix check run. ADR 0088 should record this as a known limit.
- **N6 (s163/AC6, REQ-172, still open).** `start_boundary` doesn't check `follow_task`, so a stage task can
  start while an R9 follow runs. The window is small, because the follow runs only on a CI hold.
- **N7 (s163/AC2, REQ-168).** `Overlaps._read_theirs` runs `git show f"{other.branch}:…"`
  when `other.branch` is `""`, which reads the main checkout's index. `_read_changed_files`
  splits on whitespace, so a path with a space becomes two paths.
- **N8 (s163/AC2, REQ-168).** No test shows that after a lift, the next step replays the
  branch onto the current sprint head (design §7 AC2). The replay itself is s159 code with its own tests.
- **N9 (s163/AC1, REQ-167).** After a crash, `state.landing` keeps naming the interrupted story
  while it stays at `land`. If the PO holds it, every other landing waits.
- **N10 (s163/AC3, REQ-169, new this round).** G4 treats any refused sprint push whose remote still equals
  `entry.pushed` as "re-land". When the refusal isn't a lease refusal (auth, branch
  protection, network: `push()` turns every `UpstreamError` into refusal text), each of
  `MAX_RESTARTS` (5) attempts merges, runs the full checks and waits for landing CI again,
  then holds with "the sprint branch kept moving", which is the wrong reason. Before s163 this
  halted at once. The design sanctions re-landing when `R == pushed`, so this is not a code
  defect against the design. The architect should decide at design-review whether a refusal
  with an unmoved remote should hold with the refusal text instead.
- **N11 (s163/AC3, REQ-169, new this round, unverified).** If a sprint push reports a refusal but
  actually reached the remote (`R == merge`), `follow_remote` has already cleared `landed`,
  fast-forwards to `R`, and restarts. It then merges a story branch that `R` already
  contains. I didn't trace what `merge()` does with "Already up to date". An e2e case would
  settle it.
- **N12 (test quality, s163/AC5).** `test_the_lock_can_be_taken_by_others_while_ci_waits_k1`
  asserts the same `locked() is False` as the test above it. Its name promises that another
  task takes the lock, but nothing does. It should acquire `probe.lock` inside `act` (as an
  `async` watch), or be removed. `test_a_refused_landing_whose_remote_is_ours_does_not_halt_g4`
  asserts only that the run didn't halt and that `>= 1` drop happened. It doesn't show the
  story merging afresh and landing, so E1 should cover that.
- **N13 (docs, no AC).** `protocol.md`, `SKILL.md` and `README.md` are unchanged. Design §9 gives
  them to the architect at design-review. Still open; the docs step must land them before the story closes.
