## Defects

### D1 (major): a landing revert and a land can run at once. s163/AC1, REQ-167 (design Q1, Q5)

`Scheduler.start_revert` (`scheduler.py:416-423`) does `queue.remove(call)` and then
`run_revert` calls `self.landings.begin(story.id)`. From then on the reverted story is
`state.landing`, but it is neither at `land` (it is done) nor in `runtime.revert_queue`, because it
was just removed. On the next tick `check_land`, which calls `LandingQueue.next_up()`, goes to
`_is_live` (`landing_queue.py:106-109`). That returns `False`, so `next_up()` **clears
`state.landing`** and hands the first waiting story to `check_land`. That story's land task then
starts while the revert task is still running. Nothing else stops it: `check_land` never looks at
`REVERT_KEY in self.tasks`.

This breaks Q1 ("landings stay one at a time"), Q5 ("a revert and a land never run at once") and
AC1 ("A landing revert … takes its turn in the same queue"). Both tasks merge onto the same
sprint head, and only the move lock orders them. One of them then gives up its merge (K2 step 1),
so the run stalls through restarts instead of landing serially.

Q5's stale-landing clear exists for a *restart* (the revert queue is in memory). It must not fire
while the revert task runs. A fix is for the developer to choose: keep the call queued until
`finish`, make `_is_live` true while `REVERT_KEY` runs, or make `check_land` wait on a running
revert. Whatever is chosen needs the §7 test "A revert and a land never run at once".

### D2 (minor): `find_merged` crashes with no upstream. s163/AC4, REQ-170 (design S2)

`Tools._drop_merged_entries` (`po_tools.py:371-376`) passes `rt.upstream` to
`switchover.find_merged`, which calls `upstream.missing()` right away. When `runtime.upstream` is
`None` and the stack holds an entry with a `head`, `start_sprint` raises `AttributeError`. S2 says
"With no upstream … nothing is dropped." Guard on `rt.upstream is None`. No test covers "no
upstream, or a failed fetch: nothing is dropped" (§7 AC4, last bullet).

### D3 (minor): a failed `git diff` becomes "changed files". s163/AC2, REQ-168 (design F3)

`Overlaps._read_theirs` (`overlaps.py:96-102`) checks `git show`'s exit code but not the exit
code of `git diff --name-only`. It splits the output into tokens and matches them as paths. When
the diff fails (a missing local ref, or a bad `base_sha`), the git error words (`fatal:`,
`ambiguous`, …) become the other story's files, and an ours entry such as `*` or `**` "overlaps"
them. Treat a failed diff like `git show`: it contributes nothing. Also, when `other.branch` is
empty, `git show :<design>` reads the *main checkout's index*. F3 says an other story with no
branch "contributes what it has". Say whether that is the intended source, or skip the read.
