Role steps (C7): `test_role_steps_run_fresh_and_ledger_their_reported_cost` pins
`resume is None` and unchanged cost. Checkpoint (C8):
`test_checkpoint_reflects_real_spend` gets exactly `budget checkpoint at $2.10`.

Paths I traced by hand that also hold:
- **Error result in the same session** (the common case): `_collect` raises
  before `_own_cost`, so `po_cost` keeps the pre-error total; the next query
  resumes the same session and its delta includes the errored query. ADR-004
  point 4 holds.
- **Compact renewal**: the compact turn resumes `turn.resume` and stores its
  total; the follow-up turn resumes `state.po_session`, so it deltas against
  the compact turn. If compaction ever issues a new session id, `po_cost`
  already holds that id, so the next delta is still right.
- **Fresh `start` (not resume) with an old `po_cost`**: `resume=None` → base 0.

## Non-blocking notes

1. **Reset in the middle of a query.** If a `ConversationResetMessage`
   arrived inside a resumed PO query and the post-reset total then went past
   the old base, the delta would undercount. The runner never sends `/clear`
   to the PO, so this cannot happen today. ADR-004 already tells whoever
   upgrades the SDK to re-check the evidence. No action needed.
2. **Legacy seed with a `po_session` saved by an error.** If an old
   `state.json`'s `po_session` came from a `ResultError` in a *different*
   session from the last ledgered one, C6 would subtract the wrong base once.
   The ADR's evidence shows one session across the whole ledger, so the
   design accepts this. It is one-off and only on upgrade.
