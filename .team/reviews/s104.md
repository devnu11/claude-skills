## On D1 (node-harness tests)

The design put the node-harness checks in `tests/test_s104_flow_page.py`.
But in this repo `tests/dashboard_node.run_page` is only called from
`tests/e2e/test_dashboard_e2e.py`, because it starts a `node` process. So
the tester's split follows the repo's existing convention: static source
checks go in the unit suite, and page behaviour goes in e2e. I accept it.

The behavioural items **must** land in the integration-tester's
`tests/e2e/test_s104_flow_e2e.py`, beside the design's existing e2e item.
The static checks only pin that the code is present, not how it behaves:
- AC4 cause: `flowSource` in Story scope with a focus that leaves a
  `class rN idle` line, and in Sprint scope. No `classDef` line has a
  compositing style.
- AC4 hidden then shown: use a fake `mermaidModule`. Nothing renders while
  the board tab is shown. After `showTab("flow")` there is one `initialize`
  with `useMaxWidth === false` and `fontSize === "16px"`.
- AC2: `· idle` with no `$0.00` for a role with no data, and a role with
  totals still shows its stats.
- AC5: `developer-db` `used: false` → no node; `used: true` → one node; no
  key → drawn.
- s96 labels (`⏱ running`, time span) still hold.

I'm flagging this so the e2e step doesn't drop it. It doesn't block on its
own.
