# Review: s182 (story rebase settle adds no commit; commits check names each commit)

Reviewer step, round 0. Diff read: `8eb97cf9..1cb22ec1` (story commits be03fb21 → 1cb22ec1).
Design: `agile-team/docs/design/s182.md` (R1–R9), ADR-0092. Tests were read, not run. The
runner's coverage run passed at 1cb22ec.

**Verdict: changes requested.** The code follows the design closely and reads well. But
the fix depends on real git behaviour (`reset --keep HEAD^`, `commit --amend`, porcelain
status after both), and every test of it uses `FakeSystem`. That is the same kind of blind
spot that let the original bug through. AC4 has no test. One attribution defect breaks
AC3's "who made it".

## Findings

### F1 (defect, s182/AC3, REQ-219): a role's extra commit is blamed on the runner once folded

`_add_leftovers` → `story_rebase.add_to_tip` amends whatever commit is at the tip, then
appends the new sha to `rebase.made`. Take a role that adds an extra commit `Y "wip"` on
top of the replayed commits and also leaves an in-scope edit. The rebase is foldable
(on its branch, on `onto`, HEAD ≠ onto), so the runner amends `Y` into `Y'` and records
`Y'` in `made`. `_find_changed_commits` then reports
`- extra Y' wip (made by the runner)`, but the role made that commit. The runner only
amended it. This is the s180 confusion again ("the runner added it"), and it breaks
REQ-219's requirement to say whether the role or the runner made the commit. The design's
rule (R6: "`the runner` when the sha is in `rebase.made`") produces this result, so the
fix needs a small design call. Some options:
- record the pre-amend sha in `made` as well (e.g. `made: {new: old}`) and say
  "made by the role, amended by the runner";
- or only fold when the tip's subject is one of `base..old`'s subjects (i.e. the tip is a
  replayed commit). Otherwise leave the edit, so the dirty refusal names the file.
No test covers this case. `test_an_extra_commit_in_made_is_the_runners` scripts `made` by
hand.

### F2 (test gap, s182/AC1, AC2, REQ-217, REQ-218): no real-git test of the settle

The design's test checklist says "real git in a scratch repo". The story's Tooling section
(ops-review) promises "a real-git e2e test in agile-team/runner/tests/e2e/" for AC1, AC2
and AC4. There is none: `tests/e2e/` has no s182 test, and grep finds s182 symbols only in
`test_s182_story_rebase.py` and `test_story_rebase_steps.py`, both `FakeSystem`. The
fakes check argv order only. They never prove these:
- after `guard.set_aside`, `git reset -q --keep HEAD^` removes a **tracked and an
  untracked** out-of-scope file from the worktree, keeps an unstaged in-scope edit, and
  leaves the branch at its old sha (design checklist: "tracked and untracked";
  "`guard.set_aside` keeps other unstaged edits in the worktree");
- the ref `refs/agile-team/set-aside/<sha>` holds the edit;
- after `add_to_tip`, the tip keeps its subject and author, holds the edit, and the tree
  is clean, so `find_refusal` returns `None`;
- the full step: `_settle_step_tree` followed by `_apply_rebase` adopts the branch
  (`story.rebase is None`, `onto..branch` subjects equal `base..old`). Today each half is
  tested alone with scripted replies (`finished()` scripts `status --porcelain=v1`, and the
  `_find_dirty` reply is scripted separately), so the s180 failure (settle output fed into
  the check) is never exercised.
The AC1 by-hand scenario (resolve, `rebase --continue`, then edit a conflict file) is
exactly the case to automate with `conftest` git and `set_git_identity`, following
`test_rebase_branch_confinement_e2e.py`.

### F3 (test gap, s182/AC4, REQ-221): renumbering inside the replayed commits is untested

No test has a resolution that changes ids (REQ/ADR) in conflicting files, committed through
`rebase --continue`, and checks that `find_refusal` passes and the branch is adopted.
`test_equal_subjects_with_other_shas_pass` covers "same subjects, new shas" with fakes
only. That is necessary but it is not the AC. Design checklist item "AC4: …" is unticked.

### F4 (test gap, s182/AC3, REQ-220): the advance refusal is only unit-tested

`Pipeline.ruling_move_refusal` is well covered (refused with a queued rebase, before
`ADVANCE_LAST`, other rulings pass, no rebase unchanged). The design checklist also asks
that "`story.step` and `story.rebase` are unchanged, and the next work is the rebase at the
same step", through the ruling path at `dispatch.py:2035` and the router. No test applies
an `advance` ruling to a story with a queued rebase and then checks the step, the rebase
and the next pick. The dispatch path is generic and probably correct, but REQ-220 is the
behaviour that kept s180 looping, so it deserves one test at that level.
