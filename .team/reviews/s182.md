## Changed functions

### `story_rebase.is_tip_replayed(git, rebase)` (new; s182/AC1, AC3, REQ-217, REQ-219)

**What it does.** It reads the tip's subject (`log -1 --format=%s`) and returns whether
that subject is one of `base..old`'s subjects. So a tip the role added is never amended.

**Correctness.** It is correct for the F1 case. If the role adds `Y` and leaves an in-scope
edit, the tip is `Y` and `Y` is not replayed. The edit is not folded, it stays in the
worktree, and `_find_dirty` refuses it with the file named. That matches the design's R4
"dirty" path and AC1's "bounced with a reason that names the uncommitted file". One corner
is left: the role adds an extra commit whose subject copies a replayed one. Then the fold
happens, and `_find_changed_commits` lists it as an extra `made by the role`. That is still
true, so I accept it.

**Tests: F1a, a test gap (s182/AC1, REQ-217).** No test drives the `False` branch. Both
`foldable` fakes reply with a replayed subject, so every fold test takes the `True` path.
Because the guard is the second operand of an `and` on one line (`story_rebase.py:270`),
coverage can't show that the branch is missing. Two tests are needed, and the second pass
asked for both:
1. a unit test: tip subject not in `base..old` → `is_foldable` is `False`;
2. a dispatch-level test (in the style of `test_story_rebase_steps.py`): a role-made extra
   tip plus an in-scope leftover gives the dirty refusal naming the file, no `folded` key,
   nothing added to `rebase.made`, and never `made by the runner` or `COMMITS_CHANGED`.
   This is the design checklist's AC1/R4 item (`design/s182.md:85`).

**Design drift (F1b, architect, minor; s182/AC1).** R4 (`design/s182.md:25`) and the
`is_foldable` contract (`:54`) still list four conditions and leave out the replayed-tip
one. Either the architect writes the fifth condition into R4, or the PO accepts that the
code goes further than the design. A design that doesn't match the code misleads the next
reader.

### `story_rebase.is_foldable` (changed; s182/AC1, REQ-217)

It now also requires `is_tip_replayed`. The order is right: the call is lazy, so the
`HEAD == onto` case short-circuits before any `log`. It has no defect beyond F1a.

### `story_rebase._get_maker` (unchanged since the third pass; s182/AC3, REQ-219)

**F1c, test defect (s182/AC3, REQ-219).** With the new guard, the runner folds only into a
replayed tip, and `add_to_tip` keeps that tip's subject. So every sha in `rebase.made` has
a replayed subject, and `_get_maker`'s `commit.subject not in replayed` is never true for
a real state. `RUNNER` is unreachable outside tests. The output is correct (the role made
every difference, as the story wants), but two tests still assert states the runner can
no longer produce:
- `test_an_extra_commit_in_made_is_the_runners` (`test_s182_story_rebase.py:70`);
- `test_a_reworded_commit_by_the_runner_says_so` (`:90`).

They pin a branch that only exists in fakes and read as if the runner can still add
commits. Rewrite them with a `made` sha whose subject is a replayed one, and assert
`made by the role`. If the developer and architect agree that `RUNNER` is dead, they could
also simplify `_get_maker`, which is a design change (R6 and the AC3 checklist line
`design/s182.md:89`). Don't delete the tests.
