## The three focus areas

### 1. Can the dispute route be used to dodge the round cap? No.

I traced every path out of `implement` that has a `dispute` on it:

| Path | Rounds | Bounded by |
|---|---|---|
| dispute → tests, tester changes the file, `done` → implement | 0 while `disputes <= cap` | `disputes` resets only on a ruling (`apply_ruling`) |
| dispute → tests, tester confirms (`changes_requested`, `architect`) → design | +1 (`_bounce`) | round cap |
| dispute → tests, tester `done` without changing the file | +1 (bounce to tests) | round cap |
| dispute number `cap + 1` and later | +1 each (`_dispute` → `_bounce(story, "tests")`), and it can cap the story | round cap |
| dispute at another step, or with `tests` disabled | ignored; the normal gate runs | n/a |
| dispute with `status != changes_requested` | malformed handoff → bounce at implement, +1 | round cap |

- `_raises_dispute` only fires at `implement` with `tests` enabled. `STOPPED_HANDOFFS`
  is checked first, so a `blocked` handoff with a dispute still holds. Both are tested.
- The free path needs a change to the test file between `base` and `HEAD`.
  `settle_tree` commits *before* `_apply` → `gate`, so `head()` at raise time
  includes the developer's commit, and the tester's commit is in `HEAD` when
  `dispute_settled` runs. I checked this ordering in `Runtime.settle`. A
  developer can't edit tests (scope plus quarantine), so they can't satisfy the
  diff on their own.
- `dispute_settled` passes only on exit **1**. Exit codes 0, 2 and 128 bounce,
  and all of them are tested. That is the fail-safe direction.
- In `_bounce`, confirmation needs `story.step == "tests"` and `target != "tests"`.
  `_handoff_outcome` never returns a `None` target (it defaults to
  `implement`), so a tester can't "confirm" and stay at tests. A bad handoff at
  tests bounces to `tests`, so it doesn't confirm either. Tested.
- In the over-cap dispute, `story.dispute` is set before `_bounce`, but the step
  is still `implement`, so the dispute is not wrongly confirmed. Correct.

### 2. Rulings at any step, with a report when one can't apply

- `apply_manager` → `_rule`: `ruling_refusal` → apply + `ruling` event +
  `applied: true`, or `applied: false, why` with no event and no change to the
  story. This holds for `active`, `blocked` and `needs_manager`. Refusals are
  "no story" and "done". All are tested at the dispatch level with exact text.
- `apply_ruling` resets `rounds`, `disputes` and `dispute` together. Tested.
- `handover.RULING_NOT_APPLIED` and `report_fields` (`ruling`, `ruling_why`)
  are present and tested in `test_handover.py`.
- If the Manager runs on a story and the ruling applies, `note_step` sets
  `hold = None` (no trigger), so a story held at the round cap is released.
  That is good.

### 3. Fit with s19's Router

- The Router runs the Manager story-less (`Work(MANAGER, None, …)`). A ruling
  there is refused with the "needs a story" reason. `Router._step` runs
  `handover.triggers(report)` on story-less reports too, so the PO gets the
  `ruling_not_applied` line. That is the case T12 is for.
- Role choice after a dispute: the verdict is `dispute`, not `bounce`, so
  `_bounced` is false and `step_role` falls through to `_pipeline_role` →
  `unit-tester`. A confirm (`bounce`, `next_role: architect`) leads to
  `_bounce_target` → architect at design. Architect `done` → tests →
  unit-tester. An unchanged-file bounce leads to `_bounce_source` →
  unit-tester. Every hint fits its step.
- `standard_brief` is unchanged. The dispute line comes from
  `Runtime.user_prompt` (`_story_lines`), so router briefs and PO briefs both
  get it. The end-to-end router test (`test_a_dispute_round_trip_costs_no_round_and_no_handover`)
  covers the fix path with `rounds == 0` and no hand-over. The confirm path is
  covered through `run_role` (`test_the_dispute_reaches_the_tester_then_the_architect_then_goes_away`),
  not through the Router. That's fine, because the hint logic above is s19's and
  already tested.
- `cc1f433` (s19 fixup after the s11 tests) only adds a `ClassVar` annotation
  to `Router.PICKERS`. It doesn't affect s11.

## Findings

**F1 (low, follow-up story, not blocking): a `ruling_not_applied` hold on a done
story can't be cleared with `continue_story`, so the Router never runs that
story's Scribe step.** If the PO runs the Manager on a done story and the
Manager gives a ruling, `_note_if_ran` → `note_step` sets
`story.hold = "ruling_not_applied"`. `_scribe_work` skips held stories, and
`po_tools.continue_story` refuses done stories, so the PO's "drop it" option
leaves the Scribe step skipped with nothing reported. You can recover by
`run_role scribe` on the story (its `note_step` resets the hold), or by a
Manager run with no ruling. The window is narrow: the Router runs the Scribe
straight after a story finishes unless that step raised a hand-over. The same
gap was already there for any trigger on a done story (s19). It was not
introduced here. Suggested fix, in its own story: let `continue_story` clear
a hold on a done story, or don't set holds on done stories.

**N1 (nit):** `Checks.head()` ignores a non-zero exit, and `DIFF_COMMAND`
doesn't quote `{base}`. If `rev-parse` failed, `base` would be error text, and
the diff would exit non-1 and bounce. That fails safe, so no change is needed.

**N2 (nit):** `roles.handoff_report` is public with no docstring. This
predates the move.

**N3 (nit):** The confirm path (tests → design → tests → implement) has no
Router-level end-to-end test. Only the fix path does. The confirm path is
covered through `run_role`, and the Router's role hints for it are s19's
tested code.
