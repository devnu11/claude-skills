## Defects

### D1 (major): a service that never answers is reported as "exited with code -15"

`Preparer._await_answer` calls `prepared.stop()` and then
`_not_up_reason(prepared)`. `_not_up_reason` picks its row from
`prepared.process.poll()`. After `stop()` has sent SIGTERM and waited, a real
`Popen.poll()` returns `-15`, never `None`. So the "did not answer `<url>`
within `<s>`s" row cannot happen for a real process. Every timeout is reported
as:

```text
delivery 'ui' did not start: the start command exited with code -15 before http://127.0.0.1:59999/x answered. Last output:
(no output)
```

I reproduced this outside the suite: a real `Preparer._start` running
`sleep 30`, with a probe that always fails and `attempts=3`. This is the text
that the bounced integration-tester (gate) or the returned story (Proxy) reads.
It says the command crashed, when in fact the runner killed a hung service.
That is the kind of misleading cause AC2 is meant to remove.

The design table contributes ("On failure: `prepared.stop()`, then raise
`NotUp(_not_up_reason(prepared))`"), but the reason-strings table clearly wants
the timeout row for a still-running process.

**Fix (developer-cli):** build the reason before stopping, e.g.
`reason = self._not_up_reason(prepared); prepared.stop(); raise NotUp(reason)`.

**Why the tests missed it:** `FakeProcess.poll()` returns its fixed
`returncode` (`None`) even after the runner has signalled it. See T1.

- **T1:** the timeout reason is tested only with a fake that never exits. Add
  one of these:

    `attempts=2`; assert that the text starts with "did not answer … within
    0.5s";
  - a `FakeProcess` whose returncode becomes `-15` when it is signalled. With
    the `stopped` fixture, the stub would set it, then assert the timeout
    text.

  This test must be red against the current code.
- **T2: `sandbox.py:221`, untested (the L7 SIGKILL escalation).** No test
  covers a stale group that ignores SIGTERM. Use
  `sh -c 'trap "" TERM; exec sleep 60'` with `start_new_session=True` and
  monkeypatch `sandbox.STOP_WAIT_S` to about 0.2. Assert that the process is
  gone and the pid file deleted.
- **T3: `sandbox.py:240`, untested (`http_answers` with a 2xx other than
  200).** `urlopen` raises for 4xx and 5xx, so the existing 404 and 500 cases
  go through the `except` and never reach `status != 200`. Add a 204 (or 201)
  case to the `test_http_answers` table, expecting `False`. Together with T2,
  this brings coverage back to 100%.

## Copy/paste

- `_returned` folds the two return bodies into one, and `presented_source`
  replaces the `_order` inline logic. Both are good.
- `_end_group` and `Prepared.stop` both do "TERM, wait `STOP_WAIT_S`, KILL" on
  a process group. One waits on a `Popen`; the other polls `killpg(0)` because
  the stale pid is not our child. The duplication is small and justified. Not
  a defect.
- No other repeated blocks in the diff.

## Observations (no change needed)

- `Trial` lets any `SandboxError` other than `NotUp` or `PortBusy` propagate
  out of `settle()`, as the design intends. That crashes the step after its
  commit rather than refusing it. Config validation makes this unlikely. Worth
  a follow-up if it is ever seen.
- `_end_group` on an unreaped child of the runner (a zombie) would poll for
  the full `STOP_WAIT_S`, because `killpg(0)` still succeeds. L9 stops every
  `Prepared` the runner made, so this needs a missed teardown first.
- Docs (protocol.md presentation/e2e, `gate_hold` row, `probe` key; SKILL.md;
  README) match the code.
