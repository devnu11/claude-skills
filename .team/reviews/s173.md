# Review: s173, a committed config change is live without a restart

Reviewed `61f56411^..98776b39` against `agile-team/docs/design/s173.md` (R1 to R10) and
ADR-0094. The runner's coverage run is green (98%). I read the tests and did not run them.

**Verdict: changes requested.** The code follows the design, and I found no defect in it.
The tests do not check AC1, which is the bug the story fixes. The story's Tooling section
says `tests/e2e/test_s173_*.py` exists and checks AC1 against real git. That file is not in
the diff. Three of the design's AC1 checklist items are also missing.

## Functions

### `config.py`

- **`parse_text`** (new; `read_raw` now calls it). It parses TOML and turns a decode
  error into a `ConfigError` that starts with `.agile-team.toml:`. Tested in
  `test_parse_text_*` for good and bad TOML. `read_raw` still goes through it, so its
  messages are unchanged. No defect.

### `config_reload.py` (new)

- **`ConfigChange.data`**: the event payload. Tested. No defect.
- **`read_blob`**: gives the `HEAD:.agile-team.toml` blob id, or `""` when rev-parse
  fails (R1, R3). Both cases are tested with a fake git. The real-git check the design
  asks for is missing (see F1).
- **`find_last_change`**: `git log -1 --format=%H HEAD -- .agile-team.toml`, or `""`
  on failure (R7). Both cases tested with a fake. Same real-git gap.
- **`find_changed_sections`**: the sections whose parsed values differ, in `SECTIONS`
  order. Tested for one environment, order (toolchain then gates), and equal configs.
  No defect.
- **`check_static`**: `validate` against the book's roles and the sandbox's kinds.
  Tested (clean, then `budget_usd = -1`). No defect.
- **`describe_error`**: a `ConfigError` gives its message; any other exception gives its
  class name too. Covered by the parametrised bad-blob test (`AttributeError:` for
  `team = 3`). No defect.
- **`ConfigWatch.update` / `_take` / `_read_config` / `_apply_live` / `_record`** (R2 to R7).
  Tested:
  - an unset blob is only recorded;
  - the same blob does nothing and never calls `cat-file`;
  - a new blob is taken once, keeps `run_home` and logs one event with role and story
    `None`;
  - the swap is done by assignment and `stages` is re-attached;
  - a comment-only commit gives `sections == []`;
  - the budget applies at once;
  - bad TOML, a broken rule and a wrong shape each keep `config` and `pipeline`, and each
    is logged once;
  - a missing file is reported once;
  - a good commit after a bad one is compared with the last good config;
  - an unknown role is refused.

  I checked `from_raw` for exceptions outside `BAD_CONFIG`. Its helpers raise
  `TypeError`, `AttributeError` or `ConfigError` on bad shapes. I found no `KeyError`
  path. No defect.
  - Gap (s173/AC1, REQ-262): `_apply_live` rebuilds `upstream` when `"upstream"` is among
    the changed sections. No test commits an `[upstream]` change, so that branch is
    checked by coverage only. See F3.

### `dispatch.py`

- **`Runtime._keep_live`**: the default `live_for` used without the CLI. It runs
  `check_static` and builds the pipeline from `pipeline_for`. It is used by every test in
  `test_config_reload.py`. Note: the default `pipeline_for` (`_get_pipeline`) returns the
  current pipeline, so with this default a `toolchain` change never reaches a new
  pipeline. That is fine in production, where the CLI passes `make_pipeline`. But it
  means no test here shows a new `toolchain.test` reaching a gate (F1).
- **`Runtime.update_config`**: returns `None` in a story view or while `main_lock` is
  held (R2). Both cases are tested, including taking the change once the lock is
  released. No defect.
- **`get_story_view`** (unchanged): it already calls `pipeline_for(view.config)` for each
  step's view. So R5 holds: a running view keeps its own objects, and the next view
  builds from the new config. `test_a_view_made_before_the_swap_keeps_its_config_s173`
  checks this with `copy.copy(rt)`, not with `get_story_view`. That is acceptable, but a
  test through `get_story_view` would also catch a pipeline shared by reference.

### `cli.py`

- **`check_config`**: refactored to use `check_static`. Its output is unchanged.
- **`build_live_config`**: raises `ConfigError` joining the `check_config` problems, or
  returns the parts. Both cases tested. No defect.
- **`make_runtime`**: wires `live_for` and `config_blob`. The test only checks that both
  are not `None`. It doesn't check that `config_blob` equals HEAD's blob, which the e2e
  test should cover (F1).

### `scheduler.py`

- **`update_config`**: runs in the tick before `apply_queues` (R2.1); a refused change
  queues a PO pass. Tested for order, for skipping under the main lock, and for refused
  and taken changes. No defect.
- **`add_config_change`**: runs after `dispatch` (R2.2, R8). Tested:
  - the step's own commit puts the error in its report;
  - another commit queues a pass;
  - a taken change or no change leaves the report unchanged;
  - nothing is checked while the queues may not apply;
  - nothing is checked when dispatch raises.

  No defect. One note on R8: a bad config commit that comes in through a story landing
  never matches a step's `commit`, because the landing's merge is found in a tick. So it
  always goes to the PO. That matches R8 ("a landing merge").
- **`queue_config_pass`**: tested through the two paths above. No defect.

### `handover.py`, `events.py`

- **`Trigger.CONFIG_INVALID`, `UNHELD`, the `HANDOVERS` row, `_find_config_fields`**:
  tested (scope, unheld, trigger, short sha, no hold). No defect. `EventKind.CONFIG`:
  tested.

## Findings

- **F1 (s173/AC1, REQ-262), blocking: the AC1 checks are missing.** These design
  checklist items have no test:
  1. *"commit a config adding `house-rules`; after `Scheduler.tick` a queued story
     amendment naming it is onboarded (`story-amended`, no `story-refused`) in the same
     tick."* This is the bug itself (q19 refused). The nearest test,
     `test_the_story_intake_reads_the_new_environments_s173`, only re-checks
     `rt.config.environments`. It repeats `test_update_config_takes_a_new_blob_s173` and
     never runs story intake. Its name says more than it tests.
  2. *"with `pipeline_for=cli.make_pipeline`, commit a change to `toolchain.test`; the
     runtime's pipeline and the next story view's pipeline run the new command line."*
     AC1's "a gate's test command runs with the commit's command line" is untested.
  3. *"an `add_role`/`run_role` refusal for an unknown role clears once a commit adds
     `[roles.x]`"* (the PO-tool consumer). Untested.
  4. The e2e test (`tests/e2e/test_s173_*.py`, real git) is missing. The story's Tooling
     section names it as the automatic check for AC1, so that section is wrong today. It
     should show that a storyless DevOps step commits an environment, a queued amendment
     is onboarded, and `events.jsonl` has one `config` event whose `sha`/`blob` match
     `git log` and `git rev-parse`. It is also the only check of `read_blob`,
     `find_last_change` and `make_runtime`'s `config_blob` against real git.
- **F2 (s173/AC2, REQ-263), minor: misnamed test.**
  `test_the_sections_table_covers_every_config_field_s173` checks only three entries.
  It would not fail if a new `Config` field were left out of `SECTIONS`. It should
  compare `SECTIONS`' fields with `Config`'s dataclass fields, minus `repo`, `run_home`
  and `warnings`.
- **F3 (s173/AC1, REQ-262), minor: the `upstream` rebuild is not checked by any
  assertion.** Add a test where an `[upstream]` change gives a new `Upstream` and a change
  to another section keeps the injected one.
- **F4 (no AC), minor: copy/paste.** `Runtime._keep_live` and `cli.build_live_config`
  both do "collect problems; if any, `raise ConfigError("; ".join(problems))`". A small
  shared helper (for example `config_reload.raise_problems(problems)`) would remove the
  copy. `test_s173_live_config.py` also imports `pytest`, `cli` and `config_mod` inside
  test functions instead of at the top. It is legal, but it is not the repo's style.
  `test_config_text_helper_is_valid_toml_s173` tests a test helper and adds nothing.
