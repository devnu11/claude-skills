# Review: s176, the story-rebase step moves only its own branch

Reviewer: code review, round 1. Diff `ab91c1f2..31fcb6b4` (c2bea8a6 plus 4 fixups).
Runner results: coverage 97.98 %, all green. I read the tests; I did not run them.

**Verdict: changes requested (developer).** Two command forms still move another
branch inside one Bash command without being refused (F1, F2). That is s176/AC1, REQ-209.
The AC3 backstop puts the branch back afterwards, but AC1 says "refused before it runs".
The rest is sound; the low findings below are optional.

## Findings

| F1 | **High** | s176/AC1, REQ-209 | `git_check.get_next_head` | `git checkout -` and `git switch -` switch to the previous branch, but `"-"` starts with `-`, so it is not counted as a named target and the function returns `head` unchanged. So `git checkout - && git reset --hard HEAD~3` is allowed and moves the previous branch. It should give `HEAD_UNKNOWN`, like `git checkout other`. |
| F2 | **High** | s176/AC1, REQ-209 | `git_check.get_next_head` | `"--" in rest` returns `head`, but `git checkout other --` (a `--` with no paths after it) **does** switch to `other`. So `git checkout other -- && git reset --hard X` is allowed. Only a `--` followed by at least one path is a file checkout. Test with `git checkout other --` vs `git checkout other -- f`. |

A bounce from `find_refusal` keeps the old snapshot, so the next round compares against heads from an earlier round, not from its own start. The design (B9.3) says a bounce should take a fresh snapshot "so the next round takes a fresh snapshot". Clear `heads` on every bounce; keep it only on a hold or a cut-off (B8). |

## Per function

### `git_check.py`

- `_list_args_after_sub`, `_is_long`, `_read_value_at`: small parsing helpers. Covered through the
  `find_moved_branch` table (`--create=other`, `--force-c`, `-Bother`). No defect.
- `_find_short_create`: finds `-B`/`-b`/`-C`/`-c` in a short-option cluster, with the value
  attached or not. Covered by `-B`, `-Bother` and `-fB`. No defect.
- `_find_created`: the branch that checkout/switch creates or resets. It stops at `--`. Covered.
  At 15 lines it is over the charter's "ideally under 8" (soft; the static gate passed).
- `_moves_by_checkout`, `_moves_head`, `_moves_by_stash`, `_moves_none`: rows of the
  `BRANCH_MOVES` table. Covered.
- `_moves_by_rebase` / `_split_rebase_operands`: the last operand, or `--root`'s first, else HEAD;
  the rebase operations count as detached. Covered (`--onto`, `-s`, `--root`). A valued option
  written as a separate word that is not in `REBASE_VALUED` (e.g. `--empty keep`) would shift the
  operands. That is rare, so not raised.
- `find_moved_branch`: the table lookup. Covered by 37 cases.
- `get_next_head`: **F1, F2.** The cases that are tested are right; `-` and the bare trailing `--`
  are missing.
- `find_branch_denial`: the refusal text names `site.branch` (AC1). Covered. See F5.
- `_list_positions`: carries HEAD across the links of one command. Covered
  (`checkout other && reset`, `checkout --detach && reset`).
- `_link_denial` / `_guards_branch`: the branch check runs only for LOCAL with a branch set.
  Covered (`branch=""` passes). One difference from the design: the branch check runs per link,
  not after all links pass G4–G7. The command is still refused either way. Fine.

### `guard.py`

- `_site`: reads HEAD only when `git_branch` is set. Covered both ways.
- `_read_head_branch`: exit 0 / 1 / other map to name / `DETACHED` / `HEAD_UNKNOWN`. Covered. See F5.

### `story_rebase.py`

- `read_branch_heads`: one `for-each-ref` call; filters out the rebase branch and branches
  checked out elsewhere. Covered with fakes. See F4.
- `list_moved_branches`: deleted branches and ones now checked out elsewhere are skipped. Covered.
- `put_back_branch`: `update-ref <old> <new>` guarded by the new sha; MOVED or STUCK text.
  Covered both ways. Note: if the moved branch is the one HEAD of the step worktree is now on,
  `update-ref` leaves that worktree's index/files out of step with HEAD, and the next round's
  `prepare` then runs `checkout -B`. That is an edge case, so not raised.
- `STORY_REBASE_LINES`: the new brief line is covered.

### `dispatch.py`

- `_set_story_rebase_scope`: sets `git_branch`; takes the snapshot after `prepare`, only when
  empty. Both covered (fresh, and resume keeps the old one).
- `_apply_rebase`: the put-back is checked first, so `blocked` bounces instead of holding.
  Covered. See F3. The test checks `Verdict.BOUNCE` but not that the target is `story.step`.
- `_put_back_moved`: covered for moved, stuck and nothing moved.
  `test_the_runtime_module_exposes_the_put_back_step` (`hasattr`) adds nothing; harmless.

### `story_branches.StoryRebase.heads`, `refusal.Rule.GIT_OWN_BRANCH`

- The default is per instance (covered). Design checklist item "an old `state.json` story `rebase`
  without `heads` loads" has no test. The dataclass default makes it very likely to work.

## Runner concurrency (design claim B7 / ADR-0091)

I checked whether the runner moves a *free* local branch while a story rebase step runs. That
would make the put-back undo the runner's own work. `StoryReplay.run` creates a new branch
(`checkout -b`) and leaves the old one where it is. `take_over` only renames `story.branch`.
`Replayer` (`branch -f`) and `scratch_rebase` (`worktree add -B`) run at the boundary only.
Landing uses a detached worktree. I found no conflict.
