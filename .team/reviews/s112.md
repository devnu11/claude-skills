# Review: s112, An Activity tab, Markdown in every message, and a live panel

Reviewed commits: 3a24ecb (design and customer docs), fb39d97 (tests), df65322
(code), fe36fe2 (test fix). They are mixed in with s114 commits on the branch.
694e8e4 (deleting `.team/briefs/`) is housekeeping and doesn't touch s112
behaviour. The runner's gate passes (99.53%, lint clean). That coverage is
**Python only**: none of the new JavaScript runs in any test.

**Verdict: changes requested.** The code follows the design closely and I
found no blocking code defect. Three things block shipping: AC2 and AC5 each
require a node-harness test, and neither exists; none of the new JS behaviour
is tested at all; and the "Docs at ship" updates to `protocol.md` and
`architecture.md` were not made (a house rule).

## Blocking

### B1. No node-harness tests (AC2, AC5, design test checklist): integration-tester

The design puts the page tests in `tests/e2e/test_s112_activity_page_e2e.py`
(node harness, `@needs_node`). That file doesn't exist. The only s112 test,
`tests/test_s112_activity_page.py`, greps the page source for strings. That
checks the markup but no behaviour.

- **AC2** says, word for word: "A node-harness test fails if an event kind with a
  text body isn't rendered through `md()`." Nothing does this. Checklist item
  MD1 is missing: a sample for every `TIMELINE` kind, the
  `Object.keys(TIMELINE)` equality guard, the fake markdown factory, and
  `MD:` present except for the two `PLAIN_BODIES`. The MD1 meta-escaping test
  and the MD2 behaviour test are missing too.
- **AC5** says contrast is "measured by a node-harness test". The current
  test only checks that each rule names `--ink` or `--ink-2`. It never computes
  a contrast ratio against `--surface` in the light and dark theme blocks. The
  design says to reuse the s102 `_theme_vars` and `_contrast` helpers.
- Untested behaviour (checklist items with no test at all):
  - MD4/MD5: after a failed `loadMarkdown()`, `markdownState === MD.FAILED`
    and `statusPills` contains the notice; with `MD.READY` it doesn't.
  - LP2: step, stage and idle states; the awake text, including `(may include sleep)`.
  - LP3: `waiting on m121`, then the fallback to the health reason, then to the run status.
  - LP4: the running story's message beats a newer one on another story;
    when idle, the newest of all wins; blank bodies are skipped; a throwing
    builder is skipped.
  - LP5: `clip` cases: 8 lines (keeps 6, cut), 4 lines (not cut), blank lines
    don't count, more than 600 characters (cut), and `lp-more` only when cut.
  - LP8: `openActivity("s3")` versus an unknown story.

  `clip` is the riskiest of these, with its mixed `&&`/`||` precedence. I
  traced it by hand and it is correct, but nothing pins it.

## Minor findings (not blocking; fix if cheap)

- **n1.** `latestMessage` copies and reverses the whole `view.events` array on
  every render. A backwards index loop would avoid the copy. It is cheap enough at today's sizes.
- **n2.** `panelMessageHtml` for a `PLAIN_BODIES` kind returns `esc(text)`
  with no `.md` wrapper. The `.lp-msg .md` six-line height cap then doesn't
  apply, and newlines collapse. The 600-character clip still bounds it, so this is cosmetic.
- **n3.** `tick()` rewrites only the head text. If the state's kind changes
  between snapshots (for example, the heartbeat goes stale), the `running`
  class and the message stay stale until the next snapshot. This matches
  LP7, so it is noted only.
- **n4.** The keydown listener sits on `#live-panel` and catches Enter
  bubbling up from a link *inside* the message. `preventDefault()` then
  stops that link from opening and opens Activity instead. The click path
  deliberately lets links through (LP8). The fix is to skip when
  `ev.target.closest("a")`, as the click handler does.
