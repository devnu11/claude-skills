## Findings (follow-ups, not blocking)

- **F1 (minor defect, developer):** an in-run halt and a later resume can post two
  questions for the same drift. `halt_run` posts `message() + _waits_suffix(...)`, but
  `Guard._escalate` only dedups on an exact `found.message()`. If another question was
  open at the in-run halt, the first `start --resume` while the drift remains adds a
  second checkout question. Both are answered on restore or accept, and later
  resumes do not pile up more. Fix: dedup on "an open question starts with
  `found.message()`", or on any open `CHECKOUT_HEAD` question with the same reason.
  Add a test where a question is open at the in-run halt.
- **F2 (test gap, unit-tester):** the AC6 `rebase` case (`start_rebase`) also detaches
  HEAD, so the test would pass even if rebase detection were broken. The test only
  asserts the `checkout changed: ` prefix. It should assert that the reason contains
  `with a rebase in progress`. One more end-to-end case would pin the operation check
  on its own: a merge conflict left on the recorded branch (HEAD attached, same sha,
  `MERGE_HEAD` present). Today only the unit tests `matches`/`read` cover it.
- **F3 (DRY, developer):** `Guard.accept` repeats `found.branch is None or found.operation`
  from `matches`. Extract a `Found.attached_and_idle()` (or similar) and use it in both.

## Open question for the human

- A fresh `agile-team start --task …` (not `--resume`) also checks the stale record
  left by the previous run. Pulling, merging or rebasing between runs (your
  rebase-before-main workflow) therefore exits 78 until you run `accept-checkout`.
  That matches AC2 ("on start and resume") and the design. Confirm that this is wanted
  between runs, not only for a run that is still going.
