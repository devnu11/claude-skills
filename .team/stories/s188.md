---
id: s188
title: "Bug: a PO chore commit on top of a sprint's green or merged head makes the END boundary treat it as new work: sprint 53's green PR #74 was closed and replayed as #76, and sprint 54's merged PR #82 looped on \"a check ran on another commit\""
acceptance:
  - id: AC1
    environment: cli
    text: >-
      At a sprint END boundary, a storyless-step chore commit (`chore(team): <role> step`)
      made after the sprint head went green on CI doesn't make the boundary treat the sprint
      as new work: when the replay onto the target changes nothing else, the green PR stays
      the sprint's PR, no `-r<k>` branch is pushed for the chore alone, no PR is closed or
      opened, and CI isn't waited on a second time. The chore commit isn't lost. Checked by
      hand: let the PO's CI-green step commit its handoff, then read the boundary events,
      the PR list and `git log` of the team branch.
  - id: AC2
    environment: cli
    text: >-
      The PO is told a sprint PR is ready to merge once, when the END boundary has finished,
      and the message names the PR that the boundary finished with. No ready message names a
      PR that the runner then closes.
  - id: AC3
    environment: cli
    text: >-
      An END boundary whose sprint PR is already merged, or whose last CI-green head is
      already in the target, closes as shipped, even when a chore commit was made on top of
      that head afterwards. It doesn't hold on `ci_pending` for a merged PR's checks. Checked
      by hand: merge the sprint PR by fast-forward, let the PO commit a chore, then run the
      END boundary; it finishes shipped without a `ci_pending` hold.
---

**User story.** As the human, I want a green sprint PR to stay the one I merge, so that a
bookkeeping commit after CI doesn't cost me a second CI run, a stale PR number or a boundary
that never ends.

**What happened.**
- **Sprint 53 (2026-10-25 22:17-22:20).** The END boundary's CI stage found PR #74 green at
  b59222eb (e407181). The runner handed the PO `ci_green` (e407184). The PO told the
  liaison "#74 ... is ready to merge" (m381, 22:18:31). The PO's step committed
  b8851201, "chore(team): product-owner step", which changed only `.team/po/handoff.md`.
  The replay found the branch already on the target (`outcome: current`, e407199). The
  runner still pushed b8851201 as `team/sprint-53-r1`, closed #74 and opened #76 (e407202,
  e407203, m382). It waited for CI again (e407205-e407206), and the PO corrected itself:
  "its PR is now #76, not #74" (m383). The liaison fast-forwarded main twice
  (`decisions.md:575-576`).
- **Sprint 54 (2026-10-26 00:16-01:05).** Sprint 54's PR #82 went green and the liaison
  fast-forwarded main to 6acaae73 (`decisions.md:581`), so GitHub marked #82 merged. A PO
  step had already committed 76eacf9f ("chore(team): product-owner step", handoff only),
  which isn't in main. When the job resumed, the END boundary pushed 76eacf9f to
  `team/sprint-54` (e409305) and read #82's checks. They ran on 6acaae73, so each wait held
  `ci_pending`: "a check ran on another commit than the pushed head; it does not count"
  (e409308, e409325, e409335). The PO called `continue_boundary` twice, then stopped
  (m389-m391). The liaison closed the boundary by hand: stack mode `closed`, boundary hold
  `null` (`decisions.md:584`; backup
  `backups/state.before-close-s54-boundary-20261026-0801.json`).

**Cause (fact for the code paths, read at 14c30be9; certain for how they combine).**
- `ci_green` fires on any boundary event with `ci == "green"` (`handover.py:313-318`). That
  includes the CI stage's pass event (`_ci_green`, `boundary_runner.py:1001-1003`), which
  comes before REPLAY, PUSH_REPLAYED and CI_REPLAYED (`boundary.py:247-256`). So the PO is
  told "ready" before the boundary has finished. The finish also carries `ci: green`
  (`_finish_green`, `boundary_runner.py:1005-1007`), so the same rule fires a second time
  when the boundary ends.
- The PO's own step then commits (`dispatch.py:1829`, the storyless subject).
- `_push_end_replay` compares HEAD with the pushed head only (`boundary_runner.py:917-920`).
  It doesn't check whether the replay rewrote anything, so a current replay plus one chore
  commit pushes a new `-r<k>` branch and closes the old PR (`_push_replay_branch`,
  `:939-955`).
- s183's shipped check runs only at PUSH_REPLAYED, after CI has passed
  (`boundary_runner.py:893-900`). It asks whether HEAD is in the target
  (`upstream.py:640-644`), and a chore commit on top makes that false.
- A merged PR's checks stay on its merged head, so `kind_of` calls every one stale
  (`ci_triage.py:116-119`), and `_ci_pending` holds again each time
  (`boundary_runner.py:1045-1049`).

**Placement:** Product Backlog. Files: `boundary_runner.py` (`_push_end_replay`, the CI
stage, the shipped check), `handover.py` (`ci_green`), the END boundary section of
`reference/protocol.md` and `roles/product-owner.md` (ci_green). This is the sprint-end
counterpart of s180, where the runner's own commits move the sprint head under a waiting
landing. The two should agree on where bookkeeping commits go: whether the chore commit
stays on the team branch for the next sprint, is made somewhere else, or isn't made at a
green head at all is the architect's call, not fixed by AC1. s183 covers a HEAD already in
the target, not chore commits on top of it.
