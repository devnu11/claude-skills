# s92: A gate failure goes straight to the role that owns the failing file

**Delivery:** cli

**Priority:** top of the backlog, first after the current sprint (human, t28). Cycle time is the human's top priority; this gap stalled s79, s59 and s65. Supersedes s48.

## User story

As the human, I want a gate failure in a file the current role can't edit to go straight to the role that owns that file, so a one-line fix doesn't cost a dispute, a Manager ruling and a round.

## Acceptance criteria

- AC1. When a gate fails, the runner maps each failing item to the role that owns its file: a failing test by its test file, a ruff finding by its file. The owner comes from the same file-scope table that limits each role's writes. There is one table and no per-role branches.
- AC2. If a failing item's owner is not the step's role, the runner sends the story to that owner for a fix step, then back to the step that failed. No round is counted, no dispute is opened and no Manager step runs. The step's own items stay with the step's role, as today.
- AC3. With items for several owners, each owner gets one fix step, in pipeline order, before the story returns.
- AC4. A fix step's brief lists only that role's items, with the gate output lines for them and the design rule the step cited, if any (for example "s65 G9: lay_out never wipes").
- AC5. A fix step that changes what a test asserts must name, in its handoff, the AC or design rule that makes the old assertion wrong. The code reviewer sees it in its brief.
- AC6. Tests pin three cases: an e2e test failing at implement goes to the integration-tester and back to implement with no round (the s65 case); a ruff finding in tests/ at implement goes to the unit-tester (the s48 case); a failure in the developer's own files stays with the developer.
