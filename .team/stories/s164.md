title: "Bug: the scheduler wakes itself with its own checkout-guard event, so an idle run spins at full CPU"
acceptance:
  - id: AC1
    environment: cli
    text: >-
      While a run waits (a step running, nothing else due, no new message, write from a step
      or tool, or task end), the scheduler ticks no more than once per `POLL_S` (5 s). Nothing
      the scheduler does for itself on an idle tick, such as its `checkout.guard`, wakes the
      next tick early. A write from anywhere else (a step, a tool, a PO turn, a story CI
      result) still wakes it at once, as today.
  - id: AC2
    environment: cli
    text: >-
      Over ten minutes of a run with one step running, `events.jsonl` gains no more
      `checkout.guard` events than ten minutes / `POLL_S` (120) plus the number of other
      events written in that window, and the runner process averages under 10% of one CPU,
      measured on a run started after the fix (`ps` averages over the process's life).
      Checked by hand: `ps -o pcpu -p $(cat .team/run/runner.pid)` and a count of events by
      `at` (a float epoch) in `events.jsonl`.

**User story.** As the human, I want an idle run to sit idle, so it doesn't burn a CPU and
fill `events.jsonl` with thousands of identical events an hour.

**What happened (2026-10-19, sprint 50).** With only s163's architect step running, the
runner (pid 15205) used 84% CPU. `events.jsonl` gained 4,712 `checkout.guard` events in the
ten minutes to 17:43 (7.9 a second, about 28,000 an hour) and nothing else; the file is
22 MB. The rate grew from about 50 an hour before s159 to about 2,000 an hour on 2026-10-18.

**Cause (fact for each link, read from the pinned runner; the spin itself is certain and
matches the live log).** `Scheduler.tick` calls `checkout_moved` whenever the main lock is
free (`scheduler.py:164`). Each call runs `git rev-parse` (the event's `detail`, about
22 ms), so the spin costs a git process per tick. `checkout_moved` opens the
`checkout.guard` stage (`dispatch.py:1319`), whose close emits a `runner-stage` event
(`stage_log.py:164-185`) through `EventLog.emit` (`events.py:88-95`). With the writer bound
(s159 C6), the write is queued through `RunWriter.submit`, which sets `wake`
(`run_writer.py:44`). `wait_for_change` returns at once on `wake` (`scheduler.py:222-232`),
so the loop ticks again. (`tick` drains the writer before it opens the guard, so the line is
written by the next tick, whose own event then wakes the one after it.) The stage also
writes `heartbeat.json` twice per tick (`live.py:418-427`).

**Placement:** Product Backlog. The liaison recommends it for the sprint after sprint 50. It
touches `scheduler.py` (`tick`, `wait_for_change`), `run_writer.py` and perhaps
`dispatch.py` (`checkout_moved`). s163 changes `run_boundary`/`follow_boundary` and
`landing.py`, not these; land this after s163. It shares `scheduler.py`, `run_writer.py` and
`dispatch.py` with s161 (which renames `ended`, `drain` and `at` in those files), so in a
parallel sprint it should be ordered behind s161 or given to the same team; s162 touches
none of its files. It doesn't block sprint 50: the run is correct, only wasteful.
