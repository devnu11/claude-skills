title: Gate commands and test runs have a timeout, and a hung test is named instead of hanging the runner
delivery: cli
acceptance:
  - id: AC1
    text: >-
      Gate commands have a timeout set in `.agile-team.toml`, with a sensible default
      (the full suite normally takes about a minute). `dispatch.shell_runner` today uses
      `subprocess.run` with no timeout, so a hanging test hangs the runner for good. A
      command that outlives its timeout is killed (the whole process group the runner
      started, and only that), and the gate counts it as a bounce.
  - id: AC2
    text: >-
      The bounce reason names the hanging test, for example from pytest's faulthandler
      output (`faulthandler_timeout`) or a per-test timeout, so the developer and the
      unit-tester know which test to fix. A timeout with no test to name still bounces,
      with the command and the time limit in the reason.
  - id: AC3
    text: >-
      The toolchain sets a per-test timeout for the repo's pytest run, so a test that can
      hang fails on its own instead of waiting for the gate's timeout. The setting lives
      in the runner project's pytest configuration (devops owns the config choice; no new
      runtime dependency without an ADR).
  - id: AC4
    text: >-
      Process rule, in the shared role rules and enforced where the runner can: never wait
      on a test run without a timeout. Run the suite in the foreground with a timeout, or
      give any wait loop a deadline. Seen live: s29's developer started the suite in the
      background and waited with `until grep -q "passed|failed" /tmp/run.log`, with no
      deadline, so the step sat idle for over 5 minutes. The human has already added
      "tests mock time, waits and sleeps" to `.team/roles/unit-tester.md` (6fa2fd7); this
      story adds the developer-side rule and does not repeat that one.
  - id: AC5
    text: >-
      The hanging test seen in s29, `tests/test_router.py::test_a_held_boundary_waits_when_a_question_is_open`
      (it posts a question nobody answers and calls `advance(rt)`, so the real
      indefinite wait never returns), is settled: the test checks the decision to wait
      with the wait injected (a fake clock or a wait function that returns at once), not
      the real wait. The dispute route between the developer and the unit-tester does
      this if s29 has not already; this story checks it is done and not skipped or
      deselected.
  - id: AC6
    text: >-
      Tests cover a gate command that times out (with and without a nameable test), the
      default and the configured value, and the killed group. Docs (`protocol.md`, config
      reference, `SKILL.md` if the rule is visible there) move in the same story.
      Coverage stays at or above 95%, and ruff check and ruff format are clean.

## User story

As the human, I want a hung test to fail with its name in the reason, not to hang the
runner or leave a developer idle, so a bad test costs a minute and not an hour.

## Notes

From the liaison, on s29's second implement step (developer-cli, e909). The suite hung
at about 75%, idle in a select/kqueue wait, orphaned (ppid 1). The human: "We don't need
to wait 10 minutes when 0.1 second will probably have the same result in testing the
code functionality." The human also asked whether the tester was doing something
malicious; it was not. Design U23 ("the router waits as today") was right and the test
ran the real wait.
