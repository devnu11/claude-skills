**User story.** As the human, I want s159's checks to give the same result on CI as on this Mac, so the sprint's PR goes green on code that works.

**What happened (sprint 49's end, 2026-10-18, m268–m270).** CI failed on PR #38 on Python 3.12 and 3.13. In `agile-team/runner/tests/e2e/test_s159_unattended_waiting_e2e.py`:
- `test_ac11_6_one_waiting_notice_with_the_reason_and_no_idle_stop` got `[]` instead of `['waiting for the human']`;
- `test_ac11_6_a_second_notice_only_after_progress_and_idle_stop_applies_without_waiting` counted 0 notices instead of 2.

All 6,886 other tests passed. The same two pass at the team's gates on macOS, because macOS always has `osascript`, so the fallback notifier is found there.

**Cause** (fact: the code path and PR #38's job log, run 39185861841, agree; `notify-send`'s absence on `ubuntu-latest` is certain, not checked on the runner):
- The test's driver builds its job with `Spec(JobKind.COMMAND, …, command="true")` and leaves `notify` at its default `""`.
- With no notify setting, `unattended.notify.call_for` falls back to `os_notifier` (`notify.py:114-118`). That returns a command only when the platform's tool is on PATH: `notify-send` on Linux.
- With none, `post` logs the event but never calls `spawn`, so the driver's recorded list stays empty.

A fix: give the driver's job a notify command of its own, for example `notify="true"`, which the driver's recording `spawn` never runs.

Sprint 50 holds this story and the verb-name clean-up. `suite_runs` isn't set: the failure is deterministic (a missing binary), not flaky.
