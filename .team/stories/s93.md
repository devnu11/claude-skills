## Acceptance criteria

- **AC1 [cli].** The config section is `[[environment]]`. A `[[delivery]]` section still loads as an environment. `agile-team config check` warns that it should be renamed and exits 0, and a test pins both. Using both sections in one file is a load error.
- **AC2 [review].** The names follow in the code, with no behaviour change:
  - `Config.environment(name)` and `Config.environment_refusal(name)`;
  - `sandbox.ENVIRONMENT_KINDS`;
  - `Environment` (the dataclass);
  - refusal texts that say "acceptance environment".

  The existing tests pass with only renames.
- **AC3 [review].** `presets.toml`, `onboard.py`'s generated config, the role files, `SKILL.md` and `reference/protocol.md` say "acceptance environment". `grep -ri delivery` in `agile-team/` finds only the alias and its test. The docs explain that environments are the repo's and kinds are the skill's.
- **AC4 [dashboard].** The dashboard says "acceptance environment" wherever it said "delivery".
- **AC5 [cli].** The skill gains an environment kind `document`, for ACs with nothing to run (prompt, docs or design changes): the proxy gets Read, Grep and Glob over its sandbox copy of the presentation, which holds the guide and the changed files, and judges each AC against them. Nothing is posted to the human. It's one new row in `sandbox.ENVIRONMENT_KINDS` and in `presentation.PRESENTATIONS` (guide plus files, no service), and a test pins that a `document` acceptance step posts no question.
