# s108: Bug: the review stack after a merge

**Delivery:** cli

## User story

As the human, I want every review PR in the stack ready and kept current after each merge, so I can merge them in order without hand fixes.

## Acceptance criteria

- **AC1 [cli].** Every PR in the review stack is ready (non-draft), each based on the PR below it. The base chain fixes the merge order.
- **AC2 [cli].** When the runner finds that a stack PR was merged (at a boundary, or while it waits on CI), it rebases the next PR's branch onto main, checks that the tree is unchanged, pushes it with --force-with-lease, and retargets it to main. No open PR is ever left based on a merged branch.
- **AC3 [cli].** The runner waits for CI on every PR in the stack, applying the CI rule (a sprint is done only when a green CI run is present on GitHub; see s110). When a PR has more than 100 commits (GitHub's limit for "Rebase and merge"), the report says so and gives the fast-forward command to merge it.
- **AC4 [cli].** Tests with a scratch repo and a fake gh pin: the bottom PR merged by rebase leads to the next PR being rebased, retargeted and ready; tree equality; no PR left on a merged base; the over-100 note.
