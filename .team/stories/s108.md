title: "Bug: the review stack after a merge"
depends_on: []
acceptance:
  - id: AC1
    environment: cli
    text: >-
      Every PR in the review stack is ready (non-draft), each based on the PR below it.
      The base chain fixes the merge order.
  - id: AC2
    environment: cli
    text: >-
      At sprint end only, after pushing the sprint's review branch, the runner rebases
      the team branch onto main. Then, bottom up through the stack, it brings each
      unmerged parent PR's branch up to date with main (rebase, check the tree is
      unchanged, push with --force-with-lease, retarget to main or to its parent), and
      then updates the sprint's own PR the same way. A parent PR found merged is dropped
      from the stack, and the PR above it is retargeted. Nothing is rebased or
      retargeted mid-sprint. A test pins that a merge made mid-sprint changes nothing
      until the sprint ends.
  - id: AC3
    environment: cli
    text: >-
      The runner waits for CI on every PR in the stack, applying the CI rule (a sprint
      is done only when a green CI run is present on GitHub; see s110). When a PR has
      more than 100 commits (GitHub's limit for "Rebase and merge"), the report says so
      and gives the fast-forward command to merge it.
  - id: AC4
    environment: cli
    text: >-
      Tests with a scratch repo and a fake gh pin: the bottom PR merged by rebase leads
      to the next PR being rebased, retargeted and ready; tree equality; no PR left on a
      merged base; the over-100 note.

## User story

As the human, I want every review PR in the stack ready and kept current after each merge, so I can merge them in order without hand fixes.
