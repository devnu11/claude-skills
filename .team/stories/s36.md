title: Legacy debt tooling - DevOps scripts record and track existing coverage, lint and static debt, so agents never re-derive it
delivery: cli
depends_on:
  - s31  # hooks
acceptance:
  - id: AC1
    text: >-
      DevOps owns scripts under `.team/hooks/` that record the existing debt in a repo
      the team takes on: the uncovered-line baseline, and baselines for existing lint
      and static findings, so only new findings fail. They are scripts with tests, not
      agent work. The baselines are files in the repo (or the run dir), updated by the
      scripts, with a clear format.
  - id: AC2
    text: >-
      The scripts supply the line matching across commits that s35's coverage set rule
      needs (which uncovered lines at the story's start commit are the same lines
      now), and the finding matching for lint and static. The same code is used by the
      gate and by the brief.
  - id: AC3
    text: >-
      The scripts run as hooks (s31). Agents and gates consume their output as facts in
      the brief: what is new and what is legacy. An agent is never asked to work out
      the debt itself.
  - id: AC4
    text: >-
      Legacy debt is reported per repo on the dashboard and to the Manager's insights
      (uncovered lines, lint findings, static findings, with a trend), shrinking as
      stories touch it. The snapshot fixture is updated.
  - id: AC5
    text: >-
      The runner keeps the rule (the debt may not grow); DevOps's scripts only supply
      the data the rule is checked against. A story that reduces debt records it.
  - id: AC6
    text: >-
      Onboarding a repo (`init`) can create the baselines. `roles/devops.md`,
      `reference/protocol.md` and SKILL.md describe the tooling. Tests cover each
      baseline, the matching, the hook output and the report.
---

## User story

As the human, I want the legacy-code problem solved once, by scripts DevOps
owns, so that no agent re-derives what is old debt and what is new every turn.

## Notes

Human, item 7 of the addition to Story A: "Devops should manage the legacy code
base problem by using developing scripts, instead of relying on agents to figure
it out every time."

This story supplies s35 (the coverage set rule). In this repo
(at 100%) the baseline is empty, so it matters when the team takes on another
repo.
