# s50: Find the cause of the unexplained process kills overnight

**Delivery:** agile-team runner (tests and process handling).

## User story

As the human, I want to know why the runner and the liaison's dashboard were killed with no traceback, so it does not happen again.

## Acceptance criteria

1. Explain two kills on 2026-10-11: the runner's SIGTERM at 01:13 (during s29) and the liaison's dashboard (`agile-team dashboard`, port 8770, started from the liaison's shell, outside the team's process group) which died at about 07:30 with exit 144 (signal 16) while developer-cli ran s9's implement step.
2. Check whether any test or code path signals a pid read from `runner.pid` or another pid file, or signals a process group, so that a step running in the sandbox can reach a process outside it.
3. If a cause is found, fix it with a regression test (a test must never signal a pid it did not start). If no cause is found, add logging that records the sender of any SIGTERM the runner receives and say so in the review.
4. Coverage stays at 95%+; ruff clean; docs updated if behaviour changes.

## Cause found (liaison, 2026-10-11)

At 12:20 CDT and again minutes later, during s21's implement and e2e steps, a role ran `pkill -f` with a pattern matching the agile-team dashboard command, to clean up its own test dashboard. `pkill -f` matches every process whose command line fits, so it killed the liaison's dashboard twice (exit 144) and one of the liaison's own shell commands. The 07:30 death during s9 fits the same cause. The 01:13 SIGTERM of s29's developer CLI may be another pattern kill or the sandbox group kill; check that step's transcript. Near miss: the runner was started with the whole liaison message in its command line, which often names the dashboard command, so the same pkill could have killed the runner. The liaison now passes a pointer to `.team/run/liaison/msg-<time>.md` instead.

## Added acceptance criteria

5. Rule for every role, in the `_shared` rules: never kill processes by pattern (`pkill -f`, `killall`, `kill` with `pgrep`). Stop only processes the role started, by the PID it recorded, or through s26's service lifecycle. A test dashboard runs on its own port and is stopped by its PID.
6. Enforce the rule in the guard where possible (reject those commands in a role's Bash), with a test.
7. If the runner starts test services for roles (hooks stories), they follow the same rule: started by PID, stopped by PID.

## Origin

Liaison note under the overnight authority: a second unexplained kill in one night.
