acceptance:
  - id: AC1
    environment: cli
    text: >-
      After implement, the runner runs tests, coverage, lint and static as built-in
      after-hooks (s31) with `on_fail = "block"`, bouncing to the developer. Lint and
      static are new: today no code gate runs the toolchain's lint and static commands.
      Whatever s32's fixers couldn't fix bounces to the developer, like a failing test,
      so the quality-czar starts from a clean, checked tree.
  - id: AC2
    environment: cli
    text: >-
      The coverage rule is two checks: total coverage stays at 95% or more, and the
      uncovered set may not grow. After implement, every
      uncovered line must have been uncovered at the story's start commit, or carry a
      pragma the unit-tester accepted (AC6). Deleted lines drop out. An uncovered
      changed line counts as new, and so does an unchanged line that lost its coverage.
      In a repo at 100% (this one) that means 100% everywhere: covered or exempted. In
      a repo with old debt, existing gaps are tolerated, no new ones are allowed, and
      the debt shrinks as stories touch it. It is a yes/no rule with no threshold.
  - id: AC3
    environment: cli
    text: >-
      Lines are matched across the story's commits although line numbers shift. The
      architect picks the method (for example mapping through `git diff`, or keying
      lines by content) and records it in the design with its limits. The matching is
      Python code with tests, not an agent's job.
  - id: AC4
    environment: cli
    text: >-
      A coverage bounce lists the new uncovered lines (file:line ranges, for example
      from `--cov-report=term-missing`), not just "94% < 95%", so the developer doesn't
      spend turns re-running coverage to find them.
  - id: AC5
    environment: cli
    text: >-
      A coverage bounce goes to the developer, and they get three moves. (a) Delete
      the code: it's dead or speculative, written without a failing test first. (b)
      Raise a test gap: the code is needed by the design but untested, so the story
      goes to the unit-tester for that test, as a new kind of dispute on s11's route
      (no round counted against the developer). (c) Mark the code uncoverable with the
      toolchain's pragma (AC6). The developer must not write the missing tests: a
      coverage bounce's re-handoff that only touches test files is refused in code.
  - id: AC6
    environment: cli
    text: >-
      Each pragma carries a reason, for example `# pragma: no cover - defensive:
      unreachable once validation passes`. The gate rejects a bare pragma. Each new
      pragma in a story is a coverage exemption the unit-tester reviews in a short step
      after implement. It agrees, and the exemption stands, or it disagrees and says
      why and how to test it. On disagreement the story goes back to the developer,
      who removes the pragma and either deletes the code or accepts a test from the
      unit-tester. Repeated disagreement goes to the Manager through s27's
      repeat-bounce escalation, not into a loop.
  - id: AC7
    environment: dashboard
    text: >-
      The code-reviewer sees the exemptions in its review brief. The dashboard and the
      Manager's insights count them per story, so overuse shows up as friction.
  - id: AC8
    environment: review
    text: >-
      `reference/protocol.md` (gates, coverage rule, pragmas), SKILL.md, and the
      developer, unit-tester and quality-czar role files describe the rules. An ADR
      records the set rule and the line matching. Tests cover the set rule (new
      uncovered line, lost coverage on an unchanged line, deleted lines, legacy gaps),
      the bounce listing, the three moves, the bare-pragma rejection, the
      test-files-only refusal and the exemption review.

## User story

As the human, I want a simple rule that coverage may not get worse, bounced to
the developer with the exact lines and a clear choice of what to do about them,
so that agents don't argue thresholds and tests stay the unit-tester's job.
