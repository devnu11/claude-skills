title: Resume after a session limit automatically, within limits
delivery: cli
acceptance:
  - id: AC1
    text: >-
      When the runner halts on a session or usage limit (s8), it waits until the reset
      time parsed from the limit message, plus a small margin, then resumes the run
      itself, as `start --resume` would. Status shows `waiting` with the resume time
      while it waits.
  - id: AC2
    text: >-
      Waiting and resuming are bounded by config: the number of automatic resumes per
      run, and the longest wait it will accept. If a reset time is missing or can't be
      parsed, or a limit is exceeded, it falls back to s8's clean stop, with a note
      saying why.
  - id: AC3
    text: >-
      `stop` (and `stop --now`) during the wait cancels it cleanly. A liaison note goes
      out when waiting starts and when the run resumes.
  - id: AC4
    text: >-
      SKILL.md makes resume-after-limit a standard part of the skill, and
      `reference/protocol.md` (run status and stops) and the README row are updated.
      This supersedes the "stop cleanly only" decision (m3) for limits; crashes still
      stop.
  - id: AC5
    text: >-
      Tests cover the wait-and-resume path with an injected clock, both limits, an
      unparseable reset time and stop during the wait. Coverage stays at or above 95%,
      and ruff check and ruff format are clean.
---

## User story

As the human, I want the run to pick itself up after a session limit resets,
so that a limit costs only the wait, not my attention.
