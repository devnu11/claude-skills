**User story.** As the human onboarding a Python repo, I want the runner's gate to run my
test command in my repo's environment, so that the runner's own venv neither shadows my
tools nor makes `uv` warn on every run.

**What happened (2026-10-23, issue #55 follow-up).** Issue fixes batch 1 (#55.7,
`liaison/issue-fixes-1`) strips `VIRTUAL_ENV` and the runner venv's `bin` from the
environment given to role steps (`hide_runner_venv`). The implementer and the reviewer
both noted that gate commands still inherit them: "gate commands still inherit the runner's
`VIRTUAL_ENV`, because #55.7 covers roles only"
(`reports/2026-10-23-issue-fixes-1.md:37`; `reports/2026-10-23-review-issue-fixes-1.md:80-84`,
"`uv run` warns ('VIRTUAL_ENV does not match') but ignores it"). Batch 1 is on main (0e1e0991): roles get
`hide_runner_venv` (`dispatch.py:277`, used at `:310`); gate commands still inherit.

**Cause (fact, read at 0e1e0991).** `CommandShell._watched`
(`commands.py:114-124`) builds its shell through `_build_shell` (`:126-129`), which copies
`system.environ()` whole and adds only `COVERAGE_FILE`, so the gate's child gets the
runner's `VIRTUAL_ENV` and `PATH`, the ones `uv run --project agile-team/runner` set for
the runner itself; `env` then reaches `Popen` (`system.py:318-325`). The tally path is the same:
`tally_watch.watching` yields `plugin_env(system.environ(), path)` (`tally_watch.py:89-95`).

**Placement:** Product Backlog. Files: `commands.py`, `tally_watch.py`, and reuse of
`hide_runner_venv` (`dispatch.py:277`), moved to a module both can import, so one function
builds the environment for roles and gates.
