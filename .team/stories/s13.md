title: The integration-tester presents the product to the Customer Proxy in a prepared acceptance environment
delivery: cli
acceptance:
  - id: AC1
    text: >-
      Preparing the acceptance environment is part of the integration-tester's e2e
      step, and its role rules say so. For the story's delivery it builds a
      ready-to-use customer workspace, the way the team would present the product to
      a customer. For `cli`, that is a git-initialised scratch repo with
      `agile-team init` already run and any state the story's ACs need. For
      `dashboard`, it is the same plus sample run files (state, events, ledger, outbox,
      inbox) chosen to show the story's features, so `agile-team dashboard --no-open
      --port 0` serves them. It also writes a short `PRESENTATION.md` that tells the
      customer what to try for each AC.
  - id: AC2
    text: >-
      The Customer Proxy never builds or repairs its own environment. Its role rules
      say it uses what it was presented, and that a missing or broken environment is a
      `changes_requested` back to the integration-tester, not something it works
      around.
  - id: AC3
    text: >-
      The runner enforces the handover in code. The e2e gate fails when the
      presentation (workspace plus `PRESENTATION.md`) is missing for the story, and
      the runner copies the presentation into the Proxy's sandbox before the
      acceptance step. The integration-tester's write scope includes the
      presentation location; the Proxy's read scope includes the copied workspace.
      Source and tests stay unreadable, and s7's rules still hold.
  - id: AC4
    text: >-
      For runner features that only show in a live run (sprints, stops, spend), the
      presentation includes the live run's `agile-team status` JSON, captured by the
      integration-tester or the runner. That way the Proxy judges real output.
  - id: AC5
    text: >-
      The Proxy can read and rewrite its own report `.team/acceptance/<story>.md`
      across steps. Today it can create the file but cannot Read it afterwards.
  - id: AC6
    text: >-
      `agile-team init` outside a git repo prints `agile-team init: <message>` and
      exits 1, as the docs promise, instead of a `GitError` traceback.
  - id: AC7
    text: >-
      `roles/integration-tester.md` and `roles/customer-proxy.md`,
      `reference/protocol.md` (e2e and acceptance steps, scopes) and SKILL.md describe
      the presentation. Tests cover the e2e gate check, the copy into the sandbox, the
      acceptance-file access and the init error. Coverage stays at or above 95%, and
      ruff check and ruff format are clean.

## User story

As the human, I want the team to present the finished product to the Customer
Proxy in a ready-made environment, so that acceptance judges the product as a
customer would receive it, and the Proxy never has to build its own test setup.
