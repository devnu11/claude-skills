acceptance:
  - id: AC1
    environment: cli
    text: >-
      A story-rebase step whose role finishes the rebase but leaves an in-scope edit
      uncommitted at hand-off is never refused as "a commit was added, dropped, squashed,
      reordered or reworded". It is either adopted with that edit on the rebased branch or
      bounced with a reason that names the uncommitted file; the architect picks one. Checked by hand in a scratch repo: a story with a conflicting branch, a
      rebase step that resolves, runs `git rebase --continue` and then edits one conflict file
      without committing.
  - id: AC2
    environment: cli
    text: >-
      An out-of-scope edit left by a rebase step is never reported as a commit the role
      added, dropped or reworded, and it is named in the step's report. Whether the runner
      quarantines it on the rebase branch or sets it aside off the branch is the architect's
      choice, under the same rule as AC1.
  - id: AC3
    environment: cli
    text: >-
      When the commits check does refuse, the reason lists each extra, missing or changed
      commit by short sha and subject and says whether the role or the runner made it. A Manager `advance` ruling doesn't send the
      same queued rebase back through the check under each later step name.
  - id: AC4
    environment: cli
    text: >-
      A rebase whose role renumbers requirement and ADR ids while resolving conflicts, inside
      the replayed commits and with no commit added, still passes the check and is adopted.

**User story.** As the liaison, I want a story rebase that the role did correctly to be
adopted. I don't want a check that no role can satisfy to block the story until a human
reverts it.

**What happened (2026-10-23, sprint 52).** s180's land bounced on a REQ/ADR id collision
with the landed s178/s179 (e362246). The Manager ruled a rebase-only fix with renumbering
(e362277). developer-cli rebased `team/story-s180-r1` onto a5f800da, renumbering s180's ids
to REQ-200..202 and ADR-0092 while resolving the conflicts, and handed off with "a final
architecture.md fix is uncommitted" (e362318). The check then refused: "team/story-s180-r1's
commits are not team/story-s180's commits rebased: a commit was added, dropped, squashed,
reordered or reworded" (e362319, 05:55:34). It refused again at the steps the event names
"review" and "design-review" (e362450, m361, m362), after two Manager `advance` rulings
(e362356, e362436, e362468). The PO asked the liaison three times (m359, m362, m363), and
the sprint ended with s180 reverted to the Product Backlog (m364, m365).

The refused commit was not a renumber commit, although the PO said it was (m359). On the
kept branch, the first 13 subjects in `a5f800da..liaison/s180-r1-kept` match the 13 in
`d1c33886..origin/team/story-s180` one for one; the renumber is inside them. The extras
are:
- bc397e4f (05:55:34), `fixup! feat(s180): …`, one line of `agile-team/docs/architecture.md`.
  The runner made it from developer-cli's uncommitted edit, before the check ran;
- 6dfc6e66 `chore(team): quarantine out-of-scope changes by developer-cli` and b747b922
  `Revert "chore(team): quarantine …"` (05:56:02). The second rebase step edited carry.py's
  docstring (ADR-0090 to ADR-0092), outside the rebase scope (e362335, e362336).

Hence "16 commits over a5f800da instead of 13" (e362456). developer-cli said: "The extra
commit bc397e4f was added by the runner after my last handoff … I can't remove it with the
git commands I'm allowed" (e362336).

**Cause (fact: read in the code at ab91c1f2 and in git; not reproduced in a scratch repo).**
- A step's tree is settled before its effects run. `_settle_head` calls `_settle_step_tree`
  (`dispatch.py:1506`). For a finished rebase that is `settle_tree` (`dispatch.py:1625-1629`),
  which commits every in-scope leftover as `fixup! <story subject>` (`dispatch.py:1705`,
  `_subject` `:1788-1794`) and quarantines out-of-scope edits as a commit plus its revert
  (`_quarantine` `:1711-1715`, `guard.quarantine` `guard.py:400-404`).
- Only then does `_apply_rebase` run `story_rebase.find_refusal` (`dispatch.py:1603`).
  `_find_changed_commits` compares the subject lists `base..old` and `onto..HEAD` exactly
  (`story_rebase.py:111-117`, `_list_subjects` `:119-120`), so each runner commit is an "added" commit.
  `_find_dirty` (`:97-99`) never sees the leftover, because it has already been committed.
- A bounce leaves `story.rebase` queued. Only `_take_rebase` clears it
  (`dispatch.py:1638`); neither a bounce (`gates.py:1117-1123`) nor a ruling
  (`apply_ruling` `gates.py:1125-1130`, `_forward` `:1107-1115`) touches it, and the
  router always offers a queued rebase first (`router.py:341-344`). A Manager `advance`
  moves `story.step`, so the same check re-runs under each new step name with ever more
  runner commits.
- The bounce reason (`story_rebase.py:22-25`) names no commit, so the PO and the Manager
  guessed the cause.

**Entry points:** a `StoryRebase` is queued in two places, `landing.py:370` and `replay.py:269`; both carry this check, as does the boundary rebase's subject check in `scratch_rebase.py:68-103`.

**Placement:** Product Backlog. Files: `dispatch.py` (`_settle_step_tree`, `_apply_rebase`),
`story_rebase.py` (`_find_changed_commits`, `COMMITS_CHANGED`), `router.py` (`_pick_work`).
`scratch_rebase.py:68-103` has the same subject-list check for the boundary rebase. The
architect decides whether the fix also covers it. This is a pre-condition for re-running
s180 (sprint 52's m365 item 6). It is related to, but not the same as, s176 (the rebase
step's git may move only its own branch) and s178 (unique REQ ids; the ADR-number collision
is not covered, m365 item 5).
