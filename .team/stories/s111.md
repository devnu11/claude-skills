acceptance:
  - id: AC1
    environment: cli
    text: >-
      Only green is done. A sprint boundary ends as done only when every required
      check on the review PR's head commit has a green run that the runner itself read
      from GitHub. A re-run counts only when it is green and on the same commit. No
      tool argument, note or answer can mark it done.
  - id: AC2
    environment: cli
    text: >-
      Our failure blocks. When a required check fails and its failed job ran steps
      (our code ran), `continue_boundary` at the `ci_failed` hold is refused. The
      refusal names the job and the failing step, and says to open or route a fix.
      "Flaky" is not a reason the runner accepts.
  - id: AC3
    environment: cli
    text: |-
      A broken main doesn't block the team. When a check fails, the runner looks at the same check on main's head (the PR's base).
      - If it fails there too, on the same job and step, the failure is classed `main_broken`.
      - The runner records a bug story for it (`record_ci_bug`), placed first in the next sprint.
      - The sprint ends as **"ended, CI blocked by main"**: not done, the PR stays unmerged, and the team may start the next sprint.
      - At the next sprint end the PR is checked again as usual (AC1).
  - id: AC4
    environment: cli
    text: >-
      A job that never ran is infrastructure. A failed or cancelled job with no steps
      (GitHub cancelled it, as on #19's macOS job) is re-run by the runner once. It
      counts only when that re-run is green (AC1).
  - id: AC5
    environment: dashboard
    text: >-
      The board shows which. The sprint card shows one of: green (done), "CI failed:
      <job>, <step>" (blocked), "CI blocked by main: <job>" (the team carries on), or
      "re-running <job>".
  - id: AC6
    environment: cli
    text: >-
      Tests pin: a failure with steps refused; a green re-run on the same commit
      accepted; a re-run on another commit ignored; `main_broken` lets the next sprint
      start but leaves the sprint not done; a job with no steps re-run once.

## User story

As the human, I want the runner to call a sprint done only on a green CI run of
its own head, and to tell a failure in our code from a failure already on main,
so a red sprint can't be waved through, and a broken main doesn't stop the team.

## Out of scope

- Fixing main itself: that's the bug story AC3 opens.
- Merging: still the human's click, or the liaison's fast-forward of a green head.

## Notes

From the human (t59, answering m121). Decided by the human: in AC3 the team carries on when main is broken. The sprint isn't done and its PR waits until CI is green.

Priority: important but not urgent. Backlog, after the dashboard sprint (sprint 38). Do not add it to sprint 37.
