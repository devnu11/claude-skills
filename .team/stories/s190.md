**User story.** As the PO, I want a story whose old branch is still around to either use it
or tell me what to do, so that it doesn't crash and leave me without a tool to move it.

**What happened (2026-10-25 22:35, sprint 54).** In sprint 52, s180 was reverted as an
unlanded story. The runner emitted `story-branch` `dropped` (`events.jsonl` e404665), but
the local branch `team/story-s180` stayed at 7594808e, and the liaison kept it on purpose,
with a copy on origin (`decisions.md:562`). When s180 started in sprint 54, its design step
crashed: `GitError: git branch team/story-s180 d62168555d46...: fatal: a branch named
'team/story-s180' already exists` (e407490). The story held as an error. `continue_story`
would have cleared the hold (`po_tools.py:650-658`), but the next step forks the same name
again, and no PO tool takes the story out of the sprint (see
`gap-unplan-story-tool-story.md`). The liaison deleted the local branch by hand at the
sprint's stop (`decisions.md:579`, `:581`).

**Cause.**
- **fact, read at 14c30be9:** `Workspaces.ensure` forks a branch whenever `story.branch` is
  empty. `_fork` runs `git branch <name> <sprint_head>` without checking that the name is
  free (`workspaces.py:66-79`). The name has no suffix while `replays` is 0
  (`story_branches.py:58-66`).
- **fact:** reverting an unlanded story clears `branch`, `base_sha`, `pushed` and
  `worktree_head` and emits `dropped` (`reverts.py:284-293`). It only removes the worktree,
  and "the branch stays" (`workspaces.py:81-82`).
- **certain:** every unlanded story that is reverted and later re-planned meets the same
  crash unless someone deletes its branch first. s180 is the only case seen so far.
- **possible:** s159's ACs pull in different directions here. AC3.1 says a story moved out
  of the sprint keeps its branch and is rebuilt from it. AC3.3 says `revert_story` on an
  unlanded story drops its branch (`.team/stories/s159.md:145`, `:153`). The code has both
  paths: a story that leaves the sprint through `start_sprint` keeps its branch record
  (`_release_leavers`, `po_tools.py:446-456`), so `ensure` reuses the branch and only
  rebuilds the worktree; a reverted story loses the record, so `ensure` forks the same name
  and collides. Which reading holds for a reverted story, and whether the leftover is
  adopted, renamed, set aside or held on, is the architect's call. This story asks only that
  a start never crashes on the leftover and that its commits stay reachable.

**Placement:** Product Backlog. Files: `workspaces.py` (`ensure`, `_fork`), the hold and
hand-over path for a story that can't get its branch, the story-branch section of
`reference/protocol.md`. It's small. It pairs with `gap-unplan-story-tool-story.md`, and
they can share a sprint. Kept-branch handling at revert (m365 item 10) is a separate
question.
