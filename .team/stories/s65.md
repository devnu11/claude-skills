# s65: A role's git commands never reach the team repo

**Delivery:** cli (the agile-team runner's role steps and guard).

## User story

As the human running the team, I want a role that works in a presentation or
scratch workspace to be unable to run git against the team repo, so that a
mistake in a demo builder can never move my branches.

## Why

During s61 the integration-tester built a demo workspace that had no `.git` of
its own. Its git commands found the real repo above it and ran
`checkout -B main`, which moved the human's existing local `main` (68c6c54) to
the feature branch commit. The liaison repaired it by hand. Deleting `main`, as
a first fix suggested, would have destroyed the human's branch.

## Acceptance criteria

1. For a step that works in a presentation or scratch workspace, the runner
   sets `GIT_CEILING_DIRECTORIES` (or an explicit `GIT_DIR`) so that git run
   there cannot discover the team repo above the workspace. A test shows git in
   a workspace with no `.git` fails with "not a git repository" instead of
   acting on the team repo.
2. The guard denies a git command that runs outside the role's own workspace
   (an explicit `-C`/`--git-dir`/`--work-tree` that points at the team repo
   from a presentation step counts). A test pins the denial and its reason.
3. A role's legitimate git use inside its own workspace, and the runner's own
   git use, are unchanged.
4. The behaviour is data-driven (a table of which roles and steps get the
   restriction), not a branch per role.
5. `SKILL.md`, `reference/protocol.md` and the role files that tell the
   integration-tester how to build a presentation say so, in the same story.

7. (AC7) In a presentation step (integration-tester or customer-proxy), the
   guard allows `git init`, `git -C <path>` and `git clone <src> <dst>` when
   every path argument resolves inside the story's workspace
   (`.team/run/presentation/<id>/workspace`). The same commands with a path
   outside the workspace stay denied (AC2). The rule is a table entry, not a
   new branch.
8. (AC8) A story's presentation workspace survives a bounce from acceptance
   back to e2e; only the integration-tester replaces it. A test pins it
   (bounce, then the files are still there).
9. (AC9) One e2e test, in a tmp dir holding a scratch "team" repo with the
   workspace inside it:
   (a) in the workspace, under the guard's rules and the step's environment:
   `git init demo`, a commit, `git -C demo checkout -b topic`, a commit,
   `git -C demo rebase main` and `git clone demo copy` each exit 0;
   (b) `git -C <team repo> status`, `git --git-dir <team repo>/.git log` and
   `git checkout -B main` run from the workspace with no `.git` are each
   refused: the first two by the guard, naming the team repo, the last by git
   ("not a git repository", from AC1's ceiling);
   (c) the team repo's `git for-each-ref` output and HEAD are identical before
   and after.
10. (AC10, moved from s12 AC4b) For every role, the git-commit check sees
    through command prefixes: `X=1 git commit`, `env git commit` and
    `command git commit` are denied like `git commit`. One test per form.
