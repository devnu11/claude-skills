# s59: Start-of-sprint sync survives a rebase-merge to main

**Delivery:** agile-team runner (boundary sync).

## User story

As the human, I want the sprint-start sync to recognise that main holds rebased copies of the team branch's own commits, so a rebase-merge to main does not stop every sprint with a hundred false conflicts.

## Acceptance criteria

1. Before merging, the sync compares by content, not by hash (`git log --cherry-pick --right-only HEAD...origin/main`). When nothing on main is new by content, the sync completes without human help (a merge that keeps the branch tree, `-s ours`, so main's hashes are in the history).
2. When main has new content as well, the sync merges with `-s ours` and then applies only the new content (for example the changes in the commits `--cherry-pick` lists). Plain `-X ours` is not used: it resurrects code the branch deleted.
3. A real conflict (the same lines changed differently by new commits on main) still stops with the existing `sync_conflict` hand-over, listing the conflicting files grouped by directory with a count.
4. Tests cover the three cases on a scratch repo: all rebased copies, rebased copies plus new content, and a real conflict. Never touch the real home directory.
5. Docs move with behaviour (`agile-team/SKILL.md`, `agile-team/reference/protocol.md`). Coverage stays at 95%+; ruff check and ruff format clean.

## Origin

2026-10-11, the human on m54: sprint 18's sync reported about 100 conflicts. They were not real: main holds rebased copies (new hashes) of the branch's earlier commits. The human merged by hand as 3fe1332, keeping the branch tree and taking only the new content on main (the six-hats skill and its README rows). A rebase-merge to main makes this happen every time. Alternative the human named: reset the team branch onto main after each main merge. Related to the sync story s29. Priority: backlog; before the next sprint start if possible.
