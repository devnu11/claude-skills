title: Requirement change tracking, auto-accept and requirements log
depends_on:
  - s1  # requirement file format and parser
acceptance:
  - id: AC1
    environment: cli
    text: >-
      After an Architect step, `Runtime.settle_tree` classifies every file under
      `<docs>/requirements/` from `git diff --name-status` as added, changed or
      retired (status flipped to `retired` or file removed).
  - id: AC2
    environment: cli
    text: >-
      The handoff accepts a new optional field
      `"requirement_changes": {"REQ-003": "why"}`. A changed or retired requirement
      without a reason bounces the step with "explain change to REQ-003", the same way
      a bad handoff does. Added requirements need no reason.
  - id: AC3
    environment: cli
    text: >-
      Reasons are written into the step commit as git trailers, one per requirement:
      `Requirement-Changed: REQ-003: <why>`. Git is the durable history; there is no
      extra store.
  - id: AC4
    environment: cli
    text: >-
      Each change emits a `requirement-changed` event to `.team/run/events.jsonl` with
      the requirement id, the kind (added/changed/retired) and the reason.
  - id: AC5
    environment: cli
    text: >-
      Auto-accept: other active stories that trace a changed or retired requirement and
      are past `design` go back to `design` without counting a round. Done stories that
      trace it are listed as `affected_done_stories` in the `run_role` report.
  - id: AC6
    environment: cli
    text: >-
      `agile-team requirements log` prints JSON change history parsed from the
      `Requirement-Changed` git trailers (requirement id, reason, commit sha, date).
  - id: AC7
    environment: review
    text: >-
      `architect.md` documents the `requirement_changes` handoff field;
      `product-owner.md` says to open a follow-up story for `affected_done_stories`;
      `reference/protocol.md` documents the handoff field, the trailer format, the
      event and the `requirements log` CLI row.

## User story

As the human, I want every requirement change to carry a reason recorded in
git, and stories affected by the change to be re-checked automatically, so I
can see how requirements evolved and trust that in-flight work follows the
current requirements.
