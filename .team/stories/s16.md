---
id: s16
title: Requirements are the tasks - the runner implements one requirement per developer step and ties each commit to it
delivery: cli
acceptance:
  - id: AC1
    text: >-
      At the implement step, the runner works through a story's requirements one at a
      time, mechanically and in Python: it briefs a developer with exactly one
      requirement (id, text and the ACs it covers), the developer implements it, and
      the runner commits the result as that requirement's commit. The order comes from
      the requirement files, not the PO.
  - id: AC2
    text: >-
      Each commit is tied to its requirement: the commit message carries the
      requirement id (e.g. a `Requirement: REQ-012` trailer), and the requirement's
      record lists its commit sha(s). A step that touches no files, or fails its gate,
      leaves the requirement open, and the runner says which one.
  - id: AC3
    text: >-
      The implement gate passes only when every requirement of the story has a commit
      and the whole suite passes. Requirement progress (open, in progress, done with
      sha) is in `state.json` and the snapshot.
  - id: AC4
    text: >-
      The dashboard Board shows each story's requirements as its tasks: a count on
      the card (e.g. "3/5") and an expandable list with each requirement's status and
      commit. The Requirements tab links each requirement to its commits.
  - id: AC5
    text: >-
      The developer role brief, `reference/protocol.md` (pipeline, implement step),
      SKILL.md and the snapshot fixture describe per-requirement implementation.
  - id: AC6
    text: >-
      Tests cover the per-requirement loop, commit tagging, a failed requirement, the
      gate and the snapshot/board fields. Coverage stays at or above 95%, and ruff
      check and ruff format are clean.
---

## User story

As the human, I want each story broken into the requirements the architect
writes, implemented and committed one at a time under the runner's control, so
that the board shows real tasks and every commit traces back to a requirement.

## Notes

Human, m8 Q1: "a user story is high level, the architect should already be
breaking that down into requirements. And commits should be tied to
requirements, right. Could this be something mechanical that can be controlled
explicitly via python? Developer given a requirement, implements and returns a
commit."

Depends on s1 (structured requirement files and the traced design gate). It
pairs with s2 (requirement change tracking).
