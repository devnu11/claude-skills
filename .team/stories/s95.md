# s95 (A14c): acceptance runs once per environment

**Delivery:** cli (the runner can't read per-AC environments until s94 (A14b) ships; the [tag] on each AC below is its environment).

Plan: `.team/run/liaison/plans/acceptance-environments.md` (human-approved 2026-10-13). Depends on s94 (A14b). Folds in s91 (clearer e2e gate text) as AC1's gate text.

## User story

As the human, I want a story with ACs in several environments tried in each of them, by a customer proxy that sees only that environment's ACs, so no part of a story is accepted on trust.

## Acceptance criteria

- **AC1 [cli]. Presentations per environment.** The integration tester builds one presentation per environment the story's ACs name, at `.team/run/presentation/<id>/<environment>/`. The e2e gate checks each one with that environment's recipe, and a missing one bounces, naming the environment and the files it expected.
- **AC2 [cli]. One proxy step per environment.** Acceptance runs one customer-proxy step per environment, one after another, in config order.
  - Each step's sandbox is prepared from its environment alone.
  - Each brief lists only that environment's ACs, with their ids.
- **AC3 [cli]. Every environment runs, then one verdict.**
  - All environment steps run, even after one fails, so the developer gets the full feedback in one bounce.
  - The story passes acceptance only when every environment passes.
  - Otherwise it bounces once, listing every failed environment with its failed AC ids.
  - After rework, **all** environments run again.
- **AC4 [dashboard]. One report.** `.team/acceptance/<id>.md` has one section per environment, with the AC verdicts and the evidence. The dashboard shows the story's environments, each marked pass or fail.
- **AC5 [cli]. Tests pin these cases:**
  - a two-environment story passes only after both pass;
  - a failure in the first environment still runs the second, and the one bounce lists the failures from both;
  - a rework re-runs both;
  - a `manual` environment needs no service.

## Folded in: s91 (clearer e2e gate text)

s91's text goes into AC1's gate message (human decision, t33). The refusal for a missing presentation must say what it found, per environment:
- the workspace exists but holds only `.git`: the refusal says "holds only .git" and names a file to add (the demo or evidence file);
- the workspace is missing: the refusal says "missing";
- a test pins each of the two texts;
- the integration-tester role file says the workspace must hold the demo or evidence files themselves, not only an empty repo.

Why: s89 and s59 were both refused with "workspace is missing or empty" when the workspace held only `.git`. The text hid the cause, and each time it cost a manager ruling and an extra e2e round.
