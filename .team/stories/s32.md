---
id: s32
title: After-commit lint-fix loop - fixers run after a coder commits, the coder reviews the fixes, and a loop is broken and escalated
delivery: cli
acceptance:
  - id: AC1
    text: >-
      After any coder commits (the developers and the unit-tester), the runner runs
      the configured fixers (for example `ruff check --fix` and `ruff format`) as
      `after-commit` hooks (s31). If they change nothing, there is no extra turn.
  - id: AC2
    text: >-
      If the fixers change files, the changes go in as a fixup commit, and the same
      role gets a short review turn: it approves the fixes, or amends them. Its brief
      holds the fixer diff. An approval costs one short turn and ends the cycle.
  - id: AC3
    text: >-
      An amend is run through the fixers again. The runner counts fix-and-review
      cycles per commit. At a small cap (config, default 2), or when a cycle repeats
      the same fixer diff (compared by hash), the runner stops the loop in code and
      escalates; it never starts another cycle. A role that reverts the fixes cannot
      loop forever.
  - id: AC4
    text: >-
      The escalation goes to the Manager through s27's repeat-bounce path. It carries
      the diffs of each cycle and the role's reasons, and it counts no round for the
      role. A role that disagrees with a fixer rule can say so in its review turn, and
      that reason is part of the escalation. The Manager may rule to change or turn off
      the rule (a DevOps config change), or to tell the role to accept it.
  - id: AC5
    text: >-
      Each fixer run, fixup commit, review turn and escalation is an event the
      dashboard shows, as s31's hook nodes do. Commit hashes recorded in state are not
      invalidated: fixups are new commits, and nothing is rewritten.
  - id: AC6
    text: >-
      `roles/` for the coder roles, `reference/protocol.md` and SKILL.md describe the
      loop and its cap. Tests cover no-change, a change that is approved, an amend
      that converges, a revert that repeats the same diff, the cap and the escalation.
      Coverage stays at or above 95%, and ruff check and ruff format are clean.
---

## User story

As the human, I want the linter's fixes applied right after a coder commits and
reviewed by that coder, and a fix-and-undo fight to be stopped and escalated, so
that style never reaches the quality step and nobody loops.

## Notes

Human: "The linter should run for each of the coders after they commit, and they
should get a chance to approve the fixes it makes or amend the fixes." And:
"there could be an endless loop, e.g. if the agent keeps amending the lint
fixes. Need a mechanism to break that loop and escalate."

Story B. Depends on s31 (hooks) and s27 (repeat-bounce escalation).
