acceptance:
  - id: AC1
    text: >-
      A hook (s31) can be a service hook: a start command, a stop command and a
      readiness probe, all in `.agile-team.toml`. The runner starts the service before
      the target step, waits for the probe to pass within a bounded time, and stops it
      after the step in every case (pass, fail, crash, stop request). A service that
      doesn't become ready fails the hook with the start command's output, and `block`
      or `inform` applies as for any hook.
  - id: AC2
    text: >-
      Example in this repo's config: the dev environment (the dashboard against sample
      run files) comes up before the integration-tester, and stays up for the
      customer-proxy's acceptance step when the config says so (`keep_until`).
  - id: AC3
    text: >-
      s26's presentation start and probe are generalised onto this mechanism: the
      per-delivery `prepare`, `probe` and teardown lines become service hook
      definitions, and the "presentation ready" gate is the service hook's probe. The
      s26 tests still pass, and its behaviour doesn't change.
  - id: AC4
    text: >-
      Stale services from an earlier step or a crashed run are found by a pid or port
      record in the run dir and replaced, not reused. A port conflict is reported
      clearly. Hosts and ports come from config.
  - id: AC5
    text: >-
      Service start, ready, stop and failure are events; the dashboard shows the
      service as a node bracketing its agent, up or down, as s31's hook nodes do.
  - id: AC6
    text: >-
      `reference/protocol.md`, `roles/devops.md`, SKILL.md and the README row describe
      service hooks. Tests cover start, probe pass and fail, teardown on every exit
      path, stale replacement and the s26 equivalence.

## User story

As the human, I want the environment a step needs to come up before it and go
down after it, with a check that it's really answering, so that no step fails on
a missing server.
