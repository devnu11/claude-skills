# s99 (A6b): the runner's own stages are named, timed and kept as data

**Delivery:** cli

Plan: `.team/run/liaison/plans/tool-flow.md` (human-approved 2026-10-13, about 02:15). Its sections "The names of the tools are data" and "Readability" are context for the Architect. Each AC's [tag] is its acceptance environment.

## User story

As the human, I want every stage the runner runs, before or after a step, named and timed, so the runner's time is as visible as the agents'.

## Acceptance criteria

- **AC1 [cli]. The stage table.** `stages.STAGES` lists every stage the skill runs, with a unique name, a description, `when` (before, after, or `during` for `runner-tool.*` stages that run inside an agent's step at its request) and what it attaches to (step, story or boundary). It covers:
  - `env.prepare` and `presentation.layout`, `checkout.guard`, `gate.*` and `presentation.trial`;
  - `boundary.sync`, `boundary.check`, `boundary.push` and `boundary.ci-wait`;
  - `runner-tool.<name>`.

  A stage the code runs that isn't in the table is a test failure.
- **AC2 [cli]. Repo tools.** `.agile-team.toml` accepts `[[tool]]` entries (name, description, command), owned by DevOps, as `[toolchain]` is. A duplicate name, or a clash with a built-in, is refused on load. `agile-team tools` prints the built-in and repo lists.
- **AC3 [cli]. Timed at the choke points.** Each stage is timed where it runs: `CommandShell.run` / `shell_runner`, `Git`, `Upstream.wait_checks`, `sandbox.prepare` and `presentation.lay_out`.
  - The caller names the stage, and a stage is never inferred from the command text.
  - Each run writes a `runner-stage` event with its name, story, step, `when`, command detail (80 characters), exit code, start (wall and monotonic) and awake seconds.
- **AC4 [cli]. Tests pin:**
  - every stage the code runs is in the table;
  - one event per stage run, with its `when` and attachment;
  - a repo tool's name clash refused;
  - awake seconds under a faked clock.
