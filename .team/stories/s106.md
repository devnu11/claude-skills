# s106: Bug: sprint 33's CI check "CI / test (macos-latest)" ends as cancelled on PR #19

**Delivery:** cli

## User story

As the team, I want the PR's CI to finish green on macOS, so a sprint's PR can be called ready to merge.

## Context

The sprint 33 boundary waited for the checks on https://github.com/devnu11/claude-skills/pull/19. The runner reported one failing check: `CI / test (macos-latest)`, result `cancel`, https://github.com/devnu11/claude-skills/actions/runs/38419112562/job/115371389456. The PR is NOT ready.

A `cancel` is not a test failure. It may be a job timeout, a hung test (the known flaky heartbeat tests `test_s44_live::test_heartbeat_shape_and_atomic_write` and `test_s78_health::test_the_heartbeat_is_version_2_with_a_monotonic_stamp_in_order` are candidates), a concurrency group cancelling the run after a newer push, or a runner-side cancel. The cause is not known yet; finding it is part of the story.

## Acceptance criteria

- **AC1 [cli].** The cause of the cancelled `CI / test (macos-latest)` job is found from the job log and workflow file and stated in the story's handoff (timeout, hung test, concurrency cancel, or runner).
- **AC2 [cli].** The cause is fixed in code or workflow config (a hung or flaky test made deterministic; a timeout or concurrency setting corrected), without weakening, skipping or deleting any test.
- **AC3 [cli].** If the cause is outside the repo (a GitHub-side cancel), the story says so with evidence and the fix is a documented re-run path; the boundary's `ci_failed` handling of `cancel` results is checked against that.
- **AC4 [cli].** The unit suite and the macOS job pass on the next PR run.
