# s80: Review branches carry one commit per story (autosquash at the boundary)

**CANCELLED (t15, 2026-10-12).** The human wants the team's real history on main (fixups included, rebase-merged, linear). Not built. No design or test commits existed. Do not pick this story up.

Delivery: cli (runner boundary)

## User story

As the human, I want each sprint's review branch to hold one commit per story,
so that "Rebase and merge" puts a readable history on main, not hundreds of
commits with `fixup!` entries.

## Context

Human message t8: PR #14 (sprint 21) held 500+ commits including `fixup!`
commits. Related to s29 (boundary steps) and s59 (rebase at the boundary).

## Acceptance criteria

- AC1: When the boundary builds a sprint's review branch, it autosquashes the
  `fixup!` commits into their story commits (`git rebase --autosquash` onto
  `origin/main`), so the review branch has one commit per story.
- AC2: Only the review branch is rewritten. The team branch's hashes are never
  rewritten by this step, and `state.json` story commits stay valid.
- AC3: The push uses `--force-with-lease` and only for the review branch the
  team owns (same rule as s59 AC4).
- AC4: The tree of the review branch equals the team branch's tree (no content
  lost); if it differs, or the autosquash conflicts, the boundary aborts the
  rebase, leaves both branches unchanged and raises the existing boundary
  hand-over naming the files.
- AC5: Tests on a scratch repo cover: fixups squashed into the right story,
  tree equality, a conflict, and that the team branch is untouched. Never touch
  the real home directory; set the git identity in the scratch repo.
- AC6: Docs move with behaviour (`agile-team/SKILL.md`,
  `agile-team/reference/protocol.md`). Coverage 95%+; ruff clean.

## Out of scope

Rebasing the existing `team/sprint-21` branch for PR #14: the liaison does that
once, on a scratch copy, force-pushing the review branch only.
