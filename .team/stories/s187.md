acceptance:
  - id: AC1
    environment: cli
    text: >-
      A gate-fix step's brief names the commit the gate ran on (short sha), the story's
      worktree path, and whether the worktree head is still that commit; when it has moved,
      the brief lists the commits since (short sha and subject). Checked by hand: make a
      story's implement gate fail on a file another role owns and read the fix step's
      `step-start` brief in `events.jsonl`.
  - id: AC2
    environment: cli
    text: >-
      A gate-fix step that hands off `done` with no commit and no change doesn't count as a
      fix: the story isn't sent back to the failing step to fail on the same items again as
      a new round, and the fix role (or, on escalation, the Manager) is told that the step
      changed nothing. A fix step that does commit goes back to the failing step as today.
      Checked by hand with a fix role that hands off `done` without editing anything.
  - id: AC3
    environment: cli
    text: >-
      When a repeated gate-fix setback escalates to the Manager, the Manager's context gives,
      for each round, the commit the gate ran on, each fix step's commit (or "none") and the
      worktree head, so a "the gate ran on a stale commit" ruling can be checked against
      them.

**User story.** As the human, I want a role that fixes a gate failure to test the same tree
the gate failed on, so that a real regression isn't waved through as "passes here" and
blamed on the runner.

**What happened (2026-10-25 21:03-21:12, sprint 53, s181).** The unit-tester committed
3584d6b0 (`events.jsonl` e405248). The developer's next step made no commit ("all listed
tests pass on current HEAD", e405357, `commit: null`). The implement gate's suite failed
on 5 e2e tests in integration-tester files and routed them (e405360). PR CI was red on the
same sha 3584d6b0 with the same tests (e405385). The fix brief lists the failing tests
and paths only, with no commit and no worktree (e405363). The integration-tester's `git log`
(after a relative `cd`) ended in error (`tools.jsonl:23927`, `status: error`). From its third call on it ran `cd
/Users/devans/code/claude-skills/agile-team/runner && ...`, the main checkout and not s181's
worktree, and ran the e2e files there by name (`tools.jsonl:23936-23941`). It handed off
`done`: "the three listed e2e files pass in full ... against the current worktree", with the
friction "Naming the product commit the gate ran against, and whether the worktree has moved
since, would help" (e405406). The runner recorded the fix as `commit: null,
assertions_changed: false` (e405407). The developer step failed the same way (e405508), the
setback escalated (e405511), and the Manager ruled `fault: runner`, "it gated s181 on a stale
commit (3584d6b) ... I ruled advance past the stale gate" (e405521-e405522, m377). The
failures were real regressions from s181 (createElement in the node harness, health red on
the new chore list; m378, `decisions.md:570`), and the liaison sent s181 back to its
developer by hand.

**Cause.**
- **fact, read at 14c30be9:** the brief doesn't name the gated commit or the worktree.
  `fix_brief` writes `FIX_HEADING`, the items and the doc paths only (`router.py:74-80`,
  `:178-182`). `Fix` holds role, items, rule and why, with no sha (`owners.py:87-92`).
  `FixRecord` keeps the fix's commit and `changed` (`owners.py:97-104`), but nothing
  re-checks the routed failures when a fix changes nothing: `_fix_effects` pops the fix on
  any `done` handoff, `commit` or not (`dispatch.py:1583-1591`, `fix_outcome` `:2298-2301`).
- **fact:** the Manager's repeated-setback context lists `gate`, `step-end`, `test-dispute`,
  `escalation`, `ruling` and `fault` events only (`HISTORY_KINDS`, `loops.py:58`,
  `_history_events` `:163-166`, `manager_view` `:169-181`). The `gate-fix` events, which
  carry each fix's `commit` (`dispatch.py:1690-1699`), are left out, so the Manager never saw
  `commit: null`.
- **certain:** the step tested the wrong tree. The `cd` targets are in `tools.jsonl`. At
  21:07 the main checkout didn't hold s181's code, which landed at 21:57
  (`decisions.md:573`), so the old e2e tests passed there. The step's cwd is the story
  worktree (`dispatch.py:301`), but Bash isn't path-guarded (`guard.py:15-19`), so an
  absolute `cd` leaves it, against the house rule "never `cd`" (`.team/CLAUDE.md`).
- **fact:** the gate wasn't stale. Nothing was committed between 3584d6b0 and the gate.

**Placement:** Product Backlog. Files: `router.py` (`fix_brief`), `owners.py` (`Fix`, and
where the gate builds it in `gates.py`), the gate-fix settle path, the Manager's
repeated-setback context (`loops.py`), `roles/_shared.md` (gate fix text) and the gate-fix
section of `reference/protocol.md`. Not covered by s153, s157 or s92 (gate-fix routing as
built). Confining Bash to the worktree is a separate question and isn't asked here. How AC2
is met (re-running the routed tests in the story's worktree, refusing a `done` with no
commit, or another way) is the architect's call.
