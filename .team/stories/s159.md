title: "Story branches: each story on its own branch, landed on the sprint branch only when green"
acceptance:
  - id: AC1.1
    environment: cli
    text: |-
      When a story's first step starts, the runner makes the story branch `<story_prefix><id>` (default `team/story-<id>`) from the sprint branch's head, and records that head as the story's **base sha**. The story's worktree is at `.team/run/worktrees/<id>/`, inside the repo and gitignored. The runner creates nothing outside the repo except under the system temp dir. For a step in a worktree, the guard's scope base is that worktree, so `.team/run/` being in the guard's ignore list doesn't hide the story's files. The git ceiling stays at `.team/run`, which the worktree's own `.git` file already satisfies.
  - id: AC1.2
    environment: cli
    text: |-
      Every step on that story runs in that worktree, and so do:
        - its file scopes and the guard's scope base;
        - the Stop hook;
        - the step's commands (`CommandShell`) and the stop checks;
        - the story-file reads.

        The shared run files stay in the main checkout's `.team/run/`: `state.json`, the events, the ledger, the messages and `live.json`.
  - id: AC1.3
    environment: cli
    text: |-
      The team's main checkout stays on the sprint branch. Only two things move it: landing, and the PO's story-admin commits. Both update the checkout guard's record and the sprint's `StackEntry.head` when they do.
  - id: AC1.4
    environment: cli
    text: |-
      The checkout guard checks each story's worktree before that story's step. Drift there blocks only that story, names the files, and hands over to the PO as `worktree_drift`. `accept-checkout --story <id>` works while the runner runs. It leaves a request that the scheduler applies, as `tell` and `answer` do: the worktree's head is recorded, and the story's block clears. Drift in the main checkout halts the run, and `accept-checkout` without `--story` works as today.
  - id: AC1.5
    environment: cli
    text: |-

The runner's push guard accepts branches under either prefix, and still never pushes main or the checked-out branch. Its refusal names both prefixes.
  - id: AC2.1
    environment: cli
    text: |-

It runs `git merge --no-ff <story branch>` there, with the message `merge(<id>): <title>`, so the sprint head is the first parent. This is the only kind of merge commit the runner makes.
  - id: AC2.2
    environment: cli
    text: |-

  - id: AC2.3
    environment: cli
    text: |-
      `land` is a built-in pipeline step after `acceptance`. It's in `ALWAYS_STEPS`, so no config removes it, and it's a checkpoint whose role is `runner`, so no PO `run_role` targets it. The Manager's `advance` from `acceptance` moves a story to `land`, never straight to done. `land` runs the full checks on the merge commit.
        - On red, it discards the scratch merge, so the sprint branch never moved, and the story goes back to its developer with the failures.
        - On green, it goes on to AC2.4.

        The story is done only when `land` passes. `depends_on` and the PO's renewal both key on that.
  - id: AC2.4
    environment: cli
    text: |-
      `land` pushes the merge commit to the story's **landing branch**, `<story_prefix><id>-land` (a branch creation), and waits for CI on it. The wait holds this story only, while other stories' steps keep running.
        - **Reading the CI:** the wait polls the check runs of the landing head's sha, since the landing branch has no PR, under `ci_timeout_s`. It keeps its own re-run record on the story. A head with no check runs at the timeout is `ci_pending` for that story, never green.
        - **Green:** the sprint branch is fast-forwarded to the merge, and pushed to `<prefix><N>`. The sprint's `StackEntry` (AC2.17) records the new `head` and `pushed`, and a `story-landed` event records both parents. The first landing in a sprint opens the sprint PR as a **draft** (`DRAFT`). The PR stays a draft until the sprint end, and it's reused by the number in the entry, never looked up again by branch.
        - **Red:** the story goes back to its developer with the failures. The sprint branch, local and remote, is untouched.
        - **Either way,** the landing branch is then deleted by `Upstream.delete(lease)`, which names the landing sha it expects, so the next landing creates the branch afresh. `delete` refuses any branch not under `<story_prefix>*-land`. It's the only deletion the runner makes, and it's exempt from AC2.16's ancestor check.
        - **An infrastructure failure** (as `ci.py` classifies it today) gets one re-run at the same head. If that fails too, the story hands over as `ci_infra`, and only that story waits.
        - **A rejected push** of the sprint branch is never retried. The runner fetches:
          - if the remote branch has moved ahead of the runner's record (someone pushed a fix), the runner fast-forwards the local sprint branch, `head`, `pushed` and the guard's record to it, and the story lands again from AC2.1, with a new merge, new checks and new CI;
          - otherwise the run halts as checkout drift, naming both heads, and the liaison is told.
  - id: AC2.5
    environment: cli
    text: |-
      At the sprint end, the sprint branch is **replayed** onto main, walking its first-parent line in order:
        - for a story merge `M`, the story's commits (`M^1..M^2`) are rebased onto the new tip, then merged again with `--no-ff` and `M`'s message;
        - a plain commit on the sprint branch (for example, story admin) is cherry-picked.

        The result is a first-parent line of story merges, each with its story's commits beside it. The sprint-start sync (s152, ADR-012) uses the same replay when main has moved.

    environment: cli
    text: |-
      No push replaces a branch's history. Every push the runner makes, including today's boundary pushes:
        - names the exact sha it expects on the remote, `--force-with-lease=<ref>:<sha>`. That sha is the head the runner last recorded for that branch in `state.json`: `StackEntry.pushed` for a sprint or replay branch, `StoryState.pushed` for a story branch, or "absent" for a new branch;

**User story.** As the human, I want each story built on its own branch, several at once, merged into the sprint branch only when it passes every test and CI, and replayed onto main as a clean line of story merges. Then the sprint branch is always green, a story that stops leaves nothing behind, stories can run in parallel, and main's history shows each story as one unit.

**Placement:** the human (2026-10-17): "keep it all together a mega story, but its all that goes in the sprint". It is the only story in its sprint.

**Design source:** the liaison's plan `.team/run/liaison/plans/story-branches-v10.md` (decisions and review answers) and the target flow charts `.team/run/liaison/plans/workflow-flowcharts-v9.md`. The ACs above are the plan's, verbatim.

**Notes from the plan:**
- *(Deferred: picks, draft 3's AC5.3, depend on s141, which isn't built.)*
- *Cost note:* each push to a `team/**` branch runs CI once, from the push event. A PR whose head is a `team/` branch skips its `pull_request` jobs, and nothing is cancelled (#36). That's one run per commit per open story, two per landing (the landing branch, then the sprint branch, at the same sha), and one per replay branch.

**Already done outside this story:** CI runs on pushes to `team/**` (PR #36); main's ruleset allows the story merges.

ACs written by the liaison and cross-checked by Fable twice (reports 2026-10-17-story-branches-v7-fable-review.md and -v9-push-review.md). The human approved the design decisions, not the AC text.
