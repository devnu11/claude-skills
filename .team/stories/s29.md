---
id: s29
title: Keep the team's work in sync with upstream, and deliver each sprint as a rebased stacked PR
delivery: cli
acceptance:
  - id: AC1
    text: >-
      At sprint start, before any role runs, the runner fetches upstream and merges
      upstream main into the team branch. A local merge commit is fine. The team
      branch is never rebased or rewritten, so the commit hashes the run records
      (state.json story `commit`, review and design files) stay valid. If upstream has
      nothing new, no commit is made. A merge conflict stops the sprint start and goes
      to the PO as a hand-over with the conflicting files named.
  - id: AC2
    text: >-
      After each sync, the runner runs the full checks: the toolchain's lint, tests
      and coverage gate, and the e2e suite for each delivery. This is a sprint-boundary
      step that can't be skipped, and it is code, not a prompt. A failed check becomes
      a DevOps fix step, with the check's output in the brief, before the sprint's
      stories are allowed to move. A second failure for the same reason escalates to
      the Manager (see s27).
  - id: AC3
    text: >-
      At sprint end, the runner builds a review branch: a scratch copy of the team
      branch rebased onto origin/main, in a separate worktree so the team branch and
      its hashes stay untouched. Commits already in main drop out. The runner runs the
      same full checks on that copy. A conflict or a failed check is reported with its
      output and goes to a DevOps step on the review branch, and the sprint's end waits
      for it. Nothing is pushed until the checks pass.
  - id: AC4
    text: >-
      Pull requests are stacked, one per sprint. Each PR is based on the previous
      sprint's PR, and the first is based on main. At sprint end, the runner rebases
      the whole unmerged stack once onto the latest main, rebuilding each sprint's
      review branch in order, checks the bottom one, and pushes all of them. The review
      branch names, PR numbers and bases are recorded in `state.json` and appear in the
      snapshot.
  - id: AC5
    text: >-
      Only the bottom PR is ready for review. The others are drafts. The repo's CI
      workflows skip draft PRs, so CI runs once per merge however deep the stack is
      (the workflow change is in scope). When the human merges the bottom PR, the
      runner retargets the next PR to main and marks it ready. Merges to main are
      rebase merges. The runner detects a merged PR on the next sync and drops it from
      the stack.
  - id: AC6
    text: >-
      Permission to push is asked once. On the first sprint end where it is needed, the
      PO relays one question to the human: may the team push review branches and open
      or update PRs? The answer is recorded in config or state and applied to every
      later sprint without asking again. If the answer is no, the runner prepares the
      review branch locally and reports instead of pushing. The runner never pushes the
      team branch itself, and never force-pushes to main.
  - id: AC7
    text: >-
      Git and `gh` access is one narrow, testable interface so tests use a scratch
      origin with bare repos and a fake PR service. Tests never touch the real remote
      or the real home directory. A repo with no upstream or no `gh` skips the sync and
      PR steps with a note, not an error.
  - id: AC8
    text: >-
      The dashboard shows the stack (sprint, branch, PR number, draft or ready, check
      result) in the Backlog or Flow view, and the snapshot fixture is updated.
      `reference/protocol.md` (sprints, git, sync, PR stack), SKILL.md, the README row
      and the DevOps and PO role files describe the flow. An ADR records the
      merge-in, rebased-review-branch and draft-stack decisions. Coverage stays at or
      above 95%, and ruff check and ruff format are clean.

## User story

As the human reviewing the team's work, I want each sprint delivered as a PR that
is rebased on the latest main and verified, and the team to start each sprint
from the latest upstream, so that what I merge is current, checked and does not
make CI run for every PR in the stack.

## Notes

Human's request, in their words: at the end of a sprint, push code upstream for
review, then rebase on main, verify everything still works, and repush. At the
beginning of a sprint, rebase on upstream and validate everything still works.
For PRs from prior sprints that may not have merged, update all of them at the end
with the code rebased on the latest main. Each PR depends on the one before, but CI
shouldn't be slammed.

Decisions already made by the human:
1. Never rewrite the team branch: the run records commit hashes. Sprint start merges
   upstream main in. Sprint end builds a rebased scratch review branch and checks and
   pushes that. "I only care that the code merged to main was rebased before merge."
   Merges to main are rebase merges. PR #10 was landed this way by hand.
2. Stacked PRs, one per sprint, drafts skip CI, only the bottom is ready.
3. The runner does the git work and the checks in code, as a boundary step. A failed
   check becomes a DevOps fix.
4. Push permission is asked once and applies to every later sprint.

Scheduled after s25, s26 and s27, since s27's repeat-escalation is needed here. A
second failure after a fix would otherwise loop. It depends on s19 (the runner owns
routing) and the s13 presentation interface.
