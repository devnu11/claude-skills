# claude-skills

Personal [Claude Code](https://claude.com/claude-code) skills. Standalone and
self-contained — nothing here depends on the rest of my dotfiles, so it can be
cloned on its own.

## Layout

One directory per skill, each containing a `SKILL.md` with YAML frontmatter:

```
<skill-name>/
	SKILL.md          # name + description frontmatter, then the instructions
	reference/        # optional detail SKILL.md points Claude at
	runner/           # optional Python helper (a uv project with its own tests)
```

The `name` in the frontmatter should match the directory name, and the
`description` is what Claude matches against to decide whether a skill is
relevant — write it as "use this when…", listing concrete trigger phrases.
The rules for developing skills here are in
[`.claude/CLAUDE.md`](.claude/CLAUDE.md).

## Skills

| Skill | What it does |
|---|---|
| [`agile-team`](agile-team/SKILL.md) | Hands a large task to a headless team of specialized Claude roles (Product Owner, Architect, Developers, Testers, Reviewer, DevOps, Customer Proxy, Manager; the Architect writes the ADRs as it designs) while the interactive session acts as liaison. Stories move from a backlog through sprints and a gated pipeline that the runner routes by itself, started stories first, then in an explicit priority order the PO sets (a not-started story goes ahead only with a reason; the board shows each story's position, and why a held story is waiting; a story's `depends_on` list in its file keeps it from running until those stories are done, and a bad list or a cycle stops the start), calling the PO only for judgement (DevOps reviews every design in an `ops-review` step that can't be configured away, saying how each acceptance criterion will be checked automatically, adding missing CI or toolchain config itself or naming a story for what it can't add, and the runner records the list in the story file under `## Tooling`; the requirements are files (`<docs>/requirements/REQ-NNN.md`) the Architect writes, and a new story leaves design only when each acceptance criterion is covered by an active one, which `agile-team requirements check` reports as JSON; a changed or retired requirement carries its reason as a `Requirement-Changed` git trailer (`agile-team requirements log`), and stories past design that trace it go back to design; a developer can send a story back to the unit-tester when a test contradicts the design, and a setback that repeats for the same reason, or a story bouncing between the same two steps too often for any reason, goes to the Manager instead of looping), and end with the Integration Tester presenting each story to the Customer Proxy in a ready-made workspace, once per acceptance environment its criteria name, with one verdict after all are tried (a web acceptance environment is started and must answer before acceptance begins; a `document` one, for prompt and docs changes, is read, not run). Each story runs on its own branch (`team/story-<id>`) in its own worktree inside the repo, and up to `max_open_stories` stories run their steps at the same time, while the PO gets their hand-overs one turn at a time. Each story branch is pushed to its own draft PR, whose CI is shown but holds nothing. After acceptance the runner lands the story: one `--no-ff` merge into the sprint branch, the full checks on it, and green CI on a landing branch before the sprint branch moves; only a landed story is done, stories land one at a time in the PO's order and then smallest first, a landing whose sprint head moved merges afresh instead of pushing a stale merge, and a merge conflict goes back to DevOps or the developer to rebase. Every design lists its files, and a design that overlaps another open story's files waits at design until that story lands or leaves, or the PO releases it with a reason. A landing's CI wait doesn't stall tells, answers or the PO, and a sprint boundary's checks and CI wait don't stall the PO. No push ever replaces a branch's history, and the runner never deletes a story branch. A story that leaves the sprint keeps its branch, and reverting a landed story reverts its merge through a landing. Each role's session on a story is kept and resumed until the story moves back, finishes or the role's model changes. A run waiting on you stays running and says why; a usage limit ends it with status `limit`. Each sprint starts by creating the sprint branch on the remote and, when main moved, replaying the sprint onto it (story merges re-made as merges, the recorded hashes remapped story by story; a conflict is aborted, holds nothing and is reported to you), replaying any unlanded carried-over story onto the new head, then running the full checks. A failing start check holds nothing: its failing tests are recorded as the sprint's known failures, and the PO asks the liaison for a story for them, which the liaison places at the top of the sprint or later. It ends by pushing the sprint branch as built to its draft PR and waiting for its CI. Only once that is green is the sprint replayed onto the latest main on a new `-r<k>` branch with a ready PR (a conflict goes to DevOps in a scratch replay, checked story by story, and the runner moves the sprint branch only after the full checks pass there), the old draft PR is closed with a link, and CI runs once more. A red result on the replayed push is reported but doesn't hold the team, and a fix pushed by hand to a held sprint branch is followed. main moves only by fast-forward, with the command in the report. Mid-sprint, a change the team needs now (a commit or an `A..B` range, from main or from an open PR, already fetched) comes in as a pick: `agile-team pick <commit-or-range> --reason` asks the PO, who accepts or denies it, and only you can skip the PO, with `--force` at a terminal, typing the first commit's sha. The PO can pick for itself (`pick_commits`) and revert a pick that isn't forced (`revert_pick`). Between steps the runner cherry-picks each commit with no hash rewritten, aborts the whole pick on a conflict, and bounces any step that undoes one by hand. Picks and their reverts are pushed with the sprint's history. A sprint is done only when every required check has a green run on the commit the runner pushed, read from GitHub by the runner itself; that is the only time a PR is called ready to merge, and no note or answer can make it so. A failure where our code ran can't be waved through (the runner refuses to continue) and needs a bug story. A job that never ran a step is re-run once by the runner. A failure that main's head has too ends the sprint as "ended, CI blocked by main": not done, with the PR unmerged, while the team carries on. The Board shows the sprint PR's CI state. Only the runner runs the full suite and coverage: roles get the results in their briefs, a full test or coverage run from a role's shell is denied, and developers ask the runner for named tests. When a role tries to finish, a Stop hook runs its mechanical checks (handoff, lint fixed then checked, the developer's suite and coverage, the architect's requirements, the integration-tester's presentation) and hands its own failures back to the same agent, at most 3 times, while a dispute or a block always ends the step; the implement gate reuses that run on the same tree. The runner's own work (gates, checks, boundary stages) is a table of named stages, each run logged as a timed `runner-stage` event; `agile-team tools` lists them with the repo's own `[[tool]]` rows. Permission to push is asked once, before the first push of any kind. A story step cut off by a limit, a crash or a kill keeps its edits in the story's worktree and its session; a storyless one keeps them in a reverted commit that the next step is offered, and `status` reports `interrupted` rather than `running` when the runner is dead. The budget is a ceiling: when spend reaches it, the run halts (`blocked`, exit 77) until you raise it and resume, and `status`, the dashboard and the team all see the same spend, with the PO's early overcount corrected. If anyone else moves the checkout under the runner (another branch, a detached HEAD, a reset, a foreign commit, a rebase in progress), it halts at once (`checkout-changed`, exit 78) and asks you; `accept-checkout` keeps the new HEAD. It runs on your Claude login or the repo's API key, and roles can use local models. Each session's context is kept small: the PO's session is renewed at every sprint start and finished story, and no role loads your claude.ai connectors. Every role reads the repo's own `.claude/CLAUDE.md` as text, before the team charter: imports inside the repo are inlined once, any others are left out with a note, no settings or hooks come with it, and your home `~/.claude/CLAUDE.md` is never read. `agile-team dashboard` serves a live view of the run, including turns and context per step, and a live spend pill that turns red (with a desktop notification on localhost) when turns stop, the heartbeat goes stale or the run halts. Its Backlog tab lists every story with its files and lets you reorder the backlog from localhost with the tokened link the command prints; the runner applies the move between steps, and it binds the PO unless the PO gives a reason. An open story row also holds its thread: from the same link you can write to the PO (it answers at its next turn with `reply_story`) or to the liaison (`watch` wakes it, and it answers with `agile-team reply`), and the replies show under the story. The PO adds a story to the running sprint with `add_to_sprint` and a reason, with no new sprint, boundary or Manager turn; restarting a sprint whose stories are unfinished needs a reason. A sprint ends only when every story in it is done, cancelled or reverted. When nothing in the Sprint Backlog can move, the runner hands the PO each story's stall reason, never Product Backlog stories to refill it with, and after 3 such hand-overs with no PO action on those stories it tells you and waits. The PO can `revert_story` a story (an unlanded one just drops its branch); the runner records it in the story file, the Board, the sprint's PR and the team's briefs, and a second revert asks you. The PO can park a story with `hold_story`, free it with `release_story`, and ask you to cancel one with `request_cancel`; only your "cancel" answer cancels it, and cancelled stories show in their own read-only group. The tab can also ask the liaison to review the backlog: it records its opinions with `agile-team opinion` and `agile-team reviewed`, each suggestion gets a badge (with an "only suggestions" filter), and you dismiss it or apply it (a move becomes a reorder, anything else goes to the PO on the story's thread). `agile-team tell` queues a message for the PO from a file (a running team gets it after the current step, a stopped one on resume). `agile-team share <file> --story <id>` hands the team a mock or spec the same way: the runner commits it into the design docs and records its SHA-256 in the story file, and acceptance fails if anyone changed it. The liaison writes every story: `agile-team story new <draft> --approved-by human|none` checks the draft and queues it, and between steps the runner gives it an id, commits it as `docs(sN): created story to <title>` (authored by the human who approved it, or by the liaison, with a `Human-involvement:` line), records it with the story's commits, places it and tells the PO. `agile-team story amend` replaces a story's acceptance criteria in one commit and sends it back to design. The PO schedules stories but never writes them (no role can), and asks the liaison for a bug story with `request_story`. And `agile-team watch` waits without spending tokens and prints one JSON line when a new message or a status change needs you. So an unattended job's resume command is plain `agile-team start --resume`, and the runner saves a cut-off step's edits itself. Installed skills run with `uv run --frozen` and CI with `--locked`, so the tested lock is what runs. With cadence `until-blocker`, a sprint end never stops the team: the PO must start the next sprint while ready Product Backlog stories remain, and a PR waiting for merge never holds it; the PO may report done or blocked once nothing in the Sprint Backlog can move. Role files starting with `_` are shared bases (`_shared`, `_leadership` for the PO and the Manager), and each role's addenda apply along its whole `extends` chain. To let the team work on agile-team itself, run it on a pinned copy of the runner ([`reference/self-hosting.md`](agile-team/reference/self-hosting.md)). At each sprint end whose checks pass, it re-pins itself to the checked commit and execs into it without exiting, and rolls back to the old pin if the new one fails. The header shows the pinned commit. Details: [`reference/protocol.md`](agile-team/reference/protocol.md). |
| [`unattended`](unattended/SKILL.md) | Runs a long or expensive prompt or command as a background job that waits out Claude usage limits and resumes itself, within a deadline, a resume count and a cost cap. It runs on your login or an API key, and it can wrap `agile-team start`. It waits out network failures without spending tokens and keeps the machine from idle-sleeping (`--allow-sleep` opts out). The deadline can end a run in progress: a `--stop-command` at the deadline and an optional `--hardstop` after it. `extend` changes the limits of a live job. Progress probes (output, CPU, files, JSON counters, a heartbeat, a command) raise idle and hung notices and an optional `--idle-stop`; a job whose heartbeat says it is waiting on purpose (agile-team waiting on you) gets one `waiting` notice and is never idle-stopped, and an agile-team `limit` status gives the reset time; notices go to `events.jsonl`, where `wait --until-notice` wakes on them, and to the OS notification centre. Details: [`reference/protocol.md`](unattended/reference/protocol.md). |
| [`routed-group-chat`](routed-group-chat/SKILL.md) | Holds one shared-thread group chat between you and several Claude roles (for example the agile-team leadership: liaison, manager, product owner, customer proxy). You address roles by `@name` (or `@all`; an unaddressed message goes to whoever you addressed last), and code routes it, so only those roles answer, each with the whole thread in view. A role can pass the floor with `HANDOFF: @name`, capped per message. `DECISION:`, `QUESTION:` and `RESOLVED:` lines pin a decision log that every role always sees and that is never summarized; older turns fold into a rolling summary once the thread passes a token budget. Roles run with no tools, connectors or settings, and see turns in delimited blocks so one reply cannot pose as another speaker. State is saved after every reply under a per-chat lock, so a failed model call keeps the replies already paid for (exit 1). The roster is TOML, validated on load, and unknown keys or wrong types are refused. Details: [`reference/protocol.md`](routed-group-chat/reference/protocol.md). |
| [`six-hats`](six-hats/SKILL.md) | Works through a decision or problem with de Bono's Six Thinking Hats, one hat at a time: Blue frames it and picks a sequence for the job (choose between options, judge one idea, solve a problem, generate ideas, quick check), then White, Red, Black, Yellow and Green, and Blue closes with a recommendation, the risks carried forward and the open questions. Runs solo or with the user adding points at each hat. Details: [`reference/hats.md`](six-hats/reference/hats.md), [`reference/sequences.md`](six-hats/reference/sequences.md). |
| [`house-rules`](house-rules/SKILL.md) | Checks Python against the human's code rules as code: no code in the global scope, function length in statements (warn > 8, fail > 12; case chains exempt), at most 2 parameters (fail > 3; constructors and convention-named factories exempt), no boolean parameters, verb-named functions and noun-named properties (a read-only method with no arguments should be a property), and a warning for verb synonyms. A committed baseline lets existing violations shrink but never grow. Every limit and list is repo-configurable; suppressions need a reason, refuse "tests or a design fixed the name" as one, and accept ruff `noqa` codes. Runs from the CLI, in CI, as a pre-commit hook, and as a Claude Code PostToolUse hook that shows Claude the findings in the file it just wrote. Details: [`reference/rules.md`](house-rules/reference/rules.md). |
| [`render-markdown`](render-markdown/SKILL.md) | Shows a Markdown file rendered for reading: `open` in the default browser (a readable column that follows the dark theme), `pdf` (headless Chrome in a scratch HOME), or `print` (to a CUPS printer, two-sided by default). One renderer and stylesheet serve all three, with tables, code and Mermaid diagrams drawn (a diagram that fails to parse shows its source and a note). Every PDF checks itself before it counts as done: raw Markdown outside code, an undrawn diagram, a blank page or a missing title fails it, and page 1 is drawn to a PNG for the agent to look at before printing. `print` sends the printer's raster format (URF or PWG) made locally with `cupsfilter`, and reports success only when CUPS counts printed pages; a job id alone never counts. Details: [`reference/protocol.md`](render-markdown/reference/protocol.md). |
| [`example-skill`](example-skill/SKILL.md) | Template showing the file format. |

`agile-team`, `unattended`, `routed-group-chat`, `house-rules` and `render-markdown` need [uv](https://docs.astral.sh/uv/); their
runners install their own dependencies on first use. `six-hats` is
instructions only. `house-rules` and `render-markdown` make no model calls; `render-markdown`
also needs Chrome for PDFs and CUPS for printing. The others run on your
Claude Code login, or on an API key from a key file (agile-team:
`.team/run/api-key`; both: `~/secrets/anthropic-api-key`, mode 600).

## Install

Claude Code reads personal skills from `~/.claude/skills/<skill-name>/`. The
install script symlinks every skill in this repo into place, so edits here take
effect immediately:

```sh
./install.sh            # symlink all skills into ~/.claude/skills
./install.sh --dry-run  # show what it would do
```

It only ever touches symlinks that point back into this repo, so it leaves
`~/.claude/skills/synced/` (skills synced from your Anthropic account) and any
hand-made skill directories alone.

On Windows, run it from Git Bash, or use directory junctions:

```powershell
New-Item -ItemType Junction -Path "$HOME\.claude\skills\<name>" -Target "<repo>\<name>"
```

### With chezmoi

If you manage dotfiles with chezmoi, declare this repo as an external and let a
`run_after_` script do the linking instead of running `install.sh` by hand. See
the `.chezmoiexternal.toml.tmpl` and `run_after_link-claude-skills.sh.tmpl` in
[devnu11/home](https://github.com/devnu11/home).

## Tests

```sh
sh tests/install_test.sh                         # install.sh
(cd agile-team/runner && uv run pytest --cov)    # agile-team runner
(cd unattended/runner && uv run pytest --cov)    # unattended runner
(cd routed-group-chat/runner && uv run pytest --cov)  # routed-group-chat runner
```

The install tests cover linking, idempotency (a second run changes nothing),
`--dry-run`, relinking, pruning, and leaving `synced/` and foreign links alone.
Each works in a scratch directory, never the real `~/.claude/skills`. CI runs
them on Linux (dash) and macOS (bash 3.2 as `/bin/sh`), plus shellcheck. Each
runner has its own CI workflow (ruff, and pytest with coverage of 95% or more).

## Writing a skill

See Anthropic's [skills documentation](https://docs.claude.com/en/docs/claude-code/skills).
Keep `SKILL.md` short — it is loaded into context when the skill triggers — and
push detail into supporting files the skill references by path.
