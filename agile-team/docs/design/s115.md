# s115: DevOps reviews every design before tests (ops-review step)

ADR: [0059](../../../.team/adr/0059-ops-review-is-a-built-in-checkpoint-step.md).
Developer: `developer-cli` (runner Python; one line of `dashboard/index.html`
and the built-in role file `roles/devops.md`, both under `{source}`).
The unit-tester writes the failing tests first.

## Rules

| # | Rule | AC |
|---|---|---|
| P1 | `ops-review` is a pipeline step owned by `devops` (`gates.STEP_ROLES["ops-review"] = "devops"`, placed after `"design"` in the dict). `config.PIPELINE_STEPS` lists it right after `"design"`, so a config may name it without a load error. | AC1 |
| P2 | The run's steps are `config.pipeline_steps(listed)`: the configured `[gates] steps` with every `ALWAYS_STEPS` row removed, then each row's step put right after its anchor (`("ops-review", "design")`), or first when the anchor is not listed. A config that lists `ops-review` somewhere else, or not at all, gets the same place. `Gates.pipeline` (a property) returns it. `cli` builds `gates.Pipeline` from `g.pipeline`, and the snapshot's `pipeline` is `config.gates.pipeline`. `Gates.steps` stays the configured list. | AC1 |
| P3 | Nothing moves a story at load or at start. A story at `design` goes on to `ops-review` when design passes; a story at any later step stays where it is and never visits `ops-review`. | AC1 |
| P4 | `ops-review` is a **checkpoint**: `gates.CHECKPOINT_STEPS = frozenset({"ops-review"})`. No bounce, fault, acceptance failure or revert sends a story *to* a checkpoint; a story reaches it only by passing the step before (or by the ops gate's own retry, O3). So `Pipeline.step_for_role` skips checkpoint steps, `handover._unroutable` judges against non-checkpoint steps only, and `reverts.back_step` targets the last non-checkpoint step before `tests`. A bounce or fault naming `devops` therefore behaves as today (`unroutable` / `off_pipeline_fault`: the PO briefs devops). | AC1 |
| B1 | A DevOps step on a story at `ops-review` (any step kind but a gate fix) gets a `## Ops review` brief section built by `ops_review.brief_section(ops_review.facts(config, read))`: the story's ACs (id, environment, text) as a table, the `[toolchain]` commands, the `[[environment]]` names and kinds, the `[[tool]]` names and the `ci` globs. When the story file has problems, the AC table is replaced by the problem text. Any other DevOps step (storyless, boundary fix, gate fix) gets no section. | AC2 |
| H1 | The handoff gains an optional `tooling` list, one row per AC: `{"ac", "verdict", "how", "needs", "story"}`. `verdict` is `automatic` (checked today), `added` (DevOps added it in this step) or `missing` (outside DevOps's files). `automatic` and `added` need a non-empty `how` (the command, test or CI job that checks it). `missing` needs a non-empty `needs` (what is missing); `story` names the story that will add it, or is `""`/absent while there is none. Every field present is a string. A row with `added` needs a non-empty `changed_files`. A malformed list is a handoff error (so the Stop hook's handoff check refuses it before the step ends). | AC3, AC4 |
| O1 | `done` at `ops-review` runs the ops gate (`Checks.tooling_reviewed`). In order: the story file has problems → `HOLD` with `story_spec.STORY_FILE_HOLD`; the list has problems (O2) → `BOUNCE` back to `ops-review` (a round, author role); a `missing` row has no story → `HOLD` with `UNFILED` (O4); else `PASS` with `PASSED`. A pass moves the story to the next step (`tests`). | AC3 |
| O2 | List problems, in order, each from `ops_review.PROBLEMS`: an AC of the story file with no row; a row whose AC is not in the story file; an AC with more than one row; a row's `story` that is the story itself; a row's `story` with no file `.team/stories/<id>.md`. All found problems are joined with `; `. | AC3, AC4 |
| O3 | `changes_requested` at `ops-review` bounces to the design step (`"design"` when enabled, else the first step) whatever `next_role` says, with the handoff's summary as the reason (`ops_review.REDESIGN` when the summary is empty). It counts a round, as any bounce. The `tooling` rows, if any, are not recorded. | AC3 |
| O4 | `UNFILED` names each unfiled row (`AC2: a browser harness`) and tells the PO to open a story for each (`open_story`), then `continue_story` with a note naming each AC's story. The hold is the existing `gate_hold` hand-over. When released, DevOps runs `ops-review` again with the note in its brief (`From the PO:`) and hands off the story ids. | AC3 |
| R1 | On an `ops-review` `PASS`, the runner writes the rows into the story file as a `## Tooling` section (O5), commits only that file as `chore(<id>): record the tooling review in the story file`, records the checkout, and adds `"tooling": {"file": <story file>, "commit": <sha or null>}` to the gate report. When the file text would not change, it does not commit (`commit` is `null`). | AC4 |
| O5 | The section: heading `## Tooling`, a blank line, the line `How each AC is checked automatically (DevOps, ops-review step):`, a blank line, then one line per row in the handoff's order from `ops_review.LINES`: `- AC1: automatic today: <how>`, `- AC2: added now: <how>`, `- AC3: missing: <needs> (story <story>)`. An existing `## Tooling` section (its heading line up to the next line starting `## `, or the end) is replaced in place; otherwise the section is appended at the end after one blank line. The text ends with one newline. | AC4 |
| R2 | `handoff_report` carries `tooling` (each row as a dict) when the list is not empty, so `step-end` events hold the verdicts. | AC4 |
| D1 | The dashboard's Flow group "Test" lists `ops-review` before `tests` (`FLOW_GROUPS` in `index.html`). The snapshot fixture is unchanged (its shape does not change). | AC1 |
| D2 | Docs: `roles/devops.md` gains an `## Ops review` section (developer); `SKILL.md`, `reference/protocol.md`, the README row and `docs/customer/routing.md` describe the step (architect, done at design). | AC6 |

Why P4: without it, `devops` would own a pipeline step, so every
`changes_requested` naming devops from e2e or acceptance, and every Manager
fault on devops, would send the story back to `ops-review` and through
tests, implement, quality and review again. A tooling gap found late is a
fix for DevOps, not a reason to replay the pipeline.

Why O4 is a hold and not a new PO tool: DevOps cannot open stories, and the
PO already has `open_story` and `continue_story`. One cheap extra DevOps
step records the ids; no new tool or state field is needed.

## Changes per module

### `agile_team/ops_review.py` (new, pure)

Imports no `agile_team` module at run time (`Config` and `story_spec.Read`
under `TYPE_CHECKING` only; it reads their attributes). This keeps
`roles` → `ops_review` free of cycles.

```python
STEP = "ops-review"

class ToolingVerdict(StrEnum):
    """How one AC is checked automatically."""
    AUTOMATIC = "automatic"
    ADDED = "added"
    MISSING = "missing"

@dataclass(frozen=True)
class ToolingRow:
    """One AC's verdict from the ops-review handoff."""
    ac: str
    verdict: ToolingVerdict
    how: str = ""
    needs: str = ""
    story: str = ""

REQUIRED: dict[ToolingVerdict, str] = {AUTOMATIC: "how", ADDED: "how", MISSING: "needs"}
FIELDS = ("ac", "verdict", "how", "needs", "story")
LINES: dict[ToolingVerdict, str] = {
    AUTOMATIC: "- {ac}: automatic today: {how}",
    ADDED: "- {ac}: added now: {how}",
    MISSING: "- {ac}: missing: {needs} (story {story})",
}
HEADING = "## Tooling"
INTRO = "How each AC is checked automatically (DevOps, ops-review step):"
STORY_FILE = ".team/stories/{id}.md"        # a test pins it to config.STORIES_DIR
RECORD_SUBJECT = "chore({story}): record the tooling review in the story file"
PROBLEMS = {
    "no_row": "no row for {ac}",
    "unknown": "{ac} is not an AC of the story file",
    "repeated": "{ac} has {count} rows",
    "self": "{ac} names this story as its tooling story",
    "no_story": "{ac}'s story {story} has no file {file}",
}
BAD_LIST = "the tooling list is incomplete: {problems}. Hand off again with one row per AC"
UNFILED = (
    "devops found tooling outside its files with no story yet: {needs}. Open a story "
    "for each (open_story), then continue_story with a note naming each AC's story; "
    "devops runs ops-review again and records them"
)
PASSED = "tooling recorded: {automatic} automatic today, {added} added now, {missing} missing"
REDESIGN = "devops: the design assumes tooling that cannot exist"

def row_form(value: Any) -> bool:
    """Whether one raw row is well formed (H1)."""
def rows_form(value: Any) -> bool:
    """Whether ``value`` is a list of well-formed rows (absent = [])."""
def adds(value: Any) -> bool:
    """Whether any raw row has verdict ``added``."""
def rows_of(value: Any) -> list[ToolingRow]:
    """The parsed rows of an already-checked raw list."""
def problems(ac_ids: tuple[str, ...], rows: list[ToolingRow]) -> list[str]:
    """O2's coverage problems: no row, unknown AC, repeated AC (in that order)."""
def unfiled(rows: list[ToolingRow]) -> list[ToolingRow]:
    """The ``missing`` rows with no story."""
def passed_text(rows: list[ToolingRow]) -> str:
    """PASSED with the counts."""
def unfiled_text(rows: list[ToolingRow]) -> str:
    """UNFILED with ``AC2: <needs>`` items joined by ``; ``."""
def section(rows: list[ToolingRow]) -> str:
    """The ``## Tooling`` section (O5), ending with a newline."""
def with_section(text: str, rows: list[ToolingRow]) -> str:
    """``text`` with its Tooling section replaced, or the section appended (O5)."""
def story_file(story: str) -> str:
    """The repo-relative story file of ``story``."""

@dataclass(frozen=True)
class Facts:
    """What the ops-review brief section shows (B1); primitives only."""
    criteria: tuple[tuple[str, str, str], ...]   # (id, environment, text)
    commands: tuple[tuple[str, str], ...]        # (name, command), config order
    environments: tuple[tuple[str, str], ...]    # (name, kind)
    tools: tuple[str, ...]                       # [[tool]] names
    ci: tuple[str, ...]                          # toolchain.globs["ci"]
    problem: str = ""                            # the story file's refusal, if any

def facts(config: Config, read: Read) -> Facts:
    """Facts from the config and the story file's read."""
def brief_section(facts: Facts) -> str:
    """The ``## Ops review`` prompt section."""
```

`problems(ac_ids, rows)` does `no_row`, `unknown` and `repeated`;
`Checks.tooling_reviewed` adds `self` and `no_story` after them (they need
the story id and file reads; `no_story` formats `file` with
`story_file(row.story)`). Keep each function under 8 lines; one `PROBLEMS`
key per check.

`brief_section` text (empty lists print `- (none)`; `|` in a criterion is
escaped as `\|`, newlines become spaces):

```
## Ops review

For each AC below: can it be checked automatically with what this repo has
today? If not, what is missing? Hand off one `tooling` row per AC (your role
file's "Ops review" section says how).

### Acceptance criteria

| AC | Environment | Criterion |
|---|---|---|
| AC1 | cli | ... |

### Toolchain commands

- test: `...`

### Acceptance environments

- cli (kind cli)

### Repo tools ([[tool]])

- (none)

### CI files

- .github/workflows/**
```

With `facts.problem` set, the AC table is replaced by
`The story file has problems, and the gate will hold the story: <problem>`.

  author=Author.ROLE)`. Unfiled: `Outcome(Verdict.HOLD, unfiled_text(…),
