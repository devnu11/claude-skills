# s176: a story rebase step moves only its own rebase branch

The story rebase step's git runs with `Allows.LOCAL` (s159 S2). That rule
checks the subcommand and a few flags, not which branch the command would
move. The worktree shares the repo's refs, so `git checkout -B <other>`,
`git rebase <onto> <other>`, or `git reset` while HEAD is on another branch
really moves that other branch, and the S3 checks after the step look only at
the rebase branch.

This story adds two guards. The first is a branch check in the guard, which
refuses the command before it runs. The second is a ref snapshot around the
step, compared when the step ends; any branch the step moved is put back and
the step bounces.

Traces: AC1 → REQ-209, AC2 → REQ-210, AC3 → REQ-211. Decision: ADR-0091.

Developer: `developer-cli`.

## Design review, round 2 (2026-10-25)

R1 to R6 are built as the rules below say, and this file now describes the
code as built. The code review's findings change no rule:

- `git switch --force <other>` is refused, because `--force` is a prefix
  of `--force-create` (B3's prefix rule). The rebase never needs it, so
  refusing it is the safe side.
- `git reset -- <file>` with HEAD on another branch is refused. AC1 names
  `git reset` with HEAD off the rebase branch, and B3 maps `reset` to HEAD's
  branch.
- Any `git -c …` is refused on a branch site, read-only commands included
  (B3a). Plain read-only commands still run.
- A resumed step compares against the snapshot taken before its cut-off
  (B8). If the human moves a free branch during a halt, the runner puts it
  back when the step ends. The design accepts this.
- Most of the checklist's tests are in `tests/test_s176_*.py`, not in the
  module test files the checklist names. `## Files` lists both.

## Design review, round 1 (2026-10-25)

The code follows B1 to B10 with the deviations listed under "Accepted",
which this file now describes as built. The items under "To fix" are AC1
holes or departures from a rule, and the story goes back to `developer-cli`
for them.

To fix:

- **R1. Rebase operands (B3).** `_split_rebase_operands` matches valued
  options by exact word only and treats `-S` as valued. git takes `-S`'s key
  only attached, and it accepts long abbreviations, so with HEAD on the
  rebase branch these move `other` and pass: `git rebase -S main other`,
  `git rebase --ont main <own> other`, `git rebase --roo other`, `git rebase
  -C 4 <own> other`, `git rebase --whitespace fix <own> other`. B3's rebase
  row below is the fix.
- **R2. `--update-refs` and `-c` (B3a).** `git rebase --update-refs main`
  and `git -c rebase.updateRefs=true rebase main` move every free branch
  that points into the rebased commits, such as an earlier `-r<k>` branch.
- **R3. A repo config that turns on `rebase.updateRefs` (B3a).** A plain
  `git rebase main` then moves other branches too. The step's env pins it
  off, and the step may not name `GIT_CONFIG*` variables.
- **R4. A checkout that fails (B4).** `git checkout -B <own> <bad>; git
  reset --hard X` with HEAD on another branch is allowed today. The checkout
  fails, `;` runs the reset anyway, and the reset moves the other branch.
- **R5. Resolve the worktree path (B7).** `read_branch_heads` compares
  `%(worktreepath)` with `str(git.repo)` unresolved. B7 says to resolve it.
  A symlinked repo path (macOS `/var` → `/private/var`) would drop the
  step's own worktree's branch from the record.
- **R6. Clear the record every time (B9.3).** `_put_back_moved` clears
  `rebase.heads` only when a branch moved. A step that is held (or bounced
  by S3) keeps its old record, so the next round compares against a stale
  start. Clear the record whenever the compare runs.

Accepted (the code is the better or an equal answer; the rules below match
it): the sentinel values `~detached` and `~unknown`; one refusal template per
sentinel; `find_branch_denial(site, call, head)` per link, called right after
that link passes its rule, with `Position`; `Create`/`CREATES` and
`REBASE_OPERATIONS`; `MovedBranch.branch`; the texts of `BRANCH_MOVED`,
`BRANCH_STUCK`, `PUT_BACK_MESSAGE` and the brief line; `HEADS_FORMAT` holding
`--format=`; reasons joined with `"\n"`; `_put_back_moved(plan) -> str |
None`; `_read_head_branch` running git with the worktree as its cwd.

## Rules

- **B1. The one branch.** A story rebase step may move only
  `rebase.branch` (`<story_prefix><id>-r<k>`). The runner gives it to the
  guard as `Scope.git_branch`. A scope with `git_branch == ""` (every other
  step) gets no branch check.
- **B2. HEAD at the hook.** For each Bash call of such a step, the guard
  reads which branch HEAD is on in the step's worktree:
  `git symbolic-ref -q --short HEAD`, run with the worktree as its cwd. Exit 0
  gives the branch name. Exit 1 means detached (`DETACHED = "~detached"`).
  Any other exit gives `HEAD_UNKNOWN = "~unknown"`. `~` can't be in a ref
  name, so neither sentinel ever matches a branch.
- **B3. The branch a git call moves** (`find_moved_branch`). One table,
  `BRANCH_MOVES`, keyed by subcommand. A subcommand that isn't in it moves
  no branch (`DETACHED`). B3a is checked first, for every subcommand.

  | sub | branch it moves |
  |---|---|
  | `checkout`, `switch` | the branch named by a creating option (`CREATES`: checkout `-b`, `-B`, `--orphan`; switch `-c`, `-C`, `--create`, `--force-create`, `--orphan`), else none |
  | `reset`, `commit`, `cherry-pick` | HEAD's branch (B2/B4) |
  | `rebase` | see the rebase row below |
  | `stash` | with the action `branch`, the operand after it (`git stash branch <name>`); else none |

  How options are read:
  - A long option matches when it has at least `LONG_PREFIX_MIN` characters
    and is a prefix of a listed name, as `_is_long` does (`--force-c` is
    `--force-create`, `--ont` is `--onto`).
  - A long option's value is after `=`, or else the next word.
  - In a short cluster, the first listed letter takes the rest of the
    cluster as its value (`-Bname`), or the next word when nothing follows
    it (`-fB name`).

  **The rebase row (R1).**
  1. With an action (a word in `REBASE_OPERATIONS`: `--continue`, `--abort`,
     `--skip`, `--quit`, `--edit-todo`, `--show-current-patch`, exact
     match), it moves none.
  2. Otherwise the operands are the words after `rebase` that don't start
     with `-`, minus the word after an option that git always gives a
     separate value. That is a word equal to one of `REBASE_VALUED_SHORT =
     frozenset({"-s", "-X", "-C", "-x"})`, or a long option without `=` that
     matches (`_is_long`) one of `REBASE_VALUED_LONG = ("--onto",
     "--strategy", "--strategy-option", "--whitespace", "--empty",
     "--exec")`. `-S` and `--gpg-sign` take their key only attached, so
     they never take the next word. Skipping a word git doesn't skip only
     adds a candidate, which is safe. Skipping one git keeps can hide the
     branch, so only these options skip.
  3. The candidates are every operand from index 1 on (from index 0 when a
     word matches `--root` by `_is_long`), plus HEAD's branch. Taking every
     operand from that index on, not just one, means an option git gives a
     value but this list doesn't know (a later git's `--trailer`) can't hide
     the branch.
  4. With no candidate other than `DETACHED`, it moves none. With exactly one
     distinct candidate that is not `DETACHED`, it moves that one. With more
     than one, it moves `REBASE_UNCLEAR = "~unclear"`, which is always
     refused. So `git rebase main <own>` runs with HEAD on `<own>` or
     detached, and is refused with HEAD on another branch.
- **B3a. Calls that can move other refs (R2).** A call with a `-c` option
  (`call.configs`), or a `rebase` with a word matching `--update-refs` by
  `_is_long`, moves `OTHER_REFS = "~other-refs"`, which is always refused.
  `--no-update-refs` doesn't match. **(R3)** `REBASE_FIX_ENV` gains
  `GIT_CONFIG_COUNT=1`, `GIT_CONFIG_KEY_0=rebase.updateRefs` and
  `GIT_CONFIG_VALUE_0=false`, so a repo or global config can't turn it on
  for the step's own `git rebase`. A site with `branch` set also locks
  `BRANCH_ENV_LOCKED = ("GIT_CONFIG",)` on top of `GIT_ENV_LOCKED`. The
  substring match covers every `GIT_CONFIG_*` name, and the refusal is
  the existing `GIT_ENV_DENIED`.
- **B4. HEAD across one command** (`get_next_head`, `_list_positions`). The
  guard checks a command's git calls in order, starting from B2's HEAD. Only
  `checkout` and `switch` change the HEAD that later calls in the same
  command see:
  - a creating option: the created branch;
  - `--detach` (or `-d`): `DETACHED`;
  - with a `--` word, or with no operand: unchanged;
  - any other operand, or `-`: `HEAD_UNKNOWN`, because it may be a branch,
    a commit or a path.

  **(R4)** A checkout can fail and leave HEAD where it was, and `;` or `||`
  runs the next call anyway. So `_list_positions` follows `get_next_head`
  only while the tracked HEAD is `DETACHED` or `site.branch`
  (`_is_own_or_detached`). From any other branch, or `HEAD_UNKNOWN`, the
  tracked HEAD stays as it is for the rest of the command. Getting back
  onto the rebase branch is then one Bash call (`git checkout -B <own>`,
  which moves only `<own>`), and the next call starts from B2's fresh read.

  No other subcommand changes the tracked HEAD. Any other call that ends on
  another branch has already been checked and allowed only for `git_branch`,
  and a stopped rebase leaves HEAD detached. Both are states where B5
  allows moves.
- **B5. Refused.** `find_branch_denial(site, call, head)` refuses a call
  when the branch it moves is not `DETACHED` and not `site.branch`. It runs
  for each link right after that link passes its `GIT_RULES` row, and only
  when the row allows `LOCAL` and `site.branch` is set (`_guards_branch`).
  So `branch`, `update-ref`, `symbolic-ref`, `push` and the rest are still
  refused as today, by `git-local-only`. The refusal uses rule
  `git-own-branch` (`Rule.GIT_OWN_BRANCH`) and names the one branch the step
  may move. A table picks its text: `BRANCH_DENIALS = {HEAD_UNKNOWN:
  GIT_HEAD_UNKNOWN_DENIED, REBASE_UNCLEAR: GIT_REBASE_UNCLEAR_DENIED,
  OTHER_REFS: GIT_OTHER_REFS_DENIED}`. A named branch gets
  `GIT_OWN_BRANCH_DENIED` (as built). The two new texts:

  ```
  GIT_REBASE_UNCLEAR_DENIED = Refusal(
      Rule.GIT_OWN_BRANCH,
      "{role} may not run `git rebase` in {workspace}: it could move more than one branch "
      "(HEAD's and the one it names), and this step may move only {branch}",
      "`git rebase <onto>` while HEAD is on {branch}, or `git rebase <onto> {branch}` with "
      "HEAD on {branch} or detached",
  ).text()
  GIT_OTHER_REFS_DENIED = Refusal(
      Rule.GIT_OWN_BRANCH,
      "{role} may not run `git {sub}` in {workspace}: `--update-refs` or a `-c` setting can "
      "move branches other than {branch}, the only one this step may move",
      "the same git command without `--update-refs` or `-c`",
  ).text()
  ```
- **B6. Still allowed (AC2).** `git rebase --continue`, `--abort` and
  `--skip`; `git add`; `git checkout -- <file>`; and the read-only commands
  move no branch. `git reset …` and `git commit` move HEAD's branch, which
  is allowed while HEAD is on `git_branch` or detached. `git checkout -B
  <git_branch> [<sha>]` moves `git_branch`. A plain `git checkout <other>`
  moves no branch and stays allowed. The S3 check "HEAD is not on {branch}"
  still bounces a step that ends there.
- **B7. The snapshot (AC3).** `story_rebase.read_branch_heads` reads the
  heads in one call: `git for-each-ref
  --format=%(refname:short)%09%(objectname)%09%(worktreepath) refs/heads`.
  It keeps each branch that is not `rebase.branch` and is not checked out
  in another worktree. That means `worktreepath` is empty, or
  `system.resolve(Path(worktreepath)) == system.resolve(git.repo)`
  **(R5)**. Git already refuses to move a branch that is checked out in
  another worktree from this one, and `--ignore-other-worktrees` stays
  refused. Every branch the runner moves while a step runs is checked out
  somewhere: other stories' branches in their worktrees, and the sprint
  branch in the main checkout. So none of the runner's own moves land in
  the snapshot (ADR-0091).
- **B8. When it is taken.** `_set_story_rebase_scope` takes the snapshot
  after `story_rebase.prepare`, but only when `rebase.heads` is empty. It
  stores it in `StoryRebase.heads`, which the step-start `self.save()`
  writes to `state.json` before the role launches. A step that is cut off
  never reaches its effects, so it keeps its snapshot, and the resumed step
  (s165) compares against the state before the cut-off.
- **B9. The compare.** `Runtime._apply_rebase` checks this first, before
  `_find_rebase_stop`, so it applies whatever the handoff says (`done`,
  `blocked`, `failed`, or none):
  1. `story_rebase.list_moved_branches` re-reads the heads with B7's filter.
     For each branch in `rebase.heads` that is still there with a different
     sha, it yields a `MovedBranch(branch, old, new)`. A branch that is gone,
     or that is now checked out in another worktree, is skipped. The guard
     refuses deletion (`branch`, `update-ref`), and the runner may drop a
     branch itself (`revert_story`).
  2. Each moved branch is put back with `git update-ref -m PUT_BACK_MESSAGE
     refs/heads/<name> <old> <new>`. The `<new>` argument makes the update
     fail if the branch moved again.
  3. **(R6)** `rebase.heads` is cleared every time the compare runs, whether
     or not a branch moved, so the next round (after a bounce, a hold and
     `release_story`, or an S3 bounce) takes a fresh snapshot.
  4. If any branch moved, the step bounces to `story.step`
     (`Verdict.BOUNCE`, `author=Author.ROLE`; a round, as the S3 refusals
     do). The reason is one line per branch, joined with `"\n"`:
     `BRANCH_MOVED = "branch {branch} moved from {old} to {new}; the runner
     put it back"`, or, when `update-ref` failed, `BRANCH_STUCK = "branch
     {branch} moved from {old} to {new} and moved again; the runner could
     not put it back"`. `story.rebase` stays queued, so the router runs the
     step again (S1). Its `prepare` resumes the worktree.
- **B10. The brief.** `STORY_REBASE_LINES` has a third line (as built):
  `"Move no other branch: {branch} is the one local branch this step may
  move, and the runner refuses git commands that move another."`
