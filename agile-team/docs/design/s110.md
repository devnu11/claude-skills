# s110 design: the product-owner role file states the CI rule

Story: `.team/stories/s110.md`. Builds on s81 (CI stage, `ci_green` /
`ci_failed` / `ci_pending`, `record_ci_bug`) and s106 (a cancel is re-run
once; a cancel that stays gets job-record lines: run time, runner, steps
that did not succeed). No code changes, no new ADR, no new dependency.

## Rules

- **CR1 (AC1). One rule, one text.** The CI rule below is written
  word for word in three places: the PO role file, `SKILL.md` and
  `reference/protocol.md`. Line wrapping is free; the words are not.
- **CR2 (AC1). Where it sits in the role file.** In
  `agile-team/runner/agile_team/roles/product-owner.md`, step 4's list of
  hand-overs, as a new bullet right after "Never call a PR ready from a
  `Review:` line …" (today line 117–118). The `ci_failed` bullet gains one
  sentence (CR4). Nothing else in the file changes.
- **CR3 (AC2). Where it sits in the docs.** `SKILL.md` step 8's boundary
  paragraph, after "never relay those as ready." `protocol.md`: the full
  rule in the **Ready.** paragraph of the sprint-boundary section; the
  `ci_green`, `ci_failed` and `ci_pending` hand-over rows and the `ci`
  stage's red bullet point to it ("see the CI rule under **Ready.**").
  The architect writes both docs in this story's design step (done).
- **CR4. What the PO does on `ci_failed`.** Read the failing lines first.
  Only when they show the failed job never ran our code (`no runner was
  assigned`, or a cancel whose steps never started) may the PO ask the
  human to re-run it and `continue_boundary`. Otherwise (a `fail` with
  test lines, a cancel after steps ran, or anything unclear) it opens the
  bug story and `record_ci_bug`s it, as today. It never calls
  `continue_boundary` hoping a re-run turns green.
- **CR5. No CI run is not done.** A `none` result, a `local` boundary
  (push "no", no `gh`, no remote) or a `ci_pending` is never reported to
  the human as the sprint being done with respect to CI.

### The CI rule (exact text)

```
**CI rule.** A sprint is done only when a green CI run is actually
present on GitHub. A re-run counts only when it is green, and only when
the failed job never ran our code (it was cancelled with no steps run, or
no runner was available). If a failure could be flakiness in our code, it
is a bug story, and the sprint is not done.
```

The `**CI rule.**` label is part of the text. In the role file it opens a
list bullet (`   - **CI rule.** …`, continuation lines indented 5 spaces,
as the bullets around it).

## Known limits

- The rule is prompt-only. The runner does not refuse a `continue_boundary`
  at a `ci_failed` hold whose lines show our code ran, and a human re-run
  that turns green still finishes the boundary green. Enforcing that in
  code (charter: "process in code") would be a follow-up story; raised as
  an open question.
- "Never ran our code" is read from s106's evidence lines. A `fail` check
  has only `--log-failed` lines, so it always counts as having run code.
