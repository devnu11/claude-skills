# s127: Runner tools say what they run in a few words

Story: `.team/stories/s127.md`. Builds on s118 (`design/s118.md`, FC1–FC30,
R1–R12). Here the s118 rules this story replaces are named. Every other s118
rule stands.

ADRs: **ADR-0048 amended** (a stage row has a `label`, and a `[[tool]]` row
may have one) and **ADR-0052 amended** (the snapshot's `stage_labels`, a
one-line tool box with the description in its tooltip, Leadership sized
to its content, 10-second rate windows).

Developer: **developer-gui** (page, fixture). The runner part (`stages`,
`config`, `snapshot`, `rates`; `cli` needs no change) is small and pure. The same
developer does it, because it only feeds the page.

## What changes, in short

- `Stage.as_dict` returns `{"name", "label", "description", "when",

### LB3: `agile_team/config.py`, the repo tool's label

- `Tool` gains `label: str = ""` as its **last** field (after `command`).
  `_tool` reads the keys `("name", "description", "command", "label")`.
  `asdict(tool)` in `cli.tools_report` therefore prints `label` too, with
  no code change there.
- New method `Tool.chart_label(self) -> str`: """The label the Flow chart
  shows: the row's `label`, else its name (s127 LB3).""" Returns
  `self.label.strip() or self.name`.
- `TOOL_RULES` gains one row, last (after the command rule):
  `(lambda t: len(t.label.strip()) <= stages.LABEL_MAX, "label must be at most 24 characters")`.
  A blank `label` is allowed and means "use the name". A long *name* used as
  the label is not refused, because names already have their own rules. The
  page cuts it with an ellipsis (TL1).
- Repeated labels: new `REPEATED_LABEL = "[[tool]] label {label!r} is repeated"`
  and a helper:

  ```python
  def _label_problems(tools: list[Tool]) -> list[str]:
      """A message for each chart label used twice, or used by a built-in stage (s127 LB3)."""
      labels = [t.chart_label() for t in tools]
      taken = sorted({x for x in labels if labels.count(x) > 1 or x in stages.LABELS})
      return [REPEATED_LABEL.format(label=x) for x in taken]
  ```

  `tool_problems` returns `problems + repeated-name messages + _label_problems(tools)`,
  in that order. Two rows with the same name are already refused by name,
  but their labels are compared too. So a repeated name with no labels
  gives both the name message and the label message. That is acceptable:
  every problem is listed (protocol "Repo tools").

### LB4: `agile_team/dashboard/snapshot.py`

New section `"stage_labels": _stage_labels`, right after
`"stage_descriptions"` in `SECTIONS`:

```python
def _stage_labels(files: RunFiles) -> dict[str, str]:
    """Each runner stage's and repo tool's short label, by name (s127 LB4)."""
    built_in = {str(name): stage.label for name, stage in stages.STAGES.items()}
    return {**built_in, **{tool.name: tool.chart_label() for tool in files.config.tools}}
```

Built-ins come first in the dict, as `_stage_descriptions` does it.

## Known limits

- A label longer than its box (a long repo tool name used as its label, in a
  196 px Leadership cell) is cut with `…`. The full name is the first word
  of the tooltip.
- Series written before this story are per minute. A short step from then
  still shows `too short for a sparkline` until its role runs again.

## Open question

The human's examples give built-in labels that name pytest and ruff. That
is right for this repo, but `stages.STAGES` is the same on every repo the
runner drives. If the human wants toolchain-neutral labels (`tests + coverage`,
`lint + format`), only the LB2 table and its pin change.
