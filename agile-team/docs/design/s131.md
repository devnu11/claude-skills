# s131: The Tooling record is committed before the story moves on

Story: `.team/stories/s131.md`. Requirements: REQ-028 (AC1, AC3), REQ-029
(AC2, AC3). ADR: ADR-0059, amended by s131. Developer: `developer-cli`.

## Problem

`dispatch.Runtime.gate` advances the story (`_advance_and_log`) first, and
only then runs the step's `PASS_RECORDS` row (`_record_tooling` for
`ops-review`). A crash or a failed `git.commit` between the two leaves the
story at `tests` without its `## Tooling` record (the known limit in
design/s115.md, "R1 after the advance"). `_apply_pending` already commits
the pending registry before the advance (P13). This story makes pass records
work the same way.

## Rules

| # | Rule | AC |
|---|---|---|
| R1 | When the evaluated outcome is `PASS` and the story's current step has a `PASS_RECORDS` row, `gate` runs that row **before** `_advance_and_log`. The row writes the record and commits it. The order in `gate` is `verify_checkout` → `_evaluate` → `_apply_pending` → pass record → `_advance_and_log`. The record's report fields (`"tooling": {...}`) are merged into the gate result as they are today. | AC1 |
| R2 | When the record's commit raises `GitError`, the story file goes back to its old text, the index is reset (`git reset -q`, run through `attempt`, which never raises), and the error is not re-raised out of `gate`. The pass becomes `Outcome(Verdict.HOLD, RECORD_FAILED.format(step=…, error=…))`, and **that** outcome goes to `_advance_and_log`. So the story stays at `ops-review`, no round is counted, the gate event's `reason` names the git error, and the PO gets the existing `gate_hold` hand-over ("…'s gate is on hold: <reason>; fix it, then continue_story"). The gate result has no `tooling` key. | AC2 |
| R3 | `record_checkout()` runs only after a successful record (commit or no change). After a failure the tree is back to the checkout recorded before the gate, so there is nothing new to record. | AC2 |
| R4 | No change when the text would not change: no write, no commit, `commit: null` (s115 R1 stands). | AC1 |
| R5 | For `ops-review`, the evaluated verdict and the final verdict are the same on a pass. Its `PASS` outcome carries no `output`, so `route` leaves it alone, and `screen` runs only on setbacks. Keying the record on the evaluated `PASS`, as `_apply_pending` does, is therefore exact. | AC1 |

Out of scope: a `GitError` from `_apply_pending`/`set_pending` (not asked for
here; it still propagates as before).

## Changes: `agile-team/runner/agile_team/dispatch.py`

`GitError` is already imported (`from .git_ops import Git, GitError`).

### New module-level names (next to the other message constants)

```python
RECORD_FAILED = "the {step} record was not committed: {error}"
```

```python
@dataclass(frozen=True)
class FileEdit:
    """A runner-written file: its repo-relative path, its text before and after."""

    file: str
    old: str
    new: str


@dataclass(frozen=True)
class Recorded:
    """A pass record's gate-report fields, or the hold that replaces the pass (s131)."""

    fields: dict[str, Any] = field(default_factory=dict)
    failure: Outcome | None = None
```

(`field` and `dataclass` are already imported in dispatch.py. `Outcome` and
`Verdict` come from `gates`, as they do now.)

### `Runtime.gate` (replaces the body)

```python
def gate(self, plan: Plan, handoff: Handoff) -> dict[str, Any]:
    """Evaluate the step's gate, commit its pass record, then advance the story (s131)."""
    self.verify_checkout()
    outcome = self._evaluate(plan, handoff)
    self._apply_pending(plan, outcome)
    record = self._pass_record(plan, handoff) if outcome.verdict is Verdict.PASS else Recorded()
    return self._advance_and_log(plan, record.failure or outcome) | record.fields
```

### New `Runtime._pass_record(self, plan: Plan, handoff: Handoff) -> Recorded`

Doc: "Run the step's PASS_RECORDS row; a GitError becomes a gate hold naming
it (s131 R2)."

- `row = PASS_RECORDS.get(plan.story.step)`; `None` → `Recorded()`.
- `try: return Recorded(row(self, plan, handoff))`
- `except GitError as error:` → `Recorded(failure=Outcome(Verdict.HOLD,
  RECORD_FAILED.format(step=plan.story.step, error=error)))`.

The key is now `plan.story.step` read **before** the advance. Today it is
`result["step"]`, which holds the same value (the step the gate ran for).

### `Runtime._record_tooling` (same signature, same return shape)

```python
def _record_tooling(self, plan: Plan, handoff: Handoff) -> dict[str, Any]:
    """R1: write the Tooling section into the story file and commit only that file."""
    story = plan.story.id  # type: ignore[union-attr]
    file = story_spec.file_of(self.config, story)
    old = system.read_text(self.config.repo / file)
    edit = FileEdit(file, old, ops_review.with_section(old, handoff.tooling))
    sha = self._commit_edit(edit, ops_review.RECORD_SUBJECT.format(story=story))
    self.record_checkout()
    return {"tooling": {"file": file, "commit": sha}}
```

A `GitError` from `_commit_edit` passes through (R3: `record_checkout` is not
reached) and is caught in `_pass_record`.

### New `Runtime._commit_edit(self, edit: FileEdit, subject: str) -> str | None`

Doc: "Write ``edit`` and commit only its file; None when the text is
unchanged. On a GitError, restore the old text and re-raise."

- `edit.new == edit.old` → `None` (R4).
- `system.write_text(self.config.repo / edit.file, edit.new)`
- `try: return self.git.commit([edit.file], subject)`
- `except GitError: self._restore(edit); raise`

### New `Runtime._restore(self, edit: FileEdit) -> None`

Doc: "Put ``edit``'s file back to its old text and unstage it (s131 R2)."

- `system.write_text(self.config.repo / edit.file, edit.old)`
- `self.git.attempt("reset", "-q")`. Pitfall (worth a comment in the code):
  use `attempt`, not `run`. The commit most likely failed because git itself
  is broken (a stale `index.lock`, for example), so the reset may fail too,
  and a raise here would hide the first error.

`PASS_RECORDS` keeps its type and its one row.

## Test checklist (unit-tester): `tests/test_s131_tooling_record.py`

Reuse `start` from `tests/test_s115_runtime.py` (and `run` from
`tests/test_dispatch.py`). Use the `fake` fixture with `fake.track()`.

Pitfall: the devops step's own files are also committed through
`git.commit` (`commit_step`). A faked failure must hit **only** the Tooling
commit. Two ways to do that: fail only when the message starts with
`ops_review.RECORD_SUBJECT.format(story="s1")`, or call `rt.gate(plan,
handoff)` directly after setting up the plan. Scripted `fake.reply` rules
win over the fake tree, so a non-zero reply for that one `git commit` also
works.

1. **Order (AC1, REQ-028).** Wrap `rt.git.commit` so it records
   `rt.state.stories["s1"].step` when it is called with the Tooling subject.
   After the run, the recorded step is `ops-review`, and the story is at
   `tests`.
2. **Order against the event (AC1).** The Tooling commit exists in
   `fake.tree.commits` by the time the gate event is emitted. For example,
   wrap `rt._advance_and_log` and assert inside it that the last commit's
   subject is the Tooling subject.
3. **Failed commit holds (AC2, REQ-029).** The Tooling commit raises
   `GitError("git commit: fatal: index.lock exists")`. Then
   `report["gate"]["verdict"] == "hold"`, the story's step is `ops-review`,
   `story.rounds` is unchanged, `"tooling" not in report["gate"]`, and the
   gate reason equals `RECORD_FAILED.format(step="ops-review", error=…)` and
   contains `index.lock`.
4. **Tree clean after the failure (AC2).** In the same setup, the story
   file's text equals its text before the gate, and `rt.git.is_clean()` is
   true. To cover the staged case, let the fake commit run `git add` on the
   path before it raises.
5. **Hand-over (AC2).** The hand-over / `story.hold` is `gate_hold`, as in
   `test_an_unfiled_missing_row_holds_through_gate_hold`.
6. **No record on a non-pass (R1).** On an ops-review bounce (an AC with no
   row), the Tooling commit is never attempted.
7. **Unchanged text (R4).** A second pass with the same rows makes no new
   commit, and `commit` is `None`. If an s115 test already pins this, keep
   it unchanged; if none does, add the test here.
8. **Reset failure doesn't mask (R2 pitfall).** When `git reset -q` also
   fails, the gate still holds with the commit's error in the reason.

The existing s115 tests (`test_the_commit_holds_only_the_story_file_with_its_subject`
and the others) must stay green unchanged.
