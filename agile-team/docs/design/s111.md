# s111 design: only a green CI run is done; our failure blocks, a broken main doesn't

Story: `.team/stories/s111.md`. ADR: **ADR-0064** (`.team/adr/0064-ci-failures-classed-from-github-job-data.md`);
it amends ADR-0040 (CI10, CI11) and ADR-0049 (the rule is now enforced in code).
Requirements: REQ-015 (AC1, AC6), REQ-016 (AC2, AC6), REQ-017 (AC3, AC6), REQ-018 (AC4, AC6),
REQ-019 (AC5).
Developer: `developer-cli` (runner modules, the PO role file, plus one pill in `dashboard/index.html`
and one fixture section).

## Where things stand

The CI stage (s81, `boundary_runner._ci`) reads `gh pr checks <n> --json …` per watched PR and
gives each PR a verdict from the check *buckets* only (`ci.verdict_of`). Red holds `ci_failed`.
The PO then either calls `record_ci_bug(story)` (the boundary finishes, `ci: red`) or
`continue_boundary`, which is never refused and re-reads the checks, so a re-run that turns green
finishes the boundary green. The rule "a re-run counts only when the job never ran our code"
(s110, ADR-0049) is prompt-only. Nothing checks the commit a run was on, nothing compares a
failure with main, and the dashboard shows no CI state at all.

## Rules

| # | Rule | AC |
|---|------|----|
| R1 | **The runner reads the jobs itself.** For every check whose link names an Actions job (`ci.job_of(link)`), the CI stage reads that job from GitHub (`Prs.job(link)`: its commit `head_sha`, `name` and `steps`). Nothing the PO, the human or a note says goes into a verdict. The only code path that finishes a boundary with `ci: green` is `_ci_green`, and it is reached only when the runner's own read is green. | AC1 |
| R2 | **Only the pushed head counts.** A check whose job ran on a commit other than the stack entry's `head` (the commit the runner pushed) is `stale`. It is ignored: it counts as not reported yet (verdict `pending`), never green, never red. Both SHAs are full 40-hex values (`git rev-parse` and the GitHub API), so compare them with `==`. | AC1 |
| R3 | **Required checks.** `GhPrs.checks` asks for `gh pr checks <n> --required --json …` first. When gh answers `no required checks reported`, the repo marks none as required, so every check counts (`gh pr checks <n> --json …`, as today). | AC1 |
| R4 | **Each check gets a kind** (`ci_triage.kind_of`, first match wins): (1) its job ran on another commit → `stale`; (2) bucket `pass` → `green`, `skipping` → `skipped`, `pending` → `pending`; (3) bucket `fail` or `cancel`: when its job is known and no step **ran** (R5) → `infra`, otherwise → `ours`. A failing check with no job link (not an Actions check) is `ours`, the safe side. | AC2, AC4 |
| R5 | **A step ran** when its `conclusion` is neither empty nor `skipped`, and its name is not a runner step (`RUNNER_STEPS = ("Set up job", "Complete job")`, steps GitHub runs around ours). The **failing step** of a job is its first step whose conclusion is in `FAILED_STEPS = ("failure", "cancelled", "timed_out")`; `""` when none. | AC2, AC4 |
| R6 | **A broken main.** When any check is `ours` and `[upstream] branch` is set (the target, which is the bottom PR's base), the runner reads the latest check runs on that branch's head (`Prs.main_checks(branch)`) and, for each failing one with a job link, its job. A failure on main is the pair `(check name, failing step)` of a main job that ran a step. An `ours` check whose `(name, step)` pair is in that set becomes `main`; `step` must not be empty. Main is read at most once per CI read, and only when something is `ours`. | AC3 |
| R7 | **Verdicts from kinds.** One PR's verdict is the first of `(red, infra, main, pending, green)` found among its checks' kinds, mapped by `KIND_VERDICT`: `ours`→`red`, `infra`→`infra`, `main`→`main`, `pending`/`stale`/`rerun`→`pending`, `green`→`green` (`skipped` maps to nothing). The boundary's verdict is the first of `(red, infra, main, pending, none, green)` over the PRs. A check with no kind (an old `state.json`, or a check not triaged yet) is mapped from its bucket by `BUCKET_KIND` (`fail`/`cancel` → `ours`), so it keeps its s81 meaning. | AC1–AC4 |
| R8 | **Outcomes** (`CI_OUTCOMES`): `green` → finish (done, the only "ready to merge"). `red` → hold `ci_failed`. `infra` → re-run (R9), or hold `ci_infra` when every `infra` check has used its re-run. `main` → hold `main_broken`. `pending` → hold `ci_pending`; the reason is `CI_STALE` when any check is `stale`, otherwise `CI_TIMEOUT`. `none` → finish as today. | AC1–AC4 |
| R9 | **One re-run per job and head.** For each `infra` check whose key `rerun_key(entry.head, label(check))` is not yet in `StackEntry.reran`, the runner appends the key, sets the check's kind to `rerun`, saves state, emits one `boundary` event `rerun` (`jobs`: the labels), and then calls `CiWatch.rerun(pr, check)`. That call runs `gh run rerun --job <id>` and then looks (at most `CI_LOOKS` times, `CI_POLL_S` apart) until the PR's check with the same label has a different link, which is the new attempt. The stage stays `ci` with no hold, so the next router tick reads the checks again, and only a green read of the new attempt counts (R1, R2). A key from another head never matches, so a new push gets its own re-run. A failed `gh run rerun` raises `UpstreamError` (the boundary's `error` hold); the key is already saved, so it is not tried again. | AC4 |
| R10 | **`continue_boundary` at `ci_failed` is refused**, whatever the note says. The refusal is `CI_OURS_REFUSAL` (exact text below); it names each `ours` check as `<label>, step <step>`. At `ci_infra`, `main_broken` and `ci_pending`, `continue_boundary` still releases the hold and the stage reads the checks again, with no new re-run for a used key. | AC2 |
| R11 | **`record_ci_bug(story)`** works at `ci_failed`, `ci_infra` and `main_broken` (`CI_BUG_HOLDS`), with the same story checks as today. It sets `upstream.ci_bug` (so CI14 puts the story first in the next sprint) and finishes the boundary, never as green: `ci_failed` and `ci_infra` with `CI_RED_REPORT` (`ci: red` or `ci: infra`), and `main_broken` with `CI_MAIN_REPORT` (`ci: main`), which starts "Sprint N ended, CI blocked by main". The PR stays open and unmerged; it is in the stack, so the next sprint end pushes and watches it again (R1). | AC1, AC3 |
| R12 | **The sprint card.** Each stack entry with a CI read gets a card (`ci.card_of(result)`), taken from the first row of `CARD_ROWS` whose kind is among its checks. An `ours` check shows `CI failed: <label>, <step>` (`failed`); an `infra` check shows `CI failed: <label>, no step ran` (`failed`); a `main` check shows `CI blocked by main: <label>` (`main`); a `rerun` check shows `re-running <label>` (`rerun`); `pending` or `stale` shows `CI running` (`running`); `green` shows `CI green` (`green`). Anything else (no checks, only skipped ones) shows `no CI result` (`none`). An empty step reads `step not named`. The snapshot's `upstream.stack[].ci` is `{"state", "text"}`, or `null` before the first CI read, and the Board's Review stack row shows it as a pill. | AC5 |
| R13 | **No new dependency.** Everything goes through `gh` (`gh api`, `gh run rerun`), which the CI stage already needs. | — |

**Pitfall, R9:** right after `gh run rerun`, `gh pr checks` can still show the old failed attempt
for a moment. Without the look-until-the-link-changes wait, the next read would see the old
failure with its key used and hold `ci_infra` at once.

**Interpretation (open question to the PO):** AC3 says "the runner records a bug story
(`record_ci_bug`)". The runner never writes story files (the PO does), so at `main_broken` the
runner holds the boundary, and the hand-over tells the PO to open the bug story for main and
`record_ci_bug` it in the same turn. The PO acts at once. The team does not wait for a fix, and
the next sprint starts with that story first.

## Changes per module

### `agile_team/ci_triage.py` (new, pure, imports no `agile_team` module)

Module docstring: what a CI check means for the sprint: the job data GitHub gives, and the kind
of each check.

```python
class Bucket(StrEnum)            # moved here unchanged from ci.py (ci.py re-exports it)
FAILING: frozenset[Bucket]       # moved here unchanged (fail, cancel); ci.py re-exports it
PASSING: frozenset[Bucket]       # moved here unchanged (pass, skipping); ci.py re-exports it

class CheckKind(StrEnum):
    """What one check says about the sprint."""
    GREEN = "green"; SKIPPED = "skipped"; PENDING = "pending"; STALE = "stale"
    OURS = "ours"; INFRA = "infra"; MAIN = "main"; RERUN = "rerun"

RUNNER_STEPS = ("Set up job", "Complete job")
FAILED_STEPS = ("failure", "cancelled", "timed_out")
NOT_RUN = ("", "skipped")
BUCKET_KIND = {Bucket.PASS: CheckKind.GREEN, Bucket.SKIPPING: CheckKind.SKIPPED,
               Bucket.PENDING: CheckKind.PENDING, Bucket.FAIL: CheckKind.OURS,
               Bucket.CANCEL: CheckKind.OURS}
CONCLUSION_BUCKET = {"success": Bucket.PASS, "skipped": Bucket.SKIPPING, "neutral": Bucket.SKIPPING,
                     "cancelled": Bucket.CANCEL, "": Bucket.PENDING}   # anything else -> FAIL

@dataclass(frozen=True)
class Step:
    """One step of an Actions job."""
    name: str
    conclusion: str = ""

@dataclass(frozen=True)
class Job:
    """An Actions job as GitHub reports it."""
    id: str
    head: str                   # head_sha
    name: str = ""
    steps: tuple[Step, ...] = ()

@dataclass(frozen=True)
class Seen:
    """A check's bucket and the job behind it (None: not an Actions check)."""
    bucket: Bucket
    job: Job | None = None

def job_from(raw: dict[str, Any]) -> Job          # GET actions/jobs/<id> JSON; missing conclusion -> ""
def bucket_of_run(raw: dict[str, Any]) -> Bucket  # a check-run's status/conclusion: not "completed" -> PENDING, else CONCLUSION_BUCKET.get(conclusion, FAIL)
def ran(job: Job) -> bool                         # R5
def failing_step(job: Job | None) -> str          # R5; None -> ""
def kind_of(seen: Seen, head: str) -> CheckKind   # R4
def rerun_key(head: str, label: str) -> str       # f"{head} {label}"
```

## Known limits

- A check that is not an Actions job (no job link) cannot be tied to a commit. It is taken as gh
  reports it for the PR's head; if it fails it is `ours`.
- Only a check that also runs on main's head (a push workflow) can be classed `main`. A check
  that runs only on pull requests is always `ours`.
- `gh pr checks --watch` still waits for every check, required or not.
- `main_checks` reads at most 100 check runs, and `[upstream] branch` is used as given in the
  URL (a branch name with `/` is not escaped).
