# s59: The sprint-start sync rebases the team branch onto the target

Story: `.team/stories/s59.md`. ADR: [`../adr/ADR-012-rebase-at-sprint-start.md`](../adr/ADR-012-rebase-at-sprint-start.md)
(this replaces ADR-005 decision 1, "merge in, never rewrite"). Changes
s29's U5 (start sync) and its `sync_conflict` hand-over. Everything else in
s29, s61 and s81 stays as it is.

Developer: `developer-api` (runner internals: git seam, boundary, state).
Real-git tests go in `tests/e2e/` (s71): the integration-tester writes
them. Unit tests use the fake.

## Why

Main receives each sprint as rebased copies ("Rebase and merge"). Merging
main into a team branch that still holds the originals, plus later commits
that edit the same lines, gives false conflicts: about 100 at sprint 18
(m54). A rebase drops every commit whose patch is already upstream, so
those conflicts go away. Hashes only matter within a sprint. At the boundary
the runner rewrites the hashes it recorded, so nothing it relies on goes stale.

## Rules

| # | Rule | AC |
|---|---|---|
| R1 | **Rebase, never merge.** The start-edge sync runs `Upstream.rebase_onto(old)` instead of `merge_in`. It drops merged stack entries first (U8, unchanged). The command is `git -c rebase.updateRefs=false -c rebase.rebaseMerges=false rebase --no-verify --no-autostash --no-autosquash --empty=drop <target>`, as the constant `REBASE_ARGV` + target. The `-c` pairs turn off two user configs that would change what a rebase does. Older git ignores the unknown keys, so `-c` is used rather than flags. `--reapply-cherry-picks` is **not** passed: commits whose patch is upstream are skipped. Merge commits on the old branch are dropped (the result is linear). No `merge`, no `-s ours`, no `-X ours` anywhere in `upstream.py` or `boundary_runner.py`. `merge_in`, `Merge`, `MergeOutcome`, `_failed_merge` and `MERGE_MESSAGE` are deleted. | AC1, AC5 |
| R2 | **Where the sync starts from.** `Boundary` gains `sync_from: str = ""`. The first time the start sync runs at a boundary, it sets `b.sync_from = git.head()` if it is empty. Every later run of the sync stage at that boundary (after `continue_boundary`) passes the same `b.sync_from` as `old`. A rebase the human did by hand after a `sync_conflict` is therefore paired and remapped (R5, R6) like the runner's own. An older `state.json` loads `sync_from = ""`. | AC2, AC3 |
| R3 | **Outcomes.** `rebase_onto(old)` returns a `Rebase`. **current**: HEAD after the command equals `old`; nothing to rewrite. **rebased**: HEAD differs from `old`; `sha` = new HEAD, `moved` = the R5 map. **conflict**: the command exits non-zero and `git diff --name-only --diff-filter=U` lists files. A non-zero exit with no conflicted files (dirty tree, rebase already in progress, bad target) raises `GitError(output)`, which becomes the existing `error` hold (unchanged). | AC1, AC3 |
| R4 | **Conflict leaves the branch unchanged.** On a conflict: read the files, then `commit = git rev-parse REBASE_HEAD` (the commit that failed to apply) and its subject. Then `git rebase --abort`. HEAD is back where it was before the command (byte-equal sha) and no rebase is in progress. The boundary holds `sync_conflict` (outcome `conflict`) with `files`, `commit` (12-char sha) and `subject`. Only the first conflicting commit's files are listed, because a rebase stops there. The hand-over says so. | AC3 |
| R5 | **Pairing old to new commits.** `listing(range)` runs `git log --reverse --topo-order --date=raw --format=STAMP_FORMAT <range>`, where `STAMP_FORMAT = "%H%x1f%an%x1f%ae%x1f%ad%x1f%B%x1e"`. Each record is a `Stamped(sha, stamp)`; the stamp is everything after the first `\x1f` (author, email, author date, full message), which a rebase keeps. `old = listing("<target>..<old>")` and `new = Listing(onto=<target sha>, commits=listing("<target>..<HEAD>"))`, where `<target sha>` is `git rev-parse <target>` read before the rebase. `rewrite.pair(old, new)` walks `old` oldest first with a cursor into `new.commits`. If the next new commit's stamp equals the old one's, the old sha maps to it and the cursor moves on. Otherwise the old commit was dropped (merge commit, patch already upstream, became empty): it maps to the last new sha matched so far, or to `new.onto` if none. That commit holds the dropped commit's content, because the content is in `onto`. Every old sha gets an entry. | AC2 |
| R6 | **Rewriting the recorded hashes.** `rewrite.remap_state(state, moved)` replaces each recorded team-branch hash that is a key of `moved` with its value. Any other value (an ancestor of the target, a short sha, `None`, `""`) is left alone. The fields rewritten are listed in the table `REMAPPED` below and nothing else. After the remap the runner calls `runtime.record_checkout()` (s61 K1.2), then `runtime.save()` at once, before any event or further stage. A crash after the rebase must not leave old hashes on disk. | AC2 |
| R7 | **No content lost.** `rebase_onto` checks the result before pairing. Let `base = git merge-base <old> <target>`. `upstream = diff --name-only --no-renames base <target>`. `team = diff --name-only --no-renames base <old>`. A path is **lost** when it is in `diff --name-only --no-renames <old> HEAD` but not in `upstream` (the team's version changed although only the team touched it). It is also lost when it is in `diff --name-only --no-renames <target> HEAD` but not in `team` (upstream's version changed although only upstream touched it). Paths both sides touched are trusted to git. If any path is lost, the runner runs `git reset --hard <start>`, where `<start>` is HEAD before *this* rebase command (not `old`, so a hand rebase is never thrown away). It then raises `UpstreamError(SYNC_LOST.format(team=…, target=…, paths=…))`, which gives the existing `error` hold. | AC2 |
| R8 | **Empty stack entries go.** After a `rebased` remap, the sync runs `_drop_merged(b)` again. An entry whose commits were all dropped by the rebase has `start == end` after R6, so it is dropped with the usual `MERGED_NOTE` event (and `restack` is set as today). | AC1, AC2 |
| R9 | **Events.** `BoundaryOutcome` gains `REBASED = "rebased"`, which replaces the sync's use of `MERGED`. `MERGED` stays for dropped entries (`MERGED_NOTE`). The `rebased` event carries `sha` (new HEAD) and `rewritten` (the number of recorded values R6 changed). A `current` sync emits `current` as today. The dashboard tone table maps `rebased` to `"good"`. The snapshot fixture's sync event e93 becomes `"outcome": "rebased"` with `"rewritten": 4`. | — |
| R10 | **Conflict hand-over grouped by directory.** `handover._boundary_fields` adds `file_count` (the number of `files`) and `file_groups` = `group_files(files)`. `group_files` groups paths by parent directory (`.` for the repo root). Groups are sorted by directory, names inside a group are sorted, and the output reads `dir (n): a, b; dir2 (m): c`. The `sync_conflict` line is in § Texts. It also gets `commit` and `subject` from the boundary data (add both to `BOUNDARY_TEXT`). | AC3 |
| R11 | **Push unchanged.** `Upstream.push` keeps `--force-with-lease=<ref>:<expect>`, and `_guard` keeps refusing anything but `<prefix>*` review branches: never the team branch, never the target branch. The rebase does not push the team branch. Tests pin both behaviours (they exist in s29; keep them and add the team-branch refusal if missing). | AC4 |
| R12 | **End edge unchanged.** The end sync still adds the stack entry and never rebases. Only `Edge.START` maps to the new method in `SYNCS`. | — |

### `REMAPPED`: what R6 rewrites

| Field | Rewritten? | Why |
|---|---|---|
| `stories[*].commit` | yes | the story's recorded commit |
| `stories[*].code_commits[*]` | yes | s46: the tests gate checks they are in the branch |
| `stories[*].interrupted.sha` | yes | s9 salvage commit on the team branch |
| `interrupted[*].sha` | yes | same, run-level list |
| `upstream.last_end` | yes | start of the next stack entry |
| `upstream.stack[*].start`, `.end` | yes | the entry's team range |
| `upstream.checked` | **no** | the tree now holds upstream changes; the check must run again |
| `upstream.stack[*].head`, `.checked`, `.pushed`, `.base` | **no** | review-branch commits, not on the team branch |
| `checkout` | via `record_checkout()` | s61 K1.2 |
| `boundary.failure.commit` | no | review-branch pick; a start sync has no failure |

## Changes per module

### `agile_team/rewrite.py` (new; pure, no I/O)

```python
"""Old-to-new commit pairing after a rebase, and rewriting the hashes in ``state.json``."""

@dataclass(frozen=True)
class Stamped:
    """A commit and what a rebase keeps of it (author, date, message)."""
    sha: str
    stamp: str

@dataclass(frozen=True)
class Listing:
    """The rebased commits, oldest first, and the commit they sit on."""
    onto: str
    commits: tuple[Stamped, ...]

def parse_listing(out: str) -> tuple[Stamped, ...]:
    """``git log --format=STAMP_FORMAT`` output as ``Stamped`` records (blank records skipped)."""

def pair(old: Sequence[Stamped], new: Listing) -> dict[str, str]:
    """R5: every old sha to its rebased copy, or to the last kept copy before it."""

def remap_state(state: RunState, moved: Mapping[str, str]) -> int:
    """R6: rewrite the ``REMAPPED`` fields in place; return how many values changed."""
```

`remap_state` is split into one helper per owner (`_story`, `_interruptions`,
`_upstream`), each counting its changes. Use one helper `_moved(sha, moved)`
that returns `moved.get(sha, sha)` and handles `None`. Import `RunState`
under `TYPE_CHECKING` only. `rewrite.py` must not import `state.py` at run
time.

### `agile_team/upstream.py`

- Delete `MergeOutcome`, `Merge`, `merge_in` and `_failed_merge`.
- Add:

```python
class SyncOutcome(StrEnum):
    """What rebasing the team branch onto the target did."""
    CURRENT = "current"
    REBASED = "rebased"
    CONFLICT = "conflict"

@dataclass(frozen=True)
class Rebase:
    """The result of ``Upstream.rebase_onto``."""
    outcome: SyncOutcome
    sha: str = ""
    files: tuple[str, ...] = ()
    commit: str = ""
    subject: str = ""
    moved: Mapping[str, str] = field(default_factory=dict)
    output: str = ""

class Upstream:
    def rebase_onto(self, old: str) -> Rebase:
        """R1/R3: rebase HEAD onto the target; R4 on a conflict, R7 check, R5 pairing."""
    def listing(self, span: str) -> tuple[Stamped, ...]:
        """R5: the commits of ``span`` (``a..b``), oldest first, with their stamps."""
```

Private helpers, each one job: `_failed_rebase(output) -> Rebase` (R4),
`_check_kept(spans)` (R7, raising after the reset), `_lost(spans) -> list[str]`,
`_names(a, b) -> set[str]` (`diff --name-only --no-renames a b`). `spans` is a
small frozen dataclass `Spans(start, old, target_sha)`, which keeps every
helper at two parameters or fewer. Read the target sha (`rev-parse <target>`)
once at the top of `rebase_onto`.
- `push` and `_guard`: unchanged (R11).
- Update the module docstring: "fetch, rebase, push".

### `agile_team/boundary_runner.py`

- Replace `_merge_in` with `_rebase(b)`:
  1. `b.sync_from = b.sync_from or self.runtime.git.head()`
  2. `result = self.remote.rebase_onto(b.sync_from)`
  3. conflict → `_hold(b, SYNC_CONFLICT, Out.CONFLICT, files=list(result.files), commit=result.commit[:12], subject=result.subject)`

  5. current → emit `Out.CURRENT`.
  6. `_advance(b)` on rebased and current.

- Imports: drop `MERGE_MESSAGE` and `MergeOutcome`; add `from .upstream import Rebase, SyncOutcome` and `from . import rewrite`.
- Choose between conflict, rebased and current with a dict keyed by `SyncOutcome`, not an if-chain (house rule: tables over branching).

E2E on scratch repos (`tests/e2e/test_s59_rebase_e2e.py`). Each test uses a bare `origin` plus a clone with `set_git_identity` and the `isolated_git` fixture. Never touch the real home directory.

- [ ] **All already upstream:** the team has commits A, B. Origin/main gets their rebased copies (cherry-picked in a second clone, pushed). The sync gives `rebased`, HEAD equals origin/main, the tree equals origin/main's, and `state.json` story commits map to origin/main's sha.
- [ ] **Copies plus new content (the m54 case):** the team has A, then B editing A's lines. Main has A' (a copy of A) and an unrelated U. The old merge would conflict, but the sync gives `rebased`: the history is linear (`git rev-list --merges <target>..HEAD` empty), B's content is kept, U is present, and B's recorded hash is rewritten to its new copy.
- [ ] **Real conflict:** main changes a line differently from the team. The sync holds `sync_conflict`, HEAD is unchanged, no `.git/rebase-merge` or `rebase-apply`, and the hand-over lists the files grouped with a count.
- [ ] **Hash rewrite in `state.json`:** after `rebased`, every `REMAPPED` field holds a commit reachable from HEAD; `upstream.checked` is unchanged; `state.checkout.head` equals HEAD.
- [ ] **Hand rebase after a conflict:** after the conflict, the test rebases by hand in the clone and calls continue. The second sync is `current` by HEAD, but it remaps from `sync_from`, so the story hashes point to the hand-rebased commits. (Implementation note: when HEAD is no longer `sync_from`, the outcome is `rebased` even though the command itself did nothing. R3 compares against `old`, not against the HEAD before the command.)

## Known limits

- Two adjacent team commits with the same author, second and message might pair one position off (R5). Their content is the same, so nothing that relies on the mapping breaks.
- Hashes quoted in review files, stories and designs are historical text and are not rewritten.
- The rebase lists only the first conflicting commit's files. The human sees the rest while rebasing by hand.
