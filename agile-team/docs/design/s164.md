# s164: the scheduler's own writes never wake it

Story: `.team/stories/s164.md`. ADR: **ADR-0085** (amended by s164).
Requirements: REQ-174 (AC1), REQ-175 (AC2). Developer: `developer-cli`.

## Cause, in one line

`Scheduler.tick` opens the `checkout.guard` stage on every tick; its close
emits a `runner-stage` event; `EventLog.emit` queues it through
`RunWriter.submit`, which sets `writer.wake`; `wait_for_change` returns at
once on `wake`, so the loop ticks again with no pause.

## Rules

- **W1. Own writes queue quietly.** `RunWriter.submit` called from the task
  the writer was bound to (the scheduler task, on the loop thread) queues
  the write and does not set `wake`. A submit from any other task on the
  loop (a step's `run_work`, the PO turn, a boundary stage, the follow
  task, the story CI poll, an `apply` scheduled by `call_from_thread`) or
  from a worker thread queues and sets `wake`, as today.
- **W2. Own writes land before the wait.** `Scheduler.wait_for_change`
  flushes the writer first (`RunWriter.flush`, which drains only on the
  bound loop thread), so the scheduler's own lines (the guard's stage
  event, its saves) are on disk before it waits, not up to 5 s later on
  the next tick.
- **W3. The wait itself is unchanged.** It still ends on the first of: a
  task in `self.tasks` or `po_task` ending, `wake`, or `POLL_S` (5 s).
- **W4. No behaviour relies on a self-wake.** Everything a tick changes is
  already seen by `start_turn`/`start_work` in the same loop pass. If a
  test shows a flow that needed its own write to tick again at once, set
  `self.hurry = True` at that point (the existing mechanism, as
  `follow_boundary`'s open-end case does) and name it in the handoff. Do
  not make owner writes wake again.
  - **W4a. The one flow that needed it: `check_idle`** (found at build).
    When `check_idle` queues an idle pass for the PO (after
    `queue_pass(found)`), it sets `self.hurry = True`, so the next loop
    pass starts the PO turn at once instead of after `POLL_S`.
  - **W4b. A hurry is one-shot (D1).** `hurry` is set only on the path
    that queues a pass with kinds. An ended run, a quiet idle, or a found
    pass with no kinds set nothing; and once a pass is queued, the desk is
    no longer empty, so `check_idle` returns before it can set `hurry`
    again. `run_loop` clears `hurry` every pass. No state may set `hurry`
    on every pass.
- **W5. Unbound is unchanged.** With no bound loop, `submit` still writes
  at once (CLI and tests).

The checkout guard still runs once per tick and still emits its stage
event; only the wake goes. `heartbeat.json` writes are not touched (they
fall to two per tick at the normal tick rate).

## Changes

### `agile-team/runner/agile_team/run_writer.py`

- `RunWriter.__init__`: add `self._owner: asyncio.Task | None = None`.
- `bind(self, loop: asyncio.AbstractEventLoop, task: asyncio.Task) -> None`:
  also `self._owner = task` (the parameter is already passed by
  `Scheduler`, `scheduler.py:102`, and was unused).
- `release(self) -> None`: also reset `self._owner = None`.
- New public property (the tests read it):

  ```python
  @property
  def is_on_owner(self) -> bool:
      """True when the caller runs on the bound task itself (s164 W1)."""
  ```

  Returns False when unbound (`_owner is None`) or off the bound thread,
  else `asyncio.current_task() is self._owner`; a `RuntimeError` from
  `current_task()` means False. Pitfall: check the thread first;
  `asyncio.current_task()` raises `RuntimeError` on a thread with no
  running loop. On the loop thread outside any task (a plain
  `call_soon` callback) it returns `None`, which is not the owner, so that
  write wakes.
- `submit(self, write: Write) -> None`: after queueing, call
  `self._loop.call_soon_threadsafe(self._wake)` only when
  `not self.is_on_owner`. As built, the docstring stays "Queue a write
  (thread-safe), or run it at once when unbound." and a comment on the
  wake line says the scheduler's own writes must not wake it (accepted at
  design review).
- Module docstring unchanged.

### `agile-team/runner/agile_team/scheduler.py`

- `Scheduler.wait_for_change(self) -> None`: first line
  `self.runtime.writer.flush()` (W2). Docstring: "C1 step 8: write the
  scheduler's own queued lines, then wait for a task to end, a write from
  another task or thread, or ``POLL_S``."
- `Scheduler.check_idle(self) -> None`: after `self.queue_pass(found)`,
  `self.hurry = True` (W4a, W4b).
- No other change. `tick` keeps its leading `drain()`.

No change to `dispatch.py`, `events.py`, `ledger.py` or `stage_log.py`.

## Test checklist

New file `agile-team/runner/tests/test_s164_idle_tick.py`. Unit tests, no
temp-dir fixtures (s154); use the existing in-memory `RunWriter` pattern
from `tests/test_s159_run_writer.py`.

1. **Owner submit doesn't wake (W1, REQ-174).** Bind the writer to the
   current task, `submit` a write, `await asyncio.sleep(0)`; `wake` is not
   set, and `drain()` returns 1.
2. **Another task's submit wakes (W1).** Bound to the current task, a
   second task made with `asyncio.create_task` submits; after awaiting it
   and one `asyncio.sleep(0)`, `wake.is_set()`.
3. **A worker thread's submit wakes (W1).** Bound, a submit through
   `asyncio.to_thread`; afterwards `wake.is_set()`.
4. **Unbound still writes at once (W5).** `submit` with no `bind` runs the
   write; `is_on_owner` is False.
5. **Release forgets the owner.** After `bind` then `release`,
   `is_on_owner` is False.
6. **Own lines land before the wait (W2).** A `Scheduler` with one task
   that never ends (an `asyncio.Event().wait()` task in `tasks`) and a
   submitted owner write: `wait_for_change` (with `POLL_S` patched small,
   e.g. 0.05, in `scheduler`) runs the write before it returns, and returns
   only after the timeout. Compare durations with a tolerance (REQ-025),
   reading the clock through the clock helpers (REQ-024).
7. **An idle loop does not spin (AC1, REQ-174).** Run `run_loop` with one
   never-ending step task and `POLL_S` patched to 0.05 for a bounded window
   (e.g. cancel after 0.5 s); count `tick` calls (wrap `Scheduler.tick`) and
   the `checkout.guard` `runner-stage` events: ticks ≤ window / `POLL_S` +
   2, and guard events ≤ ticks. Before the fix this count runs into the
   hundreds.
8. **A write from a step still wakes the wait at once (AC1).** Same set-up
   with `POLL_S` left at 5.0: a second task submits a write after a short
   sleep; `wait_for_change` returns well before 5 s.
9. **Off a loop thread `is_on_owner` is False** (the `RuntimeError`
   pitfall).
10. **A hurry never sticks (W4b, D1).** With one never-ending step and
    `POLL_S` patched small, the loop ticks at most window / `POLL_S` + 2
    times both when the run has ended with a pass on the desk and when the
    queued pass has no kinds.

End to end (added at build): `agile-team/runner/tests/e2e/test_s164_idle_e2e.py`
runs the idle loop against a real runtime (`make_runtime`) and checks
tests 7 and 8 there.

If an existing test now waits for a full `POLL_S` because it relied on a
self-wake, that is W4: fix the flow with `hurry`, not the test.

### By hand (acceptance, AC2, REQ-175)

On a run started after the fix, with one step running for ten minutes:

- `ps -o pcpu -p $(cat .team/run/runner.pid)` reads under 10.
- Count `checkout.guard` events in `events.jsonl` with `at` in the window;
  it is ≤ 120 plus the number of other events in the same window.
