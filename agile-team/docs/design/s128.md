# s128: The team keeps going across sprint ends, and the runner re-pins itself

Story: `.team/stories/s128.md` (the human's t94, items 1 and 4b; the ACs are
theirs, word for word). ADR: **ADR-0065** (new). Amends **ADR-0029** (the pin
script keeps the old pin and can roll back) and **ADR-0027** (`run.runner_pin`).
Requirements: REQ-021 (AC1), REQ-022 (AC2), REQ-023 (AC3). AC4 is the test
list below.
Developer: `developer-cli`. The work also touches `unattended/runner/`
(command jobs), `scripts/pin-runner.sh`, `dashboard/index.html` (one pill, one
`TIMELINE` row), the dashboard fixture sources and `roles/product-owner.md`.

There are three parts:

1. **Keep going (AC1).** With cadence `until-blocker`, a sprint end with ready
   backlog stories hands over `next_sprint`. That trigger is never quiet, so a PO
   turn that starts no sprint gets the hand-over again, up to a cap. `done` and
   `blocked` are refused while ready stories exist. A resume keeps the run's
   cadence.
2. **Re-pin (AC2).** When the end boundary's full check passes on a pinned
   runner, the runner asks to re-pin and lets its PO loop end. It releases
   `runner.pid`, pins the checked head, runs `config check` under the new pin,
   and `os.execv`s into the new pin's `start --resume`. If any step fails, it
   rolls back to `runner-pin.prev` and execs the restored pin. The process that
   starts after the exec logs `runner-repin` and, after a rollback, tells the
   human.
3. **Stop reason (AC3).** An agile-team command job that exits 0 records
   `agile-team <status>: <reason>` from `state.json`. A halt exit records the
   halt line. The runner also stores why it stopped (the PO's note, or the last
   hand-over line).

| K2 | **Next-sprint hand-over.** `Router._sprint_end()` (the `_idle` branch for "no boundary and `sprint_complete()`") checks the cadence. With `until-blocker` and a non-empty `self._ready()`, it returns `Pass([Trigger.NEXT_SPRINT], lines, [])`. `lines` are today's two lines (`Sprint N is complete…` and the `Review:` line when there is one), then `sprint_end.next_sprint_lines(stories, ready)`. | K3 | **The stuck sprint under until-blocker.** In `Router._offer`, the once-per-key rule (`key == state.offered`) does not apply under `until-blocker`. While the sprint is stuck and the ready list is non-empty, every idle pass hands over `ready_backlog`. Under `sprint` cadence it works as it does today (s124 K2). | AC1 |
| K4 | **Ask cap.** `RunState.keep_going_asks: int = 0` (persisted; old states load 0). Each `next_sprint` hand-over, and each `ready_backlog` hand-over under `until-blocker`, first checks the count. If it is below `KEEP_GOING_CAP = 3`, the router adds 1, saves and hands over. If it has reached the cap, the router hands over nothing. It does `state.mark(RunStatus.BLOCKED, text)` with `text = KEEP_GOING_STUCK`, posts `Note("blocked", text, [])`, saves, and returns `Pass([], [], [])`, so the run ends. `RunState.begin_sprint` and `RunState.add_to_sprint` reset the count to 0. | AC1 |
| K5 | **No early end.** `sprint_end.keep_going_refusal(state)` returns `KEEP_GOING_REFUSED` when `state.cadence == "until-blocker"` and `ready_backlog(state.stories, list(state.stories))` is non-empty, and `None` otherwise. `po_tools.KIND_REFUSALS` gains `"done"` and `"blocked"`, both mapped to it. `sprint-end` stays as it is: under `until-blocker` it never halts (`RunState.halted`), so it is only the review note. | AC1 |
| K6 | **Nothing else gates the next sprint.** `start_sprint` never looks at the review stack's PR states. Open, draft or unmerged PRs don't refuse it; this is how it works today, and a test now pins it. A re-pin never holds a boundary or a story. On success or rollback, the boundary resumes at the stage after `check` (P2) in the new process. | AC1 |
| K7 | **PO prompt.** The `## Cadence` bullet for `until-blocker` in `roles/product-owner.md` becomes the text in "Texts". | AC1 |
| P1 | **Pinned runner.** `repin.pinned(run_dir)` is true when `system.resolve(repin.PACKAGE_DIR)` is inside `system.resolve(run_dir / PIN_DIR)`. `PACKAGE_DIR = Path(__file__).parent` is a module constant that tests patch. Only a pinned runner re-pins. Installed skills and working-copy runs never do. `repin.pin_commit(run_dir)` is the stripped text of `runner-pin.commit`, or `""` when the file is missing. | AC2 |
| P2 | **When.** In `BoundaryRunner._check`, both pass branches (a fresh pass, and `already checked at <head>`) call `_repin_due(b, head)`. When `b.edge is Edge.END` and `repin.due(run_dir, head)` holds (`pinned(run_dir) and head != pin_commit(run_dir)`), it sets `state.repin = head`. `_advance` has already moved the boundary to its next stage, and `_step` saves. The start edge never re-pins. A boundary that is skipped (no remote, so no check stage) does not re-pin. This runs before `rebase`, so the checked head is still on the branch, as `pin-runner.sh` requires. | AC2 |
| P3 | **The loop ends cleanly.** `Router._ended()` is also true when `state.repin` is set. The PO loop ends with no hand-over, and `PoRun.run` marks the run `IDLE`. `cmd_start` exits the `pid_file` block, which removes `runner.pid`. Then, when the exit code is 0, `runtime.halted_by` is `None`, no stop was requested and `state.repin` is set, it calls `Pin.repin(...)`. With a stop requested, it returns 0 and keeps `state.repin`. The next `start --resume` then ends its loop at once and re-pins. A `start` that is not pinned and finds `state.repin` set clears it and saves before the loop (`repin.drop_unpinned`). | AC2 |
| P4 | **Re-pin.** Before the call, `cmd_start` clears `state.repin`, marks `IDLE` with `REPINNING` and saves (1). `Pin.repin(marker)` then runs these steps in order: (2) `sh <repo>/agile-team/runner/scripts/pin-runner.sh <new>` (timeout `PIN_TIMEOUT_S = 300`); (3) `<uv> run --frozen --quiet --project <run_dir>/runner-pin agile-team config check --repo <repo>` (timeout `CHECK_TIMEOUT_S = 600`; `uv` from `system.which("uv")`); (4) it writes the marker with `outcome: trial`; (5) `system.exec_replace((<run_dir>/runner-pin/.venv/bin/agile-team, *argv))`. A non-zero exit, a `TimeoutExpired`, an `OSError` or a missing `uv` in (2)–(5) calls `roll_back(marker, reason)`. The steps (2) and (3) are a table, `TRIALS: tuple[Trial, ...]`, of `(name, argv builder, timeout)`. | AC2 |
| P5 | **Exec argv.** `repin.start_argv(repo, home)` returns `("start", "--resume", "--repo", str(repo))`, plus `("--home", home)` when the original args had one. The cadence is not passed (K1 keeps it). The exec target is the new pin's venv console script: `config check` just built `<pin>/.venv` (uv's default project venv). Execing it directly adds no `uv` process per sprint. Pitfall: once step (2) has swapped the directories, the old process's editable install points at the new code. So `repin.py` imports everything it needs at module top, and nothing between (2) and the exec may import lazily. | AC2 |
| P6 | **Pin script keeps the old pin.** `pin-runner.sh <commit>` builds `runner-pin.new` as today. It then removes `runner-pin.prev` and `runner-pin.prev.commit`, moves `runner-pin` to `runner-pin.prev` and `runner-pin.commit` to `runner-pin.prev.commit` (each only if present), moves `.new` into place and writes the commit. Its output is unchanged. | AC2 |
| P7 | **Pin script rollback.** `pin-runner.sh --rollback` refuses a live `runner.pid` (`the team is running; stop it first`, exit 1) and a missing `runner-pin.prev` (`no previous pin to roll back to`, exit 1). Otherwise it removes `runner-pin.failed` and `runner-pin.failed.commit`, moves the current pin and commit to `.failed`, and moves `.prev` and `.prev.commit` back to `runner-pin` and `runner-pin.commit`. It prints `rolled back to <sha7> at .team/run/runner-pin` and exits 0. The usage line becomes `usage: pin-runner.sh <commit> \| --rollback` (exit 2). The ancestor and `pyproject.toml` checks apply only to `<commit>`. | AC2 |
| P8 | **Roll back.** `Pin.roll_back(marker, reason)` first checks `pin_commit(run_dir) == marker.new != marker.old`. Only then has the swap happened, and only then does it run `sh <PIN_SCRIPT> --rollback`. Without that check, a pin that failed before its swap would roll back one pin too far. If `--rollback` fails, it raises `RepinError(reason + "; rollback failed: " + tail)`. This is a crash: the job resumes, and the marker stays for the human. Otherwise it writes the marker with `outcome: rolled_back, reason` and execs the restored pin with the same argv (P5). The same method runs in the old process (a failed pin, check or exec) and in the new one (a failed first start, P9). | AC2 |
| P9 | **First start.** `cmd_start` builds `pin = repin.Pin(repo, start_argv(...))` before anything else. Everything from `_load_config` to the cadence and task setup runs inside `try`. On any `Exception`, it calls `repin.failed_start(pin, exc)` and then re-raises. `failed_start` rolls back (P8, reason `first start failed: <Type>: <message>`) only when the marker says `trial`, and does nothing otherwise. The checkout guard's early `return` is not a failure. When the setup succeeds, `repin.confirm(runtime)` runs just before `_run`. | AC2 |
| P10 | **Confirm and event.** `confirm(runtime)` reads `.team/run/repin.json`. With no marker, it does nothing. With `trial`, it emits `runner-repin` with outcome `pinned`. With `rolled_back`, it emits `runner-repin` with outcome `rolled_back` and posts `Note("update", ROLLED_BACK_NOTE, [])`. Either way it then deletes the marker. Event: `EventKind.RUNNER_REPIN = "runner-repin"`, role `"runner"`, story `None`, data `{"old", "new", "sprint", "outcome", "reason"}` (full shas, and `reason` is `""` when pinned). There is one event per re-pin, written by the process that runs after it. | AC2 |
| P11 | **Marker.** `.team/run/repin.json` holds `{"old", "new", "sprint", "outcome": "trial"\|"rolled_back", "reason"}` (`repin.Marker`, frozen dataclass, `Outcome` StrEnum). It is written with `system.write_text`. A marker that doesn't parse counts as absent. | AC2 |
| P12 | **Dashboard.** The snapshot's `run` gains `runner_pin: repin.pin_commit(config.run_dir)` (`""` when not pinned). The header's status row adds `pinPill(view)` right after `statePill`: when `run.runner_pin` is set, `<span class="pill" title="runner pinned at <sha>">pin <sha7></span>`, else `""`. `TIMELINE["runner-repin"]` uses from `"runner"` and to `sprint <n>`. Its `what` is `runner re-pinned` (tone `""`) or `re-pin rolled back` (tone `warning`). Its body is `<old7> → <new7>`, plus the reason on its own line. The fixture sources get `"runner_pin"` in `run.json` and one `runner-repin` event in `events.json`. Rebuild with `scripts/make_dashboard_fixture.py` (s116). | AC2 |
| S1 | **The runner says why it stopped.** `notify_user` with a status kind (`sprint-end`, `done`, `blocked`) does `state.mark(RunStatus(kind), first_line(text))`. The note's first line, cut to 200 characters, becomes `status_reason`. When `PoRun._after_po` ends the run on a quiet pass, it keeps `found.lines[0]`, and `run()` marks `IDLE` with it (for example `Nothing in sprint 4 can move.`). | AC3 |
| S2 | **The job records why.** In `unattended/.../command_job.py`, `agile_status(output)` reads `<cwd>/.team/run/state.json`. It returns `"agile-team <status>: <status_reason>"`, or `"agile-team <status>"` when the reason is empty, cut to `limits.REASON_LIMIT`. It returns `None` when there is no file, the JSON is bad or `status` is not a string. Exit 0 gives `Outcome(DONE, agile_status(output) or "")`. In `_failed`, the offline check runs first, as today. Then the reason is `exit code N` followed by `; agile-team halted: <halt_reason>` when the halt line is in the tail, else `; <agile_status>` when there is one, else nothing. A job with no state file and no halt line records exactly what it records today. | AC3 |

## Flow of a re-pin

```mermaid
sequenceDiagram
  participant B as BoundaryRunner (old)
  participant C as cli.cmd_start (old)
  participant S as pin-runner.sh
  participant N as start --resume (new pin)
  B->>B: check passes at END, pinned, head != pin
  B->>C: state.repin = head; router ends; PoRun marks IDLE
  C->>C: leave pid_file (runner.pid removed)
  C->>S: pin <head> (old pin -> runner-pin.prev)
  C->>C: uv run --project runner-pin agile-team config check
  C->>C: write repin.json {trial}
  C->>N: os.execv(runner-pin/.venv/bin/agile-team start --resume)
  N->>N: setup ok -> runner-repin {pinned}; marker removed
  Note over C,N: any failure: pin-runner.sh --rollback (only if swapped),<br/>repin.json {rolled_back}, execv restored pin,<br/>which logs runner-repin {rolled_back} and tells the human
```

## Changes by module

### `agile_team/repin.py` (new)

```python
PIN_DIR = "runner-pin"; COMMIT_FILE = "runner-pin.commit"; MARKER_FILE = "repin.json"
PIN_SCRIPT = "agile-team/runner/scripts/pin-runner.sh"; PIN_EXE = ".venv/bin/agile-team"
PACKAGE_DIR = Path(__file__).parent
PIN_TIMEOUT_S = 300.0; CHECK_TIMEOUT_S = 600.0

class Outcome(StrEnum): TRIAL = "trial"; PINNED = "pinned"; ROLLED_BACK = "rolled_back"
class RepinError(RuntimeError): """A rollback that failed; the run crashes and the marker stays."""

@dataclass(frozen=True)
class Marker:  # old, new, sprint, outcome, reason=""
    def data(self) -> dict[str, Any]: ...

def pinned(run_dir: Path) -> bool: ...
def pin_commit(run_dir: Path) -> str: ...
def due(run_dir: Path, head: str) -> bool: ...
def read_marker(run_dir: Path) -> Marker | None: ...
def write_marker(run_dir: Path, marker: Marker) -> None: ...
def start_argv(repo: Path, home: str | None) -> tuple[str, ...]: ...
def drop_unpinned(runtime: Runtime) -> None: ...      # P3
def confirm(runtime: Runtime) -> None: ...            # P10
def failed_start(pin: Pin, exc: Exception) -> None: ... # P9

@dataclass(frozen=True)
class Pin:
    """The repo's pinned runner: pin it, check it, exec it, or roll it back."""
    repo: Path
    argv: tuple[str, ...]
    def repin(self, marker: Marker) -> NoReturn: ...           # P4
    def roll_back(self, marker: Marker, reason: str) -> NoReturn: ...  # P8
    def exec(self) -> NoReturn: ...                             # P5
```

## Test checklist (AC4)

Hand-over (K1–K7):
- [ ] `until-blocker`: a complete sprint with a closed end boundary and ready backlog hands over `next_sprint`. The lines hold `NEXT_SPRINT_LEAD`, the ready ids and `NEXT_SPRINT_ADVICE`. With no ready story, it is today's `sprint_end`. Under `sprint` cadence it is always today's `sprint_end`.
- [ ] A PO turn that starts no sprint gets `next_sprint` again (the pass is not quiet). On the 4th time, the run is `blocked` with `KEEP_GOING_STUCK`, a `blocked` note is posted, and the run ends. `start_sprint` and `add_to_sprint` reset `keep_going_asks`.
- [ ] `until-blocker`, an open sprint stuck with ready stories: `ready_backlog` repeats on each idle pass (no once-per-key) and counts toward the cap. Under `sprint` cadence it is offered once, as today.
- [ ] `notify_user` `done` and `blocked` are refused with `KEEP_GOING_REFUSED` under `until-blocker` with ready stories, and nothing is posted. They are accepted with no ready story, and always under `sprint`.
- [ ] `start_sprint` is accepted while the review stack holds an open, unmerged PR entry.
- [ ] `start --resume` with no `--cadence` keeps a stored `until-blocker`. `--cadence sprint` replaces it. A fresh start with no `--cadence` uses the config.
- [ ] Old state loads `repin = ""` and `keep_going_asks = 0`.

Re-pin (P1–P12):
- [ ] A passing END check on a pinned runner whose head differs from `runner-pin.commit` sets `state.repin = head`. So does the `already checked` branch.
- [ ] No re-pin request: a failing check, the START edge, a runner that is not pinned (`PACKAGE_DIR` outside the pin), a head equal to the pin, or a skipped boundary.
- [ ] `state.repin` ends the router loop. `cmd_start` then calls the pin script, `config check` and `exec_replace` in that order (FakeSystem calls, exact argv). `runner.pid` is gone before the script runs. The marker says `trial` and `state.repin` is cleared and saved. The exec argv is `(<run_dir>/runner-pin/.venv/bin/agile-team, "start", "--resume", "--repo", <repo>)`.
- [ ] With a stop requested, there is no re-pin, exit 0, and `state.repin` is kept. The next start ends its loop at once and re-pins.
- [ ] Rollback: `config check` exits 1 → `--rollback` runs, then the marker says `rolled_back` with the reason, then the exec argv is the same path. Likewise for a check timeout and for an exec `OSError`.
- [ ] A pin script failure, with the commit file still at the old sha, runs **no** `--rollback`, writes a `rolled_back` marker and execs.
- [ ] A failing `--rollback` raises `RepinError`.
- [ ] First start: a `trial` marker and a setup that raises (e.g. preflight `CliError`) → rollback and exec. With no marker, the error propagates as today.
- [ ] Confirm: a `trial` marker → one `runner-repin` `{old, new, sprint, outcome: "pinned", reason: ""}`, the marker deleted, nothing posted. A `rolled_back` marker → the event with its reason, one `update` note (`ROLLED_BACK_NOTE`), the marker deleted. A bad JSON marker counts as absent.
- [ ] Snapshot `run.runner_pin` is the commit file's sha, or `""` when there is none. The header shows `pin <sha7>` with the full sha in its title, and no pill when empty. `TIMELINE` renders both outcomes. The fixture rebuild leaves no drift.
- [ ] `pin-runner.sh` (shell test in a scratch repo, as s62's): a second pin leaves `runner-pin.prev` and `runner-pin.prev.commit` holding the first. `--rollback` restores them, leaves `.failed` and prints `rolled back to`. `--rollback` with no `.prev` fails with exit 1. Two arguments print the new usage with exit 2.

Stop reason (S1, S2):
- [ ] `notify_user(blocked, "Need the API key.\nmore")` stores `status_reason = "Need the API key."`.
- [ ] A quiet end stores `IDLE` with the hand-over's first line.
- [ ] `command_job`: exit 0 with `state.json` `{"status": "blocked", "status_reason": "x"}` gives DONE with reason `agile-team blocked: x`. With `done` and no reason, it gives `agile-team done`. With no file, the reason is `""`, as today.
- [ ] Exit 78 with a halt line in the tail gives FAILED `exit code 78; agile-team halted: <reason>`. Without a halt line but with a state file, it gives `exit code 78; agile-team checkout-changed…`. With neither, it gives just `exit code N`, as today. An offline failure is unchanged.

## Out of scope

- Re-pinning on a sprint end whose boundary is skipped (no remote): no full
  check ran, so there is nothing safe to pin.
- Detecting a broken pin that also breaks `failed_start` itself. `config check`
  has already imported the CLI and its modules. The human rolls back by hand
  with `pin-runner.sh --rollback` (self-hosting.md).
