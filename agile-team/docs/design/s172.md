# s172: A red story CI reaches the PO with the failing job, step and lines

ADR: [0090](../../../.team/adr/0090-story-ci-describes-failing-checks.md).
Requirements: REQ-196 (AC1), REQ-197 (AC2), REQ-198 (AC3).

## Rules

1. **Story CI describes failing checks.** `StoryCiPoll.read_checks` reads the
   head's checks as today and replaces each failing Actions check
   (`bucket in FAILING` and `job_of(link)` set) with
   `StoryCiPoll.describe(sha, check)`, which fills `step` (the job's first
   failed step) and `lines` (`failing_lines` of the job's failed log). Passing,
   skipped and cancelled checks, and failing checks with no Actions job, are
   not described. A failing check is described as soon as it is read, even
   while other checks are still pending (amended at design review: the cache
   in rule 3 makes this cost no more calls, and the lines are ready when the
   last check settles).
2. **The verdict is unchanged.** `describe` takes only `step` and `lines` from
   `ci.classify_check` and keeps the check's own `kind` (`None`), so
   `verdict_of` still reads the bucket. A story CI is red exactly when it was
   red before s172. Story CI does not get infra or stale triage here. (A job
   whose head is not the sha classifies as stale and so gets no `step`; its
   lines are still shown.)
3. **Once per (sha, check).** `StoryCiPoll` keeps the described checks in
   memory, keyed `(sha, check.link)`, for the life of the run. The link names
   one job run, so a key already seen makes no API call, and a re-run job (new
   link) is described again. `UpstreamError` from `prs.job` or
   `prs.failed_log` makes the whole read "no result" (`[]`), as `list_checks`
   failing does today. Nothing is cached for that read, so the next poll tries
   again. An empty log (`failed_log` returns `""`) is cached as it is. The
   60 s gate (`STORY_CI_POLL_S`) and the order in `claim_due` stay as they
   are.
4. **The lines travel with the result.** `StoryCi` gains
   `checks: list[str]`, the output of `check_lines_of`. It is saved in
   `state.json`, and an old file without the key loads with `[]`. The
   `story-ci` event data is `asdict(found)`, which has the same keys as today
   (`sha`, `verdict`, `source`, `checks`). A landing result keeps
   `checks == []`. A new result is recorded only when it differs from
   `story.ci`, so the same lines at the same sha emit nothing.
5. **The hand-over shows the sprint form.** `story_ci_red` carries
   `found.checks`, not `[found.verdict]` (today's bug). The row prints them one
   per line, as the sprint CI rows do: `- <label>: fail at step <step> <link>`,
   then each failing line indented by four spaces.
6. **Failing lines are picked by tier** (AC2, for every caller of
   `failing_lines`: sprint, landing and story CI). The first tier in
   `ci_findings.TIERS` with a hit wins, and its hits are shown in log order,
   without repeats, capped at `MAX_LINES`. With no hit in any tier, the last
   `TAIL_LINES` lines are shown, as today. The test tier comes first, so a
   pytest log shows its `FAILED` lines and not its traceback `path:line:`
   lines.
7. **The developer's brief.** A step whose role name starts with
   `developer` (the roles that fit `implement`) on a story whose `ci` is a
   red result with `checks` gets a `## Story CI` section. The section is
   shown while that is the latest result, not just once. Other roles, green
   results and results with no `checks` get no section; a landing result
   always has `checks == []` (rule 4), so it never shows one.

## Changes per module

### New `agile-team/runner/agile_team/ci_findings.py` (pure, no I/O)

Module docstring: "The lines of a failed CI step's log that name what failed
(s172), as a table of tiers."

```python
@dataclass(frozen=True)
class Finder:
    """One kind of finding line: the pattern that spots it and how it is shown."""
    pattern: re.Pattern[str]
    shown: str = "{line}"  # str.format over the match's named groups, {line}, {previous}

@dataclass(frozen=True)
class Tier:
    """Finders that belong together; the first tier with a hit is the one shown."""
    name: str
    finders: tuple[Finder, ...]

TEST_TIER = Tier("tests", (
    Finder(re.compile(r"\bFAILED\s+\S")),
    Finder(re.compile(r"\bERROR\s+\S+::")),
    Finder(re.compile(r"--- FAIL: ")),
    Finder(re.compile(r"(?<!Found )\b[1-9]\d* (?:failed|errors?)\b")),
))
LINT_TIER = Tier("findings", (
    Finder(re.compile(r"^::error file=(?P<file>[^,]+),line=(?P<line_no>\d+)[^:]*::(?P<message>.+)$"),
           "{file}:{line_no}: {message}"),
    Finder(re.compile(r"^##\[error\](?!Process completed with exit code)(?P<message>.+)$"),
           "{message}"),
    Finder(re.compile(r"^-->\s*(?P<at>\S+?:\d+(?::\d+)?)$"), "{at}: {previous}"),
    Finder(re.compile(r"^[^\s:]+:\d+(?::\d+)?: (?!warn)\S")),
    Finder(re.compile(r"^Would reformat: \S")),
))
TIERS: tuple[Tier, ...] = (TEST_TIER, LINT_TIER)

def render_hit(tier: Tier, pair: tuple[str, str]) -> str | None:
    """``pair`` is ``(previous, line)``: the line as the tier's first matching finder shows it."""

def find_tier_lines(tier: Tier, lines: list[str]) -> list[str]:
    """Every line the tier shows, in log order (``previous`` of the first line is "")."""

def pick_lines(lines: list[str]) -> list[str]:
    """The shown lines of the first tier with a hit; ``[]`` when no tier hits."""
```

Notes on the rows:

- The named group is `line_no`, not `line`, because `{line}` is the whole
  line in `shown`. `render_hit` formats with
  `finder.shown.format(**match.groupdict(), line=line, previous=previous)`.
  Use `pattern.search`, not `match`, so the test-tier rows hit anywhere in the
  line.
- The four test rows are today's `ci.FAILING_LINE`, except the count row now
  skips a count after `Found ` (ruff's and mypy's `Found 3 errors.`). Without
  that, a lint log would win the test tier on its summary line alone.
- The annotation rows: GitHub may keep a `::error file=…,line=…,title=…::msg`
  command in the raw log, or replace it with `##[error]msg`. Both are
  findings. `##[error]Process completed with exit code N.` appears in every
  failed step and is not a finding. `::warning` and `##[warning]` lines are
  not findings: house-rules prints hundreds of warnings, and none of them
  fails a step.
- The `-->` row joins ruff's default ("full") two-line form,
  `F401 [*] \`os\` imported but unused` followed by ` --> x.py:1:8`, into
  `x.py:1:8: F401 [*] \`os\` imported but unused`. `_plain` has already
  stripped the leading space.
- The `path:line:` row covers ruff's concise form and house-rules' text form
  (`path:line: fail rule: message`). It skips house-rules' `warn` lines
  (`Level.WARN == "warn"`).

### `agile-team/runner/agile_team/ci.py`

- Delete `FAILING_LINE`. Its rows live in `ci_findings.TEST_TIER`.
- `failing_lines(log: str) -> list[str]` keeps its signature and contract:
  ```python
  lines = [text for text in map(_plain, log.splitlines()) if text]
  hits = pick_lines(lines)
  return list(dict.fromkeys(hits))[:MAX_LINES] if hits else lines[-TAIL_LINES:]
  ```
  Import with `from .ci_findings import pick_lines`.
- `classify_check` and `_add_lines` are unchanged. (Amended at design review:
  no `describe_check` is added; story CI reuses `classify_check`, see
  `story_ci.py`.)

The module stays pure; the brief section lives in `dispatch.py`.

### `agile-team/runner/agile_team/story_ci.py`

Import `FAILING`, `classify_check` and `job_of` from `.ci`; `replace` from
`dataclasses`.

- `StoryCiPoll.__init__`: add `self._described: dict[tuple[str, str], Check] = {}`.
- `read_checks(self, story)`: same docstring contract (safe in a worker
  thread; a failing `gh` is `[]`). Inside the existing
  `try/except UpstreamError`:
  `[self.describe(story.pushed or "", c) for c in self.runtime.prs.list_checks(story.pushed)]`.
  The `except` now also covers `prs.job` and `prs.failed_log` raising.
- `describe(self, sha: str, check: Check) -> Check`: a check not in `FAILING`,
  or whose link has no Actions job (`job_of(check.link) is None`), is
  returned as it is. Otherwise the key is `(sha, check.link)`, filled with
  `read_failing_lines(check, sha)` when it is missing, and its value is
  returned.
- `read_failing_lines(self, check: Check, sha: str) -> Check`:
  `found = classify_check(self.runtime.prs, check, sha)`, then
  `replace(check, step=found.step, lines=found.lines)`. Only `step` and
  `lines` are taken, so `kind` stays `None` (rule 2).
- `_record`: `found = StoryCi(sha, str(verdict_of(checks)), "pr", check_lines_of(checks))`.
  Compare it with `story.ci` as today, then emit
  `Event(EventKind.STORY_CI, None, story.id, dict(found.__dict__))` (the same
  keys as `asdict`).
- `poll` and `settle` are unchanged: both get described checks through
  `read_checks`, and `settle` still records nothing while a check is pending.

### `agile-team/runner/agile_team/scheduler.py`

`queue_story_ci`: the report is
`{"story_ci": {"verdict": "red", "sha": found.sha, "checks": found.checks}}`.

### `agile-team/runner/agile_team/handover.py`

- `STORY_CI_RED` row text:
  `"{story}: CI failed on its PR at {ci_sha}:\n{ci_checks}\nNothing is held; the story lands only on green landing CI. Brief its developer if it needs a fix."`
- `_land_fields`: `"ci_checks": "\n".join(ci.get("checks") or []) if ci else None`.

### `agile-team/runner/agile_team/dispatch.py`

- Add a module function:
  ```python
  def render_story_ci(plan: Plan) -> str:
      """The failing checks, steps and lines of a developer's story whose PR CI is red."""
  ```
  `""` when `plan.story` is `None`, the role name does not start with
  `developer`, or `story.ci` is `None`, not `"red"` or has no `checks`.
  Otherwise `"## Story CI\n\nThe PR's CI failed at <sha>:\n"` followed by
  the check lines joined by newlines.
- `Runtime.user_prompt`: `parts.append(render_story_ci(plan))` after the
  Manager context and before the follow-up section.

## Not in this story

- Infra or stale triage of story CI verdicts (rule 2).
- Changing the CI workflows' output formats.
- The dashboard. It shows only the verdict pill, and the fixture's
  `story_ci` values are all `null`, so the snapshot contract is unchanged.

## Test checklist

`tests/test_ci_findings.py` (module tests) and `tests/test_s172_story_ci_lines.py`:

- [ ] AC2: a ruff full-format log (rule line, ` --> path:12:5`, snippet lines,
      `Found 1 error.`) gives `["path:12:5: E501 Line too long (101 > 100)"]`.
      It does not give the tail, and `Found 1 error.` is not a hit.
- [ ] AC2: a ruff concise log `a.py:3:1: F401 …` gives that line.
- [ ] AC2: `Would reformat: a.py` with `1 file would be reformatted` gives only
      the `Would reformat` line.
- [ ] AC2: a house-rules github log with one `::error file=a.py,line=7,title=house-rules naming::\`compile_pattern\` should start with a verb`,
      30 `::warning …` lines, the summary line and `##[error]Process completed with exit code 1.`
      gives `["a.py:7: \`compile_pattern\` should start with a verb"]`.
- [ ] AC2: the `##[error]<message>` form gives `<message>`, and the
      `Process completed` line alone gives no hit.
- [ ] AC2: a house-rules text log keeps `fail` lines and drops `warn` lines.
- [ ] AC2: a pytest log with traceback lines `tests/x.py:12: AssertionError`
      and `FAILED tests/x.py::test_y` gives the `FAILED` and count lines,
      not the traceback.
- [ ] `test_s81_ci.py`'s `failing_lines` tests still pass unchanged (order,
      cap, tail, empty).
- [ ] `StoryCiPoll.describe`: a failing Actions check gets `step` and `lines`
      with `kind is None`. A passing check or one with a non-Actions link is
      returned as it is, with no `prs` call.
- [ ] AC1: a red story PR with a failing Actions check: the `story-ci` event
      `checks` is `["- ci / unit: fail at step Run tests <link>", "    FAILED tests/x.py::test_y"]`
      and `story.ci.checks` equals it.
- [ ] AC1: the queued `story_ci_red` pass's lines contain the check line and
      the indented failing line on their own lines (the sprint form), not the
      word `red` as the checks.
- [ ] Budget: two polls 60 s apart at the same sha with the same failing link
      make one `job` call and one `failed_log` call in total, and the second
      poll records nothing. A new link (re-run) is described again.
- [ ] A pending check among them: nothing recorded. The failing check is
      fetched once, and the poll after the pending check settles records red
      with no further fetch.
- [ ] `prs.job` or `prs.failed_log` raising `UpstreamError`: `read_checks` is
      `[]`, and the next poll describes the check again.
- [ ] Rule 2: an untriaged failing check still gives verdict `"red"`.
- [ ] `state.json` round trip keeps `StoryCi.checks`, and an old `ci` without
      `checks` loads with `[]`.
- [ ] AC3: `render_story_ci` gives `""` for no story, `ci` `None`, green, and
      a red result with no checks. For a developer on a red result with checks
      it starts with `## Story CI`, names the sha and holds every check line.
- [ ] AC3: the `developer-cli` user prompt for a story whose `ci` is red holds
      the `## Story CI` section. A non-developer role's prompt (e.g.
      `unit-tester`) and a green story's developer prompt don't.
