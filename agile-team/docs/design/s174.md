# s174 design: commands the runner runs itself don't see the runner's venv

ADR: [0091](../../../.team/adr/0091-one-module-hides-the-runner-venv.md).
Requirements: REQ-199 (AC1), REQ-200 (AC2). Developer: `developer-cli`.

## Cause

`CommandShell._watched` (`commands.py:114`) builds every command's environment from
`system.environ()` whole, and so does `tally_watch.watching` (`tally_watch.py:95`).
The runner is started by `uv run --project agile-team/runner`, so that environment holds
`VIRTUAL_ENV=<runner>/.venv` and a `PATH` that starts with `<runner>/.venv/bin`. A gate's
`uv run …` then warns "VIRTUAL_ENV does not match", and a bare `pytest` or `ruff` finds
the runner's copy. Roles have been spared since #55.7 (`dispatch.hide_runner_venv`); gate
commands were not.

The commands s174 covers all go through `CommandShell`: the gate's test, coverage and
named-test commands, the stop checks' fixers and lint, the house-rules gate and the
sprint boundary's full check (all reach it through `commands.shell_runner`, from
`cli.py:379`, `cli.py:419` and `dispatch.Runtime.shell`). So fixing `CommandShell` and
`tally_watch.watching` covers all of them. `system.run` callers (git, gh, ps, the
re-pin) are not configured commands and stay as they are.

**Out of scope.** The acceptance environments' `prepare`/`start` commands build their
environment in `sandbox.sandbox_env` and still inherit the runner's `VIRTUAL_ENV`. They
are not in s174's ACs; the PO asked the liaison for a Product Backlog follow-up story
(code review F1, non-blocking).

## Rules

| # | Rule | AC |
|---|------|----|
| R1 | **One module owns the rule.** `hide_runner_venv` moves from `dispatch.py` to a new module `agile_team/runner_venv.py`, unchanged in behaviour. `dispatch.py` imports it from there, so `dispatch.hide_runner_venv` still names it. `commands.py` and `tally_watch.py` import the module; neither imports `dispatch` (which imports `commands`). | AC2 |
| R2 | **The rule.** The runner's venv is the `VIRTUAL_ENV` of the runner process. When it is set, every `PATH` directory whose parent is that venv (`bin`, or `Scripts` on Windows) is dropped; all other directories stay, in order. When it is unset or empty nothing changes. Roles and commands use the same function for this (`strip_venv_bin`). | AC1, AC2 |
| R3 | **Commands lose `VIRTUAL_ENV` entirely.** A command's environment is built whole by the runner, so `VIRTUAL_ENV` is removed from it, not blanked: `env \| sort` shows no `VIRTUAL_ENV` line. Roles keep `VIRTUAL_ENV=""` because the SDK only adds to the inherited environment (#55). | AC1 |
| R4 | **Everything else is the runner's.** Every other variable (`HOME`, `AGILE_TEAM_HOME`, the remaining `PATH`, anything the human exported) reaches the command unchanged. The runner still adds `COVERAGE_FILE` (s60) and, inside an open stage, the tally plugin's `PYTHONPATH`, `PYTEST_PLUGINS` and `AGILE_TEAM_TALLY` (s118) on top. The config has no `[env]` table today; a variable the human sets for the run reaches the command because R4 passes it through. | AC2 |
| R5 | **Both paths.** The plain run, the tally run and the retry without the plugin all start from `get_command_environ()`. | AC1 |

As built, `get_command_environ` doesn't go through `hide_runner_venv` and then drop the
blanked key: it copies the environment without `VIRTUAL_ENV` and applies
`strip_venv_bin` itself. The result is the same, and the shared rule is still the one
function `strip_venv_bin` (design review, s174).

`strip_venv_bin` splits on `os.pathsep`, keeps `d` when `Path(d).parent != Path(venv)` and
joins on `os.pathsep`: the filter `hide_runner_venv` has today, given a name.

### `dispatch.py`

- Delete `VENV_VAR` and the body of `hide_runner_venv`; add
  `from .runner_venv import hide_runner_venv`. `build_options` is unchanged.
- Drop `os` and `Path` imports only if nothing else in the module uses them (ruff tells).

### `commands.py`

- `from . import runner_venv, stages, system, tally_watch`.
- `CommandShell._watched`: `plain = self._build_shell(command, runner_venv.get_command_environ())`.
  Nothing else changes; `_build_shell` still adds `COVERAGE_FILE`.

### `tally_watch.py`

- `from . import runner_venv, stages, system`.
- `watching(run)` keeps its signature and yields
  `plugin_env(runner_venv.get_command_environ(), path)`.

## Test checklist

Unit tests use `FakeSystem` (`fake.env = {...}`), as `test_dispatch.py:61` does.

`tests/test_runner_venv.py`:
- [ ] `strip_venv_bin("/r/.venv/bin:/p/.venv/bin:/bin", "/r/.venv") == "/p/.venv/bin:/bin"`;
      a `Scripts` dir under the venv is dropped too; a path with no venv dir is unchanged (R2).
- [ ] `hide_runner_venv` keeps the cases `test_dispatch.py:69-74` pins (launch PATH kept,
      other venvs kept, no venv → unchanged); the dispatch tests stay as they are (R1).
- [ ] `get_command_environ()` with `fake.env = {"VIRTUAL_ENV": "/r/.venv", "PATH":
      "/r/.venv/bin:/usr/bin", "HOME": "/h", "K": "v"}` is exactly
      `{"PATH": "/usr/bin", "HOME": "/h", "K": "v"}` (R2, R3, R4).
- [ ] With no `VIRTUAL_ENV` in `fake.env`, `get_command_environ()` equals `fake.env` (R2).
- [ ] With `VIRTUAL_ENV=""`, the key is gone and `PATH` is unchanged (R2, R3).

`tests/test_s118_tally_watch.py` (where `CommandShell`'s environment is already pinned,
lines 190-237; `fake.commands[i].env` is what reached the spawn):
- [ ] A command run with no open stage gets the spawn env without `VIRTUAL_ENV`, with the
      runner venv's `bin` gone from `PATH`, with `HOME` and other keys kept and with
      `COVERAGE_FILE` set (R3, R4, R5).
- [ ] Inside an open stage, both the tally run and the retry after `plugin_failed` get the
      same filtered base (R5).
- [ ] `watching(run)` yields an env without `VIRTUAL_ENV` and without the venv's `bin`,
      with the plugin entries added (R4, R5).

By hand (AC1, the Proxy or the liaison): in a scratch repo whose `[gates]` test command is
`env | sort`, run a gate from `uv run --project agile-team/runner`; the gate output has no
`VIRTUAL_ENV=` line and no `<runner>/.venv/bin` in `PATH`. With the test command
`uv run python -c pass` there is no "VIRTUAL_ENV does not match" warning.
