# s108 design: the review stack after a merge

Story: `.team/stories/s108.md`. Developer: `developer-cli`. No new ADR: this
extends s29 (review stack), s59 (merged entries dropped at sync) and s81 (CI
stage). No new dependency.

## The bug

Today only the bottom PR is ready, and every other PR is a draft based on the
branch below. When the human merges the bottom PR, the next PR stays based on
the merged branch until the next sprint boundary rebuilds the stack. If GitHub
retargets it to `main` on its own, its diff still shows the merged sprint's
old commits. The human can't merge it without fixing it by hand. While the
runner waits on CI (up to 30 min, and again after a `ci_pending` continue),
it doesn't notice the merge at all.

## Rules

- **M1 (AC1). Every PR is ready.** `_spec` gives every entry `PrMode.READY`.
  The base chain stays the same: the bottom is based on `[upstream] branch`,
  and each other entry is based on the branch below it. An open draft PR is
  made ready by the next push (`GhPrs.edit` already runs `gh pr ready`).
  `PrMode.DRAFT` stays in the enum so that an old `state.json` still loads.
  `GhPrs.edit` is unchanged.
- **M2. When a merge is followed.** The runner follows merges at two points:
  (a) in the **sync** stage on both edges, right after `remote.missing()`
  (the fetch) and before `_drop_merged`; (b) in the **ci** stage, once
  before the watch and once after it, before the verdict. It follows only
  when `upstream.push is Permission.YES` and `prs.missing() is None`.
  Otherwise the outcome is `NONE` and no `gh` lookup is made.
- **M3. What counts as merged.** These are the **leading** stack entries
  (bottom first, read lazily, stopping at the first that fails) whose `pr`
  is set and for which `prs.find(entry.branch)` returns a PR with the
  **same number** and `PrState.MERGED`. A merged entry above an unmerged one
  is not followed (see Known limits).
- **M4. Fetch first.** When at least one entry is merged, the runner fetches
  again (`remote.missing()`). If that returns a reason, it raises
  `UpstreamError(reason)`, and `_step` holds the boundary `error`.
- **M5. Drop.** Each merged entry leaves the stack through the existing
  `_drop` (`merged` event, `MERGED_NOTE`). At the START edge, dropping sets
  `b.restack = True`, as `_drop_merged` already does.
- **M6. Fast rebase, all or nothing (AC2).** In the review worktree
  (`rebuilder.prepare()` first), the remaining entries are rebased bottom
  first. The first entry is rebased with `onto` = the target
  (`<remote>/<branch>`) and `upstream` = the head of the top merged entry.
  Each later entry is rebased with `onto` = the new head of the entry below
  and `upstream` = that entry's old head. Each rebase is checked:
  - The rebase stops (any non-zero exit): it is aborted, and the plan is
    refused with `REBASE_STOPPED`.
  - The tree changed (`new^{tree} != old head^{tree}`): the plan is refused
    with `TREE_CHANGED`.

  No branch ref moves and nothing is pushed until every entry has passed.
  The tree is the same exactly when the target holds the merged PR and
  nothing else since the stack was built, which is the usual case for any
  merge method.
- **M7. Apply.** When every entry passes:
  1. For each remaining entry, bottom first, `entry.checked` becomes the new
     head if it was the old head (the same tree passes the same checks). Then
     `rebuilder.point(entry, new)` sets the branch and `entry.head`.
  2. `_push_stack(b)` runs. It is the loop of today's `_push_all`: each
     entry is pushed with `--force-with-lease` against `entry.pushed`, and
     then `_pr(entry, below)` runs. That makes the new bottom based on
     `[upstream] branch` and ready, and keeps the others on the branch
     below, ready (AC2 retarget).
  3. A `restacked` event is logged (`branches`: the moved branches). If any
     branch moved, the runner posts the `RESTACKED_UPDATE` update.
- **M8. Refused fast path.** A `rebuild` event is logged (`note`: the
  refusal). In the sync stage nothing else happens: the END edge always
  rebuilds, and M5 set `restack` at START. In the ci stage, `b.stage =
  Stage.REVIEW`, so the stack is rebuilt from the team branch, checked,
  pushed and retargeted, and its CI is watched again.
- **M9. Push rejected while following.** `_push_stack` holds
  `push_rejected` (`branch`, `reason`), exactly as `_push_all` does today. In
  the ci stage it also sets `b.stage = Stage.PUSH`, so `continue_boundary`
  pushes again and never re-watches a stale PR. In the sync stage, the stage
  stops and reruns on continue.
- **M10. CI after a follow.** If the follow is `RESTACKED`, the stage stays
  `ci`, and the next router tick runs it again on the new heads. Results
  from a watch that is followed by a merge are thrown away (the follow
  decides). If the stack is empty when `_ci` starts, the boundary finishes
  with `NOTHING_REPORT` (every sprint is in main).
- **M11 (AC3). Every PR is watched.** `_watched` is unchanged (READY entries
  with a PR), so with M1 it covers the whole stack apart from closed PRs.
  The verdict rule is unchanged: green only when every watched PR is green
  (`ci.overall`, `PR_ORDER`). A PR with no checks makes the whole verdict
  `none`, which is never "ready".
- **M12 (AC3). Over 100 commits.** `_push_entry` stores `entry.commits =
  rebuilder.count(base, entry.head)`, where `base` is `below.head`, or the
  target for the bottom. Every report that lists the stack's PRs
  (`PUSHED_REPORT`, `RESTACKED_UPDATE`, the green report and
  `CI_NONE_REPORT`) gets one `BIG_PR_NOTE` line per entry with `commits >
  REBASE_MERGE_LIMIT` (100), after the text, joined with `"\n"`.
- **M13. Ordering.** `NONE`, `RESTACKED`, `REBUILD` and `REJECTED` map to
  what each stage does next through the `AFTER_FOLLOW` table, not through
  `if` chains.

## Texts (exact)

`boundary.py`:

```python
REBASE_MERGE_LIMIT = 100
BIG_PR_NOTE = (
    'PR #{pr} ({branch}) has {commits} commits, more than the {limit} GitHub allows for '
    '"Rebase and merge". When it is the bottom of the stack, merge it by fast-forward: '
    "git fetch {remote} && git push {remote} {remote}/{branch}:{target}"
)
RESTACKED_UPDATE = (
    "Merged into {target}: {merged}. The PRs above were rebased onto it with the same tree "
    "and pushed: {prs}. The bottom one is now based on {target}; nothing is called ready "
    "before CI passes."
)
PUSHED_REPORT = (
    "Sprint {sprint}'s review branches are pushed: {prs}. The runner now waits for CI on "
    "every PR of the stack; nothing is called ready before CI passes on all of them."
)
```

`merged` is the dropped entries as `#12 (team/sprint-9)`, joined by `, `.
`prs` is the moved entries as `#13 (team/sprint-10) <url>`, joined by `; `.
`{target}` in `RESTACKED_UPDATE` is `[upstream] branch`. In `BIG_PR_NOTE`,
`{remote}` is `[upstream] remote` and `{target}` is `[upstream] branch`.

`ci.py`: `NO_OPEN_PR_WHY = "no open pull request to watch"` (drafts are
gone).

`restack.py`:

```python
REBASE_STOPPED = "{branch} did not rebase cleanly onto {onto}"
TREE_CHANGED = "{branch} rebased onto {onto} has a different tree"
```

Here `{onto}` is the target ref name for the first entry and the new head
(12 chars) of the entry below for the others.

## Changes per module

### `agile_team/boundary.py`

- `BoundaryOutcome` gains `RESTACKED = "restacked"` and `REBUILD = "rebuild"`.
- `StackEntry` gains `commits: int = 0`, after `ci`. Old state loads with 0.
- The texts above, and `PUSHED_REPORT` reworded.
- `def big_pr_notes(stack: list[StackEntry], upstream: UpstreamSettings) -> list[str]`
  returns one formatted `BIG_PR_NOTE` per entry with `commits >
  REBASE_MERGE_LIMIT`, in stack order. Import `UpstreamSettings` from
  `.config` under `TYPE_CHECKING` only.

### `agile_team/stack.py`

- `@dataclass(frozen=True) class Move` with `onto: str` and `upstream: str`.
  Its docstring: "replay `upstream..head` onto `onto`".
- `Rebuilder.rebase(self, head: str, move: Move) -> str | None` runs
  `checkout --detach --force head`, then `upstream.REBASE_ARGV` plus
  `--onto move.onto move.upstream` in the worktree. On a non-zero exit it
  runs `rebase --abort` and returns `None`. Otherwise it returns
  `self.wt.head()`. Import `REBASE_ARGV` from `.upstream`; that makes no
  cycle, because `upstream` doesn't import `stack`.
- `Rebuilder.same_tree(self, a: str, b: str) -> bool` runs
  `rev-parse a^{tree} b^{tree}` and compares the two lines.
- `Rebuilder.count(self, base: str, head: str) -> int` runs `rev-list
  --count base..head`.
- `Rebuilder.point(self, entry: StackEntry, sha: str) -> None` runs `branch
  --force entry.branch sha` in the worktree and sets `entry.head = sha`.
  `build` uses it in place of its own two lines (DRY).

### `agile_team/restack.py` (new, about 80 lines)

The module docstring says it follows merged stack PRs: it finds them and
plans the fast rebase of the PRs above them. It does no pushing.

```python
class FollowOutcome(StrEnum):
    NONE = "none"; RESTACKED = "restacked"; REBUILD = "rebuild"; REJECTED = "rejected"

@dataclass(frozen=True)
class Plan:
    """New heads for the entries above a merge, bottom first, or why the fast path was refused."""
    heads: list[str] = field(default_factory=list)
    refused: str = ""

@dataclass
class Restacker:
    prs: Prs
    rebuilder: Rebuilder
    def merged(self, stack: list[StackEntry]) -> list[StackEntry]: ...   # M3, lazy (takewhile)
    def plan(self, rest: list[StackEntry], top: StackEntry) -> Plan: ... # M6; top = last merged
```

`plan` calls `rebuilder.prepare()` first. With an empty `rest`, it returns
`Plan()`. Split the chain loop into helpers of at most 8 lines each (for
example `_next(entry, move) -> tuple[str, str]`, which returns the new head
and the refusal).

### `agile_team/boundary_runner.py`

- `restacker: Restacker = field(init=False)` is set in `__post_init__`
  (`Restacker(rt.prs, self.rebuilder)`).
- `_follow(self, b) -> FollowOutcome` covers M2–M8. It runs the guard (M2),
  finds the merged entries, returns `NONE` when there are none, fetches
  (M4), drops (M5), plans, and applies through `_apply(b, plan)`. Keep each
  function short (`_follows() -> bool`, `_fetch()`, `_apply`, `_move(entry,
  head)`, `_restacked(b, moved)`).
- `_push_stack(self, b) -> bool` is the loop taken out of `_push_all`. It
  returns `False` after it holds `push_rejected`. `_push_all` becomes `if
  self._push_stack(b): self._pushed(b)`.
- `_sync`: after `self.mine.team_branch = …`, it returns when
  `AFTER_FOLLOW` says to stop (`REJECTED`). Otherwise it goes on to
  `_drop_merged` and `SYNCS`.
- `_ci`: an empty stack means `_finish(b, NOTHING_REPORT…)` (M10). Then it
  calls `self._followed(b)` before the watch and again after it, and
  returns at once if either one followed. `_followed(b) -> bool` applies
  `CI_AFTER_FOLLOW[outcome]` and returns `outcome is not NONE`.
- `CI_AFTER_FOLLOW` is a module table mapping `NONE` and `RESTACKED` to a
  no-op, `REBUILD` to set `stage = REVIEW`, and `REJECTED` to set `stage =
  PUSH`. `SYNC_STOPS = frozenset({FollowOutcome.REJECTED})`.
- `_spec`: the mode is always `PrMode.READY` (M1).
- `_push_entry` sets `entry.commits` (M12) after a successful push (or
  when no push was needed), before `_pr`.
- `_with_big(self, text: str) -> str` appends `big_pr_notes(self.stack,
  self.runtime.config.upstream)`. It is used by `_pushed`, `_ci_green`,
  `_ci_none` and the `RESTACKED_UPDATE` post. The report saved by `_finish`
  is the same text.

### `agile_team/dashboard/index.html`

- The boundary outcome tone table (line ~1264) gains `restacked: "good"`
  and `rebuild: "warning"`. Snapshot: no change (`_stack_entry` lists its
  keys, and `commits` isn't shown).

### Unchanged

`upstream.py` (except that `stack` now imports `REBASE_ARGV` from it),
`ci.py` (except `NO_OPEN_PR_WHY`), `stages.py` (the follow runs inside
`boundary.sync` and `boundary.ci`, and its commands are noted there),

already run on `pull_request` to any base and don't skip drafts.

## Test checklist (AC4)

Use a scratch bare remote and a clone (the existing s29/s59 git fixtures)
and `tests/s29_helpers.FakePrs` (`set_state(branch, PrState.MERGED)`). To
simulate "Rebase and merge", replay the sprint branch's commits onto the
remote's `main` in a second clone with a new committer date, then push
`main`.

1. M1: every created PR has `PrMode.READY`. The bottom is based on `main`,
   and each other PR on the branch below it. A draft PR found open is
   edited to ready. **Tests that assert a draft for stacked PRs must
   change** (AC1 makes them wrong).
2. `Rebuilder.rebase`: N rebased onto the rebase-merged main gives a new
   head whose parent chain is on `origin/main`, and `same_tree(new, old)`
   is true.
3. `Rebuilder.rebase` on a conflict returns `None`, and the worktree has no
   rebase in progress (`rev-parse -q --verify REBASE_HEAD` fails).
4. Main has an extra commit after the merge: the plan is refused with
   `TREE_CHANGED`. No remote ref moved and no `edit` call was made. A
   `rebuild` event is logged, and at ci `b.stage is Stage.REVIEW`.
5. `Restacker.merged`: `[MERGED, OPEN, MERGED]` gives the first entry only.
   A different PR number isn't merged. An entry without a `pr` stops the
   scan. Lookups stop at the first entry that isn't merged (count the
   `find` calls).
6. CI stage, three-PR stack, bottom merged by rebase (AC2/AC4):
   - a `merged` event, and the entry is dropped;
   - sprint-10's remote ref equals its new head, pushed with a lease
     against the old `pushed`;
   - its PR is based on `main` and isn't a draft;
   - sprint-11 is rebased onto sprint-10's new head, with the same tree,
     pushed, and still based on `team/sprint-10`;
   - a `restacked` event, the `RESTACKED_UPDATE` post, and the stage is
     still `ci`.

   The next `step()` watches both remaining PRs, and green finishes the
   boundary.
7. No PR is left on a merged base: after 6, no open `FakePrs` PR has a
   base among the dropped branches.
8. Merge found before the watch (after a `ci_pending` continue): there is
   no `wait_checks` call before the follow.
9. Merge found after the watch: the verdict isn't applied (no `done`), and
   the stage is still `ci`.
10. Sync stage, START edge: the follow runs and `restack` is true. On the
    END edge the follow runs before the entry is added.
11. A rejected push while following at ci holds `push_rejected` and sets
    `b.stage is Stage.PUSH`.
12. `checked` carries over to the new head only when it equalled the old
    head.
13. `entry.commits`: the bottom counts against the target, and the others
    against `below.head`. `big_pr_notes`: 100 gives no note. 101 gives the
    exact line ending `git fetch origin && git push origin
    origin/team/sprint-9:main`. The line is appended to the pushed,
    restacked, green and none texts.
14. `_ci` with an empty stack finishes with `NOTHING_REPORT`.
15. The follow is skipped (no `find` call) when `push` isn't `yes` or
    `prs.missing()` returns a reason.
16. A failed fetch while following holds `error`.
17. AC3: with three ready PRs, all three are watched. One `none` makes the
    overall verdict `none`, never green.

Coverage stays at 100%, and ruff is clean.

## Known limits

- At a boundary, the stack is pushed twice (fast path, then rebuild), so
  CI runs twice on those PRs. The first push keeps the window short in
  which a PR sits on a merged base.
- A merge made after the boundary closed (green finishes it) is followed at
  the next boundary, not at once. There is no between-boundary watch.
- A PR merged above an unmerged one (merged into the branch below, not into
  main) isn't followed. The next push of the lower branch is refused by
  its lease (`push_rejected`), and the human is told.
- A dependent PR that GitHub closed because its base branch was deleted
  (not auto-retargeted) stays `closed` (`_leave`). It can't be reopened.
- The PR body's "Stacked on …" line isn't rewritten when a PR becomes the
  bottom (`edit` changes only the base and the ready state).
