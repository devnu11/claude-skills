# s108 design: the review stack after a merge

Story: `.team/stories/s108.md`. Developer: `developer-cli`. No new dependency.
This extends s29 (review stack) and s81 (CI stage). It **moves s59's team
branch rebase from the sprint start to the sprint end** (AC2, the human's
rule in t58, confirmed by m118 option b). The sprint-start sync only fetches
and reports that main moved (AC5). ADR-0041's "rebase at sprint start" is
superseded; the architect amends the ADR (AC6, "Who moves what"; s114
retired the Scribe).

## The bug

Today only the bottom PR is ready, and every other PR is a draft based on the
branch below. When the human merges the bottom PR, the next PR stays based on
the merged branch, and if GitHub retargets it to `main` its diff still shows
the merged sprint's old commits. The human can't merge it without fixing it
by hand.

## The human's rule (AC2)

The team rebases onto main **at sprint end only**. A merge made mid-sprint,
or found at a sprint start, changes nothing until the sprint ends. At sprint
end, in this order:

1. push the sprint's review branch;
2. rebase the team branch onto main;
3. bottom up, bring each unmerged parent PR up to date: rebase, check the
   tree is unchanged, push with `--force-with-lease`, retarget to main (the
   bottom) or to its parent. A parent found merged is dropped, and the PR
   above it is retargeted;
4. update the sprint's own PR the same way.

## Rules

- **M1 (AC1). Every PR is ready.** `_spec` gives every entry `PrMode.READY`.
  The base chain stays the same: the bottom is based on `[upstream] branch`,
  and each other entry on the branch below it. An open draft PR is made ready
  by its next `_pr` (`GhPrs.edit` already runs `gh pr ready`). `PrMode.DRAFT`
  stays in the enum so an old `state.json` still loads. `GhPrs.edit` is
  unchanged.
- **M2 (AC2). Stages.** `Stage` gains `REBASE = "rebase"` and `RESTACK =
  "restack"`, between `PUSH` and `CI`:
  `STAGES = (SYNC, CHECK, REVIEW, PUSH, REBASE, RESTACK, CI)`.
  At the END edge every stage runs, in that order. Steps 1–4 above are
  PUSH (1), REBASE (2) and RESTACK (3 and 4).
- **M3 (AC2, AC5). The START edge rebases nothing; it reports.** At START,
  `_sync` fetches (`remote.missing()`, unchanged) and records the team
  branch, then `_start_sync` counts how far the target moved past the team
  branch, `behind = self.remote.behind()` (M3a), and emits `pass` with
  `note = START_NOTES[behind > 0].format(target=..., count=behind)` and
  `behind=behind` in the event data, then advances. HEAD, the team branch
  ref, every recorded hash (story commits, `checkout`, stack entries) and
  `b.sync_from` are left as they are: no `rebase`, `reset`, `merge` or
  `checkout` git command runs. CHECK runs (it checks the team branch the last
  END rebased). `next_stage` skips `END_ONLY = {REVIEW, PUSH, REBASE,
  RESTACK, CI}` at START, always (`b.restack` no longer matters there). No
  stack entry is dropped, rebased, pushed or retargeted, and no `gh` lookup
  is made. A moved target waits for the next sprint end (or a pull the human
  makes by hand; no tool for a mid-sprint pull is in this story).
- **M3a (AC5). `Upstream.behind(self) -> int`.** `git rev-list --count
  HEAD..<target>`, stripped, `int(... or 0)`. Called only after `missing()`
  returned `None`, so the target exists and is fetched.
- **M4 (AC2). Mid-sprint, nothing happens.** With no boundary open, `due()`
  is `None`; nothing reads the stack or calls `gh`. A merge made mid-sprint
  is seen at the next END's RESTACK.
- **M5. SYNC at END.** Unchanged apart from the removals: it fetches,
  records the team branch and adds the sprint's entry (`_end_sync`). It does
  not follow merges and does not drop entries (`_drop_merged` is deleted).
- **M6. REVIEW builds the sprint's own entry.** `_review` builds the entries
  from index `first` up, each on the head of the entry below (the target for
  index 0). `first` is `0` when `b.restack` is set (the fallback, M12), else
  the top's index when the top is this sprint's entry (`top.sprint ==
  b.sprint`), else `len(stack)` (nothing to build). Parents keep their heads.
  `_build_one`'s drop (no picks, or head equals base) and `_check_ends` are
  unchanged.
- **M7 (step 1). PUSH pushes the sprint's review branch only.** The order of
  today's checks stays: empty stack → `pass` (note `NOTHING_TO_PUSH`) and
  advance (no finish: REBASE still runs); gh missing or permission `no` →
  `local` event (note: why, `ci`: `none`) and advance; permission unasked →
  `push_permission` hold. Otherwise, when the top is this sprint's entry and
  `pushed != head`, its branch is pushed with `--force-with-lease` against
  `pushed` (`_push_branch`). No PR is created or edited here. A refusal holds
  `push_rejected` (M13). Then `pass` (note: `pushed {branch}`) and advance.
- **M8 (step 2). REBASE rebases the team branch.** It fetches (a reason
  raises `UpstreamError`, which holds `error`), then runs today's s59 rebase:
  pin `sync_from`, `remote.rebase_onto(sync_from)`, `AFTER_REBASE`. A
  conflict holds `sync_conflict` (the stage stays `rebase`; continue reruns
  it). `_settle_rebase` no longer calls `_drop_merged`. After `rebased` or
  `current`, `b.sync_from` is cleared (and saved), so a second pass after the
  fallback pins afresh.
- **M9 (step 3). Merged parents.** RESTACK first finds the **leading** stack
  entries (bottom first, read lazily, stopping at the first that fails) whose
  `pr` is set and for which `prs.find(entry.branch)` returns a PR with the
  **same number** and `PrState.MERGED`. It looks only when the boundary
  delivers (`_local_why()` is empty; M15). When one is found it fetches again
  (a reason raises `UpstreamError`), then drops each through `_drop`
  (`merged` event, `MERGED_NOTE`).
- **M10 (steps 3–4). Fast rebase, all or nothing.** In the review worktree
  (`rebuilder.prepare()` first), every remaining entry is rebased, bottom
  first, the sprint's own entry last. The first is rebased with `onto` = the
  target and `upstream` = `below`: the old head of the last dropped entry, or,
  when none was dropped, `rebuilder.merge_base(first.head)`. Each later entry
  is rebased with `onto` = the new head of the entry below and `upstream` =
  that entry's old head. Each rebase is checked:
  - it stops (non-zero exit): aborted, the plan is refused with
    `REBASE_STOPPED`;
  - the tree changed (`new^{tree} != old head^{tree}`): refused with
    `TREE_CHANGED`.

  No branch ref moves and nothing is pushed until every entry has passed. The
  tree is the same exactly when the target gained only merged stack PRs since
  the stack was built. With nothing merged and the target unmoved, every
  rebase is a no-op (new head = old head).
- **M11. Apply.** When every entry passes, bottom first: an entry with no
  commits left (`rebuilder.count(onto, new) == 0`, listed in `Plan.emptied`)
  is dropped through `_drop` (its content is in the target, e.g. a local or
  squash merge). Every other entry gets `checked = new` if `checked` was the
  old head, then `rebuilder.point(entry, new)`. A `restacked` event is
  emitted (`branches`: the entries whose planned head differs from their old
  head, computed before the drops, so an emptied entry may be named; its
  `merged` event comes first). Then `_deliver(b)`. If the drops left the
  stack empty, it only advances (CI then finishes with `NOTHING_REPORT`,
  M14). Otherwise:
  - delivering: `_push_stack(b)`. Each entry, bottom first, is pushed with
    `--force-with-lease` against `pushed` when `pushed != head`, gets
    `commits` (M17), and runs `_pr(entry, below)`, which creates or edits its
    PR: the bottom based on `[upstream] branch`, the others on the branch
    below, all ready. A PR whose parent was dropped is retargeted here. When
    every push passed, `_pushed(b)` posts `PUSHED_REPORT` (with `_with_big`)
    as a PO update and advances to CI. It logs **no event**: the RESTACK
    stage's last outcome is `restacked`. `Out.PUSHED` stays in the enum so
    old `events.jsonl` lines still read, but nothing emits it;
  - local (M15): `LOCAL_REPORT` is posted and the boundary finishes with it.
- **M12. Refused plan (fallback).** A `rebuild` event is logged (`note`: the
  refusal), `b.restack = True` and `b.stage = Stage.REVIEW`. REVIEW then
  rebuilds the whole stack from the (rebased) team branch and checks its
  ends, PUSH pushes the sprint's branch, REBASE finds the team branch
  `current`, and RESTACK runs again on trees built on the target, so it
  passes unless the target moved again. The changed trees are checked by
  `_check_ends`, never pushed unchecked.
- **M13. Push rejected.** At PUSH or RESTACK, a refused push holds
  `push_rejected` (`branch`, `reason`), and the stage stays. Nothing after it
  is pushed. `continue_boundary` reruns the stage. A RESTACK rerun is safe:
  heads already moved rebase as no-ops.
- **M14. CI.** No merge is followed at CI (`_followed` is deleted). An empty
  stack finishes with `NOTHING_REPORT` (every sprint is in main). Otherwise
  today's watch and verdict.
- **M15. Local delivery.** `_local_why() -> str` is `prs.missing()`, else
  `NOT_PERMITTED` when `push is not Permission.YES`, else `""`. Local
  boundaries still rebase the team branch (M8) and fast-rebase the review
  branches locally (M10–M11); nothing is pushed and `gh` is never called.
- **M16 (AC3). Every PR is watched.** `_watched` is unchanged (READY entries
  with a PR), so with M1 it covers the whole stack apart from closed PRs. The
  verdict rule is unchanged: green only when every watched PR is green
  (`ci.overall`, `PR_ORDER`). A PR with no checks makes the verdict `none`,
  which is never "ready".
- **M17 (AC3). Over 100 commits.** `_push_entry` stores `entry.commits =
  rebuilder.count(base, entry.head)`, where `base` is `below.head`, or the
  target for the bottom. `PUSHED_REPORT`, the green report and
  `CI_NONE_REPORT` get one `BIG_PR_NOTE` line per entry with `commits >
  REBASE_MERGE_LIMIT` (100), after the text, joined with `"\n"`
  (`_with_big`).
- **M18. Data, not branches.** `next_stage` uses `END_ONLY`; the edge's sync
  uses `SYNCS`; the rebase result uses `AFTER_REBASE`; the CI verdict uses
  `CI_OUTCOMES`. `FollowOutcome`, `CI_AFTER_FOLLOW`, `SYNC_STOPS`, `_stay`,
  `_to_review`, `_to_push` and `RESTACKED_UPDATE` are deleted.

## Rules changed in this revision (for the unit-tester)

| Rule | Was | Now |
|---|---|---|
| M2 | follow at SYNC (both edges) and at CI | two new stages; follow at END RESTACK only |
| M3 | START follow set `restack`; s59 rebase at START | START rebases, drops and pushes nothing; it reports `behind` (AC5) |
| M3a | (new) | `Upstream.behind()` counts `HEAD..target` |
| M4 | (new) | mid-sprint: nothing due |
| M5 | merge followed before the entry is added | END SYNC only adds the entry; `_drop_merged` deleted |
| M6 | REVIEW rebuilt every entry | REVIEW builds the sprint's own entry (all only after a fallback) |
| M7 | PUSH pushed every entry and its PR | PUSH pushes the sprint's branch only, no PR call; empty/local advance |
| M8 | team rebase at START | team rebase at END, after PUSH; `sync_from` cleared after |
| M9 | merged lookup at SYNC/CI | at RESTACK; same leading/same-number rule |
| M10 | rebase only the entries above a merge | rebase the whole remaining stack, `below` from merge-base when nothing merged |
| M11 | — | emptied entries dropped; deliver pushes and retargets, or finishes local |
| M12 | ci: stage REVIEW; sync: nothing | `restack = True`, stage REVIEW, full rebuild |
| M13 | ci → stage PUSH; sync stays | stays at PUSH or RESTACK |
| M14 | follow before/after the watch | no follow at CI |
| M18 | `CI_AFTER_FOLLOW`, `SYNC_STOPS` | deleted |

Tests that must change: every test of following at the CI stage (old
checklist 8, 9, 11, the `CI_AFTER_FOLLOW`/`SYNC_STOPS` table tests, `_followed`
skips), `test_the_end_sync_follows_the_merge_before_adding_the_entry` (END
SYNC no longer follows: see checklist 3), `test_a_rejected_push_at_sync_stops_the_stage`
(now at RESTACK: checklist 11), any s59 test that expects the START edge to
rebase (now the END edge's REBASE stage), and s29 tests that expect PUSH to
push every entry or REVIEW to rebuild every entry.

## Texts (exact)

`boundary.py`:

```python
REBASE_MERGE_LIMIT = 100
BIG_PR_NOTE = (
    'PR #{pr} ({branch}) has {commits} commits, more than the {limit} GitHub allows for '
    '"Rebase and merge". When it is the bottom of the stack, merge it by fast-forward: '
    "git fetch {remote} && git push {remote} {remote}/{branch}:{target}"
)
PUSHED_REPORT = (
    "Sprint {sprint}'s review branches are pushed: {prs}. The runner now waits for CI on "
    "every PR of the stack; nothing is called ready before CI passes on all of them."
)
```

`boundary_runner.py`:

```python
START_NOTES = {
    False: "the team branch is current with {target}",
    True: (
        "{target} moved {count} commits since the last sprint-end rebase; "
        "nothing changes until the next sprint end"
    ),
}
NOTHING_TO_PUSH = "no review branch to push"
NOTHING_TO_RESTACK = "no review branch to restack"
```

`NOTHING_TO_RESTACK` is the `pass` note RESTACK emits on an empty stack
(design review: the code's answer, consistent with PUSH's `NOTHING_TO_PUSH`).

`START_NOTE` (the earlier draft's single text) is replaced by `START_NOTES`.
In `BIG_PR_NOTE`, `{remote}` is `[upstream] remote` and `{target}` is
`[upstream] branch`. `{target}` in `START_NOTES` is the target ref
(`self.remote.target`).

`ci.py`: `NO_OPEN_PR_WHY = "no open pull request to watch"`.

`restack.py`:

```python
REBASE_STOPPED = "{branch} did not rebase cleanly onto {onto}"
TREE_CHANGED = "{branch} rebased onto {onto} has a different tree"
```

`{onto}` is the target ref name for the first entry and the new head (12
chars) of the entry below for the others.

`handover.py`, `SYNC_CONFLICT` rule: `"sprint {sprint} start: rebasing"`
becomes `"sprint {sprint} end: rebasing"`; the rest is unchanged.

`stages.py` rows (same `when` and `attach` as `boundary.push`):

- `boundary.sync`: "Fetch the target and record the team branch; at a sprint end, add the sprint to the review stack"
- `boundary.rebase` (new, `Name.BOUNDARY_REBASE`): "Rebase the team branch onto the target (sprint end only)"
- `boundary.restack` (new, `Name.BOUNDARY_RESTACK`): "Bring every review PR up to date, bottom up: rebase, same tree, push, retarget"

`BOUNDARY` maps `"rebase"` and `"restack"` to them.

## Test checklist (AC2, AC4)

Use a scratch bare remote and a clone (the s29/s59 git fixtures) and
`tests/s29_helpers.FakePrs` (`set_state(branch, PrState.MERGED)`). To
simulate "Rebase and merge", replay a sprint branch's commits onto the
remote's `main` in a second clone with a new committer date, then push.

1. M1: every created PR is `PrMode.READY`; the bottom is based on `main`,
   each other PR on the branch below. An open draft is edited to ready.
   Tests that assert a draft for stacked PRs must change (AC1).
2. **Mid-sprint (M4, AC2's pinned test):** a stack of two pushed PRs, the
   bottom merged on the remote, no boundary open: `due()` is `None`, no push,
   no `edit`, every entry's `head`, `pushed` and `base` unchanged. Then open
   the END boundary and run it: only now is the bottom dropped and the next
   PR rebased, pushed and retargeted to `main`.
3. **START edge (M3, AC5's pinned test):** in a scratch clone whose remote
   `main` is two commits ahead of the team branch, and with the bottom PR
   merged, stepping the START boundary to the end makes no push, no `edit`,
   no `find`, and no `rebase`, `reset`, `merge` or `checkout` git command;
   HEAD, the team branch ref, every story's `commits`, `checkout` and every
   stack entry are unchanged; outcomes are `pass` (sync, note
   `"origin/main moved 2 commits since the last sprint-end rebase; nothing
   changes until the next sprint end"`, `behind: 2`), `pass` (check), then
   `done`. With main not ahead the note is `"the team branch is current with
   origin/main"` and `behind: 0`.
3a. `Upstream.behind()`: 0 when the target is an ancestor of HEAD; N after
   N new commits on the target (fake `system.run` or scratch repo).
4. **END order (M2, M7–M11):** a three-sprint stack, the bottom
   rebase-merged on the remote, run the END boundary to CI. In the git
   command log: the push of the sprint's own branch comes before the team
   branch `rebase`, which comes before any review-worktree `rebase` and any
   parent push. In the outcomes: `built` < `pass` (push) < `rebased` (or
   `current`) < `merged` < `restacked`, and nothing after `restacked` (M11:
   `PUSHED_REPORT` is a PO update, not an event); the stage is then `ci`. No
   `gh` PR call happens before the team rebase.
5. After 4: the dropped sprint's PR is untouched; sprint-10's remote ref is
   its new head, pushed with a lease against its old `pushed`, its PR based
   on `main` and ready; sprint-11 (the sprint's own) is rebased onto
   sprint-10's new head, same tree, pushed, based on `team/sprint-10`; no
   open `FakePrs` PR has a dropped branch as base (AC4).
6. `Rebuilder.rebase`: N rebased onto the rebase-merged main has a parent
   chain on `origin/main` and `same_tree(new, old)`. On a conflict it returns
   `None` and `REBASE_HEAD` doesn't exist. `merge_base` returns the old main
   tip after main gained commits.
7. Nothing merged, main unmoved: RESTACK moves no head, pushes nothing for
   the parents, and still runs `_pr` for each entry (the sprint's PR is
   created on its parent).
8. Main gained an unrelated commit: plan refused with `TREE_CHANGED`, no
   remote ref moved, no `edit`; a `rebuild` event, `b.restack` true, stage
   `review`; the next steps rebuild every entry, check the ends, and reach CI.
9. `Restacker.merged`: `[MERGED, OPEN, MERGED]` gives the first only; a
   different PR number isn't merged; an entry without `pr` stops the scan;
   lookups stop at the first unmerged (count `find` calls). No `find` when
   `_local_why()` is non-empty.
10. Emptied entry (local delivery, an entry whose commits are in main): it
    is dropped with a `merged` event; the entry above is based on the
    target. Local delivery posts `LOCAL_REPORT`, finishes, and makes no push
    or `gh` call, but the team branch was rebased.
11. Push rejected at RESTACK holds `push_rejected`, stage `restack`; a rerun
    after continue pushes the rest with no new rebase changes. At PUSH:
    holds, stage `push`, and REBASE hasn't run.
12. REBASE conflict holds `sync_conflict` with stage `rebase` and the
    handover line says "end"; a failed fetch at REBASE holds `error`.
    `sync_from` is empty after `rebased` and after `current`.
13. `checked` carries over to the new head only when it equalled the old.
14. `entry.commits` (bottom against the target, others against
    `below.head`); `big_pr_notes`: 100 → none, 101 → the exact line ending
    `git fetch origin && git push origin origin/team/sprint-9:main`; the line
    is in the pushed, green and none texts.
15. CI with an empty stack finishes with `NOTHING_REPORT`; CI makes no
    `find` call before or after the watch.
16. AC3: three ready PRs are all watched; one `none` makes the verdict
    `none`, never green.
17. `next_stage`: at START, after CHECK comes `None` even with `b.restack`;
    at END, PUSH → REBASE → RESTACK → CI. `stages.BOUNDARY` has a row for
    every `Stage`.

Coverage stays at 100%, and ruff is clean.

## Known limits

- The sprint's own branch is pushed twice at a sprint end with a moved main
  (step 1, then step 4), so CI may run twice on it.
- A merge made during the CI wait, or after the boundary closed, is handled
  at the next sprint end (AC2: nothing changes mid-sprint).
- A PR merged above an unmerged one (into the branch below, not into main)
  isn't followed; the next push of the lower branch is refused by its lease
  (`push_rejected`), and the human is told.
- A dependent PR GitHub closed because its base branch was deleted stays
  `closed` (`_leave`).
- The PR body's "Stacked on …" line isn't rewritten when a PR becomes the
  bottom.
- A START boundary saved mid-restack by an older runner finishes after its
  current stage without pushing; the next END brings the stack up to date.
- The rebased team branch is checked at the next START's CHECK, not at END.
- An old START boundary held at `sync_conflict` (stage `sync`) still loads;
  `continue_boundary` reruns `sync`, which now only reports, and its pinned
  `sync_from` goes away with the boundary. The team branch stays as the
  human left it, and the next END rebases it.
- Main moved since the last sprint end is reported at START but pulled in
  only at the next END. No runner tool for a mid-sprint pull exists; the
  human pulls by hand if they ask for one.
