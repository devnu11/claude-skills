# s107 design: the flaky e2e tests

Story: `.team/stories/s107.md`. Developer: `developer-cli` for the runner part
(SR rules). The e2e test part (F rules) is test code in `tests/e2e/**`, which
only the integration-tester may write, so it lands in the **e2e step**. No new
dependency, no new ADR (extends the s69 runner results and s99 stages patterns).

## Why the tests flake (evidence)

| Test | What failed | Cause |
|---|---|---|
| `test_health_goes_green_amber_red_as_the_step_goes_quiet` | gate e5118: failed under `-n auto` | It waits on real time to make the step go quiet: amber at 5 s, red at 8 s, a 13 s stream window. Under load the stream opens late or the window ends before red. Raising the numbers (s70 devops) only moved the race. |
| `test_sandboxed_curl_fails_without_local_binding` | gate e5126: `assert 2 == 1`, the Bash result was "did not complete within its 120s timeout and was moved to the background" | Wall-clock bounds: the CLI's Bash timeout (since fixed to 600 000 ms), `curl --max-time 5`, `subprocess.run(timeout=120)`. A slow host or a host sleep goes past them. |
| `test_traversal_is_404` (any test using `dash`) | dashboard start | `_read_url` gives up after 20 s and its message has no server output. Starting Python under a loaded `-n auto` run can take longer. |

## Rules

### F: e2e tests wait on conditions, never on the clock (AC1, AC2)

- **F1. One readiness module.** Every e2e wait goes through the new
  `tests/e2e/readiness.py` (below). It waits on a condition with a monotonic
  deadline of `STARTUP_S = 120.0` s. That's long enough that load never reaches it,
  and a real hang still fails.
- **F2. No fixed sleep before an assertion that load can break.** A sleep that
  waits for something to happen becomes `wait_until`/`Output.wait_for`. A fixed
  pause is allowed only as a **minimum**, where more time can only make the
  assertion easier to pass (a "nothing happened" check or a minimum duration).
  The full list is under "Reviewed, unchanged" below.
- **F3. No tight wall-clock bound.** Socket, stream and subprocess timeouts in
  e2e tests are at least `STARTUP_S`. The tests with a short limit on purpose
  are listed in "Reviewed, unchanged" (each one asserts that the limit fires).
- **F4. Health levels are driven, not waited for.** A test does not wait for
  real seconds to pass to reach amber or red. The fake step moves its own quiet
  clock back on command (`Reading.wake(now - seconds)`). The thresholds are far
  apart (amber 300 s, red 600 s), so each level holds for minutes of wall time.
- **F5. Every server start has a readiness wait with a timeout (AC2).**
  - Child processes (the `agile-team dashboard` process, the fake step, the
    pulse script): `Output.wait_for(pattern)`. If it times out, or the child
    exits first, the failure message has the child's whole output so far
    (stdout+stderr merged) and its exit code.
  - In-thread HTTP servers (proxy test): `serving(handler)` constructs the
    server, starts `serve_forever` on a daemon thread, then waits until a TCP
    connect to its address succeeds. A timeout message names the address and the
    handler class. These servers have no output stream.
  - Runner-started services (`sandbox.Preparer`, used by
    `test_service_stop_e2e` and `test_service_presentation_e2e`) already wait in
    production code (`PROBE_ATTEMPTS × PROBE_EVERY_S` = 30 s) and their failure
    text has the service log's tail. They stay as they are.
- **F6. A stream read stops on a condition.** The SSE helpers read until the
  wanted sample or bytes arrive, or `STARTUP_S` passes. They never read for a
  fixed window. A timeout failure shows what was seen.
- **F7. Assertions are unchanged.** Each test keeps what it asserts: the same
  levels and reasons, statuses and bodies. Only how it waits changes.

### SR: the runner runs the suite N times in a row (AC3)

- **SR1. Story data.** Story frontmatter can declare `suite_runs: N`, a whole
  number from 1 to `MOST_SUITE_RUNS = 10`. With no key, nothing changes. s107's
  file needs `suite_runs: 5`; the PO adds it (see handoff).
- **SR2. Where it runs.** On a `done` handoff at the **suite step**, after that
  step's own gate passes, the runner runs the toolchain `test` command N times
  in a row. The suite step is the first of `SUITE_STEPS = ("e2e", "implement")`
  that is in the pipeline, so it is the last step that changes code or tests.
  In this repo that is `e2e`, after the integration tester's fixes, and the
  `test` command is `pytest -n auto …`.
- **SR3. Stop at the first failure.** Run k fails (exit ≠ 0): stop. A timeout
  gives the usual `timed_out` outcome. Any other failure gives
  `Outcome(BOUNCE, SUITE_FAILED.format(n=k, total=N, tail=tail(out)),
  output=out)`, with no `bounce_to`, like the gate's other bounces. The output
  lets the s92 routing (`Pipeline.route`) send failing items to their file
  owners.
- **SR4. Pass text.** When all N pass, the step's outcome keeps its verdict.
  Its reason becomes `"{reason}; " + SUITE_PASSED` (just `SUITE_PASSED` when the
  reason is empty). `SUITE_PASSED = "the test command passed {total} runs in a
  row ({times})"`, where times is `"412 s, 398 s, …"` (awake seconds by
  `system.monotonic`, `:.0f`). This text goes into the `gate` event's `reason`,
  in the runner's own words.
- **SR5. Kept and shown.** Every suite run, passed or failed, is kept as one
  `Ran("suite-runs", code_of_last_run, tail)`. The tail has one `RUN_LINE` per
  run, then, on a failure, a blank line and `result_tail(out)` of the failed
  run. `BRIEF_RESULTS` shows `suite-runs` to `implement`, `e2e` and
  `acceptance`. So the Customer Proxy's brief holds the runner's own output, and
  its handoff quotes it for AC3.
- **SR6. Bad value.** A `suite_runs` that is not a whole number from 1 to 10
  (bools count as bad), or a story file whose frontmatter does not parse,
  gives `Outcome(HOLD, BAD_SUITE_RUNS…)`: the story stays, no round is counted
  and the PO sees why. A missing story file counts as no key.
- **SR7. Timing stage.** The runs happen inside a new stage
  `gate.suite-runs` (after, step). Each command is noted at
  `CommandShell.run` as usual (s99).

## Data and text (exact)

```python
# agile_team/suite_runs.py
KEY = "suite_runs"
MOST_SUITE_RUNS = 10
SUITE_RUNS = "suite-runs"                      # the Ran name and results file
SUITE_STEPS = ("e2e", "implement")
SUITE_PASSED = "the test command passed {total} runs in a row ({times})"
SUITE_FAILED = "the test command failed on run {n} of {total}:\n{tail}"
RUN_LINE = "run {n} of {total}: exit {code} in {seconds:.0f} s: {summary}"
BAD_SUITE_RUNS = (
    "story {story}'s suite_runs must be a whole number from 1 to {most}, not {value!r}; "
    "fix the story file's frontmatter"
)
BAD_FRONTMATTER = "story {story}'s frontmatter does not parse: {error}"
SUMMARY = re.compile(r"\b\d+ (passed|failed|errors?)\b")   # pytest -q summary lines
```

`summary` in `RUN_LINE` is every output line that matches `SUMMARY`, stripped
of `=` and spaces and joined with `" | "`. With none, it is the last non-blank
line, or `"no output"`. With this repo's `&&` command that gives both runners'
summaries.

Stage row (`stages._ROWS`, right after `GATE_TESTS_COVERAGE`):
`(Name.GATE_SUITE_RUNS, A, STEP, "Run the test command a story's suite_runs times in a row after its suite step's gate")`,
with `GATE_SUITE_RUNS = "gate.suite-runs"`.

## Changes per module

### `agile_team/suite_runs.py` (new, pure except `declared`)

```python
@dataclass(frozen=True)
class Wanted:
    """How many suite runs a story asks for; ``refusal`` set when the value is bad (SR1, SR6)."""
    count: int = 0
    refusal: str | None = None

def wanted(meta: dict[str, Any] | None, story: str) -> Wanted
    """SR1/SR6: no key -> Wanted(); an int 1..MOST (not bool) -> Wanted(n); else the refusal."""

def declared(stories_dir: Path, story: str) -> Wanted
    """Read ``<stories_dir>/<story>.md`` via ``system.read_text``; missing (OSError) -> Wanted();
    ``roles.split_frontmatter`` raising ``RoleError`` or ``yaml.YAMLError`` -> BAD_FRONTMATTER."""

def suite_step(steps: list[str]) -> str | None
    """SR2: the first of SUITE_STEPS in ``steps``, or None."""

@dataclass(frozen=True)
class SuiteRun:
    """One run of the test command (SR5)."""
    n: int
    total: int
    code: int
    seconds: float
    out: str = field(repr=False)

    def line(self) -> str          # RUN_LINE
def summary(out: str) -> str        # see "Data and text"
def report(runs: list[SuiteRun]) -> str
    """RUN_LINE per run; after a failed last run, a blank line and its result_tail (SR5)."""
def passed_text(runs: list[SuiteRun]) -> str   # SUITE_PASSED
```

Imports: `from . import system`, `from .roles import RoleError, split_frontmatter`,
`from .results import result_tail`. It does not import `gates` (`gates` imports it).

### `agile_team/gates.py`

- `Outcome` gains `extra_ran: tuple[Ran, ...] = ()` after `ran`: more runs to keep (SR5).
- `Checks` gains the field `suite_runs: Callable[[str], suite_runs.Wanted] = _no_suite_runs`
  after `stages` (`_no_suite_runs(story) -> Wanted()`).
- `Checks.after_suite_runs(self, story: str, first: Outcome) -> Outcome`:
  returns `first` unless it is a PASS. Otherwise it asks `self.suite_runs(story)`.
  A refusal gives HOLD with `ran=first.ran`. A count of 0 returns `first`.
  Otherwise it runs inside `self.stages(stages.Name.GATE_SUITE_RUNS)` and
  returns `_suite_outcome(first, self._run_suite(count))`.
- `Checks._run_suite(self, total: int) -> list[SuiteRun]`: runs
  `self.commands["test"]` up to `total` times, timing each with
  `system.monotonic()`, and stops after the first non-zero exit (SR3).
- Module function `_suite_outcome(first: Outcome, runs: list[SuiteRun]) -> Outcome`:
  - last run passed: `replace(first, reason=joined, extra_ran=(*first.extra_ran, ran))`;
  - timed out: `timed_out(...)` with `ran=first.ran, extra_ran=(ran,)`;
  - otherwise the SR3 bounce with the same `ran`/`extra_ran`.
  Here `ran = Ran(SUITE_RUNS, runs[-1].code, report(runs))`.
- `Pipeline._gate_for(story, handoff)`: the current body moves to
  `_step_gate(story, handoff)`. The new body is:
  ```python
  gate = self._step_gate(story, handoff)
  return self._suite_gate(story, gate) if self._suite_due(story, handoff) else gate
  ```
  - `_suite_due(story, handoff) -> bool`: `handoff.status == "done"` and
    `story.step == suite_runs.suite_step(self.steps)`.
  - `_suite_gate(story, gate) -> Callable[[], Outcome]`:
    `lambda: self.checks.after_suite_runs(story.id, (gate or _passed)())`, where
    `_passed()` returns `Outcome(Verdict.PASS)` (e2e without acceptance has no
    gate of its own).

### `agile_team/stages.py`

`Name.GATE_SUITE_RUNS = "gate.suite-runs"` after `GATE_TESTS_COVERAGE`, and the
`_ROWS` row above. `stages.reserved("gate.suite-runs")` is then true without
other changes.

### `agile_team/results.py`

`BRIEF_RESULTS`: `"implement": ("test", "coverage", "suite-runs")`, add
`"e2e": ("suite-runs",)` and `"acceptance": ("suite-runs",)`. Other rows stay as they are.

### `agile_team/dispatch.py`

`_advance_and_log`: replace `if outcome.ran: self._keep(...)` with
`self._keep_runs(story, outcome)`. That keeps each of `(outcome.ran, *outcome.extra_ran)`
that is not None, with `where=f"{step} gate"`. `step` is read before `advance`, as today:
pass it in, or read `story.step` inside before the advance (keep ≤ 2 params:
`_keep_runs(self, story, outcome)` reads `story.step`, which is still the gate's step
at that point).

### `agile_team/cli.py`

`make_pipeline`: `suite = functools.partial(suite_runs.declared, config.stories_dir)`,
passed as `gates.Checks(..., read=read, suite_runs=suite)`.

### `agile_team/dashboard/index.html`

`STAGE_NODES`: the `Implement gate` node's `stages` list gains `"gate.suite-runs"`. It
is a gate-time cost on the story's last code step, and s102's node set stays four.

### `agile_team/roles/product-owner.md`

One sentence where story files are described: "For a story that must prove a
fix holds (a flaky test, a race), add `suite_runs: N` (1–10) to its
frontmatter; the runner then runs the test command N times in a row after the
story's e2e gate (or implement, with no e2e step) and keeps the runs for the
acceptance brief."

## e2e test changes (integration-tester, e2e step)

### `tests/e2e/readiness.py` (new)

```python
"""Readiness waits for e2e tests: conditions with generous monotonic deadlines (s107 F1)."""
STARTUP_S = 120.0
POLL_S = 0.05
BOOT = "import sys; from agile_team.cli import main; sys.exit(main())"   # moved here
RUNNER = Path(events_mod.__file__).parent.parent                      # moved here
DASHBOARD_URL = re.compile(r"dashboard: (http://\S+)")
LOCAL = ("--host", "127.0.0.1", "--port", "0", "--no-open")

def wait_until(check: Callable[[], bool], what: str) -> None
    """Poll ``check`` every POLL_S; AssertionError "{what} not within 120 s" at the deadline."""

class Output:
    """A child's merged stdout, read line by line on a daemon thread and kept (F5)."""
    def __init__(self, proc: subprocess.Popen[str]) -> None
    def wait_for(self, pattern: re.Pattern[str]) -> re.Match[str]
        """The first kept line matching ``pattern``, waiting for new ones; fails with
        ``"{pattern} not printed within 120 s (exit {code}); output:\n{text}"`` at the
        deadline, or at once when the child closed its output without a match."""
    def lines(self) -> list[str]
    def text(self) -> str

@dataclass(frozen=True)
class Launch:
    """How to start ``agile-team dashboard`` for a test."""
    repo: Path
    home: Path                       # AGILE_TEAM_HOME
    args: tuple[str, ...] = LOCAL    # plus e.g. ("--token", TOKEN)

@dataclass(frozen=True)
class Dashboard:
    proc: subprocess.Popen[str]
    output: Output
    url: str

@contextmanager
def dashboard(launch: Launch) -> Iterator[Dashboard]
    """Start it (cwd RUNNER, stdout PIPE, stderr STDOUT, text), wait for DASHBOARD_URL,
    yield; finally kill and wait(timeout=10)."""

def serving(handler: type[BaseHTTPRequestHandler]) -> ThreadingHTTPServer
    """Start an in-thread server on 127.0.0.1:0 and wait until it accepts a connection (F5)."""
```

`Output` reads with a daemon thread into a list guarded by a
`threading.Condition`, and it records EOF. `wait_for` waits on the condition with
the remaining monotonic time. Pitfall: don't mix `select` with
`TextIOWrapper.readline`. A buffered second line is invisible to `select`, which
is a latent bug in today's `_read_url`.

## Known limits

- A host sleep longer than the CLI's 600 s Bash maximum can still fail the
  proxy test. That is a sleep, not load, and the test then shows the CLI's
  output.
- N suite runs cost N full suites (about 8 min each here) at the gate. That is
  why the key is per story.
