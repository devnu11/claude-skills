# s159: Story branches. Each story on its own branch, landed on the sprint branch only when green

Story: `.team/stories/s159.md` (57 ACs in 12 groups). Design source: the
liaison's plan `.team/run/liaison/plans/story-branches-v10.md`. ADRs:
**ADR-0084** (story branches, landing, replay, no push replaces history),
**ADR-0085** (parallel scheduler, one writer, hand-over scopes),
**ADR-0086** (kept sessions per story), **ADR-0087** (waiting runs and the
`limit` status). Amended: ADR-0007, ADR-0009, ADR-0017, ADR-0020,
ADR-0058 (retired), ADR-0075, ADR-0076, ADR-0077. Requirements: REQ-130 to
REQ-166.

Developer: `developer-cli` for everything. The dashboard part (AC9.x, the
Time chart split of AC7.3) is small page work in the same step. `unattended/`
is in the developer's write scope. The two CI workflow edits of AC4.1 are
DevOps's, at `ops-review`.

This is the biggest story the runner has had. Section 12 orders the work into
slices. Each slice leaves the suite green, so build and commit them in that
order.

## 1. Words

| Word | Meaning |
|---|---|
| sprint branch | The team branch checked out in the main checkout (`UpstreamState.team_branch`, the local branch today's runner already uses). Its remote mirror is `<prefix><N>`. The local branch is never named `<prefix><N>`, because the push guard refuses to push the checked-out branch. |
| story branch | The local and remote branch `<story_prefix><id>`, or `<story_prefix><id>-r<k>` after k replays. |
| landing branch | `<story_prefix><id>-land`. It is created by a push, used for one CI run, then deleted. |
| worktree | `.team/run/worktrees/<id>/`, a `git worktree` on the story branch. |
| land worktree | `.team/run/land/`, detached at the sprint head. It is made for each landing or revert and removed after its checks. |
| replay worktree | `.team/run/replay/`, detached at the target. It holds a boundary replay and DevOps's scratch replay. |
| open story | A story that has a worktree (`StoryState.worktree_head != ""`). |
| main-checkout step | A step with no story, other than the Manager: the storyless architect, devops and unit-tester, and the boundary fix steps. |
| the writer | `run_writer.RunWriter`, the one task that writes `state.json`, `events.jsonl` and `ledger.jsonl` (AC6.4). |

## 2. Rules

Each rule is numbered. Tests and reviews cite these numbers.

### Branches and worktrees (AC1.x, REQ-130 to REQ-134)

- **B1.** When a story's first step starts, `Workspaces.ensure(story)` runs
  `git branch <story_prefix><id> <sprint head>` and then
  `git worktree add <run_dir>/worktrees/<id> <branch>`. It records
  `branch`, `base_sha` (the sprint head) and `worktree_head`, and emits a
  `story-branch` event (`action: "created"`). A story that already has a
  branch but no worktree, because it was moved out (AC3.1) or pruned
  (AC10.2), gets its worktree rebuilt from the branch. No new branch is made.
- **B2.** `.team/run/` is gitignored by onboarding, and so the worktrees, the
  land worktree and the replay worktree are too. The runner creates nothing
  outside the repo except under `system.temp_dir()`. Any path under
  `.team/run/` is built from `config.run_dir`, never from
  `config.repo / ".team/run"`. The presentation (`presentation.story_root`)
  and the Proxy's sandbox (`sandbox.sandbox_root`) are such paths: from a
  worktree the briefs and gap texts name them absolutely,
  `guard.Scope.run_home` lets a worktree step write the main checkout's
  `.team/run/**` within its globs and nothing else there, and the Proxy's
  brief names the worktree as the repo holding its report
  (`acceptance.WORKTREE_LINE`).
- **B3.** A step on a story runs through `runtime.at(story)`, a view of the
  `Runtime`. The view has the worktree's `Config`
  (`config.at_worktree(path)`: `repo` is the worktree, `run_home` is the main
  checkout, so `run_dir` stays the main checkout's `.team/run`), a
  `Git(worktree)` and a `Pipeline` built for the worktree. It shares every
  run file object: state, events, ledger, relay, pulse, stage log, results,
  prs and the halt flags. So the scope base (`guard.Scope.repo`), the Stop
  hook, `CommandShell`, the stop checks, the gates and every story-file read
  run in the worktree (AC1.2). `git_check.git_env(config.run_dir)` keeps the
  ceiling at the main checkout's `.team/run`. The worktree's own `.git` file
  is found before the ceiling is reached (AC1.1).
- **B4.** Only two things move the main checkout: a landing's fast-forward and
  the runner's story-admin commits (intake, share, revert record, `settle_po`).
  Each calls `runtime.record_checkout()` and sets the sprint `StackEntry.head`
  to the new HEAD (AC1.3). A landing that has made its merge holds the sprint
  branch until its fast-forward or its discard. While it does, no story-admin
  commit is applied. The queues wait for the next tick.
- **B5.** The checkout guard checks a story's worktree before each step on
  that story (`checkout.check(Git(worktree), CheckoutRecord(story.branch,
  story.worktree_head))`). If it drifted, the step does not start.
  `story.drift` gets the changed files from `git status --porcelain`, the
  story holds, and a `worktree_drift` hand-over (per-story) names the files.
  Drift in the main checkout halts the run, as today.
- **B6.** `agile-team accept-checkout --story <id>` is allowed while the
  runner runs. It only queues `.team/run/checkouts/c<N>.json`
  (`{"story": id}`) through a `NumberedQueue`. Between steps the scheduler
  applies each request: it records the worktree head as `worktree_head`,
  clears `drift` and the hold, and emits a `checkout` event
  (`action: "accepted", story`). `accept-checkout` without `--story` is
  unchanged, and still refuses while the runner runs.
- **B7.** `[upstream] story_prefix` (default `team/story-`) must match
  `SAFE_BRANCH`, must differ from `prefix`, and neither may start with the
  other. `Upstream._guard` accepts a branch under either prefix. It still
  refuses `settings.branch` and the checked-out branch, and its refusal text
  names both prefixes.

### Landing (AC2.1 to AC2.4, AC2.9 to AC2.11, AC5.2, AC11.5; REQ-135 to REQ-137, REQ-141 to REQ-143, REQ-152, REQ-164)

- **L1.** `land` is the last pipeline step. `config.ALWAYS_STEPS` gains
  `("land", LAST)`, and `LAST` puts it at the end, which is after
  `acceptance`. `gates.STEP_ROLES["land"] = "runner"` and `land` is in
  `CHECKPOINT_STEPS`, so `step_for_role` never targets it and every
  `run_role` on a story at `land` is refused (no role fits `runner`). A pass
  at `acceptance` moves the story to `land`. So does a Manager `advance`
  from `acceptance`, through the ordinary `_forward`. Only a pass at `land`
  marks the story done.
- **L2.** Stories land one at a time, in the order they passed acceptance.
  When a story reaches `land`, the apply step appends it to
  `RunState.land_queue`. Only the head of the queue lands. Every other story
  at `land` waits (waits row `land_queue`). The head is popped when its land
  passes, bounces or holds.
- **L3.** Before its first push, a land needs the push permission (rule P1).
  While it is `unasked`, the story waits at `land` (waits row `permission`).
- **L4.** The merge: `git worktree add --detach <run_dir>/land <sprint head>`,
  then in it `git merge --no-ff --no-edit -m "merge(<id>): <title>"
  <story branch>`. The first parent is the sprint head. The story's commits
  are not rewritten, so they keep their hashes (AC2.2). The runner makes no
  other merge commits, apart from a replay's re-merges, which copy a
  landing merge (rule R1).
- **L5.** The story file (AC2.9). If git reports `.team/stories/<id>.md` as
  conflicting, or if it merged it at all, the runner writes the file as
  `git merge-file -p <story branch copy> <base_sha copy> <sprint head copy>`.
  This starts from the story branch's copy and re-applies the sprint side's
  edits since `base_sha` on top. If `merge-file` reports a conflict, that is
  a **clash**: the merge is aborted, the land worktree is removed, and the
  land holds (`Verdict.HOLD`, `LAND_STORY_CLASH`, per-story `gate_hold`), so
  the PO can have the liaison settle it with `story amend` and then
  `continue_story`. A clean result is `git add`-ed and the merge commit is
  completed.
- **L6.** Any other merge conflict (AC2.10): abort, remove the land
  worktree, and queue a `StoryRebase` (rule S3) for the role that rule O1
  picks. The outcome is `Verdict.BOUNCE` with `bounce_to="land"`, so the
  story stays at `land`, a round is counted and the hand-over is
  `land_bounced`. After the fix step adopts the rebased branch, `land` runs
  again.
- **L7.** The checks. The full checks
  (`fullcheck.run_checks(full_checks(config_at_land), Judging(shell(land),
  required))`) run on the merge in the land worktree. If they are red, the
  worktree is removed (the merge is gone with it, and the sprint branch never
  moved) and the outcome is `Verdict.BOUNCE`, `bounce_to="implement"`, with
  the failures (`CheckReport.reason()`). If they are green, the land goes on.
  In local mode (P3) a green check fast-forwards at once (L9) and the land
  passes with `ci: "none"`.
- **L8.** The landing push and its CI. The runner pushes
  `Lease(<story_prefix><id>-land, "", merge)`, a branch creation, and sets
  `story.landed = Landed(merge, pushed=merge, pr=None)` in the same apply.
  It then waits with `ci.ShaWatch.result(merge, story.land_reran)`, which
  polls `Prs.sha_checks(merge)` every `CI_POLL_S` under `gates.ci_timeout_s`.
  The wait is an async loop. Each poll runs `gh` in a worker thread, so other
  stories' steps go on. The verdicts:
  - `GREEN`: rule L9.
  - `RED` or `MAIN`: the outcome is `Verdict.BOUNCE`, `bounce_to="implement"`,
    with `ci.check_lines`. The sprint branch, local and remote, is untouched.
    `story.landed` is cleared.
  - `INFRA`: one re-run per job at this head, recorded in `story.land_reran`
    (key `ci_triage.rerun_key`), then poll again. If it is still `INFRA`, the
    land holds and the hand-over is `ci_infra` (per-story).
  - `PENDING` or `NONE` at the timeout: the land holds and the hand-over is
    `ci_pending` (per-story), never green.
  - In every case the landing branch is then deleted with
    `Upstream.delete(Lease(landing branch, merge, ""))`.
- **L9.** On green, the runner pushes the sprint branch first:
  `Lease(entry.branch, entry.pushed, merge)`. When the push succeeds, the
  main checkout fast-forwards (`git merge --ff-only <merge>`, under the main
  lock, rule C6). Then `entry.head = entry.pushed = merge`, `record_checkout`
  runs, and a `story-landed` event records `{merge, parents: [p1, p2],
  sprint_branch, pushed}`. If the entry has no PR yet, the runner creates the
  sprint PR as a draft (`PrSpec(entry.branch, upstream.branch, entry.title,
  body, PrMode.DRAFT)`) and records `pr`, `url` and `mode`. After that the PR
  is only ever found by the number in the entry. The story's own PR is closed
  with `Prs.close(story.pr, LANDED_NOTE)` (AC8.2). `landed.pr = entry.pr`,
  the outcome is `Verdict.PASS`, and the story is done.
- **L10.** A rejected sprint-branch push is never retried. The runner fetches
  and reads `R = remote_head(entry.branch)`. If `R != entry.pushed` and
  `is_ancestor(entry.pushed, R)`, someone pushed a fix. The main checkout
  fast-forwards to `R`, `entry.head = entry.pushed = R`, `record_checkout`
  runs, and the land starts again from L4 with a new merge, new checks and
  new CI (`story-landed` is not emitted for the old merge). Otherwise the run
  halts as checkout drift (`HaltKind.CHECKOUT`, reason
  `SPRINT_BRANCH_DIVERGED` naming both heads), and the halt note tells the
  liaison.
- **L11.** If the run stops after the landing push (AC11.5), `start --resume`
  finds the story at `land` with `story.landed.pushed` set. The land then
  re-enters L8's wait on that sha. It does not merge or push again.
- **L12.** The land is a runner stage: `stages.Name.STORY_LAND`
  (`"story.land"`, label `land`, `When.DURING`, `Attach.STORY`). It is opened
  for one land attempt, and its detail holds the checks summary and the CI
  verdict (AC9.2).

### Pushes (AC2.11, AC2.16, AC8.1; REQ-143, REQ-147, REQ-158)

- **P1.** The runner asks once, before its first push of any kind. The first
  time a push is due while `upstream.push is Permission.UNASKED`, it raises a
  `push_permission` hand-over once. That trigger now comes from
  `RunState.permission_asked`, not from a boundary hold. Until the answer,
  steps commit and nothing is pushed: story pushes are skipped, a land waits
  before its first push, and the start's sprint-branch creation is deferred.
  `set_push_permission` is unchanged. The `push_permission` boundary hold
  goes.
- **P2.** `Upstream.push(lease)` checks every push in code. It calls
  `_guard`. Then, when `lease.expect` is not empty, it refuses unless
  `git merge-base --is-ancestor <expect> <sha>` exits 0, returning
  `NOT_FAST_FORWARD` without sending anything. The argv is always
  `push --porcelain --no-verify --force-with-lease=refs/heads/<b>:<expect>`.
  A bare `--force-with-lease` and `--force` never appear (a test greps the
  source). `expect` is the recorded head: `StackEntry.pushed` for a sprint or
  replay branch, `StoryState.pushed` for a story branch, or `""` for a new
  branch. Callers treat a refusal like a rejection: they report it as
  `push_rejected`, post it to the liaison, and never retry it with another
  expected sha.
- **P3.** Local mode. With no remote, no PR service (`Prs.missing()`) or
  permission `no`, nothing is pushed. A land passes on green full checks
  alone, with `landed.pushed = ""` and `story-landed` `ci: "none"`, and the
  boundaries end local as today.
- **P4.** After every step on a story that made a commit, and once permission
  is `yes`, the runner pushes the story branch with
  `Lease(story.branch, story.pushed, worktree head)`. It saves
  `story.pushed` only after the push succeeds. If the story has no PR, it
  creates a draft PR (`PrSpec(story.branch, entry.branch, "<id>: <title>",
  STORY_PR_BODY, PrMode.DRAFT)`) and records `story.pr`. The push runs in a
  worker thread after the step's apply.
- **P5.** `Upstream.delete(lease)` deletes a branch by pushing
  `:refs/heads/<branch>` with `--force-with-lease=<ref>:<expect>`. It
  refuses (`REFUSED_DELETE`) any branch that does not start with
  `story_prefix` and end with `-land`. It is the only deletion the runner
  makes, and it skips P2's ancestor check.

### Story CI (AC8.3; REQ-158)

- **SC1.** Each scheduler tick, at most every `STORY_CI_POLL_S = 60` seconds
  per story, `story_ci.StoryCiPoll` reads `Prs.sha_checks(story.pushed)` for
  each open story with a pushed head. If every check is settled and the
  `(sha, verdict)` differs from `story.ci`, it records
  `story.ci = StoryCi(sha, verdict, source="pr")` and emits `story-ci`
  (`{sha, verdict, source, checks}`). The landing wait (L8) emits `story-ci`
  with `source: "landing"` for its final verdict.
- **SC2.** A `RED` story-PR result hands over as `story_ci_red`
  (per-story). It sets no hold, because it doesn't hold the run. Only the
  landing CI decides whether a story lands.

### Replay at the sprint end and start (AC2.5 to AC2.8, AC2.12, AC2.13, AC2.17; REQ-138 to REQ-140, REQ-144, REQ-148)

- **R1.** `replay.Replayer.run(spec)` replays a first-parent line onto a
  target in the replay worktree (`git worktree add --detach <run_dir>/replay
  <target sha>`). For each commit `c` of
  `git rev-list --first-parent --reverse <base>..<head>`:
  - if `c` has two parents (a story merge `M`), it runs
    `git rebase --onto <tip> M^1 M^2` (the `REBASE_FLAGS` with
    `--empty=keep`), then `git checkout --detach <tip>` and
    `git merge --no-ff --no-edit -m "<M's full message>" <rebased tip>`;
  - otherwise it runs `git cherry-pick --allow-empty <c>`.

  After each commit `tip` moves on, and `ReplayProgress.done` (an index) is
  saved before the next one. So a crash or a conflict resumes at the right
  place.
- **R2.** A replay conflict (AC2.6) leaves the stopped rebase or cherry-pick
  in the replay worktree on the branch `agile-team/replay-sprint-<N>`. It
  holds the boundary in a DevOps `rebase-fix` step (`StepKind.REBASE_FIX`,
  scope as today). The brief names the stopped story and commit
  (`REPLAY_FIX_LINES`). After DevOps hands off `done`,
  `scratch_replay.find_refusal(progress)` checks, in order: the operation is
  finished, the tree is clean, HEAD is on the scratch branch, HEAD descends
  from `progress.tip`, and the stopped story's commits match the old ones by
  subject and in order, with none of them a merge. Then
  `upstream.find_lost_paths` must find no one-sided path. The `HAS_MERGES`
  refusal is gone. If all checks pass, the replay goes on from the next
  commit (a merge step first, if it stopped inside a story). A new conflict
  is a new DevOps step, under the boundary's rounds.
- **R2a (design-review).** A sprint whose line holds no story merge
  (`Boundary.replay` is `None` or has no merges, e.g. a sprint run before the
  switch) keeps s151's plain rebase. `scratch_rebase.ScratchRebase` stays
  for it, in `<run_dir>/rebase` on `agile-team/rebase-sprint-<N>`.
  `BoundaryRunner._rebase_conflict` sets `Failure(..., plain_rebase=True)`
  on that path only. `boundary._fix_lines(failure)` gives
  `REPLAY_FIX_LINES` to a `REBASE_CONFLICT` failure unless `plain_rebase`
  is set, which gets `FIX_LINES[REBASE_CONFLICT]` (s151's text). A saved
  failure without the key loads as a replay stop (`plain_rebase=False`).
- **R3.** When the replay finishes, `Upstream.move_team_branch(old, tip)`
  moves the sprint branch (it refuses if the branch moved). Then
  `rewrite.remap_state(state, moved)` runs with the story-by-story pairs of
  R4, `record_checkout` runs, and the replay worktree is removed.
- **R4.** The remap pairs commits story by story
  (`rewrite.pair_replay(old, new)`). Each story's commits (`M^1..M^2` against
  `M'^1..M'^2`) are paired by subject, in order. Each merge `M` pairs with the
  `M'` whose subject is `merge(<id>): …` for the same id. Plain commits pair
  by subject, in order. `remap_state` also rewrites each open story's
  `base_sha`, each story's `landed.merge`, and each `RevertEntry`'s `merge`
  and `revert`.
- **R5.** The end boundary's stages become `sync, check, push, ci, replay,
  push-replayed, ci-replayed` (`Stage.REPLAY`, `Stage.PUSH_REPLAYED`,
  `Stage.CI_REPLAYED`; `LEGACY_STAGES` maps `rebase`, `push-rebased` and
  `ci-rebased` to them).
  - `sync` uses the sprint's own entry from the start (AC2.17). If
    `entry.head == entry.start`, it finishes `NOTHING_NEW`.
  - `push` pushes the as-built head if it moved, copies
    `as_is_branch = branch`, `as_is = pushed` and `as_is_pr = pr`, and keeps
    the draft PR.
  - `ci` watches the draft PR as well (`_watched` takes `DRAFT` and `READY`).
    Green is the gate (`get_rebase_refusal` reads `as_is`).
  - `replay` runs R1 to R3 onto the target.
  - `push-replayed` sets `k = entry.replays + 1` and
    `branch = <prefix><N>-r<k>`, resets `pushed` to `""`, pushes the
    replayed tip (a creation) and opens a `READY` PR from it. It closes the
    old draft PR with `Prs.close(old_pr, SUPERSEDED_BY.format(url=new_url))`
    and keeps the old branch. The entry's `branch`, `head`, `pr`, `url` and
    `mode` now describe the replay branch, and `replays = k`.
    `supersedes` keeps only PRs whose state is still open.
  - `ci-replayed` records the CI and never holds, as `ci-rebased` did.
- **R6.** main moves only by fast-forward (AC2.8). The runner never pushes
  main (the guard refuses it). `PR_BODY`, `ci.CI_GREEN_REPORT`, the
  `CI_GREEN` hand-over line and `big_pr_notes` give
  `git push <remote> <sha>:<branch>` (`FF_COMMAND`) and never "Rebase and
  merge".
- **R7.** The start boundary's stages become `sync, check, push-replayed,
  open`.
  - `sync`, when the target has moved (`behind() > 0`), replays the sprint
    branch onto it with R1 to R3. It replays from the last end's first-parent
    line, `upstream.last_end`, or from the merge base when that is empty.
    A conflict is aborted and told to the liaison, holding nothing, as s152
    did.
  - `push-replayed` runs only when the newest stack entry's PR is still open
    and `sync` replayed. It pushes to that entry's `<prefix><N>-r<k+1>` as in
    R5, under P1. With an empty stack, or a merged PR, nothing is pushed.
  - `open` (AC2.17) creates the remote `<prefix><N>` at the start head (a
    creation, under P1, deferred while permission is `unasked`) and appends
    `StackEntry(sprint=N, branch, start=head, end=head, head=head,
    pushed=head or "")`. It then replays every carried story (R8). The end's
    `sync` reuses this entry.
- **R8.** A carried story (AC2.13) is one in the new sprint, unlanded, with a
  branch whose `base_sha` is not the new head. `replay.StoryReplay.run(story,
  head)` works in the story's worktree, which it rebuilds if needed:
  - It stashes with `git stash push --include-untracked -m
    agile-team-replay` when the story has an `in_flight` step.
  - It runs `git checkout -b <story_prefix><id>-r<k>`, then
    `git rebase --onto <head> <base_sha>`, then `git stash pop`.
  - On success it remaps the story's shas (`pair_replay`), and sets
    `branch`, `base_sha = head`, `pushed = ""`, `replays = k` and
    `worktree_head`. Once permission is `yes` it pushes the new branch,
    opens a new draft PR and closes the old one with a link. The old branch
    is kept, and the kept sessions are kept.
  - On a conflict it runs `git rebase --abort` (and leaves the stash) and
    queues a `StoryRebase` (S3) with no round. The boundary goes on.

  A story in the Product Backlog with a branch is replayed by the same
  `StoryReplay` when it next starts (B1 rebuild), onto the then sprint head.
- **R9.** AC2.14: while the boundary holds on `ci_failed`, `ci_infra` or
  `ci_pending`, the scheduler calls `BoundaryRunner.follow_remote()` at most
  once per `health.beat_s`. It reads `remote_head(entry.branch)`. When that
  differs from `entry.pushed`, the runner fetches and fast-forwards the sprint
  branch to it (`git merge --ff-only`), sets `entry.head` and `entry.pushed`,
  runs `record_checkout`, sets `stage = CI`, clears the hold and emits
  `boundary` `outcome: "followed"`. If the fast-forward isn't possible, the
  run halts as checkout drift naming both heads. `continue_boundary` on
  `ci_failed` is accepted once `entry.pushed != entry.ci.head`, and refused
  as today until then. `ci_infra` and `ci_pending` keep today's acceptance:
  "refused, as today" refers only to the hold that is refused today.
  `record_ci_bug` is unchanged.

### Story rebases, the shared fix step (AC2.10, AC2.13)

- **S1.** `StoryState.rebase: StoryRebase | None` is
  `{onto, base, old, branch, files, role}` (`old` is the branch being
  replaced). Whether a round was counted is decided when it is queued
  (L6 counts one, R8 doesn't), so the record needs no flag. When it is set, the router's
  next work for the story is a `StepKind.STORY_REBASE` step for
  `rebase.role`, run in the story's worktree.
- **S2.** Before the step, the runner prepares the rebase. It runs
  `git checkout -b <branch>` (the next `-r<k>`), then
  `git rebase --onto <onto> <base>`, which stops at the conflict. The step's
  write scope is the conflicting files only (as `_set_rebase_fix_scope` does
  today). The brief is `STORY_REBASE_LINES`: resolve, `git add`,
  `git rebase --continue`, and never merge, squash, reorder or drop.
- **S3.** After a `done` handoff, `story_rebase.refusal(...)` checks that no
  operation is in progress, the tree is clean, HEAD is on `rebase.branch` and
  descends from `onto`, and the commits of `onto..HEAD` match
  `base..old branch` by subject and in order. If they do, the story adopts
  the branch (remap, `branch`, `base_sha = onto`, `pushed = ""`, `replays`,
  `worktree_head`) and pushes it under P1 with a new draft PR, closing the
  old one. `rebase` is cleared and the story is back at its step. If the
  check fails, the step bounces to the same role with the reason (a round).
- **O1.** Who resolves it. The role is `devops` when every conflicting path's
  only owner among the pipeline roles' write globs (`owners.Owners`) is
  DevOps, or no role owns it. These are the "git-owned files" of AC2.10:
  CI, lock files, `.gitignore` and the toolchain config. Otherwise it is
  the story's developer (`story.developer` or `developer`).

### Leaving (AC3.x, REQ-149, REQ-150)

- **E1.** When a story leaves the sprint (`begin_sprint` without it), its
  worktree is removed (`Workspaces.remove`). It keeps its branch, its PR stays
  a draft, and `worktree_head = ""`. A cancelled story is the same, and its
  running task is cancelled at a safe point (C8). Nothing of either reaches
  the sprint branch. The runner never deletes a story branch.
- **E2.** `revert_story` on an unlanded story removes its worktree and drops
  its branch from the story (`branch`, `base_sha`, `pushed`, `pr` and
  `sessions` cleared, `replays` kept, and the remote branch and PR left
  alone). It makes no revert commit. The story goes back as
  `reverts.back_step` says today.
- **E3.** `revert_story` on a landed story (any sprint) makes the revert in
  the land worktree: `git revert --no-edit -m 1 <landed.merge>`, with message
  `REVERT_SUBJECT`/`REVERT_BODY`. It then lands like a story (L7 to L10): the
  full checks, a push to `<story_prefix><id>-land`, CI, then the push and
  fast-forward. When it is green, the `RevertEntry` records
  `merge = landed.merge` and `revert = <sha>`, `landed` is cleared and the
  state resets as today. It runs as a runner task under the land queue
  (L2), at its head.
- **E4.** A revert is refused (AC3.5), and the sprint branch stays untouched,
  when:
  - the revert conflicts: `REVERT_CONFLICT` lists the files, and the later
    landed stories whose merges touch the same files (`git log
    --first-parent --format=%H <merge>..HEAD -- <files>`, mapped to stories
    by merge subject);
  - its checks or its CI are red: the failures, and the same later stories;
  - a started story depends on it: `DEPENDED_ON`, as today.
- **E5.** The move and cancel limits are lifted for unlanded stories (AC3.4):
  `story_admin.code_refusal` applies only to a story with `landed`. A story at
  `land` can't be moved or cancelled until its land ends.
  `request_cancel` adds `LANDING_REFUSAL`, and `start_sprint` refuses to
  leave out a story at `land` (`LAND_NOT_MOVABLE`).

### What goes away (AC4.x, REQ-151)

- **G1.** These go: `pending_tests.py`, the `pending-tests` command and
  `PENDING_ARGS`, `guard.RUNNER_FILES`' registry entry, the onboarding line

  `_apply_pending`. Any pure helper that something else still uses

- **G2.** The tests gate has no command gate. `_command_gate` keeps only
  `implement`. `Checks.tests_red`, `tests_reworked`, `_red*`,
  `_pending_or_green`, `Pipeline.reworked` and `_rework_gate` go, with
  `REWORK_UNCLAIMED`, `REWORK_PASS`, `GREEN_TOO_EARLY`, `NOT_PENDING`, the
  `PENDING_*` texts, `REGISTRY_BAD` and the `RegistryError` catch in

- **G3.** DevOps, at `ops-review`, removes the `pending-tests` step and the

### Order (AC5.x, REQ-152)

- **D1.** A story with `depends_on` starts only when every dependency's status
  is `done`, and done now means landed (L1). `dependencies.waiting_on` is
  unchanged. A test proves that a dependency at `land` still blocks.

### Parallel stories (AC6.x, REQ-153 to REQ-156)

- **C1.** `scheduler.Scheduler.run()` replaces `PoRun`'s loop and
  `Router.advance`. Each tick it does the following, in order:
  1. Drain the writer.
  2. Stop starting new work if a stop was requested, the run halted, a re-pin
     is due or a usage limit was hit.
  3. Apply the request queues for stories with no running task: the reorder
     desk, sharer, intake, clerk, reverter and checkout requests. Skip them
     while a land holds the sprint branch (B4).
  4. Check the main checkout's guard.
  5. If a boundary is due, run its stage once no step and no land is running
     (C7).
  6. Start the work the router offers, within the caps (C2, C3, C4).
  7. Start a PO turn if none is running and hand-overs are queued (C5).
  8. Wait for the next change: a task done, a write submitted, or `POLL_S`.
- **C2.** One task per story, keyed by story id: a role step, a land, a
  revert landing or a story rebase. The Manager review has its own key
  (`MANAGER_KEY`, AC6.8). It runs alongside the story tasks and blocks
  none of them. The boundary runs on the scheduler task.
- **C3.** `[team] max_open_stories` (default 5, an integer ≥ 1) caps the open
  stories. A story with no worktree starts only while
  `Workspaces.open_count() < max_open_stories`. A story that already has a
  worktree may always run.
- **C4.** The budget (AC12.1). Before starting any step, the scheduler sums
  `budget_reserve.reserve(entries, role, model, floor)` over the running
  steps, and starts nothing if
  `ledger.total() + sum >= team.budget_usd`. A step's reserve is
  `max(mean + 3·σ, floor)` over the fresh (`resumed` false, `estimated`
  false), completed ledger entries of that `(role, model)`. With fewer than
  `RESERVE_MIN_STEPS = 5` such entries it is just `floor`.
  `floor = team.step_reserve_usd` (default 1.00, ≥ 0 and < `budget_usd`).
  No running step is ever stopped for cost. `enforce_ceiling` still halts
  once spend reaches the ceiling, and the running steps finish.
- **C5.** The PO desk (`po_desk.PoDesk`) queues each `Pass` as it arrives,
  per story, and runs one PO turn at a time. A turn takes every queued pass,
  merged into one prompt (`handover.merge(passes)`: the kinds, lines and
  stories joined, in arrival order). Hand-overs that arrive during a turn wait
  for the next one. A pass is dropped from the queue only when its turn
  finished. A turn cut off by a limit or a crash leaves them queued
  (AC11.4).
- **C6.** One writer (AC6.4). In-memory `RunState` changes happen only on the
  event-loop thread. Worker threads (`system.in_thread(fn, *args)`, a new
  seam over `asyncio.to_thread`) run commands and git and return data. They
  never touch `RunState`.
  - `state.json`, `events.jsonl` and `ledger.jsonl` are written only by the
    scheduler task, in `RunWriter.drain()`.
  - `EventLog.emit` and `Ledger.record` still assign ids and times at once,
    under a lock, but hand the line to `RunWriter.submit`, which is
    thread-safe (`loop.call_soon_threadsafe`).
  - `Runtime.save()` submits a coalesced save.
  - Step tasks and PO tool calls make their state changes through
    `await writer.apply(fn)`: the scheduler task runs `fn` and returns its
    result.
  - Outside a running scheduler (CLI commands, tests that build no
    scheduler), the writer writes at once.
  - `RunWriter.check_owner()` raises `WrongWriter` if a save is submitted
    from a worker thread.
  - The live meter writes its own files (`heartbeat.json`, `turns.jsonl`,
    `sleeps.jsonl`), one entry per running step.
  - The main lock (`asyncio.Lock`, `Scheduler.main_lock`) is held by a
    main-checkout step for its whole run, by a land from its merge to its
    fast-forward or discard, and by `settle_po` and the story-admin commits.
    The Manager takes it only around its settle.
- **C7.** A due boundary starts nothing new (AC6.7). The PO desk keeps
  serving turns. The stage runs once `tasks` holds only the Manager review,
  or nothing.
- **C8.** Hold and cancel (AC11.1). A PO hold on a story with a running task
  only stops its next start. A cancel sets `StepTask.cancel_requested`. The
  step's `PreToolUse` hook then denies the next tool call and returns
  `{"continue_": False, "stopReason": STORY_CANCELLED}`. This is a safe point:
  between tool calls, never inside a commit, because commits are the
  runner's and come after the query. The settle then skips the commit and the
  gate.
- **C9.** Snapshots (AC6.5). A PO turn starts with
  `TurnSnapshot.take(state)`: one `Mark(step, status, hold, po_hold kind,
  rounds, landed)` per story. Each tool call runs through `Tools.applied`
  inside `writer.apply`. If any story the call names (`named_stories`) has a
  live mark different from its snapshot mark, the call is refused with
  `STORY_MOVED.format(id, now=<live mark text>)`. After a successful call, the
  marks of the stories it named are refreshed, so the PO's own changes never
  refuse its later calls. `run_role` and `wait_for_answers` are async. Their
  checks and the start of the step run inside `apply`, and the waiting
  happens outside it.
- **C10.** `stop` finishes every running task and starts no new one (C1,
  step 2). `stop --now` (SIGTERM) cancels every task. Each cancelled story
  step is recorded as interrupted (I1), and the run halts `sigterm`.

### Hand-over scopes (AC6.6, REQ-155)

- **H1.** `handover.Scope` is `STORY` or `RUN`, and `handover.SCOPES` maps
  every `Trigger` to one. `handover.check_scopes()` raises `ScopeTableError`
  naming any `Trigger` missing from the table. `cli.main` calls it before
  any command runs (the global-scope rule forbids an import-time check).
  - `RUN`: `ERROR`, `BOUNDARY_ERROR`, `BOUNDARY_ESCALATED`, `SYNC_CONFLICT`,
    `REBASE_CONFLICT`, `PUSH_REJECTED`, `CI_FAILED`, `MAIN_BROKEN`,
    `CI_GREEN`, `SPRINT_END`, `NEXT_SPRINT`, `STALLED` and
    `SPRINT_BACKLOG_STUCK`.
  - `STORY`: every other trigger, including the new `STORY_CI_RED`,
    `WORKTREE_DRIFT` and `LAND_BOUNCED`, and also `CI_INFRA`, `CI_PENDING`,
    `PUSH_PERMISSION`, `KNOWN_FAILURES` and `HUMAN_MESSAGE`.
- **H2.** A `STORY` pass queues for the PO, and only its story waits, through
  its hold (`note_step` → `hold_reason`). A `RUN` pass queues and also pauses
  new starts until the PO turn that receives it ends. The budget ceiling and
  a checkout halt are halts, not triggers, and they stop new starts too.
  While a boundary holds, nothing starts anyway (C7). So `CI_INFRA` and
  `CI_PENDING` raised by a boundary need no `RUN` scope.

### Kept sessions (AC7.x, REQ-157)

- **K1.** `StoryState.sessions: dict[str, KeptSession]` is keyed by role
  name: `{session, model, effort, provider, reported}`. A role step on a
  story whose role has a kept session with the same `model`, `effort` and
  `provider` resumes it (`Launch.resume = session`). Otherwise it starts
  fresh. A finished step saves its session id and the SDK's running cost.
- **K2.** A kept session ends (`kept_sessions.drop_all` / `drop_role`):
  - when the story is done or cancelled: all its sessions;
  - when `revert_story` runs: all;
  - when a bounce or return sends the story to an earlier step: all;
  - when an `override` event changes the role's model, which is how an
    `upgrade_model` ruling applies: that role's session on every story.
- **K3.** When a kept session goes past the context limit, the SDK compacts it
  (`StepResult.compacted_from`). If a resumed query fails with a
  context-limit error (`kept_sessions.CONTEXT_PATTERNS`), that role's session
  on the story is dropped, the step reports `error`, and the next step starts
  fresh.
- **K4.** A resumed step's cost is the session delta,
  `SessionCost(session, reported).own_cost(resumed, cost)`, as the PO's is.
  `ledger.Entry` gains `resumed: bool = False` and `estimated: bool = False`
  (set by `reconcile.sum_turns`). The `step-end` event gains `resumed` and
  `cache_write` (`tokens.cache_creation`). The dashboard's `step_times.Span`
  carries `resumed`, and the Time chart splits each role's bar into fresh and
  resumed segments.

### Waiting, interruptions and limits (AC11.x, REQ-161 to REQ-165)

- **I1.** A story step that is interrupted (crash, `stop --now`, usage
  limit) is recorded as `story.in_flight = InFlight(role, story, brief,
  session)`. The session is captured from the SDK's init message as soon as
  it arrives. The worktree is left as it is, and no salvage commit is made.
  `salvage`/`recovery`'s commit-and-revert stays for storyless steps only,
  and so does `RunState.in_flight`.
- **I2.** `start --resume`, for each `story.in_flight`, emits
  `step-end` `{status: "stopped", interrupted: <cause>}` unless that step
  already has a `step-end`. It keeps the session in `sessions[role]` and
  sets `story.interrupted = Interruption(role, story, brief, cause, sha=None)`
  (the fields in `salvage.Interruption`'s order; s165), so
  the next brief says the worktree still holds the cut-off edits
  (`WORKTREE_KEPT_LINE`). Then it clears `in_flight`.
- **I3.** On `start --resume`, `Workspaces.prune_stale(keep)` removes every
  worktree under `run_dir/worktrees/` whose story has no `in_flight`, removes
  `run_dir/land` and `run_dir/replay` unless a boundary replay is pinned, and
  runs `git worktree prune`. Open stories get their worktree back through B1
  at their next step.
- **I4.** Waiting on the human (AC11.3). `Router._block`, the stuck and
  keep-going caps, and `notify_user(kind="blocked")` no longer set
  `RunStatus.BLOCKED`. They post their note and set
  `state.mark(RunStatus.RUNNING, reason)`. A quiet pass no longer ends the
  run. The scheduler keeps polling every `POLL_S` and hands over an answer or
  a tell within one tick. Only `halted()` statuses end the run:
  `done`, `checkout-changed`, `blocked` (now only the budget), `limit`, and
  `sprint-end` under the sprint cadence. `notify_user(kind="done")` still
  ends it. The deadline stops it through the stop command.
- **I5.** `live.Pulse` writes `$UNATTENDED_HEARTBEAT` (read once in
  `cli.make_runtime` through `system.environ()`) on each beat:
  `{"at": now, "progress": <events.jsonl size in bytes>}`, plus
  `"waiting": <status_reason>` while the scheduler is idle with a reason
  (`Pulse.set_waiting(reason | None)`). The heartbeat's `steps` key lists
  one view per open meter, oldest first, and `step` stays the newest.
  `health.current` judges each entry of `steps` and reports the worst.
- **I6.** Usage limit (AC11.4). `RunStatus.LIMIT = "limit"`, `halted()`
  includes it, and `HALTS[HaltKind.LIMIT]` is
  `HaltRule(RunStatus.LIMIT, "blocked", 75, …)`. The liaison note kind stays
  `blocked`.
  - A step that hits the limit fails on its own and is recorded as I1.
  - `Scheduler.limited` is set, so nothing new starts.
  - A land already waiting on CI finishes its wait.
  - When no task is running, `halt_run(limit)` sets `limit` with the reset
    text in `status_reason`, and the run exits 75.
  - A PO turn cut off by the limit keeps its session, and its passes stay
    queued (C5).
  - **I6a** (added at design-review). Every table keyed by run status
    knows `LIMIT`. `health.HALTED` includes `RunStatus.LIMIT`, so a `limit`
    stop is red (`halted: limit …`), as a limit was red when it was
    `blocked`. The dashboard's `STATUS_TONE` (`dashboard/index.html`) gains
    `limit: "warning"`, the same tone as `blocked`.
- **I7.** Unattended (AC11.6).
  - `probes.Reading` gains `waiting: str | None`, read by
    `heartbeat_reading`.
  - `watch.View` gains `waiting`.
  - A view with `waiting` posts one `waiting` notice
    (`notify.Trigger.WAITING`, text `is waiting: {reason}`). The notice is
    posted again only after the liveness `moved_at` changes.
  - `_start_idle_stop` returns early while `waiting` is set.
  - `command_job.status_reason` accepts the statuses `blocked` and `limit`.
  - Acceptance runs AC11.6 in the `unattended` environment: the
    `[[environment]] name = "unattended"` entry in `.agile-team.toml`
    (a `package` install of `unattended/runner` into
    `{sandbox}/venv-unattended`). The human added it (t183/t184, the
    liaison's commit 0e984caf), and the s94 tests list it. No role edits
    the config entry or the s94 test files for this story.

### Switching over (AC10.x, REQ-160)

- **W1.** `RunState.story_branches: bool = False`. The first `start_sprint`
  after the upgrade calls `switchover.refusals(facts)` and refuses, listing
  every reason (`SWITCH_REFUSED`), when:
  - a listed story is past `design` (`Pipeline.is_past_design`);
  - `.team/pending-tests.json` exists with any id, read by a minimal JSON
    reader in `switchover` (the registry module is gone);
  - `upstream.stack` is not empty;
  - `git rev-list --count <target>..<team branch>` is not 0.

  With no refusals it sets `story_branches = True` and goes on. Afterwards
  the check never runs again.
- **W2.** An older `state.json` loads with every new field at its default
  (state's `_story` and `_upstream_state` defaults). A Product Backlog story
  already past design keeps its step, and gets its branch and worktree from
  the sprint head at that time when it next starts (B1) (AC10.3).
- **W3** (added at design-review, from the code). While `story_branches` is
  `false`, the scheduler starts one task at a time
  (`scheduler.ONE_AT_A_TIME`, from `Scheduler.check_free`), the Manager
  takes the main lock for its whole step as before
  (`Scheduler.uses_main_checkout`), steps run in the main checkout
  (`Runtime.uses_worktree` is false), and a story at `land` with no
  `branch` passes at once (`Scheduler.pass_unbranched`, a runner `PASS`
  `"landed"`). So a run that has not switched over behaves as before s159,
  apart from the `land` step.

## 7. Test checklist

Unit tests go in `tests/test_<module>.py`. They use the fake OS
(`FakeSystem`) and no temp dirs (ADR-0036). Git behaviour runs in e2e
against a scratch repo with a bare remote and a fake `Prs`, as the s151
e2e files do. One test or more per item. Every AC is pinned somewhere.

**Config and names**
- [ ] `story_prefix`: default, unsafe, equal to `prefix`, either a prefix of the other. Every refusal has its text (AC1.5).
- [ ] `max_open_stories`: 0, 1.5, `true` and 5. `step_reserve_usd`: -1, equal to budget, 0 (AC6.1, AC12.1).
- [ ] `pipeline_steps` puts `land` last with or without `acceptance`, and the config can't remove it (AC2.3).
- [ ] `story_branch`, `landing_branch`, `merge_subject` and `merge_id` round-trip.

**Push safety**
- [ ] `Upstream.push` refuses a non-descendant `expect` with `NOT_FAST_FORWARD` and runs no `push` argv. A descendant pushes with `--force-with-lease=<ref>:<expect>` (AC2.16).
- [ ] A source scan finds no bare `--force-with-lease` and no `--force` in `agile_team/` (AC2.16).
- [ ] The guard accepts both prefixes, refuses main and the checked-out branch, and its text names both prefixes (AC1.5).
- [ ] `delete` refuses anything that isn't a landing branch, sends the leased delete argv, and skips the ancestor check (AC2.4).

**Worktrees (e2e for the git parts)**
- [ ] The first step makes the branch at the sprint head and records `base_sha`, and the worktree is at `.team/run/worktrees/<id>` (AC1.1).
- [ ] A step's scope base, Stop hook cwd, `CommandShell` cwd and story-file read are the worktree, and its state, events and ledger land in the main `.team/run` (AC1.2).
- [ ] `git_env` keeps the ceiling at the main `.team/run`, and git in the worktree finds the worktree (AC1.1).
- [ ] Only a landing and a story-admin commit move the main checkout, and each updates the guard record and `StackEntry.head` (AC1.3).
- [ ] Worktree drift blocks only that story, with `worktree_drift` naming the files. `accept-checkout --story` while running queues a request that the scheduler applies. Main-checkout drift halts (AC1.4).

**Landing**
- [ ] The merge is `--no-ff` in `.team/run/land`, the first parent is the sprint head, the message is `merge(<id>): <title>`, the story shas are unchanged, and the worktree is removed afterwards (AC2.1, AC2.2).
- [ ] An acceptance pass goes to `land`, and a Manager `advance` from `acceptance` goes to `land` too. `run_role` at `land` is refused. Done only on a land pass. `depends_on` waits on a story at `land` (AC2.3, AC5.1).
- [ ] Red checks bounce to implement, and the sprint branch never moved (AC2.3).
- [ ] Green CI: the sprint branch is pushed and then fast-forwarded, `head` and `pushed` are recorded, `story-landed` has both parents, the first landing opens a draft PR, and a later landing reuses it by number with no `find` call (AC2.4).
- [ ] Red CI bounces with the sprint branch untouched. Infra gets one re-run and then `ci_infra` for that story only. No checks at the timeout gives `ci_pending`. The landing branch is deleted in every case (AC2.4).
- [ ] A rejected push when the remote moved ahead fast-forwards and lands again with a new merge. When the remote diverged, the run halts as checkout drift naming both heads and the liaison is told (AC2.4).
- [ ] Story file: the branch copy wins, the sprint edits are re-applied, and a clash holds for the PO (AC2.9).
- [ ] A merge conflict gives `land_bounced` with a round, DevOps for DevOps-only files and the developer otherwise, then the rebase step and `land` again (AC2.10).
- [ ] Two stories at `land` land in acceptance order (AC5.2).
- [ ] Resume after the landing push re-reads the CI of `landed.pushed` and makes no merge or push (AC11.5).

**Permission and story pushes**
- [ ] With `unasked`, steps commit, nothing is pushed, a land waits before its push, and `push_permission` is raised once (AC2.11).
- [ ] After a committing step with `yes`: the story branch is pushed with its lease, `pushed` is saved only on success, and a draft PR targets the sprint branch (AC8.1, AC2.15).
- [ ] Landing closes the story PR, and leaving leaves it a draft (AC8.2).
- [ ] A story-PR result is a `story-ci` event, red gives `story_ci_red` and no hold, and the landing CI decides the land (AC8.3).

**Replay (e2e)**
- [ ] The end replay walks first-parent: each story merge becomes rebased commits plus a `--no-ff` merge with the same message, and a plain commit is cherry-picked (AC2.5).
- [ ] A conflict gives DevOps's scratch replay naming the story. `find_refusal` checks story by story and has no `HAS_MERGES` (AC2.6).
- [ ] The remap pairs by subject per story and merges by `merge(<id>)`, and rewrites `base_sha`, `landed.merge` and `RevertEntry.merge` (AC2.7).
- [ ] The replay goes to the new `<prefix><N>-r<k>` with a `READY` PR. The old PR is closed through `Prs.close` with a link, and the old branch is kept. The entry keeps `as_is_*`, and `supersedes` lists only open PRs. The texts give `FF_COMMAND` and never "Rebase and merge" (AC2.8, AC2.12).
- [ ] At the start, with main moved and an open PR, the replay goes to `-r<k+1>`. With an empty stack or a merged PR it replays locally and pushes nothing (AC2.12).
- [ ] A carried story is replayed to `-r<k>`: stash and pop for an interrupted step, `pushed` reset, a new draft PR with the old one closed, sessions kept, and a conflict becomes its next step while the boundary goes on (AC2.13).
- [ ] A CI hold follows a moved remote head: fetch, fast-forward, record, re-enter CI. A non-fast-forward halts as drift. `continue_boundary` on `ci_failed` is accepted after a move and refused before one (AC2.14).
- [ ] The start creates `<prefix><N>` remotely and the entry with `start`, `head` and `pushed`, and the end reuses it (AC2.17).

**State**
- [ ] A `StoryState` round-trip with every new field, and an old `state.json` loads with the defaults (AC2.15, AC10.2).

**Leaving and reverting**
- [ ] A moved-out story keeps its branch, its worktree is removed and later rebuilt from the branch (AC3.1).
- [ ] A cancelled story keeps its branch, and nothing of it reaches the sprint branch (AC3.2).
- [ ] A revert of an unlanded story drops the branch with no commit. A revert of a landed story runs `revert -m 1` in the land worktree and lands through checks, a landing branch and CI (AC3.3).
- [ ] An unlanded story at `implement` can be moved and cancelled. A story at `land` can't (AC3.4).
- [ ] A revert conflict or red checks or CI leave the sprint branch untouched and name the later stories touching the same files. A dependent started story refuses the revert (AC3.5).

- [ ] A tests step with passing tests hands off `done` and passes, with no claim. The red stages are gone from `STAGES`. A `tests` key in a handoff is ignored (AC4.2).

**Scheduler**
- [ ] Two stories run steps at once, one per story. Hand-overs are gathered per story. The meter and the heartbeat have two `steps`. Acceptance sandboxes are keyed by story and environment (AC6.2).
- [ ] `max_open_stories` stops a new story but not an open one (AC6.1).
- [ ] Passes queue during a turn and reach the next turn merged (AC6.3).
- [ ] Every save and event line is written by the scheduler task. A save from a worker thread raises `WrongWriter` (AC6.4).
- [ ] A PO call on a story that moved since the turn began is refused with the new state, and the PO's own earlier change doesn't refuse it (AC6.5).
- [ ] `check_scopes` fails on a missing trigger. A per-story pass holds only its story, and a run-wide one stops new starts (AC6.6).
- [ ] A due boundary starts nothing new, still serves PO turns, and runs once idle (AC6.7).

- [ ] `stop` lets the running steps finish, and `stop --now` cancels them all (AC6.2).

**Sessions and budget**
- [ ] The second step of the same role on a story resumes the session. A different model starts fresh (AC7.1).
- [ ] Each drop rule: done, cancelled, revert, bounce, override. A context-limit failure leaves the next step fresh (AC7.2).

**Interruptions and waiting**
- [ ] A hold takes effect after the running step. A cancel stops at the next tool call, before any commit (AC11.1).
- [ ] An interrupted story step gets `in_flight` with its session and no salvage commit. Resume marks it stopped, and the next step resumes in the same worktree (AC11.2).

## 8. Known limits

- Two stories designed at once may pick the same requirement id, ADR number
  or design-index line. That shows up as a landing conflict (L6). The
  architect's brief gives the next free REQ id counted over the sprint head
  and every open story branch
  (`requirements.next_id` over `git ls-tree` of each). ADR numbers and the
  index rows still conflict. A conflict in them is settled in the rebase
  step, whose scope covers the conflicting files.
- The boundary stages and the story-admin queues still run on the scheduler
  task, so a long boundary CI wait pauses PO tool calls until it ends.
- Tools run from the main checkout must ignore `.team/run/`. ruff and
  house-rules already do (gitignore, s157). DevOps checks the rest at
  `ops-review`.
- R2a picks the fix text with the `plain_rebase` bool rather than a table
  row. A follow-up for the Product Backlog (review D12, N1, N2) gives the
  stopped replay its own `FixCase` with a `FIX_LINES` row, removes the bool
  and the duplicated text, and adds a JSON round-trip test.
