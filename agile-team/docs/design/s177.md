## The problem

`push_and_follow` calls `follow_remote` on any refused sprint push.
`follow_remote` gives up the merge first, then fetches, and follows when
`is_ancestor(pushed, remote)`. That is also true when the remote equals
`pushed` (it didn't move: a dead remote, auth, branch protection) and when
it equals the merge (the push went through, the reply was lost). Both
re-land up to `MAX_RESTARTS` times and then hold with "the sprint branch kept
moving".

## Rules

R1. **Fetch before giving anything up.** On a refused sprint push the lander
    fetches the sprint branch and reads its remote head `R` first. Only then
    does it decide, by `R`:

| `R` | name | what happens | AC |
|---|---|---|---|
| `R == attempt.merge` (non-empty) | `HAS_MERGE` | the push went through: carry on exactly as after a successful push | AC2 |
| `R == entry.pushed` | `UNMOVED` | hold at once with the refusal text; keep the merge | AC1 |
| `pushed` is an ancestor of `R` | `MOVED_ON` | give up the merge, follow `R`, land again (today's path) | AC3 |
| anything else, or `R` empty | `DIVERGED` | give up the merge, halt as checkout drift (today's path) | — |

   The checks run in that order. `HAS_MERGE` comes first, so a merge that
   equals `pushed` can't happen (the merge is always a new commit).

R2. **UNMOVED holds and keeps the merge (AC1).** No `give_up`, so
    `story.landed` keeps `merge` and `pushed`, and no `landing-dropped` event
    is logged. The landing branch is **not** deleted (see R4). The land step
    reports `Verdict.HOLD` with the reason
    `SPRINT_PUSH_REFUSED.format(branch=entry.branch, why=<refusal text>)`,
    which is `pushing the sprint branch <branch> was refused: <why>`, and
    `land.merge = attempt.merge`. `continue_story` and `release_story` need no change.
    The next `land` step goes through `run_land`'s existing resume path
    (`story.landed.pushed` is set): `check_resume`, then `finish_pushed`
    reads the CI of the same sha again, and on green `move_sprint` pushes the
    same merge again. This is the path a held landing CI already uses.

R3. **HAS_MERGE is a made push (AC2).** `push_and_follow` goes on as if the
    push had returned `None`: `entry.pushed = attempt.merge`, then
    `apply_carry` (moves the main checkout with `advance_to`; then
    `record_checkout` sets `entry.head` to the checkout's head). `move_sprint`
    then runs `complete`, which records the story landed with `ci: green`.
    With carried commits the checkout and `head` go to the carry's tip, as
    after any successful push (ADR-0093). With none, `pushed` and `head`
    both equal the merge.

R4. **The landing branch stays only for a kept merge.** `finish_pushed`'s
    `finally` deletes the landing branch unless `attempt.kept == merge`.
    `hold_refused` sets `attempt.kept = attempt.merge` for a story landing.
    A landing revert (`attempt.revert_of` set) records no revert merge in
    `landed`, so its release reverts afresh and its landing push needs the
    branch gone. A revert's `kept` stays `""`, so its landing branch is
    deleted as today and only the hold is new.

R5. **Restart limits by cause (AC3).** A land restarts (merges afresh) for
    two causes: a followed remote (R1 `MOVED_ON`) or a carry the landing
    refused (`build_moved_drop`). Each gets its own limit of `MAX_RESTARTS`:
    - `attempt.remotes` lists each remote head followed, oldest first. When it
      reaches `MAX_RESTARTS` the land holds with
      `KEPT_MOVING.format(count=len(remotes), heads=", ".join(h[:SHORT] ...))`.
      The heads are distinct by construction: each followed `R` becomes
      `pushed`, and the next one must descend from it and differ from it.
    - `attempt.restarts` counts every restart. When
      `restarts - len(remotes)` reaches `MAX_RESTARTS` the land holds with
      `HEAD_KEPT_MOVING.format(count=MAX_RESTARTS)`.
    The loop ends: each pass that doesn't return adds 1 to `restarts`, and so
    to one of the two counts, so it runs at most `2 * MAX_RESTARTS - 1` passes.
    A drop in `run_land`'s `check_resume` happens before the loop and isn't a
    restart.

R6. `DIVERGED` and `MOVED_ON` keep today's order of effects after the fetch:
    `give_up(attempt, Drop(GIVE_UP_REFUSED))`, then follow or halt. The
    fetch now runs before `give_up`, so a fetch that raises leaves the merge
    and `landed` as they were (the stage records the error, s175).

## Known limits

- A remote that descends from the merge (the push went through, then
  something else was pushed on top) is `MOVED_ON`. The merge is given up
  and the story merges again onto a head that already has it. This is the
  same bounded loop as before. The story's ACs don't cover it.
- `push()` still can't tell a lease refusal from other failures. R2 holds
  on the text whatever it says, and that is the point: the PO reads why.
- No new event: AC2's refusal leaves only the normal `story-landed` record.
