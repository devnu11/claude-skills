# s45: Manager step crash, crash log, fault rulings, blocked release

Story: `.team/stories/s45.md`. Developer: `developer-cli`.

What went wrong in sprint 16, in order:

1. The router ran the manager on s29. `Runtime._fault` called
   `self.emit(EventKind.FAULT, plan, **report)`, and `report` has a `kind` key.
   That clashed with emit's `kind` parameter (TypeError). HEAD already fixes
   this: `Runtime.emit(self, kind, plan=None, /, **data)` makes both parameters
   positional-only (dispatch.py:335). **Keep that signature. Do not change it.**
2. The crash happened in `settle`, which is outside the `try` in
   `_run_planned`, so nothing wrote it to `crash.log`. The router's `error`
   hand-over still said "details in .team/run/crash.log".
3. The PO then ran the manager on s29, which was not `repeated`. `_rulings`
   ignored `handoff.fault` without saying so.
4. The PO called `continue_story` on s29 (status `blocked`). The hold cleared
   but the story stayed `blocked`, so the sprint stalled.

## Rules

### Crash log (AC3)

- **C1** Every exception raised by a role step after `refusal` (in
  `settle_po`, `_unpresented`, `plan`, `_take_off`, `_execute`, `settle` or
  `note_step`) is appended to `.team/run/crash.log` **exactly once**, and
  then re-raised unchanged. `Runtime.run_role` is the one place that logs
  it. The exception is not swallowed: the router still turns it into an
  `error` report, and the PO still sees it as a tool error.
- **C2** A crash in `_execute` **or** `settle` goes through `_step_failed`,
  so the cut-off step's edits are saved (`Cause.ERROR`) the same way for
  both. `settle` therefore moves inside the `try` in `_run_planned`.
- **C3** A limit (`halt.limit_halt(exc)` is not None) is still caught in
  `_step_failed`, logged there, and turned into a `halted` report. It does
  not reach `run_role`'s handler, so it is logged once too.
- **C4** The router (`router._dispatch`) and `cli._halt_exit` stay as they
  are. The router does not log, and the PO loop's top-level handler logs
  only what escapes the PO loop. A role-step crash never escapes it.

### Manager rulings (AC5, AC6)

- **M1** The Manager's handoff goes through the **fault path** when it names
  a fault (`handoff.fault` is non-empty) **or** the story is `repeated`.
  Otherwise only `ruling` is considered, as today.
- **M2** In the fault path the refusals are checked in this order. The
  first one that applies wins, and nothing changes:
  1. no story: `a fault needs a story; run the manager on that story`
  2. done story: `story {id} is done; a fault cannot move it`
  3. no fault (only possible when `repeated`): `FAULT_MISSING` (unchanged)
  4. unknown role: `FAULT_UNKNOWN` (unchanged)

  Steps 1 and 2 reuse `gates.ruling_refusal(story, "a fault")`.
- **M3** An applied fault behaves the same on any story, `repeated` or not
  (for example `blocked`, or `needs_manager` from a round cap or a
  unit-tester's `escalate`):
  - `step` becomes the named role's step (kept for an off-pipeline role or
    `runner`).
  - `status` comes from `FAULT_STATUS` (`runner` → `blocked`, a role →
    `active`).
  - `hold` becomes `None`.
  - `rounds`, `disputes`, `dispute`, `streak`, `run`, `repeated` and
    `escalated_by` are cleared (`Pipeline._clear`).

  `note_step` then sets `hold` again from the report as usual. A `runner`
  fault re-holds with `runner_fault`. A pipeline fault leaves the story free.
- **M4** The fault's `reason` (in the report, the `fault` event and the
  runner-fault note) is `gates.setback_reason(story)`. That is
  `story.repeated` if set, else `story.previous.reason` if there is a
  previous step, else `""`. Read it **before** `apply_fault` clears
  `repeated`.
- **M5** A `ruling` in the same handoff applies after an applied fault and
  wins (unchanged). If the fault was **not** applied, the ruling is not
  applied either, and the report says so. It does not drop the ruling
  silently:
  `"ruling": {"ruling": <r>, "applied": False, "why": "the fault was not applied, so the ruling was not either"}`.
  Both `fault_not_applied` and `ruling_not_applied` then hand over.
- **M6** Every fault or ruling the Manager names shows up in the step
  report as `"fault": {...}` and/or `"ruling": {...}` with
  `applied: true|false`, and `why` when the value is false. The PO gets it
  in `run_role`'s result. When the router ran the step, it gets the
  hand-over lines. Both go through `Runtime.run_role` → `settle` → `_apply`,
  so the dict is the same either way. A Manager handoff with neither a fault
  nor a ruling, on a story that is not `repeated`, reports neither (as
  today).
- **M7** Wording is no longer tied to "repeated":

  | Where | Exact text |
  |---|---|
  | `dispatch.RUNNER_FAULT_NOTE` | `Runner fault on {story}: no role can fix this setback: {reason}. The manager says: {summary} The story is blocked until the runner is fixed.` |
  | `handover` `OFF_PIPELINE_FAULT` line | `{story}: the manager puts the setback ({fault_reason}) on {fault}, which owns no pipeline step; brief {fault} yourself, then continue_story` |
  | `handover` `FAULT_NOT_APPLIED` line | `{story}: the manager's fault ruling was not applied: {fault_why}; run the manager on {story} again` |

### Releasing a blocked story (AC7)

- **B1** `continue_story` on a story whose `status` is `blocked` is refused
  whether or not it has a hold, and nothing changes. Releasing the hold
  would leave the story `blocked`, and the router only moves `active`
  stories. Reason:
  `story {id} is blocked (escalated to the human); continue_story would leave it stalled. Run the manager on {id} with a ruling or a fault to move it`
- **B2** Done stories and every other status behave as today. A done
  story's hold is still cleared (s24).
