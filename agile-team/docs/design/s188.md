# s188: bookkeeping commits on a green or merged sprint head are not new work at the END boundary

Story: `.team/stories/s188.md`. ADR: ADR-0094 (new); ADR-0075 amended by s188.
Requirements: REQ-242 (AC1), REQ-243 (AC2), REQ-244 (AC3).
Developer: `developer-cli` (runner internals and the PO's role file; no page work).

## Cause in one line

The END boundary compares HEAD with the sprint's pushed sha, so a
`chore(team): <role> step` commit made after CI judged that sha looks like new
work: the push stage pushes it (sprint 54), `push-replayed` pushes it as
`-r<k>` and closes the green PR (sprint 53), and the shipped check misses a
target that holds the pushed sha (both). Separately, `ci_green` fires on the
CI stage's `pass`, before the boundary has finished (sprint 53's early
"#74 is ready").

## The decision: the boundary judges the work head; bookkeeping rides to the next sprint

The story leaves open where bookkeeping commits go. **They stay on the team
branch, unpushed, and ship with the next sprint's PR**, the same answer s180
gave for a landing (ADR-0093, "the carried commits stay local until the next
landing or the sprint end"). Nothing is deferred, made elsewhere or rewritten.
Deferring would have to stop every writer (the PO's own step, the intake,
shares) while a boundary runs, which is s180's rejected option.

## Rules

| # | Rule | AC |
|---|------|----|
| W1 | **A bookkeeping commit** is a commit with exactly one parent whose changed paths (`--name-only --no-renames`) all lie under the team dir `config.TEAM_DIR` (`.team`), i.e. each path is `.team` or starts with `.team/`. A commit that changes no path counts as bookkeeping. A merge never does. This covers the storyless steps' `chore(team): <role> step` commits (`.team/po/handoff.md`), story-file intake and share commits. A commit that touches any other path (a DevOps fix, a quarantine, a held-back requirement edit) is work. | AC1, AC3 |
| W2 | **The work head.** For the sprint's own entry `own`, the work head is `own.pushed` when `own.pushed` is set, differs from HEAD, is an ancestor of HEAD (`git merge-base <pushed> HEAD` prints `<pushed>`), and every commit of the first-parent line `<pushed>..HEAD` is a bookkeeping commit (at least one listed). Otherwise the work head is HEAD. The check needs git's output to name the commits; an exit code alone is never taken as "yes" (the `FakeSystem` pitfall from s183). | AC1, AC3 |
| W3 | **The push stage pushes the work head.** `_push_as_is` sets `own.head = own.end = upstream.last_end = <work head>`, not HEAD. When the work head is the sha the landings already pushed, nothing is pushed and the PR stays as it is, so CI is read (and triaged) on the pushed sha. A PR whose checks ran on that sha, merged or not, reads green, never `stale`. | AC3 |
| W4 | **`push-replayed` judges the work head.** On the END edge, after the fetch: the shipped check (s183) asks whether the target contains the **work head**; if so, the sprint closes as shipped with `sha = <work head>` in the report, the PR note and the `done` event. Otherwise, when the work head equals `own.pushed`, the replay changed nothing: today's `_report_unchanged` (pass event, draft made ready, `_finish_green` with the entry's CI). Only a work head that differs from `own.pushed` (the replay rewrote the line, or real work came after CI) pushes `-r<k>`, opens a ready PR and closes the old one, as today. | AC1, AC3 |
| W5 | **The bookkeeping commits are kept.** Nothing resets, rewrites or drops them: they stay on the team branch above the work head. `last_end` is the work head, so they fall in the next sprint's range and reach main with the next sprint's PR (the next start's sync finds the team branch already on the target, `current`, and keeps it). The green report's fast-forward command names `own.pushed`, the work head. | AC1 |
| W6 | **`ci_green` fires once, at the finish.** The `ci_green` hand-over rule matches only a boundary report whose `outcome` is `done` and whose `ci` is `green`. The CI stage's `pass` event keeps its `ci: green` field (the Board and the event log read it), but it raises no hand-over. The only `done` events with `ci: green` are `_finish_green`'s (from `_report_unchanged` or `ci-replayed`), and they carry the PRs the boundary finished with (`prs`), so no ready line names a PR the runner later closes. | AC2 |
| W7 | **What doesn't change.** The green gate (REQ-015): `replay` still refuses without green CI on `own.pushed`, so shipped and unchanged are only reached after it. The START edge, the CI verdict table, `follow_remote`, the replay itself, the shipped report texts and REQ-222's rule (a target that contains HEAD also contains the work head) stay. A work head with real work after it is HEAD, so everything is as before. A boundary saved before s188 with a chore already pushed (sprint 54's state) is not migrated; the liaison closed it by hand. | all |

AC map: AC1 is W1, W2, W4 (unchanged branch), W5. AC2 is W6. AC3 is W1 to W4
(shipped branch); the sprint-54 path is W3, then green CI on the merged PR's
head, a `current` replay and W4's shipped close.

## Changes per module

### `agile_team/upstream.py`

Import `TEAM_DIR` with the existing line: `from .config import TEAM_DIR, UpstreamSettings`.

Module constant and pure helpers, next to the other parsers:

```python
TAIL_MARK = "\x1e"  # starts each commit in a tail listing (s188)
TAIL_MARK_FORMAT = "%x1e%H %P"  # git's spelling of TAIL_MARK, then the sha and parents


@dataclass(frozen=True)
class TailCommit:
    """One commit after the pushed head: its sha, how many parents it has and its paths."""

    sha: str
    parents: int
    paths: tuple[str, ...]


def parse_tail(out: str) -> tuple[TailCommit, ...]:
    """The commits of a ``git log --format=%x1e%H %P --name-only`` listing, as git lists them."""


def is_bookkeeping(commit: TailCommit) -> bool:
    """W1: a plain commit whose paths all lie under the team dir (one with no paths too)."""
```

- `parse_tail`: split `out` on `TAIL_MARK`, skip blank chunks. In each chunk
  the first line is `<sha> <parent> [<parent> …]`: `sha` is its first word and
  `parents` the count of the rest. The other non-blank lines, stripped, are the
  paths.
- `is_bookkeeping`: `commit.parents == 1 and all(p == TEAM_DIR or
  p.startswith(f"{TEAM_DIR}/") for p in commit.paths)`.

Method on `Upstream`:

```python
def has_only_bookkeeping(self, base: str) -> bool:
    """W2: True when ``base`` is under HEAD and every commit of ``base..HEAD`` is bookkeeping."""
```

- `False` unless `self.git.attempt("merge-base", base, "HEAD")` returns code 0
  and output `base` (stripped). Same equality pattern as `is_in_target`.
- Then `commits = parse_tail(self.git.run("log", "--first-parent",
  "--no-renames", "--name-only", f"--format={TAIL_MARK_FORMAT}", f"{base}..HEAD"))`
  and return
  `bool(commits) and all(is_bookkeeping(c) for c in commits)`.
- Keep it under 8 lines; a private `_is_base_of_head(base) -> bool` for the
  merge-base check is fine.
