# s173: a committed config change is live without a restart

Bug fix. `cli._load_config` reads `.agile-team.toml` once and the `Runtime`
keeps that `Config` for the whole run. Intake (`story_intake.Intake._known`)
checks environment names against `runtime.config.environments`, gates take
their commands from `runtime.pipeline` (built from that config), and nothing
notices a commit that changes the file. Each such commit cost the team a stop
and a `start --resume` in sprint 51.

Traces: AC1 → REQ-262, AC2 → REQ-263, AC3 → REQ-264. Decision: ADR-0094.

Developer: `developer-cli`.

## Rules

- **R1. The runner follows the committed file.** The run's config is the
  `.agile-team.toml` blob at the main checkout's `HEAD`
  (`git rev-parse HEAD:.agile-team.toml`). The working tree and story
  worktrees are never read for it. The runtime keeps the blob id it last
  took or refused in `Runtime.config_blob`. `make_runtime` sets it at start.
  When it is `None` (a runtime built in a test), the first check only records
  the current blob and changes nothing.
- **R2. One check point: the scheduler's safe point.** `Runtime.update_config`
  runs:
  1. in `Scheduler.tick`, inside `if self.may_apply_queues:`, right after the
     `rt.checkout_moved()` check and before `self.router.apply_queues()`. So
     the intake, shares, clerk and checkout requests of the same tick see the
     new config;
  2. in `Scheduler.run_work`, right after `dispatch` returns a report and
     before `report_back`, only while `self.may_apply_queues` holds. There is
     no `await` between the end of the step's `async with` lock and this
     check, so the step that committed the change is the one that sees it.
  `Runtime.update_config` itself returns `None` without reading git when it
  is a story view (`worktree_of is not None`) or while `main_lock` is locked.
  So it never swaps the config under a main-checkout step, a landing's git
  move or a non-story-branch story step. `may_apply_queues` also keeps it out
  of a running boundary stage.
- **R3. Same blob, nothing to do.** When the `HEAD` blob equals
  `config_blob`, `update_config` returns `None`. A missing file (rev-parse
  fails) reads as blob `""`, and from then on it is handled like any other blob:
  `""` differs from the kept id, the parse fails (R6), and the error is
  reported once. A landing carry (ADR-0093) that gives the config commit a
  new sha keeps the blob, so it triggers nothing.
- **R4. A new blob is parsed, checked and swapped as one.** The text is
  `git cat-file blob <id>`, parsed with `config.parse_text` and built with
  `config.from_raw(old.repo, raw)`. Then `run_home` is copied from the old
  config. Then `live_for(new)` builds the parts that derive from the config
  (`LiveConfig`), and it raises `ConfigError` on any problem. On success the
  runtime swaps these, each by assigning a new object and never by mutating
  the old one:
  `config`, `book`, `pipeline` (and sets `pipeline.checks.stages =
  self.stage_log.open` as `__post_init__` does), `providers`, `shell`. It
  also swaps `upstream = Upstream(self.main, new.upstream)`, but only when
  `"upstream"` is among the changed sections. This keeps an injected fake
  upstream in tests.
- **R5. A running step keeps its config (AC2).** A story view copies the
  runtime when its step starts (`get_story_view`). Its `config` and
  `pipeline` are its own, and its `book`, `providers`, `shell` and
  `upstream` are references to the objects of that moment. Because R4
  assigns new objects, a swap never reaches a running view. That step's stop
  checks and its gate run in the same view, so they also keep the old config.
  The next step's view, and so its gate, is made from the new config. Main-checkout steps are
  covered by R2's lock rule. The PO turn is not frozen: each PO tool call
  reads `runtime.config` live (AC1, "PO tool call").
- **R6. A bad blob changes nothing but is reported once (AC3).** An error
  from `parse_text`, `from_raw` (`renamed`, `_tools`, `_toolchain` …) or
  `live_for` keeps every live part as it was. `from_raw` doesn't check
  value types, so a wrongly shaped section (`team = 3`, an `[environment]`
  table instead of `[[environment]]`, an environment row without a
  required key) raises `AttributeError` or `TypeError`. The watch catches
  every class in `BAD_CONFIG = (ConfigError, TypeError, AttributeError,
  ValueError)`, so none of them stops the run. A `ConfigError` gives its
  message as is, and any other class gives `f"{type(exc).__name__}:
  {exc}"`. The runtime
  still sets `config_blob` to the new id, so the same bad blob is reported
  only once, and the next commit is compared against the last good config.
- **R7. One `config` event per new blob.** `EventKind.CONFIG = "config"`,
  role `None`, story `None`, data `ConfigChange.data`:
  `{"sha": <commit>, "blob": <id>, "sections": [...], "error": <text or "">}`.
  `sha` is `git log -1 --format=%H HEAD -- .agile-team.toml`, the commit
  that last changed the file. `sections` lists the TOML section names whose
  parsed value differs from the last good config, in `SECTIONS` order (empty
  on an error, or for a comment-only change). Exactly one event is logged
  for each new blob, taken or refused.
- **R8. Who hears about a bad blob.** In `run_work` (R2.2), when the change
  has an error and `change.sha == report.get("commit")`, the step's own
  report gets `report["config"] = change.data`. The step's hand-over then
  carries the error. Otherwise (a tick, an outside commit, a landing merge,
  or a sha that doesn't match), the scheduler queues
  `Pass([Trigger.CONFIG_INVALID], lines, [])` for the PO. A taken change
  reaches no hand-over and is only in the event.
- **R9. `config_invalid` holds nothing.** The new trigger is story-scoped (not
  in `RUN_WIDE`) and in `UNHELD`, so it pauses no starts and holds no
  story. The run goes on with the last good config.
- **R10. Read at start only.** These keys still take effect only at the next
  `start`: `[team] auth`, `key_file`, `cadence` (the runtime's `env`,
  `secrets` and `state.cadence` are not rebuilt) and `[health] beat_s` (the
  `Pulse` keeps its beat). `[dashboard]` is read by the dashboard itself, as
  before. Every other key, `budget_usd`, `max_open_stories`,
  `step_reserve_usd` and `round_cap` included, is read from `runtime.config`
  where it is used, so it applies at once.

`ConfigWatch.update` steps (one private helper each, all verb-named, for
example `_read_config(blob) -> Config`, `_take(blob) -> ConfigChange`,
`_apply_live(live, sections)`, `_record(change)`):

1. `blob = read_blob(rt.main)`. If `rt.config_blob is None`, set it and
   return `None` (R1). If `blob == rt.config_blob`, return `None` (R3).
2. Set `rt.config_blob = blob` first (R6).
3. Try: `new = replace(config_mod.from_raw(rt.config.repo,
   config_mod.parse_text(rt.main.run("cat-file", "blob", blob))),
   run_home=rt.config.run_home)`, then `live = rt.live_for(new)`. A
   `BAD_CONFIG` error gives `ConfigChange(sha, blob, [], <R6 text>)`. A blob of
   `""` raises `ConfigError(f"{CONFIG_NAME} not found at HEAD")` before
   git is called. The catch also takes `GitError`, so a `cat-file` that
   fails is refused like a bad blob instead of stopping the run. The R6
   text comes from `describe_error(exc: Exception) -> str` in
   `config_reload` (design review, round 2: the code's choice is kept).
4. On success: `sections = find_changed_sections(rt.config, new)`, apply
   `live` (R4), `ConfigChange(sha, blob, sections, "")`.
5. Emit `Event(EventKind.CONFIG, None, None, change.data)` and return the
   change.

### `agile_team/cli.py`


It builds `book = role_book(config, place.home)`, raises

### `agile_team/scheduler.py`

```python
    def update_config(self) -> None:
        """R2.1, R8: take a new committed config in the tick; a refused one goes to the PO."""

    def add_config_change(self, report: dict[str, Any]) -> dict[str, Any]:
        """R2.2, R8: after a step, ``report`` with its own refused config, else unchanged."""

    def queue_config_pass(self, change: ConfigChange) -> None:
        """R8: a ``config_invalid`` pass for the PO about an outside or unmatched commit."""
```

- `tick`: `if rt.checkout_moved(): return`, then `self.update_config()`,
  then `self.router.apply_queues()`.
- `run_work`: `report = self.add_config_change(await self.dispatch(work))`
  inside the existing `try`. On an exception from `dispatch`, no config check
  is made (the next tick makes it).
- `add_config_change`: if not `self.may_apply_queues`, return `report`. Else
  call `change = self.runtime.update_config()`. If there is no change or no
  error, return `report`. If `change.sha == report.get("commit")`, return
  `report | {"config": change.data}`. Otherwise call
  `queue_config_pass(change)` and return `report`.
- `queue_config_pass`: `lines = handover.report_lines({"config": change.data},
  None)`; `self.queue_pass(Pass([Trigger.CONFIG_INVALID], lines, []))`.

## Test checklist

Unit tests go in `tests/test_config_reload.py`, in the existing
`test_config.py`, `test_handover.py` and `test_cli.py`, and, for the
scheduler and runtime wiring, in `tests/test_s173_live_config.py` (there is
no `test_scheduler.py`; follow `test_s180_scheduler.py`). Unit tests use
no temp dir and no real git (REQ-108, REQ-109). They fake the `Git` calls the
watch makes (`attempt("rev-parse", …)`, `attempt("log", …)`, `run("cat-file",
…)`) with a table of blob id → text. Real git runs only in the e2e test below:

- [ ] `parse_text` parses TOML. Bad TOML raises `ConfigError` starting with
      `.agile-team.toml:`. `read_raw` gives the same messages as before.
- [ ] `read_blob` returns HEAD's blob id, and `""` when rev-parse fails.
      `find_last_change` returns the stripped `log` output, and `""` on failure.
      The e2e test checks both against real git.
- [ ] `find_changed_sections`: one changed `[[environment]]` gives
      `["environment"]`; `toolchain.test` and `gates.round_cap` give
      `["toolchain", "gates"]` in `SECTIONS` order; equal configs give `[]`.
- [ ] AC1 / R2, R4: commit a config adding an environment `house-rules`;
      after `Scheduler.tick` (or `Runtime.update_config`), a queued story
      amendment naming `house-rules` is onboarded (`story-amended`, no
      `story-refused`) in the same tick.
- [ ] AC1 / R4: with `pipeline_for=cli.make_pipeline`, commit a config that
      changes `toolchain.test`; the runtime's pipeline and the next story
      view's pipeline run the new command line (a fake shell records it).
- [ ] AC1 / R4: after a taken change, `runtime.book`, `runtime.providers`
      and `runtime.shell` are the objects `live_for` returned, and
      `runtime.pipeline.checks.stages` is `runtime.stage_log.open`.
- [ ] AC1: the PO tool that reads environments or roles after the swap sees
      the new values. An `add_role`/`run_role` refusal for an unknown role
      clears once a commit adds `[roles.x]` with a role file.
- [ ] AC2 / R5: a story view made before the swap keeps its `config`,
      `pipeline`, `book` and `shell` after it. A view made after it gets the
      new ones.
- [ ] AC2 / R2: `update_config` returns `None` and logs nothing while
      `main_lock` is held, and in a story view. Once the lock is free, the
      next call takes the change.
- [ ] AC2 / R7: one taken change logs exactly one `config` event with `sha`
      (the commit), `blob`, the changed `sections` and `error == ""`. A
      second `tick` with the same HEAD logs none. A comment-only commit logs
      one event with `sections == []`.
- [ ] R3: a new HEAD that keeps the blob (another file changed, or a
      rewritten sha) logs nothing.
- [ ] AC3 / R6: a commit with bad TOML, one breaking a rule (`[team]
      budget_usd = -1`), and one with a wrongly shaped section (`team = 3`,
      which raises `AttributeError` inside `from_raw`) each keep the old
      `config` and `pipeline`. Each logs one `config` event with the error
      text (`AttributeError: …` for the last) and `sections == []`.
      Ticks after that log nothing more. A later valid commit is taken, and
      its sections are compared against the last good config.
- [ ] AC3 / R8: a storyless step whose report `commit` is the bad config's
      commit gets `report["config"]`, and its hand-over line names the sha
      and the error. A bad commit found in a tick, or with a different
      `commit`, queues one `config_invalid` pass with no stories.
- [ ] R9: `config_invalid` is in `UNHELD`, has `Scope.STORY`, and
      `hold_reason` of a report with only `config` is `None`.
- [ ] cli: `build_live_config` raises `ConfigError` listing the
      `check_config` problems, and returns the parts otherwise.
      `make_runtime` sets `config_blob` and `live_for`. `check_config`'s
      output is unchanged for a valid and an invalid config.

End-to-end (`tests/e2e/`, real git, scratch `HOME`): a run whose storyless
DevOps step (fake query) commits a new `[[environment]]` onboards a queued
amendment naming it without a restart, and `events.jsonl` has one `config`
event naming that commit (its `sha` equals `git log -1 --format=%H --
.agile-team.toml`, its `blob` equals `git rev-parse HEAD:.agile-team.toml`).
